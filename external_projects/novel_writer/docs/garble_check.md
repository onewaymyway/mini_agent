# 关键文件乱码检测（garble_check）

> 对应方案：`next_doc/novel_writer_garble_post_step_check_plan.md`
> 当前进度：**G1–G4 全部完成**。G1：配置 + 注册表 + 只读体检 + 驾驶舱入口 + report 模式记录；G2：skill 步骤内重试环；G3：所有步骤的统一守卫（归因、上游重置、计数、挂起问作者）；G4：驾驶舱状态展示与端到端回归。

## 1. 为什么需要

正文乱码已有 `garble_guard` 守卫，但章节总结、全书章节索引、人物档案、伏笔账本等由 agent 顺手写出的文件没有检测。乱码内容会被下游步骤当作输入继续使用（例如第 13 章总结乱码，写到第 14 章才被发现）。

乱码无法转码还原，唯一修复方式是让产出它的步骤重新生成，因此本机制的核心是：**检测 → 找到产出者 → 重跑产出者**。

## 2. 检测什么

关键文件注册表 `WATCH_GLOBS`（`novel_writer/garble_watch.py`）：

| 类别 | 匹配 |
|---|---|
| 章节总结、全书章节索引 | `章节总结/*.md` |
| 记忆摘要、上下文包 | `项目状态/memory/ch_*.json`、`项目状态/memory/context_ch*.md` |
| 蓝图 | `大纲规划/蓝图/_index.md`、`大纲规划/蓝图/*.md` |
| 人物档案 | `大纲规划/人物设定/角色索引.md`、`大纲规划/人物设定/角色/*.md` |
| 伏笔账本 | `大纲规划/线索设定/伏笔/_index.md`、`伏笔/*.md`、`伏笔注册表.md`、`故事线状态.md` |
| 世界观与规划文档 | `world_bible.json`、`主题设计.md`、`节奏规划.md`、`前三章开篇设计.md`、`结局设计.md` |

排除：`_studio/`、`导出/`、`_drafts/`、`*.bak`，以及非 `.md` / `.json` / `.txt` 后缀的文件。

判定沿用 `garble.is_garbled`（替换符 / 私有区 / 控制字符、汉字旁半角 `?`、生僻字比例），阈值不变。读取一律使用 `repair=False`，检测过程**不改写任何文件**。

## 3. 配置

`_studio/settings.json`：

```json
"garble_check": {
  "mode": "off",
  "max_reruns": 2,
  "watch_extra": []
}
```

| 字段 | 说明 |
|---|---|
| `mode` | `off`（默认，与旧行为逐字节一致）；`report`：步骤结束后检测本步骤改动过的关键文件，只写运行日志与 `_studio/inbox/garble_<步骤>.json`；`rerun`：skill 步骤内发现乱码即让同一步骤 agent 重写（G2）；所有步骤结束时统一守卫（G3）：自动重做、重置上游、或挂起问作者，原文件先备份 |
| `max_reruns` | 同一「producer 步骤 + 文件」自动重做上限（默认 2），用尽后挂起等待作者决定；文件通过检测后计数清零 |
| `watch_extra` | 额外守卫的相对路径或 glob，如 `["自定义/*.md"]` |

也可在 **审校页 → 🧪 乱码体检** 中切换模式。

## 4. 只读体检

- 接口：`tool_api.scan_garble(workspace)`，返回 `files_checked`、`garbled_count` 与每个命中文件的 `reasons`、`writer`（最后写入者）、`writer_kind`（declared / agent / author）、`auto_rerunnable`、`note`。
- 归因规则：最后写入者是已知流水线步骤 → 可自动重跑；作者手改或查不到写入记录 → 只提示，不替作者决定重生成。
- 驾驶舱：审校页「🧪 乱码体检（关键文件）」→「开始体检」。对可自动重跑的命中项提供「重跑产出者」按钮，它只是把步骤重置为待执行（等同于总控台的重跑），之后到总控台运行。

## 5. rerun 模式：步骤内重试（G2）

skill 步骤的重试环（`runner._run_skill_step_inner`）在回执、产出、内容校验都通过之后，再检查本步骤改动过的关键文件（含声明产出）：

1. 命中乱码 → 原文件先复制到 `_studio/backup/garbled/<步骤>_<时间>/`（不删除）；
2. 把问题清单（「`文件` 疑似乱码（原因）。请重新完整撰写该文件并覆盖写入同一路径，文件名保持不变」）写入本次 hint，同一步骤重做；
3. 与回执 / 产出 / 内容问题共用 `MAX_RECEIPT_ATTEMPTS`（3 次）上限，用尽则步骤失败，由 worker 的自动重跑接管（G3 会改为计数与挂起问作者）。

「钉死输出」：提示明确要求覆盖写入同一路径，文件名不变。python 步骤不经过此重试环。

## 6. report 模式的执行位置

`runner.run_step` 中：

1. 步骤开始前，`garble_watch.snapshot()` 记录关键文件指纹（`mode=off` 时直接返回空，零开销）；
2. 步骤将要置为 `passed` / `waiting_review` 时，`report_step()` 比较前后指纹，并把步骤声明的产出一并纳入检测；
3. 命中则写运行日志（`⚠ 乱码检测：…`）与收件箱记录。

该过程**不改变步骤状态**，任何异常都被吞掉并记入返回值，不影响步骤结果。

## 7. 统一守卫（G3）

每个步骤将要结束（`passed` / `waiting_review`）时，`garble_watch.guard_after_step` 在**写入者记录之前**执行（rerun 模式）：

检测范围 = 本步骤改动的关键文件 ∪ 本步骤声明产出 ∪ 本步骤读取的关键文件（下游发现上游乱码）。

| 归因结果 | 动作 |
|---|---|
| 产出者是本步骤 | 本步骤标为失败，错误信息作为重试提示，worker 自动重跑（计数 +1） |
| 产出者是上游步骤 X | 重置 X 与本步骤为待执行，调度器按顺序先跑 X（计数 +1） |
| 作者手改 / 查不到写入者 | 只写 `_studio/inbox/garble_<步骤>.json` 与运行日志，不改变流水线 |
| 次数已达 `max_reruns` | 本步骤挂起 `waiting_user`，给出三个选项 |

每次只处理第一条可自动处理的命中。挂起后作者的答复在该步骤下次开始时处理（`handle_pending`）：

- **再重新生成**：计数清零；产出者是本步骤则重跑本步骤，是上游则重置上游与本步骤；
- **我手动修改后重新核查**：不重新生成，只检测该文件；通过则步骤通过，否则再次挂起；
- **接受当前内容（风险自负）**：记录该文件当前指纹，指纹不变时不再检测，步骤直接通过。

状态存放在 `_studio/pipeline_state.json` 的 `garble_reruns`、`garble_accepted`、`garble_pending` 三个键中。

## 8. 驾驶舱与端到端（G4）

- **体检结果附带守卫状态**：`scan_garble` 返回 `reruns`（每个「产出者 + 文件」已自动重做次数 / 上限）、`waiting`（挂起的步骤及其状态）与 `accepted`（作者已接受风险的文件）。审校页「🧪 乱码体检」展示这些内容。
- **挂起决定的入口**：挂起的步骤在总控台以 `waiting_user` 显示，选项就是守卫写入的 `needs_user`，与其它 needs_user 的处理方式相同（选择后该步骤下次开始时生效）。
- **端到端回归**（`tests/test_garble_check_g1.py`，完整流水线 + 桩执行器）：
  - rerun 模式下，第 1 章总结第一次写成乱码，agent 重写后，流水线自动完成，最终文件干净；
  - 默认 off 模式下，乱码总结不会被重做，与旧行为一致。

## 9. 与 garble_guard 的关系

`chapter_ops` 中的 `chNN.garble_guard`（正文守卫）保持原样不动。rerun 模式下：正文通常已在 skill 步骤内（G2）修好，`garble_guard` 成为第二道保险；off/report 模式下，行为与之前完全一致。两者的挂起选项文字相同，但各自记录在不同的步骤状态中，互不干扰。

## 10. 已知限制

- 统一守卫依赖步骤的 `outputs` 声明：python 步骤若不声明产出，重复写出完全相同的乱码内容无法被识别为本步骤产出；
- 归因依赖 `file_writers` 记录，历史上未登记写入者的文件只会被提示，不会自动重跑；
- 每次收尾只处理一条自动命中，多个乱码文件会分轮处理；
- 误报风险：生僻字阈值来自少量样本，集中出现人名/古字的规划文档可能误判，建议先用 `report` 观察；
- 收件箱记录目前只落盘为 JSON，尚未接入收件箱页面的汇总展示；
- 本机制不解决乱码产生的根因（例如 Windows 下的写入编码），需另行排查。
