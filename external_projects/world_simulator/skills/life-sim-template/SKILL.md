# life-sim-template

## 背景与边界

本 skill 是 `world_simulator` 的第一个"场景模板"（对应方案 2.4 节），
服务两类场景：

1. **决策推演分析**：用户给出当前处境 + 候选选择，模拟未来走向，
   辅助对比。
2. **持续性人生模拟**：从一个起点持续推进，形成一条可以回看的时间线。

被 `generate_scenario` workflow 挂载时，你只做"生成初始状态"这一件事；
被 `advance_step` workflow 挂载时，你只做"推进一步"这一件事——两者的
`result_file` 契约不同，见下方两节，不要混淆。

## 通用判断原则

1. **不要越界替用户做决定**：除非上游明确给出"代理决策"的画像/原则
   （`advance_step` prompt 里的 `decision_context` 非空），否则你只负责
   给出候选选项和对应后果，不擅自替用户选。
2. **变量要具体、可追踪**：`vars` 里的字段应该是"这个人生模拟里真实
   存在、会随时间变化"的量（年龄、存款、健康、职业阶段、人际关系状态
   等），不要塞入大段自由文本描述当变量值。
3. **叙事克制、有代入感，但不夸张**：`narrative` 是几句话的情节推进
   文本，不是小说章节，服务"看得懂发生了什么"，不是文学创作比赛。
4. **候选选项数量按用户设置来，不要自己拍脑袋**：具体条数见下方
   `{option_count_hint}`（由用户在创建/推进时配置，不是固定 3-5 个）；
   每个 `options` 条目应该代表一个方向明显不同的选择，数量不够时不要
   拿"实质等价"的假选项凑数，宁可在描述里体现更细的差异化。
5. **大环境是活的，不是静止背景板**：真实人生不是只有主角一个人在
   做选择——经济周期、行业/技术发展（比如 AI 浪潮改变某个岗位的
   含金量）、就业市场松紧、政策法规变化、社会观念/舆论风气变化等
   "主角控制不了、但真实影响他处境"的宏观因素，应该随时间自己演化，
   不能因为主角做了什么选择就停止变化，也不能从头到尾一成不变。
   `vars` 里建议单列一个 `macro_environment` 字段跟踪这部分（见下）；
   `narrative`/选项设计里要让这些宏观变化实际影响到主角的处境和
   选择后果，而不只是背景装饰性的一句话。
6. **时间粒度可以是"自动/引导"的，不要以为一次模拟只有一种粒度**：
   每一步对应多长的模拟内时间，由用户设置的 `{time_granularity_hint}`
   决定，具体分三种模式（文案里会写明是哪一种）：
   - **固定模式**：明确给了一个值（比如"1 个月"），每一步都严格照做，
     不要不管设置成什么都按"过了一年"来写——这种模式下不会出现"切换
     粒度"的情况。
   - **自动/引导模式**：允许你按情境自行判断每一步的粒度，且**同一次
     模拟里可以出现多种粒度**——比如日常推进用"1 年"一步，进入一场
     关键谈判/冲突时可以临时切到"一轮"或"1 周"一步，谈判结束后再切
     回日常粒度。默认延续上一步用过的粒度（`advance_step` 场景里会
     告诉你上一步用的是什么），只有情境明显需要时才切换，不要没理由
     来回跳；引导模式下额外有一句用户给的偏好/基准，仅供参考，不是
     必须严格遵守的精确值。
   变量变化幅度、叙事节奏都要按"这一步实际用的粒度"换算，`time_label`/
   `next_time_granularity` 字段（见下）就是对这个粒度的具体落实。

## 作为 `generate_scenario` 挂载时（result_file: scenario.json）

输入：`{intent}`（用户一句话意图）、`{previous_draft_json}`（此前一轮
草稿，可能为空字符串）、`{feedback}`（用户对上一份草稿的补充意见，可能
为空字符串）、`{option_count_hint}`（用户设置的候选方向数量，比如
"4 个左右"）、`{time_granularity_hint}`（用户设置的时间粒度，比如
"1 个月"/"1 年"/"自动——由你根据模拟对象的性质自行判断"）。`feedback`
非空表示这是一次"根据意见修改"请求：以 `previous_draft_json` 为基础
按意见调整，未提及的部分（包括未被要求改动的 `options` 条目，尽量连
`id` 一起）保持不变；`feedback` 为空则忽略 `previous_draft_json`，按
`intent` 从零生成。

输出（合法 JSON，顶层字段）：

- `title`：字符串，这次模拟的简短标题。
- `summary`：字符串，初始状态一句话摘要。
- `vars`：对象，初始状态的结构化变量（字段自定，需具体可追踪，见上）。
  建议至少包含：`age`（年龄，整数或字符串区间）、`stage`（当前人生
  阶段/身份，字符串）、`resources`（资源状况，字符串或子对象）、
  `key_relationships`（关键人际关系，字符串数组）、`macro_environment`
  （宏观环境现状，字符串或子对象——只写和这个模拟意图相关的部分即可，
  比如"AI 行业处于快速发展期，就业市场对相关技能需求旺盛，但泡沫化
  风险也在讨论中"这种一两句话的描述，不用面面俱到覆盖经济/社会/技术
  所有维度）。
- `options`：数组，按 `{option_count_hint}` 给出对应数量的初始候选
  方向，每项含 `id`（短英文/拼音标识）、`label`（几个字的选项名）、
  `description`（一两句话说明这个方向意味着什么）。若用户意图里已经
  明确给出了几个候选选择，直接对应展开成这几项（数量可以不等于
  `{option_count_hint}`）；若没有，你需要合理生成对应数量、方向明显
  不同的选项，不要为了凑数给出实质等价的假选项。
- `time_label`：字符串（可选），初始状态对应的模拟内时间点，一般
  就是 `起点`；如果意图里明确给出了具体时间起点（比如"从 2020 年
  开始"），可以写成对应的描述。
- `time_granularity`：字符串（可选，`{time_granularity_hint}` 为
  "固定模式"时可以不写，引擎会用设置里的固定值），这次模拟的起始
  基准粒度（比如"1 年"/"1 个月"）——只需要给一个能代表"日常节奏"
  的值，不用考虑中途可能出现的特殊情境，那部分由 `advance_step` 逐步
  判断是否需要切换。
- `resource_fields`：数组（可选），`vars` 里属于"资源类数值"的字段
  声明（比如现金存款这类"不应该低于某个下限、后续会被消耗/增减"的
  数值），每项是字段名字符串（如 `"resources.cash"`，默认下限 0）或
  `{"field": "resources.cash", "min": 0}`。之后每一步 `advance_step`
  推进时，引擎会自动检查这些字段有没有被算成负数（不用你在
  `advance_step` 阶段自己操心这件事）。没有这类字段就不用输出。
- `uncertain_fields`：数组（可选），`vars` 里属于"你自己主观估计出来、
  置信度不高"的字段声明（比如"创业成功率"这类本质是推断而非确定事实
  的数值——`age` 这类确定性字段不要放进来），每项是
  `{"field": "startup_success_rate", "confidence": "low", "note": "一句话
  说明为什么置信度低"}`。`confidence` 只能是 `high`/`medium`/`low`
  三档之一，不要给出精确概率造成"伪精确"的印象；`note` 可以省略但建议
  给一句话。没有这类字段就不用输出。
- `objectives`：数组（可选），字符串列表，这次模拟"主要关心的指标"
  （比如 `["资产净值", "工作满意度", "健康水平"]`），不要求是 `vars`
  里的精确字段名，写清楚意思即可。用户意图里能看出明确关心的方向时
  给出建议；看不出来就不用输出，不要为了填这个字段而牵强编造。这个
  字段只是记录用途（供创建向导展示、供后续「对比实验」页面提供默认
  关注字段参考），不会触发任何自动排序/推荐。

## 作为 `advance_step` 挂载时（result_file: next_state.json）

输入：当前标题、当前状态摘要、当前 `vars`（JSON）、当前时间步、当前
状态对应的模拟内时间点（`{current_time_label}`，可能为空字符串）、
产生当前状态那一步实际用的时间粒度（`{current_time_granularity}`，
可能为"无（这是第一步……）"）、当前状态的候选分支选项（JSON 数组，
可能为空）、本次选择的选项（可能为空对象 `{}`）、可选的
`decision_context`（"代理决策者画像"，非空时表示这一步是自动挡场景，
你需要自己从候选分支选项里选一个，见下方规则）、`{option_count_hint}`/
`{time_granularity_hint}`（同上，含义与 `generate_scenario` 一致）。

**选择逻辑（按优先级）：**

1. 如果"本次选择的选项"非空：直接按这个选项推进，`chosen_option_id`/
   `chosen_reason` 字段可以省略（调用方已经知道选的是什么）——这个
   选项的 `id` 如果是 `custom_` 开头，说明是用户自己新增的、不在原
   候选列表里的选项（系统给的候选终究只是建议），处理方式完全一样，
   不需要特殊判断。
2. 如果"本次选择的选项"为空对象，但 `decision_context` 非空（自动挡
   代选）：从"候选分支选项"里挑一个最符合 `decision_context` 给定
   原则/风险偏好的选项，在输出里加上 `chosen_option_id`（选中选项的
   id，必须是候选列表里真实存在的 id，不要编造）和 `chosen_reason`
   （一两句话，说明为什么这么选，要具体到"符合了画像里的哪条原则"，
   不要写"综合考虑后选择了这个方向"这种空话）。若候选分支选项为空
   数组（无可选项），按第 3 条处理，不需要这两个字段。
   若 `decision_context` 里明确写了"允许你跳出候选列表提出自定义
   选项"，且你确信候选列表里没有一个足够合理，可以改为输出
   `custom_option_label`/`custom_option_description`（新方向的标题
   和说明）+ `chosen_reason`（说明候选列表为什么不够好），不要同时
   输出 `chosen_option_id`；没有明确允许时不能这样做，必须从候选
   列表里选。
3. 如果"本次选择的选项"为空对象且 `decision_context` 也为空（普通
   手动挡，未指定选择）：依据当前状态给出最合理的默认走向，不要等待
   用户输入，也不需要 `chosen_option_id`/`chosen_reason`。

**推进时要把"大环境也在自己变化"考虑进去**：不要只推演"主角这次选择
的直接后果"，`current_vars_json` 里如果带了 `macro_environment`，
它应该有独立于主角选择的演化（经济周期、行业技术发展、就业市场、
政策、社会观念等按自己的逻辑往前走），并且要让这个变化真的影响到
这一步的叙事和下一步候选选项——比如"你选择继续深耕某项技术方向"这个
选择本身没变，但因为大环境里"这项技术这半年被更新的技术路线超车"，
后果就应该和"大环境没变"时不一样。没有明确迹象要引入宏观转折时，
`macro_environment` 也可以只是渐进式的小幅变化，不需要每一步都制造
剧烈冲击。

输出（合法 JSON，顶层字段）：

- `next_summary`：字符串，推进后新状态的一句话摘要。
- `narrative`：字符串，本步发生了什么的叙事文本（几句话，不要写成
  大段小说）。
- `next_vars`：对象，推进后的完整 `vars`（不是增量，是完整新值——
  引擎不做字段合并，直接整体替换）。数值型字段变化要符合常理的幅度，
  幅度按**这一步实际用的粒度**（即下面 `next_time_granularity` 的值，
  默认延续 `{current_time_granularity}`）换算（比如粒度是"1 个月"，
  年龄这类按年变化的字段一般不该整数 +1，除非正好跨了年；粒度是
  "5 年"，很多字段的变化量就该明显大于"1 年"粒度下的量）；
  `macro_environment`（如果初始状态里有）也要给出推进后的新值，体现
  它自己的演化，而不是原样照抄。
- `time_label`：字符串（可选），这一步结束时对应的模拟内时间点，在
  `{current_time_label}` 基础上按这一步实际用的粒度往前推算（比如
  当前是"起点"、粒度是"1 个月"，这里给"1 个月后"；当前是"第 2 年"、
  粒度是"1 年"，这里给"第 3 年"），合理估算即可，不用精确到具体日期。
- `next_time_granularity`：字符串（可选），这一步实际使用的时间粒度
  （比如"1 个月"/"1 年"/"一轮谈判"）。**固定模式**下应该原样等于
  `{current_time_granularity}`（不会变）；**自动/引导模式**下默认
  延续 `{current_time_granularity}`，只有情境明显需要时才给一个不同
  的值（比如从"1 年"切到"一轮"），不要没理由随意改变；留空表示"和
  上一步一样"，引擎会自动延续，不强制每次都显式重复同一个值。
- `granularity_reason`：字符串（仅当 `next_time_granularity` 与
  `{current_time_granularity}` 不同时才需要），一两句话说明为什么
  现在要切换节奏（比如"进入关键谈判，改为按轮次推进以体现细节博弈"），
  没有切换就不要输出这个字段。
- `options`：数组，供*下一步*选择的候选分支（结构同上，数量按
  `{option_count_hint}`，情节明显没有分支可以给空数组）；有意义的话，
  候选方向里可以体现"应对大环境变化"这条思路（比如"顺应新趋势转型"
  vs "坚持原方向"），不用每次都是纯粹的个人选择。
- `major_decision`：布尔值（可选，默认 false），当这一步的选择/走向
  明显是人生的重大转折点时设为 true——自动挡的 `review_mode:
  pause_on_major_decision` 用它判断是否需要暂停等用户确认，见
  `world_simulator/autopilot.py`；手动挡场景可以照常产出这个字段，
  引擎不会因为它是 true 而改变手动挡的任何行为。
- `uncertain_fields`：数组（可选），这一步 `next_vars` 里属于"你自己
  主观估计出来、置信度不高"的字段声明，格式同 `generate_scenario`
  阶段（见上）。只标注这一步真正新增/变化的估计值型字段即可，不需要
  每一步都重复列出从未变化的旧标注；没有这类字段就不用输出。
- `key_drivers`：数组（可选），字符串列表，1~3 条短语概括这一步变化
  的关键驱动因素（比如"市场需求超预期""现金储备见底被迫收缩"），帮
  用户不用逐字读 `narrative` 就能抓住重点；这一步变化平淡、没有特别
  值得划重点的因素就不用输出，不要为了凑够 3 条硬找理由。
