# mini_agent 重构方案评估：合理性与改进方向

> 本文评估 `00-original-architecture-proposal.md`（原始重构设计文档）的合理性，
> 并指出其在"落地颗粒度"上的结构性缺口。评估基于实际代码库现状核对
> （494 个 Python 文件 / 约 19.2 万行 / 67 个 evolution 模块 / 70 个 perception
> 模块 / 398 个测试文件，与文档描述完全吻合）。

---

## 一、结论先行

原方案在**方向**上是对的，诊断准确：当前问题不是能力不够，而是缺少统一语义层。
但方案目前更接近一份**架构宣言**，还不是一份可以直接排期的工程计划。
需要补的不是"要不要做"，而是"怎么一步步做、每步怎么验证没做坏"。

---

## 二、值得肯定的部分

1. **诊断准确**：Self / World / Experience / Goal / Capability / Action /
   Simulation / Runtime 这 8 个核心概念确实覆盖了当前散落的所有子系统，
   且互相边界清晰，不是简单的"再加一层抽象"。
2. **不做 Big Bang Rewrite，走 Compatibility Layer + Adapter**：194K 行代码
   不可能停下来重写，这个选择是对的。
3. **先挑 Goal 做第一条迁移链**：选得好。`goal_mode/` 只有约 3000 行，体量小、
   边界相对清楚（`spec.py / state.py / executor.py / runner.py`），适合当
   "试验田"。
4. **有 Phase 1 完成的判定标准**（原文 §61）：不是以"新代码写了多少"衡量，
   这个意识很关键，且是原文档里少数几处有具体验收标准的地方。

---

## 三、结构性缺口

### 1. 没有回答"谁来做、按什么节奏做、怎么知道没做坏"

原文档从 Phase 0 到 Phase 9 给出了顺序，但每个 Phase 之间没有：

- 明确的**退出条件**（除了 Phase 1 有 §61，其余 Phase 2-9 都没有"完成标志"）
- 每个 Phase 的**工作量级**（是 3 天还是 3 周？）
- **失败/回滚条件**：如果某个 Adapter 迁移后发现旧行为变了，怎么处理？

### 2. Compatibility Layer 的方向性没定死

原文档里 `GoalState`、`SelfState` 等是 dataclass，但没规定：

- 新旧数据的**转换是单向还是双向**？（旧 Goal → GoalAdapter → GoalState，
  那 GoalState 变化后要不要写回旧 Goal？如果不写回，旧系统的其它 397 个
  测试还认不认这个状态？）
- Adapter 层本身谁维护、放哪、命名规范是什么——现在只说"建立 Adapter"，
  没有一个"Adapter 接口契约"的雏形。

### 3. 缺少"并发影响面"分析

67 个 evolution 模块、70 个 perception 模块互相之间大概率有隐式耦合（比如
perception 写的状态被 evolution 读）。原文档假设"先做 Goal 这条链稳定了，
再迁移 Memory"是线性的，但实际执行中大概率会遇到：*移动 Goal 相关代码时，
扯出跟 Memory/Wiki 共享的字段*。

**建议**：在 Phase 0 增加一步——画一张现有模块间的依赖图（哪怕是脚本跑一遍
import 关系），否则"不小心动了别的系统"的风险在 494 个文件的规模下非常真实。

### 4. 测试策略提得晚，且仍偏概念

原文档 §45-46 才提测试，且停留在概念层面。对于一个已经有 398 个测试文件的
项目，"重构是否安全"几乎完全取决于测试网是否能捕捉行为差异。

**建议**：把"为待迁移模块补充特征测试（characterization tests）"提到 Phase 0，
而不是等 Phase 1 做完再考虑测试模型。

### 5. "第一阶段"和"第一条迁移链"是两条并行叙事，没有合并

原文 §51（建文档目录）、§52（建 core/ 目录）、§53（迁移 Goal）读起来像是三件
独立的事，执行时容易变成"文档先写了一堆，代码却没有跟着走"。

**建议**：把它们编成一条时间线，见 `02-executable-sprint-plan.md`。

### 6. 没有"最小可验证收益"（quick win）

整个计划要看到 Self/World/Experience/Goal 等全部跑起来才算"阶段完成"，
中间没有一个可以给团队/用户看到的**阶段性成果演示**，容易在实施过程中
失去动力或被质疑"到底值不值得"。

---

## 四、额外的改进方向（原文未覆盖）

- **Adapter 契约先行**：在写任何具体 Adapter 之前，先定义一个
  `Adapter[Old, New]` 的最小协议（`to_new(old) -> New` /
  `to_old(new) -> Old`），所有后续 Adapter（Goal / Memory / Self）都实现
  同一协议，避免每个子系统发明一套自己的转换风格。
- **依赖图作为持续产物**，不是一次性任务：建议把 import 依赖扫描脚本
  留在仓库里（比如 `scripts/dep_graph.py`），每个 Sprint 结束都跑一次，
  对比迁移前后模块耦合度是否真的在下降——这也是衡量"架构收敛"是否
  真的发生的量化信号，而不是全凭感觉判断。
- **给旧系统打"迁移完成度"标签**，而不是模块整体二元的"迁移了/没迁移"：
  比如 `goal_mode/runner.py` 可能只有 30% 的路径真正走了新 Adapter，
  这个中间状态需要被记录（可以简单地用注释或一个 `MIGRATION_STATUS.md`
  跟踪表），否则容易出现"看起来迁移完成、实际只做了一半"的假象。
- **给每个 Sprint 设一个可以被否决的检查点**：如果 Sprint 1 做完后发现
  Adapter 模式在 Goal 这条链上就已经很别扭，应该有一个明确的"止损"机制，
  而不是硬着头皮把同一套模式推广到 Memory / Self。

---

## 五、总结

原方案的"八大核心概念 + 渐进迁移 + Compatibility Layer"整体判断是对的，
不需要推翻。真正需要补的是**可执行的颗粒度**：把"Phase"落成"Sprint"，
把"建立 Adapter"落成"哪个函数、双向还是单向、放在哪个文件"，把"测试策略"
从 Phase 1 之后提前到 Phase 0 之前。具体的可执行计划见
`02-executable-sprint-plan.md`。
