# 执行规范：代码变更与文档同步

> 本文档是所有 Phase（`02` - `11`）执行时**必须遵守**的操作规范，
> 不是可选建议。目的是避免出现"代码改了、文档没跟上"或者"文档写得
> 很美、代码其实没有真正走新链路"这两种最常见的重构失败模式。

---

## 一、基本原则

1. **文档滞后不可接受，但文档先行也不可接受**：不允许"先把 11 个
   Phase 文档全部写细节再动代码"，也不允许"代码合并了但对应 Sprint
   文档没有任何更新"。正确顺序永远是：**改代码 → 当天/当次提交内更新
   对应文档 → 才算这个任务完成**。
2. **一次提交，双重产出**：任何涉及"完成标志"清单里某一项的代码改动，
   对应的 PR/commit 必须同时包含该 Phase 文档里勾选框的更新
   （`- [ ]` → `- [x]`），否则视为未完成，不合并。
3. **文档改的是"状态"，不是"计划"**：Sprint 计划文档（`02`-`11`）本身
   一旦评审通过，**任务表和验收标准不能随意改**；如果执行中发现计划
   需要调整，走本文档第四节的"计划变更流程"，不能直接悄悄改掉原文。

---

## 二、每次代码改动后必须更新的三类文档

### 1. 对应 Phase 文档里的"完成标志"清单

- 位置：每个 Phase 文档末尾的 `## 完成标志` 小节。
- 规则：只有当验收标准（该 Phase 文档里的"验收标准"小节）已经**通过
  实际运行验证**（不是"代码写完了应该没问题"），才能把对应的
  `- [ ]` 改成 `- [x]`。
- 谁来改：完成任务的开发者本人在提交代码的同一个 PR 里改，不由旁人
  代劳，避免"看起来完成了但其实没验证"。

### 2. `MIGRATION_STATUS.md`（贯穿全部 Phase 的迁移完成度台账）

这是本次重构新增的一个**必须存在**的文档，放在
`refactor_plan/MIGRATION_STATUS.md`，用于记录"迁移完成度"这种
`01-evaluation-and-gaps.md` 里提到的"中间状态"，避免"看起来迁移完成、
实际只做了一半"的假象。格式规定见第三节。

### 3. 依赖图 / inventory 文档（如受影响）

- 如果本次代码改动**新增或删除了模块间的 import 依赖关系**，必须
  重新跑一次 Sprint 0 建立的 `scripts/dep_graph.py`，并更新对应 Phase
  文档里提到的 `phaseN-xxx-inventory.md`。
- 如果本次改动是"把某个旧模块移入 `legacy/`"（Phase 10 阶段），必须
  同步更新 `11-phase10-legacy-decommission-plan.md` 里的映射表状态。

---

## 三、`MIGRATION_STATUS.md` 格式规范

每个被迁移的模块占一行，最小字段如下（Markdown 表格）：

```markdown
| 模块 | 所属 Phase | 状态 | 走新链路的路径占比 | Adapter 是否双向 | 最后更新 | 负责人 |
|---|---|---|---|---|---|---|
| goal_mode/runner.py | Phase 1 | 部分迁移 | 30% | 是 | 2026-09-26 | @xxx |
```

字段说明：

- **状态**：只允许四种取值 —— `未开始 / 部分迁移 / 完全迁移 / 已降级到 legacy`。
  不允许自造其它状态词，保证可以脚本化统计。
- **走新链路的路径占比**：诚实估算，哪怕是粗略的百分比也比不写好。
  如果确实无法估算，写"未知，待补充"，**不允许留空**。
- **Adapter 是否双向**：对应 `02-executable-sprint-plan.md` 里定义的
  `Adapter[Old, New]` 协议，标注这个模块的 Adapter 是否同时实现了
  `to_new` 和 `to_old`。
- **每次相关 PR 合并后，负责人必须更新这一行**，而不是等到 Sprint
  复盘时才批量补。

---

## 四、计划变更流程（当执行中发现原 Sprint 计划不合适时）

参考各 Phase 文档里的"止损条件"——止损条件触发后，不能直接删掉原计划
另起炉灶，必须按以下步骤留痕：

1. 在对应 Phase 文档末尾新增一个 `## 变更记录` 小节（如果还没有的话）。
2. 按此格式追加一条记录：
   ```markdown
   ### 变更记录 2026-XX-XX
   - 触发条件：<对应哪一条止损条件>
   - 原计划：<引用被改动的任务/验收标准>
   - 实际情况：<发现了什么问题>
   - 调整后方案：<新的做法>
   - 影响范围：<是否影响后续 Phase 的前置条件>
   ```
3. 如果调整影响到后续 Phase 的前置条件假设，必须同步在被影响的
   Phase 文档开头的"前置条件"小节加一句提示，并 @ 相关负责人确认。
4. 只有走完以上留痕流程，才能修改任务表本身；**严禁直接覆盖原文字**
   而不留下变更痕迹，否则复盘时无法判断"计划为什么变成现在这样"。

---

## 五、Sprint / Phase 结束时的复盘产出（最低要求）

每个 Sprint 结束（不只是 Sprint 3 的正式复盘），至少产出以下内容，
可以是 PR 描述、也可以是简短的 issue，但必须存在：

- 本 Sprint 验收标准是否全部达成（逐条对照，不是笼统写"完成"）
- 是否触发了任何止损条件；若触发，是否已按第四节流程留痕
- `MIGRATION_STATUS.md` 是否已同步更新
- 下一个 Sprint 开始前，是否需要更新任何依赖它的 Phase 文档的
  "前置条件"

---

## 六、文档写作规范（保持所有 Phase 文档的一致性）

为了让 11 个 Phase 文档保持统一可读性，新增/修改文档时遵守：

1. **每个 Phase 文档结构固定**：现状盘点 → Sprint 划分（任务表 +
   验收标准 + 止损条件）→ 完成标志。新增 Phase 文档必须遵循同样结构，
   不要发明新格式。
2. **验收标准必须可验证，不能是主观描述**：
   - ❌ "系统运行良好"
   - ✅ "现有 398 个测试中，与 goal_mode 相关的部分全部通过"
3. **止损条件必须包含触发信号 + 应对动作**，缺一不可：
   - ❌ "如果有问题就调整"
   - ✅ "如果 Adapter 双向转换出现数据丢失，暂停向 Memory 推广，
     先在本 Sprint 内部把协议改稳"
4. **任何"占位/暂不实现"的设计，必须在文档里显式标注 TODO 和填充
   时机**（参考 `05-phase4-unified-state-sprint-plan.md` 里
   SelfState/WorldState 占位的写法），不允许留下没有说明的空实现。
5. **评估迁移链耦合度时，`scripts/dep_graph.py --module` 要按"具体
   要迁移的类/子模块"扫描，不要只扫顶层包**（
   Sprint 1.5 教训，见
   `03-sprint1.5-memory-perception-coupling-assessment.md` "一、
   现状盘点"）：像 `perception/` 这种把多个不相关概念（Memory、
   Self、GoalBacklog、system_events……）捆在一个顶级包里的模块，
   直接扫整个包会把互不相关的耦合来源加在一起，得到一个夸大且
   无法拆解行动的数字（例如"inbound 69"）；改成
   `--module perception.memory_store`、`--module perception.self_model`
   这样按子模块/类分别扫描，才能定位到真正需要处理的耦合点，
   也才能对"哪个概念可以先迁移、哪个需要先做 facade"给出有区分度
   的建议。

---

## 七、与本目录其它文档的关系

- 本文档规定的是"过程规范"，不改变 `02`-`11` 里已经定好的任务和
  验收标准本身。
- 如果本规范自身需要调整（比如发现 `MIGRATION_STATUS.md` 的字段
  不够用），按第四节"计划变更流程"的方式，在本文档追加"变更记录"
  小节留痕，同样不允许静默修改。
