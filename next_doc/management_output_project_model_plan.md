# 管理项目与产出项目模型改进计划

> 状态：**设计已确认（含第 12 章决议），待实施，尚未动代码**
> 关联文档：`goal_tree_system_plan.md`、`output_projects_root_and_git_isolation_plan.md`、`output_projects_intro_and_kanban_plan.md`、`goal_cron_output_directory_convention_plan.md`、`mini-agent-philosophy-and-roadmap.md`

---

## 0. 本文档管什么

本文档统一 mini_agent 中"目标、项目、产出物"三者的概念与关系，明确：

- 目标树的结构如何从"固定层级"转为"通用递归 + 节点属性"；
- 什么样的目标才算"项目"，并给出判断标准与范例；
- **管理项目**（持续推进的工作）与 **产出项目**（交付对象的容器）是两个不同维度的概念，如何关联；
- 产出项目的版本如何管理；
- 全局产出根目录（`output_projects_root`）、注册表与定期巡检如何组织；
- 如何与现有目录和数据**兼容**，且不做破坏性更新。

本文档**不管**：具体的 UI 样式、单个 cron 任务的内部实现、代码级别的函数签名（这些在各阶段实施记录中补充）。

## 1. 背景

### 1.1 现状：产出散落，目标与产出之间缺少关联

当前与"产出"相关的存放位置至少有六处：

| 位置 | 来源 | 与目标的关联 |
|---|---|---|
| 会话目录 `session_dir/output` | 普通对话产出 | 无 |
| adhoc 工作目录 | 无会话绑定的临时任务 | 无 |
| workflow 会话目录 | 工作流执行 | 无 |
| `.agent/daemon_run_outputs/goals/<id>/` | 周期性 Goal 每轮产出与 manifest | 仅能通过 goal_id 反查 |
| `goal.user_output_dir` | 用户为目标指定的交付路径 | 仅是一个路径字符串 |
| `output_projects_root`（默认 `./output_projects/`） | 调研、产出类独立项目 | **无**：只是目录扫描，没有 id，不知道属于哪个目标 |

此外，`external_projects/` 是另一套独立机制（有 `project.yaml`、调度入口、账本），本质是长期运行的服务，不属于产出链路，本计划不改动它。

### 1.2 现状：目标树结构与执行语义耦合

目标树（`perception/goal_backlog.py`）当前定义了五个固定层级：

```
ultimate → domain → stage → goal → objective
```

其中只有 `goal` 与 `objective` 参与执行语义（GoalJudge、调度）。这带来两个问题：

1. **层级决定行为**：改变一个节点的层级，等于改变它是否被执行，语义耦合过紧。
2. **"方向"概念被硬编码为层级**：`domain` / `stage` 实际承担了"长期方向"的角色，但它们与执行语义绑定，无法自由组合。

### 1.3 现状：管理与产出混在一起

"构建一个 xxx 系统"既是一段持续推进的管理工作（有阶段、决策、复盘），又是一个最终留下系统本身的产出对象。当前代码中两者没有区分，导致：

- 同一个目标无法表达"这段工作的管理过程"与"它交付的对象"的区别；
- 后续"优化 xxx 系统"这类迭代工作，无法自然地复用同一个产出对象，只能另起炉灶；
- 版本的概念缺乏归属：版本属于交付对象，但目前没有任何结构承载它。

## 2. 设计目标

1. **统一目标树结构**：目标树为通用递归结构，任意深度；节点行为由属性决定，层级只作为可读标签。
2. **给出可操作的"项目"判断标准**，使用户和 agent 能一致地判断某个目标是否应成为项目。
3. **区分管理项目与产出项目**，并允许两者多对多关联，关联带角色（build / iterate / reference）。
4. **产出版本可追溯**：版本属于产出项目，通过手动发布打点，每个版本可回溯到来源。
5. **产出的组织有统一根目录**：`output_projects_root` 作为全局产出根，项目相关的交付物最终落在项目目录内，与项目无关的产出保持现状。
6. **全局可见**：通过注册表管理所有产出项目（包括游离项目），并通过定期巡检报告其状况。
7. **零破坏兼容**：现有目录、数据、配置全部保留；新概念以可选字段叠加，不删除、不改名、不覆盖。

## 3. 非目标

- 不做"系统自主生成目标"（遵循理念文档第一节，明确排除）。
- 不做大范围的自动迁移：历史产出默认只登记引用，不搬运文件。
- 不改动 `external_projects/` 的调度与账本机制。
- 不要求所有目标都成为项目：纯意图节点、单次任务仍然保持现有行为。
- 不在本阶段引入新的数据库依赖，存储沿用 JSON / JSONL + 原子写 + 文件锁的既有模式。

## 4. 设计理念

本计划遵循以下原则，与 `mini-agent-philosophy-and-roadmap.md` 保持一致：

1. **以减少用户显式交代为北极星**。每个新概念都要能回答："它让用户下次少解释了什么？"如果答案是"没有"，就不引入。
2. **属性优于层级**。行为由节点属性推导，层级只是标签，避免"改层级即改行为"。
3. **关系优于目录**。项目之间的父子、组成、归属关系存放在注册表中，目录尽量平铺。目录移动或改名不应破坏语义。
4. **管理与产出分离**。"我们在做什么、进展如何"与"最终留下什么、现在是哪个版本"是两个维度，分别建模。
5. **版本由人决定何时打点**。发布是一个有意义的动作，不应由系统每次执行自动生成，否则会产生大量噪音快照。
6. **可靠先于主动**。注册、关联、版本发布都先由用户确认；巡检只生成报告与建议，不执行破坏性动作。
7. **注册表可重建**。注册表是索引与缓存，删除后可以从文件系统与节点数据重建，不是单点真相源。
8. **兼容是硬约束**。任何阶段都不能让已有数据失效或需要人工迁移才能继续工作。

## 5. 核心概念

### 5.1 目标树：通用递归结构 + 节点属性

目标树只有一种节点类型，可任意深度嵌套。每个节点具有四个布尔属性，执行语义由属性推导：

| 属性 | 含义 | 决定 |
|---|---|---|
| `verifiable` 可验收 | 有可判定的完成标准 | 是否进入 GoalJudge 判定 |
| `executable` 可执行 | 能被一次执行推进 | 是否可绑定执行入口与调度 |
| `recurring` 持续性 | 需要周期性推进与复盘 | 是否挂周期任务 |
| `deliverable` 有交付 | 会留下可持久的东西 | 是否需要绑定产出项目 |

层级标签 `ultimate / domain / stage / goal / objective` 保留为**分类标签**，只用于展示与筛选，不再决定执行行为。

**旧数据兼容**：加载旧 `goals.json` 时，根据旧层级为节点补充默认属性（如 `objective` 默认 `executable=true`、`verifiable=true`），旧标签原样保留。

### 5.2 "项目"的判断标准

一个目标节点，满足以下四条中**至少三条**，即可视为项目：

| 标准 | 含义 | 反例 |
|---|---|---|
| **持久交付** | 完成后留下一组文件或系统，而非一次性回答 | "回答一个问题" |
| **结构化容器** | 交付物有多个部分，需要组织（模块、文档集、版本） | "写一个单文件脚本" |
| **跨多次执行** | 不能在一次执行或一次会话内完成 | "整理一份今天的日报" |
| **可检视结果** | 能回答"现在完成到什么程度"，有里程碑或验收 | "提升某项能力"（无明确结果） |

**范例对照**：

| 目标 | 是否项目 | 满足的标准 | 说明 |
|---|---|---|---|
| 写一篇行业分析文章 | 否（任务） | 0–1 条 | 一次执行，一个文件，无需容器 |
| 写一本小说 | 是（产出项目） | 4 条 | 多章节、多设定文档，跨多次执行，可按章检视 |
| 提升英语口语 | 否（纯意图节点） | 0 条 | 没有持久交付物，属于个人状态目标 |
| 构建一个 xxx 系统 | 是（管理项目 + 产出项目） | 4 条 | 持续推进，最终留下系统本身 |
| 每周更新一次股票池 | 管理项目，但产出不一定是项目 | 持续性强，交付形态为滚动数据 | 属于周期管理，是否产出项目取决于交付是否需要容器 |
| 修复某个 bug | 否（任务） | 0–1 条 | 一次执行，无容器 |

**关键区分**：任务与项目的分界不在复杂度，而在**是否需要持久容器**。一个有 20 个步骤、只为得到一个文件的任务，仍然不是项目。

**判断入口**：当节点的 `deliverable` 属性为真，系统应提示用户"是否将此节点设为项目"，并展示四条标准的命中情况，由用户确认。系统不自动把节点升格为项目。

### 5.3 管理项目

**管理项目是目标树中的一个子树根**。

- 它是一个目标节点，带有 `kind=management` 标记；
- 它的子树是这段管理工作的目标结构；
- 它拥有：阶段（子节点或标签）、决策记录、复盘节奏、状态（进行中、暂停、完成、归档）；
- 它可以通过关联指向一个或多个产出项目。
- **完成后可以重新打开**。重新打开需要记录原因；每次状态流转（完成、重新打开、归档）都追加到状态历史中，不覆盖旧记录。

**管理项目的边界**：当目标的内容或目标本身发生实质变化时，应开启新的管理项目，而不是在旧项目上继续堆叠。判断标准：

- 目标没变、只是继续推进 → 同一管理项目；
- 目标变了（如"构建"变为"优化"）→ 新的管理项目，通过关联指向同一产出项目，角色为 `iterate`。

### 5.4 产出项目

**产出项目是一个交付对象的容器**，与管理项目是不同维度的概念。

- 它对应 `output_projects_root` 下的一个目录（或注册表中的一条记录）；
- 它拥有：稳定 id、产出物目录、版本列表、状态（活跃、冻结、归档）；
- 它可以由多个管理项目操作，也可以操作多个产出项目；
- **版本属于产出项目**，不属于管理项目。

### 5.5 管理-产出关联

管理项目与产出项目之间是多对多关系，关系本身带角色：

| 角色 | 含义 | 示例 |
|---|---|---|
| `build` | 管理项目负责从零构建该产出 | "构建 xxx 系统" → xxx 系统 |
| `iterate` | 管理项目负责对已有产出做迭代优化 | "优化 xxx 系统" → xxx 系统 |
| `reference` | 管理项目只读引用该产出 | "撰写 xxx 系统使用手册" 引用 xxx 系统 |

**范例**：

```
管理项目 A："构建 xxx 系统"（2026 Q1）     role = build
        ↓
产出项目 X："xxx 系统"  v0.1 → v0.2 → v1.0
        ↑
管理项目 B："优化 xxx 系统"（2026 Q3）     role = iterate
```

### 5.6 产出版本

- **粒度**：按发布手动打点。每次发布是一个有意义的动作，由用户或 agent 在用户确认后触发。
- **内容**：每个版本记录版本号、发布时间、来源管理项目与目标节点、变更说明、快照引用。
- **快照引用**：若产出项目为 git 仓库，同时打 git tag 作为引用；无论是否为 git 仓库，都在 `releases/<version>/` 下**复制全部内容**作为快照。快照是只读的，不随后续修改变化。
- **版本与执行的关系**：版本只记录"发布了什么"，不替代执行过程记录（cycle manifest、run 记录仍留在 `.agent/`）。
- **版本号**：**强制语义化版本**（`MAJOR.MINOR.PATCH`），系统校验格式合法，并校验新版本号大于已发布的最大版本号。不符合格式的发布请求直接拒绝。

### 5.7 项目之间的两种关系

项目之间存在两种**互相独立**的关系，必须分开存储：

| 关系 | 含义 | 存储 |
|---|---|---|
| **管理归属（管理树）** | 管理项目嵌套于目标树中 | 目标树节点的 `parent_id` |
| **组成（part_of）** | 产出项目 A 是产出项目 B 的一部分 | 注册表中的边 |

**组成与独立产出的判断**：若一个部分没有独立的版本与发布节奏，视为**模块**（产出项目内部的子路径，无独立 id）；若有独立版本或能被其他项目单独引用，视为**独立产出项目**，通过 part_of 挂在上层。

### 5.8 目录平铺，关系由注册表管理

- `output_projects_root` 下的产出项目目录**默认平铺**，以 slug 命名。
- 父子、组成、归属关系全部存放在注册表中，目录结构不承载语义。
- 允许（但不要求）用户或 agent 把组成关系的项目放在嵌套目录中；嵌套只是物理便利，系统不依赖它推断语义。

### 5.9 "ultimate" 根节点

- `ultimate` 保留为**可选的根**，对应"人生层面"的根目标，用于组织顶层目标树；
- 它不是强制的层级，没有 ultimate 的目标树同样合法；
- 它不承担产出语义，不能绑定产出项目。

## 6. 目录与数据布局

### 6.1 全局产出根

```
<output_projects_root>/                  # 复用现有配置项，默认 ./output_projects
  _registry/                             # 以下划线开头，列表时排除
    index.json                           # 总表：索引所有产出项目（id、标题、状态、slug、所属管理项目），以及组成关系与管理-产出关联
    projects/<id>.json                   # 每个项目一份独立记录：版本列表、状态历史、引用方、巡检结论等
  <project_slug>/                        # 产出项目目录，平铺
    PROJECT_INFO.md                      # 已有约定，保留
    PROJECT.json                         # 新增，机器可读元数据；仅在受管新建或被明确接入时写入
    output/                              # 项目根的交付物
    <module>/output/                     # 模块级交付物
    releases/<version>/                  # 发布快照（无 git tag 时使用）
    notes/  scratch/                     # 内部过程数据（沿用四目录模型思路）
```

### 6.2 `PROJECT.json` 结构（概念层）

```
id              string     稳定标识，旧项目取目录名
title           string
kind            "output"   产出项目（预留扩展位）
status          "active" | "frozen" | "archived" | "floating"
owner_goal_id   string?    所属管理项目（游离项目为空）
goal_refs       [string]   其他引用该项目的管理项目
parts           [{id, kind: "module"|"project"}]   组成关系的冗余副本，权威在注册表
versions        [{version, released_at, source_goal_id, changelog, snapshot}]
managed         bool       是否由系统受管（旧项目默认 false）
```

### 6.3 目标节点新增字段（全部可选）

```
attributes      {verifiable, executable, recurring, deliverable}   缺省由旧层级推导
management      bool       为 true 时该节点是管理项目根
output_links    [{output_id, role}]   仅管理项目根使用
```

## 7. 兼容性约束（硬约束）

每个阶段都必须满足：

1. **不改名、不移动、不覆盖**任何现有目录与文件。
2. **旧项目 id 取目录名**，接入注册表时只记录，不改动目录内容。
3. **`PROJECT.json` 只在受管新建或被用户明确接入时写入**。无此文件的旧项目视为 `managed=false`，行为与现状一致。
4. **`list_projects` 行为保持**：下划线开头的目录（如 `_registry/`）需要被排除，避免出现在看板列表中。
5. **目标节点新字段全部可选**，已有 `goals.json` 无需迁移即可加载。
6. **旧层级标签保留**，只补充属性，不删除任何字段。
7. **`goal.user_output_dir` 继续生效**。它被视为一条遗留绑定，用于推导产出项目路径，但不移动文件。
8. **"方向"相关的已有数据**（如独立表中的记录）先保持只读，待映射确认后再合并进目标树，不做覆盖式迁移。
9. **注册表可删除、可重建**。删除注册表不得丢失任何用户数据。

## 8. 方案详述

### 8.1 目标树属性化

- 为每个节点补充四个布尔属性，旧节点按层级推导默认值；
- 执行入口（GoalJudge、调度、周期任务）改为读取属性，而非层级；
- 层级标签保留在展示层，用于筛选和看板分组。

### 8.2 项目判定与提示

- 当节点 `deliverable=true` 时，系统给出"是否设为项目"的提示，并展示四条标准的命中情况；
- 用户确认后，节点被标记为管理项目根（`management=true`），并在注册表中创建对应的产出项目记录（或关联到已有产出项目）；
- 判定结果与用户的选择都记录下来，便于后续复盘判定标准是否合理。

### 8.3 产出路由

- 绑定了产出项目的执行，其交付文件直接写入对应模块的 `output/`，而不是先写到会话目录再搬运；
- 未绑定产出项目的执行，输出位置保持现状，不做任何改动；
- 过程数据（manifest、cycle 记录）仍留在 `.agent/`，不进入产出项目目录。

### 8.4 版本发布

- 提供"发布版本"动作（工具与 API 同时提供），输入版本号与变更说明；
- 动作需要用户确认；
- 版本号必须符合语义化格式（`MAJOR.MINOR.PATCH`），且大于已发布的最大版本号，否则拒绝发布；
- 发布时在 `releases/<version>/` 下复制产出项目的**全部内容**作为快照；若为 git 仓库，同时打 git tag；
- 版本记录写入该项目的独立记录表（`_registry/projects/<id>.json`），只追加，不修改已发布的条目；
- 同时在总表 `_registry/index.json` 中更新项目的最新版本号。

### 8.5 注册表与全局管理

**存储结构：总表 + 分表**

- **总表** `_registry/index.json`：索引所有产出项目，每条记录包含 id、标题、状态、slug、所属管理项目（可空）、最新版本号，并记录组成关系与管理-产出关联。总表是列表、筛选、看板展示的入口。
- **分表** `_registry/projects/<id>.json`：每个项目一份独立记录，包含完整的版本列表、状态历史、引用方、巡检结论。分表按项目拆分，避免所有项目的写操作争用同一个文件。
- 总表与分表的关系：总表是分表的索引，两者不一致时以分表为准，并由巡检报告标记不一致项。

**与 `PROJECT.json` 的关系**：受管新建的项目在目录内同时保留一份 `PROJECT.json` 作为镜像，便于目录被单独拷贝时仍能识别；旧项目不写入任何文件，其记录只存在于注册表中。

**可重建**：删除 `_registry/` 后，可以从文件系统重建：扫描一级目录，读取 `PROJECT.json`（如存在），缺失信息用默认值补齐。注意：分表中的版本历史与状态历史无法仅从目录推断，因此删除注册表会丢失这部分记录，这与"可删除、可重建"的约束存在冲突，必须在 P3 前通过在 `PROJECT.json` 中同步写入版本历史来解决（见第 13 章问题 A）。

**游离项目**

- agent 可以在无管理项目的场景下自动创建游离项目（`status=floating`），无需用户事先确认；
- 游离项目后续可以通过以下两种方式进入管理体系：
  1. **绑定到已有管理项目**：把游离项目关联到一个现有的管理项目，角色可选 build / iterate / reference；
  2. **派生新的管理项目**：根据游离项目的内容创建一个新的管理项目，并把它挂到目标树的某个节点下，再建立关联。
- 巡检报告会列出游离项目，并给出建议的归类去向，但归类动作仍需用户确认。

### 8.6 定期巡检

在维护档位下，定期（建议每日一次）运行巡检任务，只生成报告，不执行破坏性动作：

| 检查项 | 说明 |
|---|---|
| 未登记目录 | 候选接入的产出项目 |
| 缺失 `PROJECT_INFO.md` | 提示补充介绍 |
| 停滞项目 | 长期无更新，超过阈值 |
| 孤儿项目 | 所属管理项目已完成或归档 |
| 断链 | 关联或绑定指向的目标或项目不存在 |
| 游离项目 | 数量与建议归类去向 |
| 版本缺口 | 有大量未发布变更，但长期没有打点 |
| 体积与磁盘 | 占用过大的项目 |

报告写入现有的 `reports_store`，并通过现有通知渠道呈现。

## 9. 分阶段实施计划

| 阶段 | 内容 | 对现有数据的影响 | 退出条件 |
|---|---|---|---|
| **P0 只读盘点** | 扫描 `output_projects_root`，生成注册表草稿；列出六处产出位置与目标节点的对应关系；不写任何现有文件 | 无 | 能正确列出所有现有产出项目，且无误报 |
| **P1 目标属性化** | 节点增加属性字段；旧数据按层级推导默认值；执行入口改读属性 | 无（行为保持） | 现有目标的执行行为与改造前一致（特征测试通过） |
| **P2 管理项目与关联** | 支持管理项目作为子树根，建立管理-产出关联（build / iterate / reference）；支持游离项目绑定到已有管理项目或派生新管理项目 | 无（只增字段） | 能在看板上看到目标与产出项目的关联 |
| **P3 受管新建与版本** | 新建产出项目带 `PROJECT.json` 与骨架；提供手动发布版本的动作 | 只影响新项目 | 版本可回溯到来源，快照只读 |
| **P4 产出路由** | 绑定了产出项目的执行，把交付物写入模块 `output/` | 只影响绑定后的新执行 | 绑定执行的产出全部落在项目目录内 |
| **P4.5 数据采集** | 巡检以只采集、不告警的模式运行，积累停滞、版本缺口等指标的实际分布 | 只读 | 形成阈值校准所需的样本数据 |
| **P5 全局巡检** | 注册表完整化，定期巡检任务生成报告；依据 P4.5 数据设定阈值 | 只读 | 报告准确，无误判导致的不必要打扰 |
| **P6 接入辅助** | 对巡检发现的未登记项目，提供"一键接入"，需用户确认 | 仅在用户确认后写入 `PROJECT.json` | 接入后不影响原目录内容 |

**阶段之间的依赖**：P0 是后续所有阶段的前提；P1 与 P2 可并行推进的部分较少，建议顺序执行；P4 依赖 P2 的绑定结构。

## 10. 验收指标

| 指标 | 说明 | 目标 |
|---|---|---|
| **零破坏** | 现有目录与文件在每个阶段前后的内容哈希一致（P0–P2 期间） | 100% 保持 |
| **判定一致性** | 同一目标在不同时间被判定为项目的结果一致 | 与人工判断的一致率持续提升 |
| **产出可找到率** | 绑定了项目的执行，其交付物能从目标节点一步找到 | 接近 100% |
| **交代成本下降** | 用户为了找到产出、登记产出、确认版本而需要手动操作的次数 | 逐阶段下降 |
| **巡检有效率** | 巡检报告中被用户采纳的建议比例 | 持续跟踪，用于调整阈值 |

## 11. 风险与应对

| 风险 | 说明 | 应对 |
|---|---|---|
| 概念过多，用户难以理解 | 管理项目、产出项目、版本、关联角色等概念较多 | 界面上以"这段工作"与"这个成果"两种视角呈现，隐藏内部术语 |
| 注册表与文件系统不一致 | 文件被手动移动或删除 | 巡检检测断链；注册表可重建 |
| 项目判定标准过严或过松 | 四条标准可能不适用于所有领域 | 判定结果与用户选择都记录，定期复盘调整 |
| 版本快照占用空间 | 频繁发布会导致快照膨胀 | 优先使用 git tag；巡检报告体积；允许用户清理旧快照 |
| 与现有机制冲突 | `goal.user_output_dir`、daemon_run_outputs 与新路由并存 | 第 7 节兼容约束；新路由只作用于绑定后的执行 |
| 旧"方向"数据无法自动映射 | 独立表中的数据与目标树的映射关系不明确 | 保持只读，待人工确认映射后再合并 |
| 范围膨胀 | 理念文档提醒新增子系统需要减少用户操作 | 每个阶段都以第 10 节指标检验，不达标则暂停后续阶段 |

## 12. 已决议事项

以下事项已经由项目负责人确认，作为本计划的既定决策：

| 事项 | 决议 |
|---|---|
| 版本号格式 | **强制语义化版本**（`MAJOR.MINOR.PATCH`），系统校验格式与递增关系 |
| 快照范围 | 非 git 项目**复制全部内容**到 `releases/<version>/`，不只复制 `output/` |
| 游离项目创建 | agent 可以在无管理项目时**自动创建**游离项目；后续支持绑定到已有管理项目，或据此派生新的管理项目并挂到目标节点 |
| 巡检阈值 | "停滞"与"版本缺口"的阈值**在 P5 前用实际数据校准**，不预先拍定 |
| 注册表存储 | **总表 + 每项目一份分表**，见 8.5 |
| 管理项目重新打开 | **允许**，需记录原因，状态历史只追加 |
| 管理项目与目标节点 | 管理项目是目标树的子树根（已确认） |
| ultimate 节点 | 保留为可选根（已确认） |

## 13. 仍需解决的问题

以下问题不阻塞 P0 与 P1，但需要在对应阶段前处理：

A. **分表与可重建性的冲突**（P3 前必须解决）。版本历史与状态历史只存在于分表中，删除 `_registry/` 会丢失它们。建议在每个受管项目的 `PROJECT.json` 中同步写入版本历史与状态历史的追加副本，使注册表真正可重建。旧项目没有 `PROJECT.json`，其历史只能从注册表恢复，这一限制需要在文档和巡检报告中明示。

B. **巡检阈值的初始值**（P5 前）。阈值以实际数据为准。P4 阶段应先只采集数据、不触发告警，积累足够样本后再设定默认值。

C. **游离项目派生管理项目时的目标节点选择**：派生后挂到哪个节点，是由用户指定，还是由系统给出候选。建议默认给出候选，由用户选择。

## 13. 与理念文档的对齐检查

按 `mini-agent-philosophy-and-roadmap.md` 的要求，每个阶段都需要回答以下问题：

- 这一阶段让用户下次少解释了什么？
- 新增的数据有没有明确的消费者？（避免"采集先于消费"）
- 是否在"可靠"成熟之前引入了"主动"？（巡检只报告，不执行）
- 是否推进了"自我诊断"的数据基础？（版本缺口、停滞、断链等检查项可以作为失败模式的输入）

若某阶段无法回答上述问题，应暂缓该阶段。

**A.1 写小说（项目判定为是）**

```
管理项目："写一部长篇小说"（kind=management，子树根）
  ├─ 子目标："完成世界观设定"        executable, verifiable
  ├─ 子目标："完成第一卷大纲"        executable, verifiable
  └─ 子目标："完成第一卷正文"        executable, verifiable, recurring
产出项目："novel_xxx"
  ├─ output/        正文、设定文档
  └─ releases/v0.1  首卷发布快照
关联：管理项目 → 产出项目，role=build
```

**A.2 构建与迭代 xxx 系统**

```
管理项目 A："构建 xxx 系统"（build）
管理项目 B："优化 xxx 系统"（iterate）
产出项目 X："xxx 系统"  v0.1 → v0.2 → v1.0 → v1.1
```

**A.3 写一篇文章（不是项目）**

```
目标节点："写一篇行业分析文章"
  attributes: executable=true, deliverable=true, verifiable=true
  判定：持久交付=是，结构化容器=否，跨多次执行=否，可检视结果=是 → 命中 2 条，不设为项目
  产出：写入现有路由（未绑定项目），保持现状
```

**A.4 提升英语口语（不是项目）**

```
目标节点："提升英语口语"（纯意图节点）
  attributes: deliverable=false
  不进入项目判定，不绑定产出项目

  判定：持久交付=是（滚动数据），结构化容器=待定，跨多次执行=是，可检视结果=是
  若命中三条及以上则设为产出项目；否则只作为管理项目，不绑定产出项目
```
