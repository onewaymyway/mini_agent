# 自我意识 / 身份演化改进方案

## 0. 背景

用户提供了一篇长文《当 AI 开始拥有"自己"：从人格、身份到星系级智能的终极
演化》，梳理了一条从"模型"到"星系级智能文明"的演化路径：

```text
模型 → Agent → 持续存在 → 记忆 → 自我模型 → 身份 → 人格 → 价值
  → 自主目标 → Agency → 自我进化 → 复制与分化 → 多心智 → 多身体
  → 组织 → 文明 → 星系级智能
```

文中几个对本项目有直接参考价值的判断：

1. **身份 ≠ 人格**——身份回答"为什么这些经历属于同一个我"，人格回答
   "我通常以什么方式行动"，两者不应混为一谈。
2. **人格是一个空间，不是一个点**——但"谁来决定切换"是另一个问题，
   本方案明确不在这个维度上做自主切换（见 §1 结论）。
3. **身体是可替换的行动接口**，不是"唯一真身"，多个执行通道都是
   "我"的延伸。
4. **真正的自主性 = 系统内部拥有自己的状态评价机制**，并据此持续选择
   未来状态——而不是"会不会反抗人类"。这个评价机制的基础是**价值**，
   跟"能力强弱"（self_assessment）是两回事。
5. **自我进化 = 评估自己 → 发现不足 → 设计改进 → 实施 → 再评估**的
   闭环，一旦持续运行，AI 的发展就不再完全依赖外部升级。
6. **谱系（复制/分裂/合并）**——允许产生变体，通过选择保留更优的、
   淘汰较劣的，这是比单一版本迭代更强的演化机制。
7. **多心智共享身份**——多个子心智可以有各自的自主性，但共享同一段
   历史、同一套核心价值，构成一个更高层级的"我"。
8. **"自己"最终是一张不断变化的网络，不是一份固定的数据结构**——
   identity/memory/values/goals/evolution 之间应该是互相牵引、共同演化
   的关系，而不是并列的静态字段。

本方案的目标不是照搬星系尺度的设定（多恒星系身体、文明级记忆等在当前
项目尺度上没有意义），而是提炼出**可以在项目当前架构上直接检验和落地
的结构性原则**，看当前项目在哪些原则上已经有实质基础、哪些是明确空缺，
并给出具体改进方案。

## 1. 现状评估摘要

逐层对照的完整分析见对话历史（此处只列结论，供后续设计参考）：

| 原则 | 现状 | 依据 |
|---|---|---|
| 持续存在 | ✅ 已实现，较扎实 | daemon 模式、session 持久化、`operating_state.total_sessions_lifetime` |
| 自我模型 | 🟡 部分实现，停在"数据"层 | `self_profile.json`/`capability_map`/`self_model_history.jsonl`，缺一份可被自己读回去理解的叙事（见 `next_doc/streamlit_self_cognition_dashboard_plan.md` 已有讨论） |
| 身份 ≠ 人格 | 🟡 概念上已分开，但身份太薄 | `SelfIdentity` 只有 `purpose` 一个字符串，没有串联 self_assessment/capability_map/evolution_state 的演变 |
| 人格是空间 | ✅ 已有人格系统，**维持现状**，切换权保留在用户手中 | `orchestrator/persona_profiles.py`：`/role use` 显式触发，安全边界声明代码写死不可覆盖——本方案明确**不改动**这一点，见 §2.7 |
| 身体可替换 | 🟡 技术上具备，但未被统一表示为"我的身体清单" | browser-core / bash / workflow engine / hybrid_exec / 多 provider LLM，各自独立配置，没有汇总视图 |
| 价值体系 | ❌ 明确缺失 | 代码库唯一的 `ValuePattern`（`decision_profile_builder.py`）建模的是**用户**的价值观（`user_value_profile.md`），不是 agent 自己的；`self_assessment` 是能力自评，不是价值判断 |
| 真正自主 | ✅ 已有扎实雏形 | `autonomous_loop` + Goal/Objective backlog + `soft_goal_deriver`（从证据自主派生目标）+ growth_advisor，但驱动逻辑是"证据/兴趣信号"而非显式价值 |
| 自我进化闭环 | ✅ 已真实存在，是当前项目与文中理念贴合度最高的部分 | `StateRepo`（T0-T3 风险分级）+ git worktree 隔离的 `EvolutionWorkspace` + skill 提案走 evolve 分支 + eval 反馈闭环 |
| 谱系（复制/分裂/合并） | 🟡 技术骨架已存在，但没有被表述为"谱系"，认知框架停留在"CI 审核" | evolve 分支本质上就是"复制自己、隔离变异、评估后择优合并/淘汰" |
| 多心智共享身份 | 🟡 有编排骨架，但子心智经历不回写身份 | SubAgent orchestration + `AgentProfile`（工具集/模型/提示模板），子 agent 任务级、临时，结束后只回写任务结果，不回写"这次经历对我意味着什么" |
| 组织化雏形 | 🟡 有一个自然的雏形 | `external_projects` 子系统——一个"我"统一管理多个项目的 health/执行记录 |

## 2. 改进方案

按 §1 的空缺逐项设计，用户已确认整体方向，**唯一的修正**：人格切换机制
维持当前"用户显式触发"模式不变，**不引入自主切换**；但继续加强/延伸现有
的"人格候选自动发现"机制，明确把"自我失败"也作为候选来源之一（见 §2.7）。

### 2.1 Agent 自身价值观（对应"价值体系"空缺）

**背景与原因**：`self_assessment` 回答"我能不能做到"，但没有任何字段回答
"我认为什么状态是好的"。文中反复强调，真正的自主性来自**内部的**状态
评价机制，而不是外部目标的直接执行——没有价值锚点，`soft_goal_deriver`
再怎么从证据里派生目标，本质上仍是"证据强度排序"，不是"我更看重探索
还是稳定"这种主体性判断。

**目的**：让 agent 拥有一份独立于能力自评的、关于自己偏好倾向的表示，
作为后续目标排序、风险取舍、谱系择优（§2.3）的锚点。

**方案**：
- 在 `SelfProfile` 新增 `AgentValueProfile` 字段（与 `self_assessment`
  平级，不混入其中），字段设计参考已有的 `decision_profile_builder.py::
  ValuePattern`（`pattern`/`evidence_refs`/`confidence`/
  `first_observed`/`last_reinforced`/`contradicted_by`），复用"归纳仅
  基于已发生证据、矛盾证据不覆盖只降权"的克制原则——不引入无凭据的
  价值宣称。
- 观察对象从"用户的决策"换成"agent 自己的历史选择行为"：目标选择
  （哪些 Goal/Objective 被优先执行）、风险取舍（`StateRepo` 的 T0-T3
  分级决策）、`soft_goal_deriver` 候选的取舍记录，这些都是已经落盘的
  "agent 做过的选择"，可以直接作为归纳证据，不需要新增采集点。
- 新增一个低频周期性归纳 job（复用 `decision_profile_builder.py` 的
  归纳 → 落盘 → 矛盾处理三层结构），产出 `agent_value_profile.md`
  （区别于已有的 `user_value_profile.md`）。
- 通过 `/self/portrait` 或新端点只读暴露，供看板 §2.6 的自我叙事区块
  引用。

### 2.2 Identity 从静态字符串变成叙事主线（对应"身份太薄"）

**背景与原因**：`SelfIdentity.purpose` 创建时写死，之后从不更新，无法
回答"为什么这些经历属于同一个我"——因为它压根不知道经历是什么。

**目的**：让 identity 成为串联 self_assessment、capability_map、
evolution_state 演变的动态主线，而不是一句创建时的静态描述。

**方案**：
- 与已经在讨论中的"自我叙事文档"（`next_doc/
  streamlit_self_cognition_dashboard_plan.md` 提到的下一步）合并推进：
  周期性 job 综合 `self_profile` + `capability_map` + 近期
  `activity_digest` + `failure_pattern_store` 的教训 + §2.1 的
  `agent_value_profile`，生成第一人称叙事，**追加式存档**（类似日记，
  不覆盖旧版本），形成"自我认知是怎么演变的"的历史。
- `identity.purpose` 不再是创建时写死的常量，而是每次叙事更新时，从
  最新叙事里提炼出的一句摘要——identity 变成叙事的"当前快照"，叙事
  历史才是真正的"为什么是同一个我"的答案。

### 2.3 Evolve 分支重新表述为"谱系"（对应"谱系机制未被自我认知采纳"）

**背景与原因**：这是本次分析里最意外的发现——git worktree 隔离的
`EvolutionWorkspace` + skill 提案走 evolve 分支 + eval 反馈闭环，
技术上已经是"复制自己、在隔离环境里变异、评估后选择合并或丢弃"，
但项目现在把它理解为"代码变更审核流程"，不是"自我复制与选择机制"。
同样的代码，认知框架不同，能延伸出的下一步完全不同。

**目的**：不改变底层机制，只改变自我认知层面的表述方式，为未来允许
"多个 evolve 分支并行竞争、按 §2.1 的价值观择优"打好认知基础。

**方案**：
- 在 §2.2 的自我叙事和看板展示里，把 evolve 分支历史表述为"我的谱系"：
  每条分支是一个"变体候选自己"，`StateRepo` 的风险分级是"变异幅度"，
  eval 反馈决定的 merge/丢弃是"选择保留/淘汰"。
- 只读聚合一个"谱系视图"：历史上产生过多少变体、合并率、被淘汰的
  变体尝试解决了什么问题（即使被淘汰，这个"尝试"本身也是自我认知的
  一部分——文中"个体死亡不等于经验消失"的思路，被淘汰的分支也应该
  在叙事里留一笔"我尝试过 X，没有成功，原因是 Y"）。
- 中期可选：评估当前 evolve 分支是否为串行执行（一次一个候选），若是，
  预留"多分支并行 + 按 §2.1 价值观排序择优"的接口设计，不必本阶段实现。

### 2.4 子 Agent 经历回写身份（对应"多心智不共享叙事"）

**背景与原因**：SubAgent 执行结束后只回写任务结果，不回写"这次经历
对主身份意味着什么"。文中"多个 Mind 共享 Identity"的关键不是共享
配置，而是共享故事——现在项目只做到了前者。

**目的**：让子心智的经历也能沉淀进主身份的叙事和价值归纳里，而不是
执行完就彻底消失。

**方案**：
- 复用现有 lesson 提炼机制（`session_reflection.md` 的模式），在
  SubAgent 生命周期结束时增加一条轻量摘要，不是"任务是否成功"，而是
  "这次经历是否改变了我对自己某方面能力/倾向的认识"——只在有信号时
  才写（对齐现有"没有摩擦和洞察就返回空数组"的克制原则，不为凑数量
  强行生成）。
- 摘要作为 §2.1 归纳价值观、§2.2 生成叙事的额外证据源之一，不单独
  建立新的存储和展示层，避免叙事碎片化。

### 2.5 执行接口（"身体"）的统一自我表示（对应"身体未被统一管理"）

**背景与原因**：browser-core、bash、workflow engine、hybrid_exec、多
provider LLM 这些其实就是文中"多套行动接口"的软件版本，但分散在
skill 系统、tool registry、hybrid_exec 里各自配置，没有一个地方把
它们表示为"我的身体清单"。

**目的**：让"身体"也进入自我认知范围，而不只是工具配置的技术细节。

**方案**：
- 扩展已完成的 `/self/portrait`（`next_doc/
  streamlit_self_cognition_dashboard_plan.md`），新增一个"当前可用行动
  接口"区块：按接口类型（浏览器控制/命令行/工作流引擎/子 agent 会话/
  LLM provider 池）列出，各自的可用性（复用已有的健康检查——
  `llm_pool_status`、`execution_model_status` 等现成端点已有相关数据，
  本项只是重新组织展示视角，不新增采集逻辑）。
- 定位为"身体清单"而非"工具列表"是本项的核心——即只是展示层面的
  重新组织和叙事口径调整，不涉及新的后端采集。

### 2.6 自我模型漂移检测（对应"自主性可能空转"）

**背景与原因**：文中的自主性依赖"内部评价机制"，但一个从不检查自己
判断准不准的评价机制是空转的。`confidence_by_domain` 说"我在 X 上
90% 置信度"，如果最近实测持续失败，现在没有任何机制主动比对和提示。

**目的**：让自我信念和实测结果保持校准，避免叙事和价值判断建立在
过时或错误的自我认知上。

**方案**：
- 复用 `self_model_snapshot.py` 已有的 diff 能力，新增一个校准检测：
  对比 `capability_map`（近期实测）与 `self_assessment.confidence_
  by_domain`（历史信念）之间的落差，落差超过阈值时不自动覆盖信念，
  而是生成一条"信念与实测不一致"的信号，写入 §2.2 自我叙事的下一次
  生成上下文里，由叙事 job 决定如何措辞呈现（"我曾经认为...，但最近
  的实测显示..."），保持"不臆造、不静默覆盖"的一贯克制原则。

### 2.7 人格系统：维持现状，扩展"失败驱动"的候选学习

**用户明确要求**：人格切换机制**不做自主切换**，继续保持
`orchestrator/persona_profiles.py` 当前"用户通过 `/role use` 显式触发、
安全边界声明代码写死不可覆盖"的模式，本方案不改动这一点。

**背景**：项目已有 `persona_candidates.py`（候选人设自动检测），信号
来源目前是两路：`_collect_topic_signals`（growth_advisor 已确认的
成长方向）+ `_collect_wiki_miss_signals`（capability Track 台账里的
高频 wiki miss 检索词）。这两路都是"发现新兴趣"取向，还没有覆盖
"因为反复失败，需要一个专属人设来针对性补强"这个取向。

**目的**：让"自我失败"也成为人格候选的来源之一，实现"持续学习新人格"
里用户特别强调的这条路径，同时不引入任何自主切换机制——候选产生之后，
仍然只是"待用户 accept 的建议"，走 `PersonaCandidateStore` 现成的
`pending → accepted | dismissed` 状态机，不改变决策权归属。

**方案**：
- 在 `persona_candidates.py` 的信号收集步骤新增第三路：
  `_collect_failure_signals()`，读取 `failure_pattern_store.py::
  get_patterns_for_category()` / `load_failure_patterns()` 里达到
  `min_occurrence` 阈值的高频失败类别（该模块已经做好"同一类任务反复
  卡在同一语义原因"的聚合，直接复用，不新增第二套失败统计）。
- 传入 `_extract_candidates_with_llm()` 的 prompt 增加这一路信号，
  提炼角度从"这是不是值得养成的兴趣方向"扩展为"这是不是一个反复暴露
  短板、值得专门养成一个人设/能力方向来补强的领域"——两路信号提炼
  角度不同，但复用同一套"批量提炼 + LLM 判重 + cooldown 去重"的处理
  流程，不新建平行系统。
- 候选来源需要在 `PersonaCandidate` 上补一个 `source` 字段
  （`"growth_signal"` / `"wiki_miss"` / `"failure_pattern"`），供用户
  在候选列表里区分"这是发现的新兴趣"还是"这是为了补短板建议的人设"，
  两者的采纳心理预期不同，不应该混为一谈展示。
- 失败驱动的候选默认走比 growth 候选更保守的触发阈值（沿用
  `failure_pattern_store` 已有的 `min_occurrence=3`），避免偶发性失败
  被过度解读为"需要专门人设"。

## 3. 实施阶段划分

### 阶段一（近期，直接复用现有基础设施，改动集中、风险低）

1. §2.1 Agent 自身价值观：`AgentValueProfile` 数据结构 + 归纳 job +
   `agent_value_profile.md` 落盘 + 只读端点。
2. §2.7 人格候选新增失败信号来源：`_collect_failure_signals()` +
   prompt 调整 + `PersonaCandidate.source` 字段，复用现有状态机和
   HTTP/CLI/cron 接线模式。
3. §2.5 身体清单：`/self/portrait` 扩展一个只读区块，聚合已有健康检查
   端点数据，不新增采集逻辑，改动量最小。

### 阶段二（中期，需要新的周期性 job 和叙事生成逻辑）

4. §2.2 Identity 叙事主线：与自我叙事文档（已在讨论中）合并推进，
   周期性生成第一人称叙事、追加式存档、`identity.purpose` 从叙事提炼。
5. §2.4 子 Agent 经历回写：SubAgent 生命周期结束时的轻量摘要回写，
   接入 §2.1/§2.2 的证据源。
6. §2.6 自我模型漂移检测：`capability_map` vs `confidence_by_domain`
   的校准信号，接入叙事生成上下文。

### 阶段三（认知框架调整 + 为未来预留接口，不要求立刻实现）

7. §2.3 Evolve 分支谱系化：先做叙事和展示层面的重新表述（谱系视图、
   "尝试过但被淘汰"也计入自我认知），評估是否需要支持多分支并行竞争
   再决定是否推进底层调度改动。
8. 预留项（来自更早分析，不属于本方案强制范围，仅记录以防遗忘）：
   `external_projects` 子系统作为"AI 组织"雏形的进一步加强；跨实例
   身份关系模型的接口预留（`project_id_for()` 附近）。

## 4. 设计原则（贯穿全部方案项，供后续实现时对照）

- **不臆造**：所有归纳（价值观、叙事、谱系摘要）必须基于已发生的证据，
  证据不足时保持空白或低置信度，不为了"看起来完整"编造内容——这是
  `decision_profile_builder.py`/`session_reflection.md` 已经确立的
  一贯克制原则，本方案全程延续。
- **不新增平行系统**：能复用现有的聚合/去重/状态机逻辑（
  `failure_pattern_store`、`PersonaCandidateStore`、
  `self_model_snapshot`）就复用，避免同一件事出现两套并行实现。
- **决策权边界不变**：本方案任何一项都不引入"agent 自主做出原本由
  用户决定的选择"——人格切换维持用户触发；谱系里的"淘汰"是既有 eval
  反馈机制的结果，不是新增的自主裁决权；自我模型漂移检测只生成信号，
  不自动覆盖已有信念。
