# 信息聚合与播报系统（info_hub）外部项目方案

- **版本**：v2.0（修订草案，待确认后实施）
- **位置**：`external_projects/info_hub/`（独立外部项目）
- **前序**：v1 草案曾设计为 SQLite + 本地音频 + 主 agent 内置抓取能力，本版按用户反馈全面调整

> **修订（看板形态）**：旧的原生 HTML 看板（`ui/`、`server/app.py`、`cli.py serve`）已移除，**Streamlit 看板（`app.py`）是唯一看板**。下文凡提到 `ui/`、`server/app.py`、`info_hub serve`、HTML 前端的位置，均以 Streamlit 实现为准；`server/api.py` 保留为业务层。详见实施记录“阶段：移除旧 HTML 看板”。

---

## 1. 背景

用户希望有一个系统，能够定时从多个信息源获取内容（各平台热榜，如知乎热榜、微博热搜；推荐流，如知乎随机推荐、小红书热点；关注的小说与视频更新），经过整理后生成报告，并能在看板上直接听取。

这类需求有三个特点，决定了架构方向：

1. **信息源变化快**。网页改版、接口下线、反爬策略调整是常态，抓取脚本需要频繁迭代。如果抓取逻辑放在 mini_agent 主项目里，每次修改都会牵动主项目，风险和回归成本都很高。
2. **部分信息源需要登录**。登录一次之后应当长期有效，不希望每次抓取都要重新登录。
3. **信息源会持续增加**。今天是热榜和推荐流，之后可能加入更多订阅类来源，系统需要允许"加一种新类型"与"加一个新实例"两种扩展方式互不干扰。

因此，本方案将信息聚合作为一个**完全独立的外部项目**来做，与主项目之间只保持弱耦合。

---

## 2. 目标

### 2.1 必须达成

1. **独立**：抓取能力、解析脚本、整理逻辑全部位于 `external_projects/info_hub/` 内，不依赖、不修改主 agent 内置的 skill 与 generative_capability。主项目升级不影响本项目，反之亦然。
2. **可读**：所有产出（快照、日报、索引、运行记录）均为纯文本，即 markdown 或 json，人可以直接用编辑器打开查看。不使用 SQLite 或其他二进制存储。
3. **登录一次**：需要登录的站点通过有头浏览器由用户手动登录，登录态保存在一个共享的浏览器数据目录中，后续自动复用。
4. **定时生成报告**：支持按可配置的间隔（如每 3 小时、每天）生成报告，不限于日报。
5. **看板听报**：播报由浏览器自带的语音合成（Web Speech API）完成，在看板上手动触发，不生成本地音频文件。
6. **扩展机制**：新增信息源实例只需要改配置；新增信息源类型只需要新增一个适配器模块，无需修改核心代码。

### 2.2 明确不做（本期）

- 不做 SQLite、ORM 或任何数据库。
- 不生成本地音频文件，不做音频缓存。
- 不做服务端 TTS 合成。
- 不在抓取与整理阶段调用 LLM，保证定时任务成本可预测。LLM 仅作为可选项用于生成摘要，且默认关闭。
- 不替代主项目的 cron 调度，本项目自带调度器，主项目可以在后期通过 manifest 将其作为外部项目接入，但这不是前置条件。

## 3. 方案总览

```
┌──────────────────── 看板（浏览器）────────────────────┐
│ 报告列表 │ 信息源管理 │ 登录管理 │ 听报（Web Speech） │
└──────────────────────────┬───────────────────────────┘
                           │ 本地 HTTP
┌──────────────────────────▼───────────────────────────┐
│ info_hub 服务进程                                      │
│                                                       │
│  调度器 Scheduler ──▶ 适配器 Adapter ──▶ 原始快照      │
│  (按源/按报告间隔)     (按 kind 分派)     (raw/*.json)  │
│                                   │                    │
│                                   ▼                    │
│                       归一化 + 增量对比 + 去重            │
│                                   │                    │
│              ┌────────────────────┴──────────────┐     │
│              ▼                                   ▼     │
│       报告生成 Digest                    订阅检测 Subscription │
│       (定时, markdown + json)            (章节/视频更新)  │
│                                                       │
│  浏览器会话管理 BrowserSession（共享 profile 目录）        │
└───────────────────────────────────────────────────────┘
```

核心原则：**抓取、整理、报告全部由确定性脚本完成**。LLM 只在"帮用户生成新信息源脚本"这一个环节可选出现，且不在定时任务中出现。

## 4. 目录结构

```
external_projects/info_hub/
  PROJECT.md                  # 项目说明、运维命令、扩展指南
  project.yaml                # 对外契约（入口、参数声明），daemon 可读，但不依赖其内部代码
  config/
    settings.yaml             # 全局配置：报告间隔、语音默认参数、浏览器 profile 路径
    categories.yaml           # 分类定义（用户可编辑）
  sources/
    _index.json               # 信息源注册表（唯一真相来源，人可读）
    <source_id>/
      source.yaml             # 单个信息源的声明（类型、URL、调度、分类、字段映射）
      script.py               # 可选，仅当适配器类型为 script 时存在
      samples/                # 最近一次原始响应样本，用于调试与回归测试
  adapters/                   # 适配器类型（扩展点，见第 6 节）
    base.py
    rss.py
    json_api.py
    html_list.py
    script.py
    subscription.py
    registry.py               # 自动发现与注册
  core/
    scheduler.py              # 定时调度
    pipeline.py               # 归一化、去重、增量对比
    digest.py                 # 报告生成
    browser_session.py        # 有头/无头浏览器与共享 profile 管理
    store.py                  # 文本文件读写（原子写入、文件锁）
    speech_text.py            # 报告转朗读文本
  data/
    raw/<source_id>/<YYYY-MM-DD>/<HHMMSS>.json     # 每次抓取的原始归一化结果
    items/<source_id>/<YYYY-MM-DD>.jsonl           # 按日追加的条目记录（每行一条 JSON）
    state/<source_id>.json                          # 去重索引、上次快照指针、订阅游标
    runs/<YYYY-MM-DD>.log.md                        # 每日运行记录（markdown，人可读）
  reports/
    <YYYY-MM-DD>/<HHMM>.md                         # 报告正文（markdown）
    <YYYY-MM-DD>/<HHMM>.json                       # 报告结构化数据（给看板用）
    latest.json                                    # 指向最新报告的指针
  browser/
    profile/                                       # 共享浏览器用户数据目录（登录态所在，敏感，不入库）
    login_status.json                              # 各站点登录状态记录（非敏感元数据）
  app.py                                           # Streamlit 看板（唯一看板）
  dashboard/                                       # 听报播放器组件
  server/
    api.py                                         # 看板业务层（无 HTTP）
  tests/
  skills/
    add-source/SKILL.md                            # 项目内的信息源添加指南（仅本项目使用）
```

**关于 `data/` 与 `reports/` 的文本格式**：

- 快照与报告的正文使用 markdown，便于直接阅读。
- 结构化数据使用 json，给看板渲染使用。
- 按日追加的条目使用 jsonl（每行一条 json），既保持可读性，又避免频繁重写大文件。它仍然是纯文本，可以用 `cat`、`grep`、`jq` 直接查看。
- 所有写入采用"临时文件 + 原子重命名"，并配合文件锁，避免定时任务与看板同时写入造成损坏。

## 5. 信息源模型

### 5.1 信息源声明（source.yaml）

```yaml
id: zhihu_hot
name: 知乎热榜
category: 热点社区            # 引用 categories.yaml 中的分类 id
tags: [中文, 社区]
kind: hot_list                # hot_list | feed | recommend | subscription | custom
adapter: html_list            # 决定使用哪个适配器，见第 6 节
enabled: true
schedule:
  every: 60m                  # 抓取频率，支持 Nm / Nh / cron 表达式
browser:
  required: true              # 是否需要浏览器渲染
  login_site: zhihu.com       # 需要登录时，引用的站点标识，用于登录状态检查
  headless: true              # 默认无头；登录流程强制有头
request:
  url: https://www.zhihu.com/hot
parse:
  list_selector: ".HotItem"
  fields:
    title: ".HotItem-title"
    url: "a@href"
    heat: ".HotItem-metrics"
policy:
  max_items: 50
  retain_days: 14
  dedup_by: url
```

### 5.2 统一条目（Item）

所有适配器输出统一结构，报告与看板不关心具体来源：

```json
{
  "id": "zhihu_hot:https://www.zhihu.com/question/123",
  "source_id": "zhihu_hot",
  "category": "热点社区",
  "title": "某个热榜标题",
  "url": "https://www.zhihu.com/question/123",
  "summary": "",
  "rank": 3,
  "heat": "1200 万热度",
  "published_at": null,
  "fetched_at": "2026-11-11T10:00:00+08:00",
  "extra": {}
}
```

### 5.3 五种信息源类型的整理方式

| kind | 含义 | 整理方式 | 报告中的呈现 |
|---|---|---|---|
| hot_list | 有序热榜 | 保存每次快照的排名，与上次对比 | 新进、上升、下降、掉出 |
| feed | 增量信息流 | 按 `dedup_by` 去重，只关注新条目 | 本周期新增条目 |
| recommend | 个性化推荐（如随机推荐、热点流） | 去重并留存样本，不做排名分析 | 当前样本列表，注明"非稳定数据" |
| subscription | 关注的更新（小说、视频） | 维护游标（章节号、视频 id），检测新增 | 更新提醒，置顶显示 |
| custom | 完全由脚本决定 | 脚本返回标准 Item 列表 | 按通用规则渲染 |

## 6. 扩展机制（核心设计）

扩展分为两个层次，互不影响。

### 6.1 第一层：新增信息源实例（日常操作）

只新增一个目录与一条 `_index.json` 记录，不需要改代码。适用于大多数情况：配置一个 RSS、一个 JSON 接口、一个热榜页面的选择器。

### 6.2 第二层：新增适配器类型（扩展能力）

当现有适配器无法覆盖某类来源时，新增一个适配器模块。所有适配器实现同一个接口：

```python
# adapters/base.py
class Adapter(ABC):
    kind_name: str                       # 适配器标识，如 "rss"
    requires_browser: bool = False

    @abstractmethod
    def validate(self, source: SourceSpec) -> list[str]:
        """校验 source.yaml 配置，返回错误列表。"""

    @abstractmethod
    def fetch(self, source: SourceSpec, ctx: FetchContext) -> FetchResult:
        """执行抓取，返回归一化 Item 列表或错误。"""

    def preview(self, source: SourceSpec, ctx: FetchContext) -> FetchResult:
        """抓取前几条用于看板预览，默认复用 fetch。"""
```

`adapters/registry.py` 启动时扫描 `adapters/` 目录，自动注册所有继承自 `Adapter` 的类。新增适配器的步骤只有三步：

1. 在 `adapters/` 下新建一个模块。
2. 实现 `validate` 与 `fetch`。
3. 为其编写至少一个样本测试。

无需修改调度器、报告生成或看板代码。

### 6.3 subscription 类型的扩展

订阅类源需要定义"什么算更新"。这一部分同样走适配器扩展：每个订阅站点提供一个 `Checker`，返回当前最新的游标值（如最新章节号、最新视频 id）。调度器比较游标，发现变化即产生一条更新 Item。

### 6.4 script 适配器（承接脚本生成）

当声明式配置无法表达某个站点时，使用 `script` 适配器，由 `script.py` 实现统一函数：

```python
def fetch(ctx) -> list[dict]:
    # ctx 提供 ctx.browser（共享 profile 会话）与 ctx.http
    ...
```

脚本只允许返回标准字段的字典列表，不允许直接写入 `data/` 目录，写入由核心代码统一完成。这样即使脚本出错，也不会破坏已有数据。

## 7. 添加信息源的流程

### 7.1 三种途径

| 途径 | 适用场景 | 操作方式 |
|---|---|---|
| 表单添加 | RSS、公开 JSON、简单热榜 | 看板填写 URL、选择 adapter、配置选择器，点击"预览" |
| 对话生成脚本 | 页面结构复杂，需要探索 | 在看板输入"添加微博热搜"，由项目内的 `add-source` 指南驱动生成 |
| 手写 | 高级用户 | 直接编辑 `source.yaml` 与 `script.py` |

### 7.2 对话生成脚本的具体流程

这里需要明确：**生成流程只使用本项目自己的能力，不调用主 agent 的 skill 或 generative_capability**。具体如下：

1. 本项目提供 `browser/explore` 工具，使用共享 profile 打开目标页面，输出页面结构摘要、候选列表容器、网络请求中的 json 接口列表。
2. `skills/add-source/SKILL.md` 指导生成方（一个 LLM 会话，仅读取本项目配置的 LLM provider）基于探索结果选择最合适的 adapter，优先顺序为 rss > json_api > html_list > script。只有前三者都不适用时才写 script。
3. 生成结果写入 `sources/<id>/` 并自动运行一次 `preview`。
4. 看板展示预览的前 10 条与字段完整性检查结果，用户确认后才正式启用。

### 7.3 查重机制

新增信息源前必须执行查重，这一点是吸取了 browser_site_scraper 反复生成重复 member 的教训：

- 按 `kind + 域名（去掉协议与子域名的通配）+ 列表选择器或接口路径` 计算指纹。
- 指纹命中已有源时，看板提示"已存在相似信息源：<id>，是否修改该源而不是新建？"
- 域名匹配必须同时兼容裸域名与带 `www.` 的域名，避免重复前车之鉴。

## 8. 登录与共享浏览器会话

### 8.1 设计要点

- **单一共享 profile**：所有需要登录的站点共用同一个浏览器用户数据目录 `browser/profile/`。登录一次，各站点的 cookie 与本地存储都保存在其中，之后的无头抓取自动复用。
- **登录由用户触发**：看板上每个需要登录的站点旁有"登录"按钮。点击后启动**有头**浏览器，打开该站点的登录页，用户手动完成登录，关闭窗口后系统记录该站点的登录状态。
- **登录状态检测**：每次抓取前，适配器可调用站点的 `is_logged_in` 检查（如访问个人页面是否跳转到登录页）。失效时，该源标记为"需要重新登录"，不会静默失败。
- **互斥**：同一个 profile 同一时间只能被一个浏览器进程占用。登录与抓取通过 `browser_session` 的文件锁串行化。登录进行时，依赖浏览器的抓取任务排队等待。
- **敏感性**：`browser/profile/` 包含登录凭据，必须加入 `.gitignore`，并在看板文档中注明不要分享此目录。`login_status.json` 只记录站点名与最后检查时间，不包含任何凭据。

### 8.2 需要说明的风险

- 浏览器 profile 在某些平台上可能因版本变化而失效，此时需要重新登录，这是正常现象。
- 有些站点会对频繁的无头访问做风控，建议抓取频率不要过高，并在 `settings.yaml` 中设置站点级的最小间隔。

## 9. 定时报告

### 9.1 报告间隔可配置

`settings.yaml` 中定义报告计划，不限于日报：

```yaml
reports:
  - id: rolling
    every: 3h                  # 每 3 小时生成一份
    window: 3h                 # 覆盖最近 3 小时的增量
    categories: all
  - id: daily
    at: "08:00"                # 每天固定时间生成
    window: 24h
    categories: all
```

### 9.2 报告内容结构

每份报告是一个 markdown 文件，结构如下：

```markdown
# 信息报告 2026-11-11 15:00（窗口：12:00–15:00）

## 概览
- 本周期新增 128 条，热榜更新 4 个源，订阅更新 2 条，失败源 1 个

## 订阅更新
- 《某小说》更新至第 320 章（上次：第 318 章）

## 热点社区
### 知乎热榜
- 新进：……
- 上升：……（3 → 1）
- 掉出：……

## 资讯
...

## 异常
- 微博热搜：需要重新登录
```

同时生成对应的 `.json`，结构与 markdown 对应，供看板渲染与听报使用。

### 9.3 报告与抓取的关系

- 抓取由各信息源自己的 `schedule` 驱动，可以快于或慢于报告间隔。
- 报告只读取窗口内的 `items/*.jsonl` 与状态文件，不触发抓取。
- 报告生成失败不影响抓取数据，已生成的报告保持不变。

## 10. 听报（看板手动触发）

### 10.1 行为

- 在看板的报告页面，每份报告旁有"听报"按钮，也可以对单条内容点击"朗读"。
- 朗读由浏览器的 Web Speech API（`speechSynthesis`）完成，全部在前端执行，服务端不生成音频。
- 播放器支持：播放、暂停、继续、停止、上一段、下一段、语速、音色（取决于浏览器提供的语音列表）。
- 播放进度与语速偏好保存在浏览器本地存储中，刷新页面可恢复。

### 10.2 朗读文本的生成

`core/speech_text.py` 负责把报告 json 转成适合朗读的段落列表：

- 去除 url、markdown 符号、表情符号与多余空白。
- 按小节切分为段落，每段不超过一定长度，避免单段过长导致语音合成中断。
- 数字、英文缩写保持原样，由浏览器语音引擎自行处理。
- 段落列表由服务端返回，前端逐段调用 `speechSynthesis`。

### 10.3 与小说听书的复用

`novel_writer` 的 listen 组件已经实现了播放队列与重试逻辑。本项目参考其队列设计，但不直接依赖其代码，避免跨项目耦合。如果后续需要统一，可以将播放器抽取为共享前端模块，这属于后期优化项。

### 10.4 已知限制

- Web Speech 的语音列表因浏览器与操作系统而异，中文语音是否可用取决于用户环境。
- 部分浏览器要求用户先有一次点击操作才能发声，播放按钮需要满足这个前提。
- 语音只在打开看板的浏览器标签页中播放，无法在后台或手机锁屏时播放。

## 11. 订阅来源（小说、视频等）

> **实现说明（P8）**：Checker 返回“最新在前的候选游标列表”，游标比较由 pipeline 完成，首次只记基线；内置 feed_latest / json_latest / html_latest 三个通用检查器（包装现有列表适配器）。详见 PROJECT.md“订阅源”与实施记录 P8。

订阅类源是后续最可能持续增加的部分，因此单独设计。

- 每个订阅源由一个 `Checker` 实现，接口为：输入配置，输出当前游标（如 `{"chapter": 320, "title": "..."}`）。
- 游标保存在 `data/state/<source_id>.json` 中。
- 调度器比较新旧游标，只有变化时才产生更新 Item，并标记为"订阅更新"进入下一份报告。
- 订阅源的配置中可以定义过滤条件，例如只关注某个作者或某些关键词。

第一批计划支持的订阅形式（具体站点待你确认）：

- 小说：按作品页的最新章节号检测。
- 视频：按 UP 主或频道的最新视频 id 检测。

后续新增订阅站点，只需要实现一个 `Checker` 并在 `sources/` 中添加实例。

## 12. 看板功能

| 页面 | 功能 |
|---|---|
| 报告 | 按时间倒序列出报告，可查看 markdown 渲染结果，支持听报、下载原文件 |
| 信息源 | 列表（按分类分组）、启停、立即抓取、最近结果、健康状态、编辑配置 |
| 添加信息源 | 表单添加 / 对话生成 / 预览确认 |
| 热榜 | 单源的排名历史（读取 items 文件绘制变化） |
| 订阅 | 所有订阅源的当前游标与最近更新 |
| 登录 | 需要登录的站点列表、登录状态、"打开有头浏览器登录"按钮 |
| 运行记录 | 每次抓取与报告生成的耗时、条数、错误信息，直接读取 `runs/*.log.md` |
| 设置 | 分类管理、报告计划、语音偏好、全局抓取间隔 |

所有页面都直接读取文件，不依赖数据库查询，因此人工修改文件后刷新页面即可生效。

## 13. 运行与调度

- 项目提供命令行入口：`streamlit run app.py`（启动看板，进程内带后台调度）、`info_hub run <source_id>`（立即抓取单源）、`info_hub report <plan_id>`（立即生成报告）、`info_hub login <site>`（打开有头浏览器登录）。
- 调度器为单进程，内部按各源与报告计划的间隔排队执行。浏览器类任务串行执行，HTTP 类任务可以并发。
- 项目的 `project.yaml` 声明入口与参数，供主项目后期接入时使用。接入不是必须的，本项目可以独立运行。

## 14. 容错与可观测性

- **失败隔离**：单个源失败只影响该源，不影响其他源与报告。
- **健康状态**：连续失败 N 次后自动降低频率并在看板标红，连续失败 M 次后自动暂停，需用户手动恢复。
- **原始样本保留**：每次失败保存原始响应的前若干字节到 `samples/`，便于排查与生成回归测试。
- **运行日志**：每日一个 markdown 文件，记录每次执行的开始时间、耗时、条数、错误摘要。
- **不静默**：任何被跳过或失败的内容，都会在报告的"异常"小节中出现。

---

## 15. 安全与合规

- 凭据只存在于 `browser/profile/` 中，不写入配置文件，不进入日志或报告。
- 看板默认只监听本机地址，不对外暴露。
- 只抓取用户自己有权访问的内容，并以个人阅读为目的。对明确禁止抓取的站点，在 `source.yaml` 中标注，并由用户自行判断是否启用。
- 对推荐流类内容不做二次分发，报告中只保留标题与链接，不保存完整正文。

## 16. 实施计划

每个阶段都有明确的交付物与验收标准，完成一个阶段后再进入下一个。

### P0：项目骨架（约 0.5 天）
- 创建 `external_projects/info_hub/` 目录结构，写入 `PROJECT.md`、`project.yaml`、`config/` 默认文件。
- 实现 `core/store.py`：原子写入、文件锁、按日期路径生成。
- 验收：目录结构就位，`info_hub --help` 可运行，单元测试覆盖原子写入与文件锁。

### P1：适配器框架与首批适配器（约 1 天）
- 实现 `adapters/base.py`、`registry.py`（自动发现）。
- 实现 `rss`、`json_api` 两个适配器。
- 实现 `sources/_index.json` 的读写与 `source.yaml` 的校验。
- 验收：通过 `info_hub run <id>` 抓取一个 RSS 与一个 JSON 接口，生成 `data/raw/` 与 `data/items/` 文件，内容可直接用编辑器打开阅读。

### P2：归一化、去重与增量（约 1 天）
- 实现 `core/pipeline.py`：统一 Item、按 `dedup_by` 去重、与上次快照比较。
- 实现 `hot_list` 的排名变化计算（新进、上升、下降、掉出）。
- 验收：对同一源连续抓取两次，能正确输出变化；重复条目不会重复写入。

### P3：浏览器会话与 html_list 适配器（约 1.5 天）
- 实现 `core/browser_session.py`：共享 profile 管理、有头/无头切换、profile 文件锁。
- 实现 `html_list` 适配器，支持选择器配置。
- 实现 `info_hub login <site>` 命令，打开有头浏览器，登录后记录状态。
- 验收：登录一次后，关闭进程再次运行无头抓取，仍能获取需要登录的内容。

### P4：定时报告（约 1 天）
- 实现 `core/digest.py`：按窗口读取条目，生成 markdown 与 json。
- 实现调度器的报告计划（按间隔与按固定时间两种）。
- 验收：`reports/` 下按时间生成 `.md` 与 `.json`，`latest.json` 指向最新报告，报告内容包含异常小节。

### P5：看板基础版（约 1.5 天）
- 实现看板基础页面：报告、信息源、运行记录、设置（最初为原生 HTML，现已由 Streamlit `app.py` 取代）。
- 信息源页面支持启停与立即抓取。
- 验收：在看板上能查看报告、立即抓取单源、看到运行记录。

### P6：听报（约 1 天）
- 实现 `core/speech_text.py`，将报告转为段落列表。
- 前端实现基于 `speechSynthesis` 的播放器：播放、暂停、继续、停止、上下段、语速。
- 验收：在看板中点击"听报"可以完整朗读一份报告，刷新页面后可恢复进度。

### P7：添加信息源（约 1.5 天）
- 看板表单添加与预览。
- 实现查重指纹与提示逻辑。
- 实现 `browser/explore` 工具与 `skills/add-source/SKILL.md`，支持对话生成 `script` 类型源。
- 验收：通过对话成功新增一个需要脚本的源，查重能拦截重复添加。

### P8：订阅源（约 1 天）
- 实现 `subscription` 适配器与 `Checker` 接口。

- 验收：游标变化能产生更新条目并出现在下一份报告中。

### P9：健壮性与收尾（约 1 天）
- 健康状态机（降频、暂停、标红）。

- 验收：人为制造一个源的连续失败，系统正确降频与暂停，报告中正确显示异常。
