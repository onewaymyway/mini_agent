# 个人助理能力对照：Personal Researcher 与 Personal Coach 缺口改进方案

> **实施状态（见配套的
> `personal_researcher_and_coach_capability_gap_implementation_record.md`）**：
> R1（通用调研模板 `research_topic`）、C1（Goal 的"长期方向"分组）、
> R2（信源可信度标注）、C2（`decision_profile` 参与 Goal 创建提示）
> 均已落地。C3/C4/R3 按第 3 节的优先级建议继续延后，尚未实施。

> 前置阅读：`docs/mini-agent-philosophy-and-roadmap.md`（项目理念与当前
> 优先级）、`docs/growth-advisor-guide.md` 1.5 节"设计理念"（本文档的
> "持续调研"部分完全延续这条理念，不推翻其中任何一条约束）、
> `next_doc/growth_advisor_autonomy_deepening_plan.md` /
> `next_doc/growth_advisor_ideal_advisor_gap_and_roadmap_plan.md`（两份
> 已有的成长顾问改进规划，本文档与它们的关系见 0.3 节）。

## 0. 这份文档解决什么问题

### 0.1 背景

对照一份外部文档（个人 AI 助理的能力框架：Memory / Context /
Intelligence / Agency / Action / Trust / Learning 六大系统 + 分级功能
清单）梳理 mini_agent 现状时，识别出两个"底子已有、但没有长成一等公民
功能"的方向：

- **Personal Researcher**（持续追踪一个研究主题、交叉验证、形成观点）
- **Personal Coach**（长期目标 → 阶段目标 → 今天该做什么的层级拆解）

### 0.2 结论先行

两个方向都不需要从零搭建，而是需要**把已经在 `growth_advisor.py` 里
验证过的子能力（增量约束、跨轮次记忆、置信度衰减、主题地图聚合展示）
抽出来，做成不专属于"成长顾问"场景的通用底层机制**：

- Personal Researcher 缺的是一个**不依赖成长顾问信号扫描触发**的通用
  调研入口，复用 `growth_pursuit` 已经验证过的"持续追加同一份 wiki
  页面 + 跨轮次去重"机制
- Personal Coach 缺的是一根**"多个 Goal 是否服务于同一个更高层方向"**
  的连接轴，`decision_profile`（记录你的价值取向）和
  `next_action_advisor`（在已有 Goal 里排序）已经覆盖了"记录"和"排序"，
  唯独缺"聚合"这一层，而这一层可以直接复用成长顾问"成长主题地图"的
  现成聚合展示模式

### 0.3 与已有 growth_advisor 改进规划的关系

`next_doc/growth_advisor_autonomy_deepening_plan.md`（及 v2）和
`next_doc/growth_advisor_ideal_advisor_gap_and_roadmap_plan.md` 两份
文档，视角都是"如何把成长顾问自己打磨成一个理想的顾问"——改进范围
限定在"从用户历史交互里信号扫描发现的成长方向"这个场景内部。

本文档的视角不同：**不是继续打磨成长顾问本身，而是把成长顾问已经
验证好的引擎能力，抽出来提供给"成长顾问触发场景之外"的两类新入口
使用**——用户直接指定的任意调研主题（不限于自我成长）、以及跨越
多个 Goal 的方向性聚合（不限于成长顾问候选落地的 Goal）。两条改进线
不冲突、不重复，`growth_advisor.py` 内部的持续打磨可以按原计划继续
推进，本文档提议的改动大多是"从中抽取通用能力"，尽量不改变
`growth_advisor.py` 现有行为。

### 0.4 本文档的范围声明

**这份文档本身不引入新的执行代码**，只做差距梳理、方向提议和优先级
建议，是"已识别但尚未实施"的规划文档，具体哪几项进入下一轮实施，
由后续单独排期决定。

## 1. Personal Researcher：从"成长顾问的副产品"到"通用调研引擎"

### 1.1 现状（已核实）

已有的持续调研能力完全长在成长顾问内部，具体是
`GrowthAdvisorConfig.auto_pursue_on_accept` 触发的
`auto_pursue_candidate()` 链路（`docs/growth-advisor-guide.md` 
演进日志 2.12 节）：

- 用户采纳一个成长顾问候选后，自动落地为 Goal 并绑定周期性执行
  （默认 `interval:86400`，即每天一轮）
- 执行规范用专用模板 `growth_pursuit`（
  `src/mini_agent/perception/goal_execution_spec_templates/growth_pursuit.json`），
  产出物固定是 `wiki/growth/<topic>.md`，每轮**追加**而非新开文件
- 模板的 `handoff_fields` 定义了三个跨轮次记忆字段：
  `covered_subtopics`（已讲过的子话题，避免重复）、
  `open_questions`（上一轮留下待深挖的方向）、
  `last_source_urls`（引用来源去重）
- `per_cycle_criteria` 强制"本轮必须比上一轮有实质性增量"

这套机制本身设计得相当细致——`growth_advisor_autonomy_deepening_plan.md`
后续又补上了饱和度检测（连续低增量提示"疑似饱和"）等能力。**唯一的
限制是入口单一**：只能从"成长顾问信号扫描 → 用户采纳候选"这条路径
触发，服务对象被限定为"从用户历史对话里挖出来的、可能与自我成长相关
的主题"。

### 1.2 缺口

用户没有办法直接说"帮我持续追踪一下某个技术方案的社区讨论进展"
这类**不来自成长顾问信号扫描、且与"自我成长"这个框架不完全贴合**的
调研需求（比如追踪一个第三方项目的动态、持续关注某个行业话题）。
现在唯一能做的一次性替代方案是让 agent 在单次对话里调用 `web_search`
做一次性调研，用完即走，不会持续、不会跨轮次记忆已覆盖内容。

### 1.3 改进方向

#### R1. 把 `growth_pursuit` 泛化成一个不依赖成长顾问触发的通用模板

新增一个执行规范模板（暂命名 `research_topic`），复用
`growth_pursuit` 已验证的骨架（追加式产出物 + 三个跨轮次
`handoff_fields` + "本轮必须有实质性增量"的 `per_cycle_criteria`），
但去掉"必须来自成长顾问候选"这个前提：

- 用户可以直接通过 `/agent goals add <题目>` 或对话里表达"帮我持续
  研究一下 XX" 创建一个 Goal，agent 判断这是"调研类"需求后（可以
  复用现有 Goal 执行规范生成时的关键词粗筛机制，`research_topic`
  模板的 `keywords` 字段命中即可，与其它模板走同一套匹配路径，不
  需要新增判定逻辑）选用 `research_topic` 模板并绑定周期性执行
- 产出物路径改为 `wiki/research/<topic-slug>.md`，与
  `wiki/growth/` 区分开——两者数据结构和推进逻辑相同，只是命名空间
  和触发场景不同，wiki 索引/巩固循环等下游消费者不需要额外区分对待
  （两个命名空间可以共用同一套 wiki 治理机制）
- `growth_pursuit` 与 `research_topic` 两个模板可以共享同一份
  "增量校验 + 跨轮次记忆"底层实现（如果未来要抽公共函数，落在
  `perception/goal_execution_spec_templates/` 的模板本身是纯配置，
  真正的执行逻辑在 Goal 执行阶段读取模板骨架时统一处理，抽取成本低）

#### R2. 补一层"信源可信度"标注（轻量级，不引入额外 LLM 调用）

`last_source_urls` 目前只做去重，不区分信源质量。改进方向：

- 在追加内容块时，要求标注的来源附带一个粗粒度类型标签
  （如 `official`/`community`/`secondary`，三选一，规则可以简单
  到"域名是否匹配已知官方文档域名列表"这种零成本判定，不强求
  语义级判断）
- wiki 页面的 frontmatter 或内容块本身可以携带这个标签，供用户
  一眼看出"这段内容的信源可信度如何"，不需要打开每个链接自己判断
- 这一步是可选增强，不是通用调研引擎能跑起来的前置条件，优先级
  低于 R1

#### R3.（可选，优先级最低）交叉验证质量门

如果后续观察到"持续调研"产出的内容存在事实性错误堆积的问题，可以
考虑给 `per_cycle_criteria` 增加一条可选的"质量评估"检查（类似让
agent 对本轮新增内容做一次自我核验，标注置信度），但**不建议无条件
默认开启**——这类质量门通常需要额外一次 LLM 调用，与项目"默认零
成本、增强能力 opt-in"的一贯取舍一致，应做成配置项而非模板固有步骤。
这一步优先级明显低于 R1/R2，且收益能否覆盖成本目前没有证据支撑，
建议观察 R1 落地后的实际使用情况再决定是否投入。

### 1.4 非目标

- 不打算做"多信源交叉验证"的复杂实现（比如自动检测多个来源之间的
  矛盾并裁决）——这类能力的工程复杂度和当前证据支撑的收益不成比例，
  R3 的自我核验已经是更现实的替代方案
- 不打算把这个能力做成完全独立于 Goal/wiki 体系的新模块——复用现有
  基础设施是这份方案的核心前提，重新发明会造成能力重复

## 2. Personal Coach：补上"多个 Goal 是否服务于同一方向"这根轴

### 2.1 现状（已核实）

三个相关模块已经覆盖了教练能力的一部分，但彼此之间缺少连接：

| 模块 | 做什么 | 局限 |
|---|---|---|
| `evolution/decision_profile_builder.py`（`decision-profile-guide.md`） | 从历史决策记录归纳"用户反复表现出的价值取向"，产出 `wiki/user_value_profile.md` | 纯**回溯性**：只回答"你过去为什么这么选"，不参与"你接下来该往哪走"的决策 |
| `evolution/next_action_advisor.py`（`next-action-advisor-guide.md`） | 在已有 `GoalBacklog` 内部排序，找出"停滞目标"和"注意力错配"两类候选 | 排序发生在**已有 Goal 集合内部**，不追问这些 Goal 是否服务于一个更大的方向；候选发现规则目前只有两条，比成长顾问的置信度衰减/证据分布度这套机制简单得多 |
| `perception/goal_backlog.py::GoalNode` | 已有 `parent_id` / `children_ids` 字段 | 但 `level` 字段只有两个固定值 `"goal"` / `"objective"`，`parent_id` 链条的语义是"Objective 属于哪个 Goal"，不支持"多个独立的 Goal 共同服务于一个更高层、没有验收标准的长期方向"这种分组 |

`sys:decision_profile_update` cron job 默认关闭（需要用户手动开启，
避免样本不足导致画像失真），`decision_profile` 目前只服务两个只读
消费场景：决策问答检索、`next_action_advisor` 排序加权。

### 2.2 缺口

参考文档强调的教练式拆解是"长期目标 → 阶段目标 → 今天该做什么"，
本质是一个**跨 Goal 的聚合与关联层**。现有的 Goal Backlog 数据模型
没有这一层：一个用户可能同时有"工作项目""投资学习""内容创作"等好
几条独立的 Goal 线，系统目前没有任何机制识别"这几个 Goal 其实都是在
服务同一个更大的方向"，也不会在新建 Goal 时提示"这个方向和你过去
反复表现出的某个价值取向倾向是否一致"。

### 2.3 改进方向

#### C1. 给 Goal 引入一层可选的"长期方向"分组（不改变现有两级模型）

不建议改动 `GoalNode.level` 的既有两值约束（`"goal"`/`"objective"`），
避免牵动 Goal 执行判定、GoalJudge 等大量已经稳定运行的逻辑。改为
新增一个**独立于 GoalBacklog 执行语义的轻量聚合结构**：

- 新增可选字段 `GoalNode.direction_id: Optional[str] = None`——
  只是一个分组标签，不参与 GoalJudge 判定、不影响执行调度，纯粹
  用于展示聚合
- "长期方向"本身不是 `GoalNode`，不需要验收标准、不需要完成态判定
  （这是与"Goal"的本质区别：Goal 是"要做完的事"，Direction 是
  "一个不会真正'完成'的方向"），可以是一个更简单的数据结构（标题 +
  创建时间 + 关联的 `direction_id` 列表），类似成长顾问"成长主题
  地图"里对主题的聚合方式，但不需要 growth_advisor 那套置信度/衰减
  机制（那套是为"候选要不要生成"这个决策服务的，Direction 分组
  只是纯展示聚合，不需要决策逻辑）
- 展示层面：复用 growth-advisor 看板"🗺️ 成长主题地图"折叠区块的
  现成 UI 模式（按方向聚合展示状态/证据走势），在"📌 目标看板"tab
  加一个同构的"按长期方向聚合视图"，不需要重新设计交互

#### C2. 让 `decision_profile` 参与 Goal 创建时的提示，而不只是被动查询

现状 `decision_profile` 只有两个只读消费场景（决策问答检索 +
`next_action` 排序加权），建议补第三个：

- 用户新建 Goal，或成长顾问生成候选待采纳时，检查标题/描述与
  `user_value_profile.md` 里的高置信度模式是否有明显关联（可以先
  用简单的关键词/标签匹配，不必一开始就上 LLM 语义判断），命中时
  给一句提示——"这个方向和你过去反复表现出的 XX 倾向一致"或
  "这个方向和你过去的 XX 决策有出入，确认要往这个方向走吗"
- 这一步**只是提示，不阻断创建**，与 `decision_profile` 现有的
  "矛盾不覆盖、只记录"设计取舍一致——教练的价值在于"提供参照"，
  不在于"替用户决定"
- `sys:decision_profile_update` 目前默认关闭，这条改进方向依赖用户
  已经手动开启并积累了足够样本，属于自然的"锦上添花"依赖关系，不
  需要额外处理"画像为空时怎么办"——直接跳过提示即可

#### C3.（可选，需要评估收益）把 `next_action_advisor` 的规则第三条复用成长顾问的证据走势判断

`next_action_advisor` 目前只有"停滞目标"和"注意力错配"两条规则。
成长顾问的证据分布度/突增检测（`docs/growth-advisor-guide.md` 2.1/2.3
节，P5-2/P5-4）本质上回答的是同一类问题（"用户最近是不是真的在往
这个方向投入"），只是应用在不同的候选集合上。可以评估是否值得把这段
判断逻辑抽成公共函数，供 `next_action_advisor` 作为第三条规则复用
（"最近证据走势上升"优先于"证据走平"），而不是重新发明一套类似的
统计口径。

**这一步优先级低于 C1/C2**：`next_action_advisor` 目前的两条规则
已经在稳定运行，加第三条规则需要先确认"证据走势"这个信号对 Goal
排序确实比现有两条更有效，建议先观察 C1/C2 落地后的实际效果，再
决定是否投入这项重构。

#### C4.（可选，依赖 C1）月度复盘扩大到全部 Goal

`sys:growth_monthly_retrospective` 目前只统计成长顾问自己的候选/
采纳率，不覆盖用户全部 Goal。C1 落地、有了 Direction 分组之后，可以
评估是否要做一份"全部 Goal 综合月报"（复用现有 digest 生成管线），
但这依赖 C1 先落地、且需要先看 C1 的分组是否被用户实际使用起来，
不建议在 C1 之前独立启动。

### 2.4 非目标

- 不打算改动 `GoalNode.level` 的两值约束，也不打算让"长期方向"参与
  Goal 执行判定——Direction 是纯展示聚合，混入执行语义会显著增加
  GoalJudge/卡住恢复/公平调度等已经稳定的逻辑的复杂度，收益不成比例
- 不打算做参考文档里"年度/季度/月/周"这种固定层级的目标体系——
  `direction_id` 是单层扁平分组，不是多级树；如果后续证明确实需要
  多级，应该在验证单层分组有实际使用价值之后再考虑，而不是一步到位

## 3. 优先级与实施顺序建议

| 方向 | 内容 | 依赖 | 建议优先级 |
|---|---|---|---|
| R1 | 通用调研模板 `research_topic` | 无，可独立实施 | 高——直接补上一个现在完全没有的入口 |
| C1 | Goal 的"长期方向"分组 + 看板聚合视图 | 无，可独立实施 | 高——是 Personal Coach 缺口里最基础的一块，其余方向都建立在有了分组之上 |
| C2 | `decision_profile` 参与 Goal 创建提示 | 依赖用户已开启 `sys:decision_profile_update` 并积累样本 | 中——收益明确，但受限于前置条件的开启率 |
| R2 | 信源可信度标注 | 依赖 R1 | 中——低成本增强，不阻塞 R1 本身可用 |
| C3 | `next_action_advisor` 复用证据走势规则 | 建议先观察 C1/C2 效果 | 低——需要先验证信号有效性 |
| C4 | 全部 Goal 综合月报 | 依赖 C1 | 低——依赖 C1 落地且被验证有实际使用价值 |
| R3 | 持续调研的交叉验证质量门 | 建议先观察 R1 落地后的实际使用情况 | 低——成本（额外 LLM 调用）与当前证据支撑的收益不成比例 |

建议顺序：**R1 与 C1 优先且可以并行**（互不依赖，且都是"补齐一个
现在完全没有的入口/分组"这类最基础的缺口）；C2/R2 在各自的依赖方
落地后跟进；C3/C4/R3 留待前几项落地并观察实际使用效果后再评估是否
投入。

## 4. 与项目现有理念的一致性检查

对照 `docs/mini-agent-philosophy-and-roadmap.md`"长期规划应遵循的
理念"（持续提高对用户建模精度、任务自主执行程度、自我诊断与改进
能力，让用户显式交代的比例持续下降），本文档提议的方向：

- R1/R2 提高的是"任务自主执行程度"——用户表达一次调研意图，后续
  持续推进不需要反复交代
- C1/C2 提高的是"对用户建模精度"——让已经积累的价值取向画像真正
  参与到后续决策里，而不是只能被动查询
- 都不涉及"系统自主生成/修改自身目标"，Direction 分组和调研 Goal
  始终由用户显式创建或采纳，与理念第一条"明确排除系统自主生成目标"
