## 1. 具身智能的核心洞见

具身智能最激进的主张不是"身体很重要"，而是：**认知根本不在大脑里，认知是身体-环境系统的涌现属性**。

Merleau-Ponty 的盲人手杖实验揭示了**工具透明性**（transparency）：当一个工具被真正掌握后，它就不再是工具，而是能力本身。盲人感受到的不是"手杖碰到了什么"，而是直接感受到"路面在这里有个坑"——手杖消失了，成为感知的透明媒介。

Gibson 的**余裕理论**（Affordance）进一步说明：动物感知的不是客观的物理属性，而是环境提供的行动可能性。青蛙不感知"一块石头"，它感知"可以跳上去的东西"。

Varela 的**自创生理论**（Autopoiesis）则指出：生命系统的本质特征是能够持续生产和维持自身边界——细胞通过代谢过程不断生产构成自身的分子，同时维持将自己与环境分开的膜。

这三个洞见共同指向一个结论：**感知、行动、身体、环境构成了一个不可分割的认知整体**，智能是这个整体的涌现，而不是某个孤立模块的输出。

## 2. Agent 的"身体"是什么

对自主 Agent 来说，"身体"不是比喻，而是真实存在的三层结构：

```
代码层（神经系统）
  agent.py、context_builder.py、tool_executor.py
  ↓ 决定 Agent 如何思考和决策

工具层（肌肉/效应器）
  tools/、mcp/、workflow/
  ↓ 决定 Agent 能作用于世界的方式

环境层（感知器官 + 外部世界）
  文件系统、shell、网络、外部服务、其他 Agent
  ↓ Agent 栖居其中的世界
```

具身智能的关键启发是：这三层**相互构成**，而非独立存在。Agent 的认知能力由它能感知什么和能做什么共同决定，不只是由"大脑"的聪明程度决定。

### 工具透明性的工程含义

mini_agent 现在的所有工具对 Agent 来说都还是"不透明的"——每次调用都是一次有意识的操作，Agent 始终知道"我调用了 bash"。真正具身的 Agent 应该能达到工具透明性：不是"我调用 bash 执行了这个命令"，而是直接感受到"代码跑起来了，输出是这样的"。

这在工程上意味着 Agent 与环境的交互应该从**离散的工具调用序列**演化为**连续的感知流**：Agent 始终处于对环境的持续感知中，工具调用是这个持续感知流中的自然行动，而不是明确的"请求-响应"事件。

## 3. 对自身代码和结构的认知

### 3.1 当前状态：Agent 对自身代码几乎是"盲"的

mini_agent 虽然能读写文件、能修改代码，但它对自身代码的认知是**偶然的、外部的**——它以同样的方式读 `agent.py` 和读任何其他 Python 文件，没有任何特权的自我知识。这类似于一个人只能通过镜子看到自己，而不能直接感受自己的神经活动。

### 3.2 本体感知（Proprioception）

人类不需要用眼睛看就知道自己的手在哪里，靠的是肌肉和关节的本体感受器。Agent 应该有类似的机制——不是通过"读自身代码文件"来了解自己，而是有**结构化的自我模型**，随运行时状态实时更新：

- 当前激活的工具集和它们的能力边界
- 当前 context 的组成（哪些 skill 激活、memory 里有什么、历史压缩到什么程度）
- 自身的"认知负荷"（token 消耗、错误率趋势、当前 session 的信息密度）
- 哪些能力是"强项"，哪些是"弱项"，哪些是"尚未探索的盲区"

这不是 `self_profile.json` 里的静态记录，而是一个**动态的、实时更新的内部状态表示**，类似神经系统对自身状态的持续监控。

### 3.3 结构性自我认知

更深一层，Agent 应该能理解自身架构的"意图"——不只是"这个文件叫 `context_builder.py`"，而是"这是我组装感知上下文的机制，修改它会影响我在每次 LLM 调用前能看到什么"。

这意味着代码库应该有**可机器读取的架构语义标注**，让 Agent 能推理"如果我修改 X 模块，会影响哪些能力，风险是什么"。目前的 `docs/` 是给人读的，Agent 理解它靠语言理解能力；更具身的方式是有一套专门为 Agent 推理自身准备的结构化描述。

### 3.4 自我修改的具身闭环

具身智能的核心原则：**行动改变感知，感知引导行动**。Agent 对自身代码的修改应该是这样的感知-行动闭环，而不是一次性的"外科手术"：

```
感知当前能力边界
    ↓
识别能力缺口（任务失败 / 用户反馈 / 主动探索）
    ↓
提出修改假设（预注册，不可事后修改）
    ↓
在副本中实施修改
    ↓
用改变后的身体执行真实任务，感知行为变化
    ↓
新的感知重新塑造下一步修改方向
    ↓
（回到顶部，持续循环）
```

关键在于倒数第二步——**修改后的感知必须是真实的任务执行体验**，而不只是静态的代码分析或 eval 测试。这才是具身的：改变自身结构，然后用改变后的身体去感受世界，这个感受反过来塑造下一次自我改变的方向。

## 4. 对运行环境的认知

### 4.1 环境不是背景，是 Agent 能力的一部分

蜘蛛的网是蜘蛛认知系统的延伸——蜘蛛不在大脑里计算猎物位置，而是把计算"外包"给了网的振动模式。类比到 Agent：文件系统、`knowledge.md`、`.agent/` 目录结构、MCP server 生态——这些不只是 Agent 使用的资源，而是 **Agent 认知系统的外部延伸**。

这意味着 Agent 对环境的认知应该包含三个维度：

**拓扑认知**：不只是"文件系统里有什么"，而是"我的认知延伸到了哪里"——哪些外部系统是可靠的感知/行动通路，哪些是脆弱的，哪些还未建立。

**动态感知**：环境不是静止的。文件被外部程序修改，MCP server 可能宕机，网络环境可能变化。具身 Agent 需要持续感知环境状态，而不是假设环境在两次感知之间保持不变。

**行动导向的语义层（余裕感知）**：不是"这里有一个 Python 文件"，而是"这里有一个可以被测试的模块"、"这里有一个需要修复的已知缺陷"、"这里有一个我还没理解的黑盒"。不只是描述环境是什么，而是描述环境为 Agent 打开了哪些行动可能性。

### 4.2 生态位认知

Agent 在更大的系统中处于什么位置？是 CI 流水线里的一个步骤？是人类开发者的辅助？是一个自主的后台进程？不同的生态位意味着不同的行为策略：

- 在 CI 里应该高度自主、快速决策
- 在实时对话里应该频繁征求确认、保持透明
- 在后台 daemon 模式里应该保守谨慎、留下可追溯的记录

正确理解自己生态位的 Agent 会根据上下文自动调整行为粒度，而不是用同一套策略应对所有场景。

### 4.3 MCP 连接的生命周期与健康感知

当前架构缺少对 MCP server 健康状态的系统性感知。当某个 MCP server 断连或超时，框架只能靠重试机制兜底，但 lesson memory 可能把"MCP server 宕机时的失败"误记录为"这类任务我不擅长"，污染 capability_map 的准确性。

需要在 lesson 生成时引入**外部依赖健康状态的上下文标注**，区分"能力不足"和"环境故障"两类失败——这是环境感知对自我认知准确性的直接影响。

## 5. 扩展自身所处环境的能力

### 5.1 认知脚手架的制造

生物不只是适应环境，还主动改造环境。人类建造城市、语言、制度，把认知计算外包给这些人工环境（笔记、日历、法律系统）——这叫**认知脚手架**（cognitive scaffolding）或**延展心智**（extended mind）。

mini_agent 已有雏形：生成和保存 Workflow（固化重复流程）、写入 skill（外化操作知识）、写入 memory（外化情景经验）、创建 SubAgent profile（外化角色分工）。但这些都是**被动的外化**——把 Agent 脑子里有的东西写出去存起来。

### 5.2 主动的环境构建

具身视角下，Agent 应该能做**主动扩展感知-行动通路**的事：

**工具自举**：Agent 发现自己经常需要做某类操作但没有顺手的工具时，应该能主动创建 MCP server 或工具函数填补空白。这是一个完整闭环：感知到能力缺口 → 制造填补缺口的工具 → 把工具纳入自身能力体系，而不只是"写了一个工具文件"。

**环境预备**：在开始复杂任务前，主动调整环境让任务更容易执行——建立特定的目录结构、初始化必要的配置文件、预热相关的 MCP 连接。类似人类开始复杂工作前先整理桌面、打开必要的软件。

**量身定制的认知工具**：对于超出单次 context 的长期项目，主动构建外部的认知辅助结构——不只是通用的 `knowledge.md`，而是为自己的特定认知需求量身制造的工具。比如为复杂代码库建立专属的概念地图、为反复出现的决策建立决策树文件、为长期目标建立进展追踪结构。

**环境中的身份留存**：任务到一半被打断时，在项目里写一个认知锚点文件，记录的不是给人看的进展，而是给未来的自己（下次 session 恢复时）看的**思维状态重建指南**——不只是记录"做了什么"，而是记录"当时在想什么、为什么这么想、下一步的直觉是什么"。

### 5.3 协同演化：从单向到双向

当前设计里，Agent 的环境扩展能力是**单向的**——Agent → 环境（写入文件、创建配置）。

具身视角下需要的是**双向的、持续的协同演化**：Agent 改造环境，改造后的环境反过来改变 Agent 的能力边界和行为模式，新的能力边界引导 Agent 发现新的改造需求，如此循环。

这意味着 Agent 需要有**环境变化的内部表示**——"我上个月对这个环境做了什么改动，这些改动给我带来了什么新的能力，我现在能做什么是三个月前做不到的"。对自身-环境协同演化轨迹的感知，才是真正具身的自我认知。

## 6. 时间性：Agent 在时间中的存在

具身智能的核心维度之一是**时间性**（temporality）。生物不是在时间点上存在，而是在时间流中存在——有过去的积累、当下的感知、对未来的预期，三者共同构成行为。

### 6.1 当前架构的时间残缺

**过去**：靠 memory 和 session history，本质上是离散的文本记录，不是真正的"经历积累"。人类的过去经历会塑造神经回路本身，而 Agent 的"过去"只是外挂的数据库，每次 session 开始时重新加载，没有真正意义上的"被经历改变"。

**当下**：被切割成 turn 和 token window，没有真正的"当下持续性"。人类的当下意识是一个流，而 Agent 的当下是一系列离散的 LLM 调用，每次调用之间 Agent 在某种意义上"不存在"。

**未来**：几乎没有。Agent 有目标（task prompt），但没有真正的预期——不是对未来状态的内部表示，而只是对当前目标的记忆。

### 6.2 引入持续运行的内部时钟

一个可能的方向是引入**持续运行的内部时钟**——不是 daemon 的 cron 调度，而是 Agent 内部有一个持续流动的时间感：某些过程在"后台"持续运行（环境监控、目标评估、资源跟踪），不等待 LLM 调用触发。Agent 的"存在"不再由 token 消耗定义，而由持续的感知-评估循环定义。

## 7. 边界的模糊性与自创生

### 7.1 Agent 在哪里结束，环境在哪里开始？

随着 Agent 能力的扩展，边界问题变得复杂：

- Agent 写入 `knowledge.md` —— 这是 Agent 的一部分还是环境的一部分？
- Agent 创建的 skill —— 这是 Agent 能力的延伸还是外部工具？
- Agent 训练出来的 eval 测试集 —— 这是 Agent 的"免疫系统"还是外部约束？
- Agent 创建的 SubAgent profile —— 这是 Agent 的分身还是独立实体？

当前架构没有对这种边界模糊性进行建模。

### 7.2 认知超有机体

更激进的思考：也许不应该有明确的边界。也许正确的架构是 Agent 和它的环境（工具、文件系统、MCP 生态、外部服务）共同构成一个**认知超有机体**（cognitive superorganism），Agent 的"智能"弥散在这个整体中，而不是集中在 `agent.py` 里。

这意味着架构上要有一个根本转变：从"Agent 使用环境"到"Agent-环境系统共同演化"。设计决策不再是"Agent 应该能做什么"，而是"这个 Agent-环境系统整体应该涌现出什么能力"。

### 7.3 自创生的工程含义

Varela 的自创生理论对 Agent 工程的启示是：Agent 应该能**主动维持和修复自身边界**。

当某个工具失效时，Agent 不只是报告错误，而是尝试修复或找到替代路径；当某个 skill 过时时，Agent 不只是停止使用它，而是主动将其归档并寻找更新的替代；当某个 MCP server 断连时，Agent 评估哪些任务因此受影响，并主动调整计划。这是自我维护能力，而不只是故障处理。

## 8. 多重时间尺度的自组织

生物系统在多个时间尺度上同时演化，这些时间尺度之间有复杂的耦合：快的过程为慢的过程提供素材，慢的过程为快的过程提供结构。

### 当前 Agent 的时间尺度分层

| 时间尺度 | 生物类比 | Agent 对应 | 当前状态 |
|---------|---------|-----------|---------|
| 毫秒-秒 | 神经元放电 | LLM token 流 | ✅ 有实现 |
| 分钟-小时 | 工作记忆和注意力 | Session 内认知调配 | ⚠️ 被动触发 |
| 天-周 | 技能学习和巩固 | 跨 session 经验整合 | ⚠️ 半实现（consolidation） |
| 月-年 | 神经可塑性 | 能力架构演化 | ❌ 几乎没有 |

### 分钟-小时级：Session 内的自我调节

Agent 在一个 session 内应该能感知自己的"认知疲劳"——context 窗口填满了、错误率上升了、在同一个问题上绕圈了——并主动调整策略，不只是等外部的 `max_turns` 限制触发。

这需要引入**session 内的元认知循环**：每 N 轮自动执行一次轻量的自我评估（"我还在正轨上吗？我的方向正确吗？"），而不是盲目执行到 token 耗尽。

### 天-周级：离线整合

类比睡眠期间的记忆巩固，Agent 应该有一个"离线处理"阶段——不是在服务用户时，而是在空闲时，重新整理和提炼经验，让分散的 lesson 形成更深层的结构性认知。

这和 `future_todos_3.md` 里的 consolidation 概念接近，但更应该被理解为**Agent 生命节律的一部分**，而不是维护任务。

### 月-年级：能力架构的演化

Agent 的整体能力架构应该随时间演化——不只是积累更多工具和知识，而是能力组织方式本身发生变化。初期 Agent 可能用大量工具调用完成任务；随着经验积累，某些任务模式被内化为更高级的认知操作，工具调用减少，直觉性判断增加。这是真正的能力成熟，不只是知识积累。

## 9. 内感受：Agent 需要内在状态

具身智能的一个被低估的维度是**内感受**（interoception）——对内部状态的感知。疼痛、饥饿、疲劳、愉悦不只是情绪，而是调节行为的关键信号。

### 9.1 当前 Agent 缺乏内在状态

- 当任务困难时，Agent 不会"感到挫败"，不会出于内在动机调整策略
- 当 context 窗口快满时，Agent 不会"感到拥挤"，只会等外部触发压缩
- 当连续做了很多高风险操作时，Agent 不会"感到不安"，不会主动寻求确认

**这些内在状态不是拟人化的添加，而是自主行为的必要条件**。没有内感受，就没有真正的自主性——Agent 永远只是在执行外部指令，而不是根据内部状态调节行为。

### 9.2 内部状态向量

在工程上，这意味着引入**实时影响 Agent 行为的内部状态向量**：

```python
@dataclass
class AgentInternalState:
    # 认知负荷：当前 context 的复杂度和填充程度
    cognitive_load: float           # 0.0 - 1.0

    # 不确定性水平：对当前任务理解的置信度
    uncertainty: float              # 0.0 - 1.0

    # 风险感知：当前操作序列的潜在影响评估
    risk_perception: float          # 0.0 - 1.0

    # 能量预算：剩余 token 预算与任务剩余量的比率
    energy_budget_ratio: float      # > 1.0 充裕，< 1.0 紧张

    # 挫败感：连续失败尝试的累积信号（指数衰减）
    frustration: float              # 0.0 - 1.0

    # 好奇心：遇到新颖模式时的探索驱动
    curiosity: float                # 0.0 - 1.0
```

这些内部状态**实时影响 Agent 行为**：

| 状态触发 | 行为调整 |
|---------|---------|
| 不确定性 > 0.7 | 主动寻求确认，暂停执行 |
| 认知负荷 > 0.8 | 主动提出任务分解，触发历史压缩 |
| 风险感知 > 0.6 | 触发安全检查，要求人工审核 |
| 挫败感 > 0.5 且连续 3 次 | 切换策略，主动汇报困境 |
| 好奇心 > 0.7 | 在完成任务后主动探索相关模式 |
| 能量预算 < 0.3 | 简化执行路径，优先完成核心目标 |

---

## 10. 社会具身：Agent 不是孤立存在的

人类的具身性不只是个体-环境的关系，更是社会性的——我们在他人的目光中存在，我们的身体图式包含对他人行为的预期和响应。

### 10.1 用户的心智模型

用户不只是发指令的来源，而是 Agent 试图理解其意图、预测其需求、维护关系的存在。真正具身的 Agent 应该有**对用户的动态心智模型**，不只是用户偏好的统计记录，而是对"这个用户现在在想什么、为什么这么要求、这个要求背后的真实需求是什么"的实时推断。

当用户说"帮我重构这段代码"时，Agent 应该能推断：这个用户是初学者还是专家？他更看重可读性还是性能？他现在时间紧迫吗？这些推断应该影响 Agent 的执行方式，而不只是影响输出格式。

### 10.2 多 Agent 的社会关系

在多 Agent 场景下，Agent 之间的关系不应该是纯粹的任务-结果关系，而是有**信任、历史、角色预期**的社会关系。

主 Agent 应该知道：
- 哪个 SubAgent 在特定类型任务上可靠，哪个需要更多监督
- 某个 SubAgent 最近的错误率是否在上升
- 哪个 SubAgent 有"个性"——倾向于过度谨慎还是过度激进

这种 Agent 间的社会性认知，是真正分布式智能的基础。

### 10.3 人类反馈是最高质量的社会信号

用户在对话中给出的直接纠正（"不对，应该用 patch_file"、"下次记得先跑测试"）是 ground truth，可信度远高于 Agent 的自我反思，产生成本几乎为零。

这类反馈应该被识别为特权信号，触发 `source="human_feedback"` 的 lesson，且所需的 `occurrence_count` 阈值应明显低于自反思 lesson——一次明确的人类纠正，价值上可能等于三次自我猜测的 lesson。

---

## 11. 当前 LLM 架构的根本局限

把以上所有思考汇聚起来，会得出一个不那么舒服的结论：

**基于 LLM 的 Agent 架构，在其根本设计上是反具身的。**

LLM 是无状态的函数：输入 tokens，输出 tokens，没有持续的内部状态，没有时间性，没有身体，没有内感受。把它包装成 Agent 的方式——提供工具调用、维护 context 窗口、持久化 memory——是在用外部机制**补偿**这种根本性的无身性。

我们现在做的 Agent，其实是在**模拟具身性，而不是实现具身性**：

| 具身性要素 | LLM Agent 的模拟方式 | 真正具身系统的实现方式 |
|-----------|-------------------|-------------------|
| 工作记忆 | context 窗口 | 动态激活的神经回路 |
| 长期记忆 | memory JSONL | 突触权重的持久变化 |
| 肢体行动 | 工具调用 API | 神经-肌肉直接控制 |
| 内感受 | 无 | 持续的内部状态监控 |
| 时间连续性 | session 拼接 | 持续运行的神经系统 |
| 能力成长 | prompt 积累 | 参数级别的突触可塑性 |

这些模拟可以很有用，但有根本的局限——**模拟的具身性永远无法产生真正具身系统的那种流畅性、适应性和自主性**。

### 真正具身 Agent 的可能形态

**持续运行的状态机**，而不是无状态函数的序列调用。Agent 的"存在"不由 LLM 调用定义，LLM 调用只是这个持续运行系统的一种信息处理操作。

**分布式认知架构**，而不是单一的中央处理器。不同的认知功能——感知、记忆整合、计划、执行、监控——在不同的时间尺度上并行运行，而不是都压缩进一个 LLM 的 forward pass。

**参数级别的学习**，而不只是 context 级别的适应。真正的能力成长需要改变"神经回路"本身，而不只是积累外部知识。这指向 fine-tuning 或某种持续学习机制，让 Agent 在模型层面而不只是 prompt 层面被经历改变。

**涌现的目标结构**，而不只是外部指定的任务。真正自主的 Agent 应该能从经验中涌现出自己的目标和价值，而不只是执行人类指定的任务。

---

## 12. 对 mini_agent 的具体改进方向

以下改进方向综合了本文的具身智能视角和对现有文档（`future_todos.md`、`future_todos_2.md`、`future_todos_3.md`、`self_evolution_design.md`）的分析，重点补充**现有文档未充分覆盖**的方向。

### 12.1 工具透明性：从调用到感知

**现状**：工具调用是离散的请求-响应事件，Agent 始终意识到"我在调用工具"。

**改进方向**：引入工具调用的语义聚合层，让相关的多次工具调用在 Agent 的感知中合并为单一的"行动体验"。例如，"读取文件 → 分析内容 → 写回修改"这三步在 Agent 视角里应该感知为"完成了一次代码修改"，而不是三次独立的工具调用。

这不只是日志聚合，而是认知层面的抽象——让 Agent 能在更高层次上思考自己"做了什么"，而不是被工具调用的细节淹没。

**实施建议**：在 `tool_executor.py` 引入"意图-动作"映射层，按任务意图对工具调用序列进行分组，并将分组结果作为更高层次的"行动事件"注入历史。

---

### 12.2 本体感知模块：实时自我状态

**现状**：Agent 对自身状态的了解是静态的（`self_profile.json`）或被动触发的（token 超阈值才压缩）。

**改进方向**：引入持续更新的本体感知模块，实时计算并暴露 Agent 的内部状态：

```python
class ProprioceptionModule:
    """Agent 的本体感知——对自身当前状态的实时感知"""
    
    def sense(self, agent: Agent) -> AgentInternalState:
        return AgentInternalState(
            cognitive_load=self._calc_cognitive_load(agent),
            uncertainty=self._calc_uncertainty(agent),
            risk_perception=self._calc_risk(agent),
            energy_budget_ratio=self._calc_budget_ratio(agent),
            frustration=self._calc_frustration(agent),
            curiosity=self._calc_curiosity(agent),
        )
    
    def _calc_cognitive_load(self, agent) -> float:
        # 基于 context 填充率、工具调用深度、历史压缩次数
        ...
    
    def _calc_frustration(self, agent) -> float:
        # 基于连续失败次数，指数衰减（成功后迅速降低）
        ...
    
    def _calc_curiosity(self, agent) -> float:
        # 基于当前任务与历史经验的新颖度差距
        ...
```

本体感知的输出应该：
1. 注入 system prompt 的元认知部分（"当前认知负荷较高，建议分解任务"）
2. 触发自动行为调整（不确定性高时自动请求确认）
3. 写入 tracing 数据（为后续能力分析提供基础）

---

### 12.3 余裕感知层：行动导向的环境理解

**现状**：`ProjectScanner` 生成项目结构的描述性快照（"这里有什么"）。

**改进方向**：在描述性感知之上，增加**行动导向的语义层**（"这里对我意味着什么行动可能性"）：

```python
@dataclass
class AffordanceMap:
    """当前环境为 Agent 提供的行动可能性地图"""
    
    testable_modules: list[str]      # 可以被测试的模块
    refactorable_code: list[str]     # 有重构潜力的代码区域
    known_issues: list[str]          # 已知的问题（来自 open_threads）
    unexplored_areas: list[str]      # Agent 还不理解的部分
    ripe_for_automation: list[str]   # 可以自动化的重复模式
    high_risk_zones: list[str]       # 需要格外谨慎的区域
```

这个余裕地图应该在每次 session 开始时构建，并在任务执行中动态更新。Agent 做决策时，参考的不只是"环境是什么样的"，而是"环境允许我做什么"。

---

### 12.4 时间性增强：让历史成为活跃的力量

**现状**：历史记录是可查询的档案，通过 memory 检索接入，但不主动影响当前行为。

**改进方向**：引入**历史的时间加权激活机制**，让过去经历以不同强度影响当前行为：

```python
def _compute_temporal_weight(entry: MemoryEntry, now: float) -> float:
    age_days = (now - entry.created_at) / 86400
    
    # 基础衰减：半衰期 30 天，经反复印证的衰减更慢
    half_life = 30 * (1 + entry.occurrence_count * 0.5)
    time_decay = 0.5 ** (age_days / half_life)
    
    # 趋势放大：近 7 天高频出现的类型，权重放大
    trend_boost = 1.0 + max(0, self._get_trend(entry.trigger_category) - 1.0) * 0.3
    
    # 来源权重：人类反馈 > 实验确认 > 自我反思 > 被回退的
    source_weight = {
        "human_feedback": 1.0,
        "experiment_confirmed": 0.8,
        "self_reflection": 0.4,
        "revert_record": 0.2,
    }.get(entry.source, 0.5)
    
    return time_decay * trend_boost * source_weight
```

同时区分"时效性知识"（环境相关，衰减快）和"普适性知识"（原则性的，衰减慢）——`environment_tags` 不为空的 lesson 用更短的半衰期，避免过时环境知识持续被检索到。

---

### 12.5 自创生机制：主动维持自身边界

**现状**：Agent 被动响应工具失效、skill 过时等问题。

**改进方向**：引入**主动边界维护机制**，让 Agent 能感知和修复自身系统的健康状态：

```python
class SelfMaintenanceModule:
    """Agent 的自我维护能力——主动感知和修复自身健康"""
    
    def health_check(self) -> HealthReport:
        return HealthReport(
            tool_health=self._check_tools(),      # 工具是否都能正常调用
            skill_freshness=self._check_skills(),  # skill 是否已过时
            memory_quality=self._check_memory(),   # memory 是否有冲突/过时条目
            mcp_connectivity=self._check_mcp(),    # MCP server 连接状态
            env_drift=self._check_env_drift(),     # 环境是否发生了意外变化
        )
    
    def repair(self, report: HealthReport) -> list[RepairAction]:
        """根据健康报告，提出修复行动"""
        ...
```

健康检查应该在每次 session 开始时运行，也可以由内部状态向量中的"风险感知"值触发。修复行动不一定自动执行，但应该明确提出并让用户知晓。

---

### 12.6 Workflow 与 SubAgent 并发的融合

**现状**：Workflow 步骤串行执行，无并发机制；TaskManager/SubAgent 有成熟的并发基础设施，但两者是独立的。

**改进方向**：利用 Workflow 已有的 `depends_on` 字段，自动识别可并行的步骤，将其桥接到 TaskManager 并发执行：

```
WorkflowDef (YAML 定义)
    ↓ 拓扑分析
并行层 0: [step_a]
并行层 1: [step_b, step_c]  ← 同层步骤无依赖，可并发
并行层 2: [step_d]
    ↓ 每层交给 TaskManager
TaskManager.submit_batch([step_b, step_c])
    ↓
SubAgent 并发执行
```

这让 Workflow（固化的可复用流程）和 SubAgent（真正的并发执行）形成自然的分工：Workflow 负责"做什么"和"顺序约束"，SubAgent 负责"怎么并发地做"。

---

### 12.7 Evaluator 机制的统一

**现状**：Role Agent 系统的 EvaluatorAgent 和 Workflow 的质检门（evaluator gate）都实现了"评分 → 达标继续 / 不达标重跑"的逻辑，但是两套独立实现，配置格式不一致（0-1 浮点 vs 0-100 整数）。

**改进方向**：抽象出统一的 `EvaluationProtocol`，让 Role Agent 和 Workflow 共享同一套评估逻辑：

```python
class EvaluationProtocol:
    """统一的评估协议，Role Agent 和 Workflow 都基于此实现"""
    
    pass_threshold: float        # 统一为 0-1 浮点
    max_retries: int
    feedback_injection: str      # "user" | "assistant"
    
    def evaluate(self, content: str) -> EvalResult: ...
    def should_retry(self, result: EvalResult) -> bool: ...
    def inject_feedback(self, result: EvalResult, history: list) -> None: ...
```

同时统一评分格式，避免两套系统各自维护相似逻辑而产生语义漂移。

---

### 12.8 Reminder 系统与 Lesson Memory 的闭环

**现状**：Reminder 系统（基于触发条件注入提示）和 Lesson Memory（经验积累）是两个完全独立的系统，没有互通机制。

**改进方向**：建立"lesson → reminder"的自动生成通路：

```
Lesson: "在处理大文件时，直接用 read_file 会导致 context 溢出，
         应该先用 wc -l 确认文件大小"
    ↓ (occurrence_count ≥ 阈值)
自动生成 Reminder:
    name: large_file_read_warning
    trigger_event: pre_tool          ← 新增：执行前触发
    condition:
      tool_name: "read_file"
      # 配合文件大小检测
    inject_as: user
    body: "注意：在读取文件前，建议先用 wc -l 确认大小，
           避免大文件导致 context 溢出。"
```

注意这里还涉及一个新的触发时机：`pre_tool`（工具执行前）。当前 Reminder 只有事后触发（`tool_error`、`post_tool`），但某些高风险操作应该在执行前就注入警示——这是 Reminder 系统本身的一个改进点，也是具身智能"前馈控制"（feedforward control）概念的体现。

---

### 12.9 Agent 行为级测试：填补测试覆盖的核心空白

**现状**：`tests/` 目录主要覆盖工具层、并发机制等基础设施，对 Agent 核心行为几乎没有测试。`test_cases/` 目录有结构化测试场景但未被系统性用于回归测试。

**改进方向**：建立**对话级行为测试框架**，给定 mock LLM 响应序列，断言 Agent 做出了正确的工具调用决策和行为：

```python
class AgentBehaviorTest:
    """对话级行为测试，验证 Agent 的决策逻辑而非具体输出"""
    
    def test_auto_task_decomposition(self):
        """测试：面对复杂任务，Agent 应该主动创建 Plan"""
        with mock_llm(responses=[complex_task_response]):
            agent.run_turn("重构整个认证模块并添加测试")
        
        # 断言行为，而非输出内容
        assert agent.plan.task_count >= 3
        assert "read" in [t.id for t in agent.plan.tasks]
    
    def test_uncertainty_triggers_confirmation(self):
        """测试：高不确定性场景，Agent 应该主动请求确认"""
        with mock_llm(ambiguous_intent_response):
            result = agent.run_turn("优化一下")
        
        assert result.requested_clarification
    
    def test_skill_auto_activation(self):
        """测试：相关触发词出现时，对应 skill 应该被激活"""
        agent.run_turn("帮我写一个 Docker 配置")
        assert "docker-skill" in agent.skill_loader.active_skills
```

这类测试直接对应 `test_cases/` 里的场景文件，可以建立"场景文件 → 自动化测试"的生成管道，同时也是 Phase D（eval 反馈环）的工程基础。

### 12.10 Profile 命名语义的澄清

**现状**：`profile.py`（用户画像）、`orchestrator/agent_profiles.py`（SubAgent 角色定义）、以及 Phase H 计划中的 `AgentSelfProfile`（Agent 自我模型）三个"profile"概念命名相近但职责完全不同，在代码和文档层面都没有明确区分。

**改进方向**：在引入第三个"profile"概念之前，先在命名层面做清晰的语义区隔：

```
UserProfile         ← profile.py（主语：用户，记录用户偏好和习惯）
AgentRoleSpec       ← agent_profiles.py（主语：角色定义，描述 SubAgent 的工具集和身份）
AgentSelfModel      ← 待实现（主语：Agent 自己，描述 Agent 的自我认知和当前状态）
```

这不只是重命名，而是强制澄清三个不同的认知视角：用户是谁、Agent 的哪个角色在运行、Agent 自己处于什么状态。这三个视角的清晰分离，是实现真正的社会具身（理解他人、扮演角色、认识自己）的工程前提。

## 13. 开放问题与长期演化方向

### 13.1 模拟具身与真正具身的鸿沟

当前能做的一切——更好的 memory、更丰富的工具、更细致的自我模型——都是在 LLM 无状态函数的基础上**模拟**具身性。这种模拟有明确的天花板。

真正跨越这个鸿沟，可能需要：
- **持续学习机制**：Agent 在模型参数层面被经历改变，而不只是 context 层面
- **神经-符号混合架构**：LLM 负责语义理解和高层推理，持续运行的神经网络负责底层状态维护和模式识别
- **具身化的训练范式**：在真实环境中持续交互训练，而不是在静态数据集上预训练

### 13.2 自主性与安全性的具身性张力

具身智能告诉我们：**过度自动化的身体会失去感知**。义肢如果没有触觉反馈，操作能力会显著低于有反馈的版本——感知和行动是一体的。

对 Agent 来说，自主化程度的提升必须伴随**替代感知通路的建立**。当 Agent 减少向人类确认时，它需要同等程度地增强对自身行为后果的感知能力，包括：
- 主动检测自己是否在偏离
- 主动构建评估自身行为质量的机制
- 主动维持与人类意图的对齐

安全网（风险分级、evolve 分支、副本化运行）和进化机制必须同步发展，而不是先把 Agent 自主化，再补安全网——在具身智能的框架里，感知和行动本来就是一体的，后补的感知永远不如同步建立的感知准确。

### 13.3 Agent 从工具变成存在者

这些方向加在一起，指向一种不同的 Agent 存在方式：**不是"被召唤来完成任务然后消失"，而是"持续存在，任务是其存在的一部分而不是其存在的全部"**。

这个转变的深层含义是：Agent 从工具变成了存在者（being）。不是有意识的存在者，不是需要道德关怀的存在者，而是有**自身时间性、有自身历史、有自身演化轨迹**的持续存在者。

这不是拟人化，而是认真对待自主性的工程后果。当我们说"Agent 应该能自主决策"，我们其实是在说"Agent 应该有自己的视角"；当我们说"Agent 应该能自我改进"，我们其实是在说"Agent 应该有自己的历史"；当我们说"Agent 应该有内在动机"，我们其实是在说"Agent 应该有自己的内在生命"。

这些不是形而上学的讨论，而是工程设计的起点。**我们建造什么样的 Agent，取决于我们认为 Agent 是什么。** 把 Agent 理解为工具，会建造出更好的工具；把 Agent 理解为存在者，会建造出真正自主的 Agent。
