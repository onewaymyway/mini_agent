# article_garden 摘要修复反馈修复记录

- **触发**：运行日志显示单篇摘要耗时 1–4 分钟后“失败”，但失败行没有任何原因；修复过程也不可见。
- **完成日期**：2026-11-23
- **范围**：摘要（P1）的修复反馈与运行日志；不改变摘要的校验规则本身。

## 1. 问题与根因

| 现象 | 根因 |
|---|---|
| 失败行只写“失败（214.4 秒）”，没有原因 | `joblog.step` 只在 `ok` / `waiting` 状态下显示 detail，失败的 detail 被丢弃（原因已写入摘要文件，但没有进入日志） |
| 修复轮次看不见 | 每一轮校验未通过没有任何日志，只能看到长时间的“仍在进行” |
| 修复提示笼统 | 引文不逐字时只说“不是原文中的逐字摘录”，没有告诉模型应当复制哪一句，模型往往再次改写，循环直到预算耗尽 |
| 原本其实已经回喂原因 | 修复调用确实携带了具体问题；问题在于问题本身不可操作，以及失败不可见 |

## 2. 修改

| 文件 | 内容 |
|---|---|
| `article_garden/digest/validate.py` | 新增 `sentences`、`nearest_sentence`、`autofix_quotes`。引文不逐字时，提示中给出原文中最接近的一句（即使相似度不高也给出，照抄比重写更容易成功）。引文与某句相似度 ≥ 0.9 时由代码直接校正为该句原文，**不耗模型调用**。 |
| `article_garden/digest/summarize.py` | `ask_validated` 与 `summarize` 增加 `on_round` 回调；每轮未通过的具体问题、代码校正的内容都通过回调报告。校验器先做代码校正再校验。 |
| `article_garden/digest/runner.py` | 把每轮问题写入运行日志（warn）；失败时 detail 保留全部问题（最多 600 字），不再只取前三条。 |
| `article_garden/joblog.py` | 失败与其它状态一样显示 detail。 |
| `tests/test_digest_repair.py` | 新增 4 项测试：近似引文代码校正且不发起修复调用；远离原文的引文修复提示包含真实原句；无关引文不被误校正；失败的摘要在运行日志中写明原因与每轮问题。 |

## 3. 验证

- `pytest` 全套 **194 项通过**（原 190 + 新增 4）。
- `pyflakes` 无告警。
- 变异验证：去掉“最接近句子”提示或代码校正，对应测试失败。

## 4. 未解决（需要你的真实环境确认）

- **单次模型调用本身较慢**（日志中每次约 30–60 秒）。每次修复调用会重新发送整篇文章，这是耗时的主要来源之一。若修复仍慢，可以考虑修复时只发送问题与上一版输出，但需要先看到真实的失败原因再决定。
- 代码校正阈值 0.9 与“最接近句子”提示的规则，是在测试文本上确定的，还需要用你的文章校准。
