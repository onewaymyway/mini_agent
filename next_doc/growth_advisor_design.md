## -1. 战略定位：这不是一个锦上添花的功能

在深入架构之前，先把这件事的分量说清楚，因为它直接决定了后面所有默认值该怎么设。

**问题**：现在的 mini_agent（以及大多数 Agent 产品）有一个共同的结构性缺陷——它是"你问我答""你派任务我执行"的被动工具。用户要获得价值，前提是用户自己先想清楚"我要 Agent 做什么"，这本身就是一道门槛。大量潜在用户从未跨过这道门槛：他们打开一次、随便聊两句、感受不到"这东西懂我""这东西替我操心"，然后就流失了。

**这个能力恰恰是补上这道门槛的切入点**：
- **零成本起点**：用户什么都不用做——不用会写 prompt，不用想清楚自己要什么，甚至不用打开 App。Agent 自己观察、自己调研、自己把结果准备好，用户只需要"看一眼、要不要采纳"。这是目前所有交互模式里，对用户认知负荷要求最低的一种。
- **主动权是核心价值主张**：Agent 与传统工具的本质区别，不在"能不能执行任务"，而在"要不要等你下指令"。一个从不主动开口的 Agent，本质上和一个更聪明的搜索框没有区别。**主动为用户的成长打算，是"自主 Agent"这个概念第一次能被用户直观感受到的场景**——不是通过一句"我是自主 Agent"的自我介绍，而是用户某天打开看板，发现 Agent 已经默默帮他把下一步该学什么、该看什么材料都准备好了。
- **复利效应**：这个能力用得越久，画像越准、推荐越准、用户越信任，进而越愿意把更多真实状态暴露给 Agent（对话、目标、决策），形成数据飞轮，这和第一版方案第 0 节提到的"数据飞轮"是同一个道理，但对象换成了用户侧留存本身。

**因此，这份方案里所有"要不要默认开启、多久推一次"这类问题，判断标准不应该是"保守起见先关着看看"，而应该是：这是这个产品最重要的价值入口，宁可在克制机制上下狠功夫做对，也不能让它一开始就被做成一个默认关闭、无人问津的边缘功能。** 第 4、5、8 节的默认值都按这个原则重新设定。

## 0. 为什么是"复用"而不是"新建一套"

现有代码里 `evolution/` 目录已经是一个成熟的闭环系统，只是服务对象是 **Agent 自己**：

| 现有模块 | 做的事（服务对象：Agent 自己） |
|---|---|
| `decision_profile_builder.py` | 从历史决策归纳"Agent 的价值观模式" |
| `soft_goal_deriver.py` | 从能力短板 / 停滞工作线 derive 出 Agent 自己该做的 Goal |
| `next_action_advisor.py` | 对候选排序，决定这次该提醒"做哪件事" |
| `self_model_snapshot.py` | Agent 能力自画像的时间序列快照 |
| `monthly_trend_retrospective.py` | 月度回顾自己变化了什么 |
| `AutonomousLoop`（`_tick_passive/_tick_maintenance/_tick_autonomous`） | 三档 daemon 节奏，驱动以上模块周期运行 |

**核心判断**：这套架构本身是通用的（信号 → 候选 → 排序 → 执行 → 交付 → 反馈），跟服务对象是"Agent"还是"用户"无关。与其单独设计一套新系统，不如做一个平行的 **用户成长顾问（Growth Advisor）** 子系统，命名和分层习惯向 `evolution/` 看齐，但**明确写清楚它是关于用户的，不是关于 Agent 自己的**（这一点在第 8 节详细展开，是最容易踩坑的边界）。

同时，项目里已经有 `profile.py` 的 `UserProfile`（`preferences` + `derived`，从记忆生成 `summary/tech_stack/habits`），这正好是 GrowthProfile 的地基，不用从零建用户画像。

## 1. 目标与非目标

**目标**：
- Agent 能主动、克制地观察用户的状态变化（不是盯梢，是"记性好的朋友"），发现值得推进的成长方向
- 对推荐方向做实际调研（web_search + 已有 wiki 沉淀），产出可执行的报告，而不是一句空泛建议
- 通过看板 + 通知，把"研判过程 - 推荐结果 - 用户反馈"这条链路完整暴露给用户，而不是黑箱推送
- 全程可关闭、可追溯、可解释

**非目标（本方案不做）**：
- 不做心理评估/性格测试类的主观判断（参考 `user_wellbeing` 类原则，Agent 不该给用户下诊断式结论）
- 不采集额外的敏感数据（如生物特征、位置轨迹），只用 mini_agent 现有掌握的数据
- 不追求"预测用户想要什么"，只做"基于已发生事实的克制归纳 + 调研"，这一点直接继承 `decision_profile_builder.py` 的克制原则

## 2. 整体架构：三层闭环

```
┌──────────────────────────────────────────────────────────────────┐
│                     感知层 Signal Collection                       │
│  数据源：memory（对话历史）/ profile.py derived / Goal 完成与放弃记录 │
│         / cron 任务产出 / watchlist 关注列表 / wiki 已沉淀的 decision │
│  产出：GrowthSignal（结构化、带时间戳、带来源引用，不做主观解释）      │
└───────────────────────────────┬──────────────────────────────────┘
                                 ▼
┌──────────────────────────────────────────────────────────────────┐
│                     研判层 Candidate Derivation                   │
│  归纳规则（只允许总结已发生事实，证据不足不落地，规则同                │
│  decision_profile_builder.MIN_EVIDENCE_COUNT）                    │
│  产出：GrowthCandidate（写入 growth_backlog，含 evidence_refs）      │
│  排序：GrowthAdvisor（next_action_advisor 风格，规则优先，LLM 排序可选）│
└───────────────────────────────┬──────────────────────────────────┘
                                 ▼
┌──────────────────────────────────────────────────────────────────┐
│                     执行层 Research Execution                      │
│  cron 周期任务：对 Top 候选做 web_search 调研，                     │
│  产出结构化 GrowthReport（Markdown，含学习路径/资源/预估投入/第一步） │
│  归档：wiki/growth/*.md + growth_reports.jsonl（元数据索引）        │
└───────────────────────────────┬──────────────────────────────────┘
                                 ▼
┌──────────────────────────────────────────────────────────────────┐
│                     交付层 Delivery & Feedback                     │
│  NotificationDispatcher（复用 email/kanban channel）+               │
│  看板新增「🌱 成长顾问」tab，用户 采纳/忽略/展开详情 三个动作         │
│  反馈写回 growth_feedback_ledger，供研判层下次调整候选置信度          │
└──────────────────────────────────────────────────────────────────┘
```

## 3. 数据模型设计

### 3.1 扩展 `UserProfile.derived`

在 `profile.py` 现有 `derived`（`summary/tech_stack/habits`）基础上新增字段，不改变现有字段语义：

```jsonc
"derived": {
  "summary": "...",
  "tech_stack": [...],
  "habits": [...],
  // 新增：
  "growth_focus_areas": ["近期高频提及/投入时间的领域，附权重"],
  "growth_gaps": ["从对话中识别出的、反复出现但未系统解决的知识/技能缺口"],
  "growth_signals_updated_at": 1700000000.0
}
```

### 3.2 新增 `GrowthCandidate`（growth_backlog.jsonl）

结构对齐 `soft_goal_deriver.py` 产出 Goal 的字段习惯：

```jsonc
{
  "candidate_id": "growth:2026-08-07:001",
  "title": "系统学习 Rust 异步编程",
  "reason": "近 3 周内 7 次对话涉及 tokio/async-std 报错排查，均为临时解决，未系统学习",
  "evidence_refs": ["conv:2026-07-20#12", "conv:2026-07-28#3", "..."],
  "confidence": 0.72,
  "status": "pending",          // pending | accepted | dismissed | expired
  "source": "agent_derived",
  "created_at": 1700000000.0
}
```

克制阈值：证据条数 < `MIN_EVIDENCE_COUNT`（默认 3，可配置）不生成候选，避免"一次性话题"被过度解读。

### 3.3 新增 `GrowthReport`（wiki/growth/*.md + growth_reports.jsonl 索引）

报告正文存 Markdown（复用 wiki 沉淀模式），索引文件字段参考 `notification/reports_store.py` 的 `reports.jsonl` 写法：

```jsonc
{
  "report_id": "growth_report:2026-08-07:001",
  "candidate_id": "growth:2026-08-07:001",
  "title": "Rust 异步编程学习路径调研",
  "path": "wiki/growth/2026-08-07-rust-async.md",
  "sources": ["https://...", "https://..."],   // web_search 引用来源
  "generated_at": 1700000000.0,
  "acknowledged": false
}
```

报告正文结构建议固定模板（便于看板统一渲染）：
1. **为什么推荐**（复述 evidence，不新增未经证实的判断）
2. **现状简述**（该领域的学习曲线 / 当前用户已具备的基础）
3. **建议学习路径**（分阶段，附预估投入时间）
4. **推荐资源**（web_search 得到的具体书籍/课程/文档，标注来源链接，遵循项目版权引用规范）
5. **可以现在就做的第一步**（具体到"打开哪个链接/跑哪个命令"，不是"多学习"这种空话）

### 3.4 新增 `growth_feedback_ledger.jsonl`

记录用户对候选/报告的操作（采纳/忽略/展开查看/多久后真的开始行动），参考现有 `suggestion_feedback_ledger.py` 的模式，供后续排序校准使用。

## 4. Daemon 自动执行设计（复用 AutonomousLoop 三档节奏）

| 挂载点 | 新增内容 | 频率/成本 |
|---|---|---|
| `_tick_passive()` | `growth_signal_scan()`：低成本扫描最近对话/Goal 记录，更新 `derived.growth_focus_areas`，只做信号提取，不生成候选 | 高频、低成本，跟随现有 tick（分钟级） |
| `_tick_maintenance()` | `growth_candidate_derive()`：仿 `soft_goal_deriver`，日频运行，把信号归纳成 `GrowthCandidate` 写入 growth_backlog，做去重/克制阈值判断 | 日频 |
| 新增 cron 任务 `sys:growth_advisor_daily` | 读取 growth_backlog 中 `pending` 且置信度 Top-N 的候选 → 逐个做 web_search 调研 → 生成 GrowthReport → 归档 wiki → 通过 NotificationDispatcher 推送（`source="growth_report"`） | **默认每天一次（daily）**，可配置为更高频（如每 12 小时）或降频（周/双周/月/关闭） |
| 新增 cron 任务 `sys:growth_monthly_retrospective` | 仿 `monthly_trend_retrospective.py`：汇总"这个月推荐了什么、用户采纳了什么、实际有没有推进"，生成一份月度复盘报告 | 月频 |

### 4.1 默认策略：默认开启 + 每日至少一次，但"频率"和"打扰"要分开治理

呼应第 -1 节的定位判断，这里做一个关键的设计取舍：

- **功能开关默认 = 开启（opt-out，而非 opt-in）**。这是本方案与上一版最大的改动。理由见第 -1 节——如果默认关闭，绝大多数用户永远不会主动去配置里找到它、打开它，那这个"最零成本的价值入口"就名存实亡了。
- **daemon 生成频率默认 = 每天至少跑一次**（`sys:growth_advisor_daily`），且信号扫描和候选生成本身（`_tick_passive`/`_tick_maintenance`）保持分钟级/小时级的高频观察——**生成频率高，不代表打扰频率高**，这两者必须在设计上明确拆开：
  - **生成（generation）**：daemon 每天都可以跑，哪怕跑出来发现"这次没有新的、够格的候选"，也完全可以什么都不产出，成本很低（只是一次 tick + 可能的 0 次 web_search）
  - **推送打扰（interruption）**：是否要把生成结果推送给用户（notification/邮件），要单独有一套节流策略，不能和生成频率划等号
- **频率必须可配置**，在「⚙️ 配置」里提供预设档位而不是要求用户填 cron 表达式：
  - `daily`（默认）/ `every_12h` / `weekly` / `manual`（只在用户主动点"帮我看看"时触发）/ `off`（完全关闭）
  - 每个档位对应的是"生成频率"，"推送频率"作为独立的二级选项（见 4.2）

### 4.2 推送节流：默认开启，但绝不"日推轰炸"

生成默认每天跑不代表用户每天都会收到一条通知，具体节流规则：

- **看板常驻展示不受节流限制**：只要生成了新候选/新报告，看板「🌱 成长顾问」tab 随时可见（这是"零成本"的核心——用户想看的时候随时有得看，不想看的时候也不会被打扰）
- **主动推送（通知中心 + 可选邮件）默认节流为"每天最多 1 条，且必须是当天新生成里质量最高/置信度最高的一条"**，而不是每条候选都单独推一次
- **同一天内若多次生成但都低于"值得推送"的置信度阈值，则只更新看板、不发通知**，避免"为了凑数硬推"
- 同一 `candidate_id` 被 `dismissed` 后，30 天内不再重复调研同一方向（复用 `soft_goal_deriver.py` 里 reject 30 天冷却的做法）
- 所有生成动作失败时按项目统一约定 `log_exception(e, where="mini_agent.growth_advisor.xxx")` 兜底，不让 daemon 因单次异常中断（对齐我们之前给 `error_log_stats` 加的错误日志统计 tab，这类异常也能在"📛 错误日志"里被看到、被统计）

## 5. 与用户的交互设计（看板）

新增标签页 **「🌱 成长顾问」**，布局：

1. **顶部：成长画像摘要卡**
   - 数据来自 `UserProfile.derived`（`summary` / `growth_focus_areas` / `growth_gaps`）
   - 纯展示，不做评分/打标签式的主观定性（避免"系统说我是什么样的人"带来的不适感，措辞上只呈现"最近你在忙这些"）

2. **中部：待处理推荐列表（growth_backlog，status=pending）**
   - 每条展示：标题、推荐理由（含 evidence 摘要）、置信度
   - 三个操作按钮：**采纳**（生成/加速对应 GrowthReport）/ **忽略**（写入 feedback ledger，30 天冷却）/ **展开详情**（看完整证据引用）
   - 空状态提示："最近没有发现明显的成长信号，继续用起来，我会持续观察"（避免为了"有东西展示"硬凑候选）

3. **底部：调研报告归档（growth_reports 时间线）**
   - 折叠展示 Markdown 报告正文，含生成时间、引用来源链接
   - 与「关注与通知」tab 联动：新报告生成会同时出现在通知列表里（复用 `reports_store.py` 已有机制，不需要新建通知系统）

4. **设置入口**（可以放在「⚙️ 配置」tab 里新增一节，而不是塞进成长顾问 tab 本身）：
   - 总开关（**默认开启**，用户可随时一键关闭；首次进入看板时用一条轻量提示告知"已为你开启成长顾问，会做什么/怎么关闭"，而不是强制弹窗打断）
   - 生成频率档位：`daily`（默认）/ `every_12h` / `weekly` / `manual` / `off`
   - 推送频率（独立于生成频率）：`daily`（默认，最多 1 条/天，见 4.2）/ `weekly 摘要`（把一周内的报告打包成一条）/ `仅看板不推送`
   - 关注领域白名单/黑名单（用户可以说"不要帮我调研理财方向"）
   - "立即为我看看"按钮：不等 cron 周期，随时手动触发一次生成（进一步降低"零成本"的门槛——第一次使用时不用等一天）

## 6. 反馈闭环与自我校准

- 用户的采纳/忽略行为写入 `growth_feedback_ledger.jsonl`
- `growth_candidate_derive()` 在生成新候选时，读取该 ledger：如果同类主题此前被多次忽略，降低同类候选的默认置信度（不是完全屏蔽，避免"用户当时忙、后来又感兴趣"的情况被永久拒绝）
- 月度复盘报告里包含"推荐命中率"这类自我评估指标，暴露给用户，也用于后续调参——这一点跟 `self_model_snapshot.py` 让 Agent 能回答"能力弱点清单是变短了还是变长了"是同一个思路，只是问题换成了"给用户的推荐，用户实际用上了多少"

## 7. 与现有模块的边界（重要，避免混淆）

| 模块 | 服务对象 | 产出物 |
|---|---|---|
| `soft_goal_deriver.py` / `next_action_advisor.py` | **Agent 自己** | Agent 该做的 Goal / 该优先处理的候选 |
| 本方案新增的 Growth Advisor | **人类用户** | 用户的成长方向候选 / 调研报告 |

两者在 daemon 挂载点（`_tick_passive/_tick_maintenance`）和数据结构风格上高度相似，**这是有意为之的复用**，但产出物的读取方入口必须分开（Agent 自己的 Goal 走 `/goals accept/reject`，用户成长候选走看板的采纳/忽略按钮），文案上也要明确区分，避免用户误以为"Agent 在给自己安排学习任务"或反过来。

## 8. 隐私与克制原则（必须前置，不是事后补充）

这里是本方案里唯一一处"默认开启"不适用的地方——**功能默认开启，不代表隐私克制可以打折扣**。恰恰因为默认面向所有用户开放，隐私和克制机制必须做得比"默认关闭"的方案更扎实，这是让"默认开启"能够成立的前提条件：

1. **默认开启，但首次触达必须透明告知**：不是静默开启后什么都不说，而是用户第一次打开看板时，用一条不打断使用的轻量提示说明"已经为你开启成长顾问、会用哪些已有数据、在哪里关闭"。默认值改变了，但知情权不能省略。
2. **只用本地已有数据，不新增采集**：对话历史摘要、Goal 记录、已生成的 wiki decision，不额外采集设备/生物特征/位置等敏感数据
3. **证据可追溯**：每条推荐必须能点开看到具体的 `evidence_refs`（哪几次对话/哪个 Goal 记录支撑了这个判断），不允许"感觉你应该学 XX"式无依据结论
4. **不做主观定性判断**：只呈现"你最近在忙什么"，不呈现"你是什么样的人""你该改掉什么毛病"这类评价性语言（避免触及 `user_wellbeing` 相关的边界）
5. **打扰频率克制**（见 4.2）：生成可以每天跑，但推送默认每天最多 1 条，且看板展示不算"打扰"——这是"默认开启"能够被用户接受、而不是被当成骚扰关掉的关键
6. **可关闭、可清除**：关闭开关的同时提供"清除已生成的成长档案数据"选项，关闭后不留痕迹地退回到"纯被动工具"模式

## 9. 分阶段落地路线图

路线图本身仍然分阶段验证，但和上一版的关键区别是：**默认开启、每日生成这两个目标值不因为"分阶段"而被推迟**——分阶段的是"推送/自动化程度"逐步放开，而不是"要不要认真做"逐步犹豫。P1 就应该让功能对所有用户可见、可用，只是推送渠道保守。

| 阶段 | 内容 | 周期估计 | 验证目标 |
|---|---|---|---|
| **P1** | 数据模型（GrowthProfile 扩展字段 + growth_backlog + growth_reports）+ 看板 tab 上线，**默认开启，接入 `sys:growth_advisor_daily`（每日生成）**，但推送**只走看板展示，不发通知/邮件** | 1-2 周 | 验证"每天生成一次"的报告质量够不够格、候选克制阈值是否合理，同时让功能从第一天起就对所有用户可见 |
| **P2** | 接入 NotificationDispatcher，打开 4.2 节的推送节流策略（默认每天最多 1 条），加入"立即为我看看"手动触发按钮 | 1-2 周 | 验证推送节流是否让用户觉得"恰到好处"而不是被打扰；观察关闭率作为核心健康指标 |
| **P3** | 反馈闭环（growth_feedback_ledger）+ 排序校准 + 月度复盘 cron + 邮件渠道 | 2 周 | 验证反馈校准是否让推荐质量随时间提升，形成第 -1 节提到的数据飞轮 |

## 10. 开放问题（留给评审讨论）

1. **冷启动**：新用户/低频用户信号不足，如何避免"很长时间没东西可推荐"显得系统很鸡肋？在"默认开启、每日生成"的前提下，冷启动问题会被放大——一个刚注册就每天被"暂无推荐"刷屏的用户体验很差。建议：
   - 信号不足时，看板呈现"我还在了解你，多聊几次/设几个目标，我会开始主动帮你想"，而不是空白或负面反馈
   - 提供"你可以手动告诉我你想成长的方向"的显式入口，作为被动观察不足时的补充信号来源，尤其对新用户重要
2. **报告质量的自证**：默认开启意味着报告质量的下限直接决定了这个功能会不会被大量用户当天就关掉。P1 阶段必须先人工抽查若干份报告，评估是否达到"用户看完能直接采取行动"的标准，这一验证不能省略或压缩，即使这会让"默认开启"的上线时间往后推一点。
3. **多用户场景**：`profile.py` 已经为多用户预留了 `user_id` 扩展点，本方案的 growth_backlog / growth_reports 存储路径也应该从设计之初就带上 `user_id`，避免 P1 阶段图省事写死单用户路径，P2 再返工。
4. **"默认开启"的健康度指标**：既然这是战略级入口，建议从 P1 起就埋点跟踪几个核心指标（哪怕先落在本地日志/看板里而不是做成完整的数据看板）：**当天关闭率**（开启后 24 小时内主动关闭的比例，是最敏感的预警信号）、**推荐采纳率**、**报告展开率**。这些指标应该比功能本身更早被确定下来，否则"默认开启"这个决策就没有办法被验证和调整。
