# info_hub 推荐信息流：设计方案（待确认，尚未实施）

> 状态：P1 已实施（2026-11-12，见第 11 节）；P2–P4 尚未实施。第 1–10 节为实施前的方案，保留原文以便对照。
> 目标：抓取内容越来越多后，不再让用户在平铺列表里自己找，而是由系统先筛选、去重、聚合、排序，再分区展示；放在一个**新的标签页**里，原有“抓取结果”页保持不变，作为原始数据视图。

---

## 1. 现状与问题

### 1.1 现有机制（已读代码确认）
- 排序只有一个维度：`core/profile.py` 的 `score_item`——标题/摘要的 2~4 字子串与“已学关键词权重”相加，加手写主题/屏蔽词、LLM 关键词、来源权重。输出是一个分数，**只在单个信息源内**排序。
- 反馈信号：👍/👎/⏰（含原因标签）、停留时长（≥30 秒才算正向）、打开记录。关键词权重按 30 天半衰期衰减。
- 合并视图（`core/merged.py`）能跨源、按时间窗合并，但只有三种简单排序，没有去重聚合、没有多样性控制。
- 评估（`core/evaluation.py`）记录曝光/打开/反馈，能比较 ranked 与 plain 两种视图。

### 1.2 数据变多之后暴露的问题
| # | 问题 | 现状表现 |
|---|------|----------|
| 1 | 没有分诊 | 用户面对几百条平铺列表，要自己扫、自己判断 |
| 2 | 重复 | 同一事件被多个源、同一源多次报道，各占一行 |
| 3 | 老条目霸榜 | 热榜里一直挂着的条目在“最近 24 小时”里每次都出现 |
| 4 | 处理过的还在 | 点过 👍/👎、打开过的条目下次仍原样出现 |
| 5 | 单一信号 | 只有“关键词命中”，没有新鲜度、重要性（多源同报、排名上升）、来源质量 |
| 6 | 回音室 | 越点越窄，没有探索；一个主题可能占满首屏 |
| 7 | 冷启动/稀疏反馈 | 新用户或新信息源没有画像，排序几乎无效 |
| 8 | 不可解释 | 只显示“推荐分”，用户不知道为什么推它，也无从纠正 |
| 9 | 无法验证好坏 | 只有线上统计，没有离线回放来比较“新排序是否真的更好” |

## 2. 设计原则
1. **先分诊，再阅读**：首屏给出少量精选，其余折叠；目标是“10 分钟内处理完今天最值得看的”。
2. **事件为单位，而不是链接为单位**：先聚合，再排序。
3. **多信号、可解释、可调**：每个分数分量可见，权重在配置里，默认值保守。
4. **反馈要便宜**：一键处理，处理过的不再打扰。
5. **不依赖 LLM 也能工作**；LLM 是可选增强，默认关闭（与现有“保守默认”约定一致）。
6. **纯文本存储、可回放**：不引入数据库；所有曝光与决策落 JSONL，便于离线评估。
7. **可验证**：上线前能用历史反馈做回放对比，不靠感觉。

## 3. 总体架构：五段流水线

```
抓取快照 ──► ① 候选池 ──► ② 聚合去重 ──► ③ 多信号打分 ──► ④ 重排(多样性+探索) ──► ⑤ 分区展示
                │                                              ▲                        │
                └── 已处理/已隐藏过滤                          └─── ⑥ 反馈与评估 ◄───────┘
```

### ① 候选池
- 来源：`core/merged.py` 已有的“时间窗合并”（同源同条目去重，带 first_seen / seen_count / is_new / rank）。
- 过滤：
  - 已反馈（👍/👎）、已打开、已被“不再显示”的条目默认不进候选（可在页面里切换“显示已处理”）。
  - ⏰“稍后看”的条目进入专门的“稍后看队列”，不重复出现在精选里。
  - 命中“屏蔽词”的条目直接剔除。
- 规模上限：候选最多取最近 N 条（默认 2000），防止首次打开卡顿。

### ② 聚合去重（“事件”）
- 方法：标题字符二元组 Jaccard 相似度 + 倒排索引分桶（只比较共享 n-gram 的条目，避免 O(n²)），并查集合并。URL 完全相同直接合并。
- 一个**簇**就是一个“事件”：代表标题取最短且信息完整的一条（或来源优先级最高的一条），保留全部成员（来源、链接、时间）。
- 小实验（手写的 7 组样例标题，**仅作可行性示意，不代表真实数据**）：

  | 标题对 | 关系 | 二元组 Jaccard |
  |---|---|---|
  | 央行发布三季度货币政策执行报告 / 央行三季度货币政策执行报告发布 | 同事件 | 0.75 |
  | 三季度GDP同比增长4.5% / 国家统计局：前三季度GDP同比增长4.5% | 同事件 | 0.65 |
  | 苹果发布新款M5芯片MacBook / 新款MacBook Pro搭载M5芯片发布 | 同事件 | 0.52 |
  | 英伟达财报超预期，股价盘后大涨 / 英伟达发布财报 营收创新高 | 同事件（弱） | 0.14 |
  | 央行发布三季度货币政策… / 央行宣布降准0.5个百分点 | 同主题不同事件 | 0.04 |
  | 苹果发布新款M5芯片MacBook / 苹果公司回应数据泄露传闻 | 同主体不同事件 | 0.04 |

  结论：阈值取 ≈0.45 能把前三类“同一事件”聚起来，且不会把“同主题不同事件”误并；像第四行这种措辞差异很大的同一事件会漏聚，这类只能靠可选的 LLM/向量层补（第 9 节）。**宁可漏聚，不要误并**，阈值默认偏保守，可配置。
- 簇的“重要性”信号：成员数、覆盖的**不同来源数**（多源同报）、最高排名、排名上升速度。

### ③ 多信号打分（可解释的线性组合）
每个簇得到若干 0~1 的分量，再按配置权重相加。默认权重给一个保守起点，后面可由数据学习（第 6 节阶段 3）。

| 分量 | 含义 | 来源 |
|---|---|---|
| `interest` | 与用户兴趣的匹配度 | 复用现有 `score_item`（关键词/手写主题/LLM 关键词），按分布做分位数归一化到 0~1，**不再用原始分数直接比较** |
| `source_affinity` | 来源偏好与质量 | 现有来源权重 + 该来源历史“被标记感兴趣/被打开”的比率（带平滑，样本少时回落到先验） |
| `freshness` | 新鲜度 | 距 first_seen（或 published_at）的指数衰减；半衰期按信息源类型区分（资讯流短、热榜更短、订阅较长） |
| `importance` | 重要性 | 多源同报数（对数）、窗口内最高排名、排名上升、热度分位数 |
| `persistence_penalty` | 老条目惩罚 | 只靠“一直在榜”出现（`is_new=False` 且 seen_count 很大）的簇降权，解决“热榜霸屏” |
| `fatigue_penalty` | 曝光疲劳 | 已被展示 ≥K 次却从未被点击/反馈的簇逐步降权（隐式负反馈） |

- 每个簇保存各分量值与最大贡献项，用于生成**一句话理由**：“命中关注主题『大模型』· 3 个来源报道 · 30 分钟前出现 · 排名上升 5 位”。
- 屏蔽词与“最近一次反馈为不感兴趣”的条目不进候选，而不是靠 -1000 分沉底。

### ④ 重排：多样性与探索
- **多样性（MMR 思路）**：逐个挑选时，对与已选结果同簇/同主题/同来源的候选减分；每个来源在一屏内设上限，避免一个源占满首屏。
- **探索位**：固定比例（默认 15%）的位置留给“画像之外”的候选——来自低证据主题或新信息源、但重要性高的簇，并明确标注“探索”。用户对探索项的反馈同样学习，防止回音室。
- **冷启动**：没有画像或反馈很少时，`interest` 分量权重自动降低，改由 `importance + freshness` 主导（即“今日要闻”模式）；并提供“快速分诊”模式（第 5 节）尽快积累反馈。

### ⑤ 分区展示（新标签页“推荐”）
不再是一张平铺表，而是按用途分区，每区有数量上限，其余折叠：

1. **今日精选**（Top 10）：综合得分最高的簇，带理由。
2. **多源热点**：被 ≥3 个来源同时报道的事件，卡片可展开看各来源链接。
3. **你关注的主题**：按画像里 Top 主题分组（每组 3~5 条），主题来自手写主题与已学关键词。
4. **探索**：画像之外但值得看的内容，标注为探索。
5. **稍后看**：⏰ 队列，按加入时间。
6. **其余**：折叠，需要时展开或回到“抓取结果”页看原始列表。

卡片统一：标题 · 来源（多源显示“+N”）· 首次出现时间 · 一句话理由 · 👍 👎 ⏰ 打开 · “不再显示此来源/此主题”快捷项。页面顶部筛选：时间范围（沿用 1 小时~30 天）、分类/类型（沿用现有筛选）、“显示已处理”开关。

## 4. 数据与存储（仍为纯文本）
| 文件 | 内容 | 用途 |
|---|---|---|
| `data/feed/state.json` | 每个条目：展示次数、最近展示时间、是否隐藏/稍后看；簇缓存（簇 id → 成员 id） | 疲劳惩罚、已处理过滤、避免每次重算聚类 |
| `data/feed/shown.jsonl` | 每次展示一批结果：时间、视图 `feed_v1`、条目 key、**位置**、所在分区、各分量值 | 离线评估、学习权重（位置是评估排序质量的必要信息） |
| `config/settings.yaml` 新增 `feed:` 段 | 权重、阈值、探索比例、分区数量、半衰期 | 全部可调，默认值保守 |

复用：反馈（`feedback/events.jsonl`）、停留与打开（`exposure`）、画像（`profile.json`）、合并窗口（`core/merged.py`）。曝光记录沿用现有 `record_impression` 的格式并增加 `position` 字段，向后兼容。

聚类缓存按“条目 id 集合”增量更新：新抓取的条目只与近期簇比较，不必每次全量重算。

## 5. 反馈回路

### 5.1 显式反馈（已有）
👍/👎/⏰ 与原因标签。新增两个更省力的入口：
- **快速分诊模式**：一次一张卡片，键盘/按钮 👍 / 👎 / ⏰ / 跳过，目标是几分钟内给 20~30 条打标，用来解决冷启动。
- **不再显示**：对来源或主题一键屏蔽（写入手写屏蔽词/来源权重，可在画像面板撤销）。

### 5.2 隐式反馈
- 打开、停留（已有）→ 正向。
- **展示但无动作**：同一簇被展示 ≥K 次（默认 3）仍无任何点击/反馈 → 疲劳惩罚，视为弱负向。注意这是**弱**信号，不并入画像关键词的负权重，只影响展示频率，避免误伤。
- 反馈结果回写到分量层面（该簇的哪些分量高、用户却点了 👎），为阶段 3 的权重学习提供样本。

## 6. 分阶段实施（每阶段都可独立上线、独立回退）

| 阶段 | 内容 | 是否需要 LLM/外部依赖 | 默认 |
|---|---|---|---|
| **P1 骨架** | 新标签页“推荐”；候选池 + 已处理过滤；聚合去重；`interest / source_affinity / freshness / importance / persistence_penalty` 打分；分区展示（精选、多源热点、关注主题、稍后看、其余）；一句话理由；曝光记录增加位置 | 无 | 新标签页本身默认可见，但**不替换**“抓取结果”页 |
| **P2 行为闭环** | 曝光疲劳；多样性重排与来源上限；探索位；快速分诊模式；“不再显示”；**离线回放评估**（见第 7 节） | 无 | 探索位默认 15%，疲劳默认开启，均可在配置关闭 |
| **P3 学习权重** | 用 `shown.jsonl + 反馈` 训练极简逻辑回归（纯 Python），在数据足够（如 ≥200 个带标签样本）且回放显示优于手工权重时才启用，否则回落默认权重 | 无 | **默认关闭**，需在页面明确开启 |
| **P4 LLM 增强（可选）** | 给 Top 簇生成主题标签与一句话摘要；补聚措辞差异大的同一事件；对精选做小批量重排与理由润色；按条目缓存、设每日调用上限 | 需要已配置的模型 | **默认关闭**，需明确开启，并显示本次预计调用量 |

建议先做 P1+P2，看实际数据效果与回放结果，再决定是否值得做 P3、P4。

## 7. 如何验证“更好”（不靠感觉）
1. **离线回放（P2 交付）**：取历史反馈作为标签（👍/打开/长停留=正，👎=负），对每次历史展示，比较“现有排序”与“新排序”的 **NDCG@10 / 精选前 10 的正例率 / 前 10 的 👎 率**。样本不足时页面明确显示“样本不足，结果仅供参考”。
2. **线上对比**：新视图的曝光、点击、👍 率、👎 率、停留，与现有 ranked/plain 并排显示（沿用评估面板，新增视图名 `feed_v1`）。
3. **体验指标**：首屏精选的 👎 率；重复率（首屏内同一事件出现次数，应为 1）；单来源占比上限是否生效；已处理条目是否再出现（应为 0）。
4. **单元与端到端测试**：聚合（正反例阈值）、各打分分量（边界与单调性）、多样性与探索位占比、疲劳衰减、已处理过滤、冷启动降级、渲染与按钮行为。

## 8. 风险与取舍
- **聚类误并**会让用户漏看内容：因此阈值保守、保留“展开成员”入口，宁可漏聚。
- **多信号权重**初期是经验值，可能不准：所以每个分量可见、权重可配、有回放可对比；P3 才引入学习。
- **探索位**会让一部分首屏内容看起来“不相关”：占比可调，且单独标注。
- **聚合后条目数变少**：首屏更干净，但需要“其余/抓取结果”作为兜底，保证不丢信息。
- **性能**：候选上限 + 倒排分桶 + 簇缓存；P1 要在真实数据量上测首屏耗时（目前沙箱里没有真实数据，**这一点未验证**）。
- **隐私**：全部在本机；P4 若启用才会把标题发给所选模型，需要明确提示。

## 11. P1 实施记录（2026-11-12）

### 11.1 第 9 节决策的采用情况
用户要求“按规划一个阶段一个阶段执行”，因此第 9 节的待决项按文档中的推荐值采用，请在后续阶段前确认：
1. **范围**：只做 P1。P2、P3、P4 未做。
2. **标签页**：新增“推荐”页签，位于“抓取结果”之前；“抓取结果”页保持原样。
3. **默认值**：已处理条目默认隐藏（已实施，可用“显示已处理”开关查看）。探索位与曝光疲劳属于 P2，尚未实施，因此现在没有开关。
4. **聚合阈值**：采用 0.45，宁可漏聚，不要误并。
5. **LLM 预留字段**：**未预留**。文档建议预留“主题/摘要”字段，但 P1 没有任何读取它的地方，空字段只会增加迁移成本。P4 启用时再增加。这是与文档建议的唯一偏差。

### 11.2 实现与设计的差异和具体化
- **代表标题**：设计写的是“最短且信息完整”。实现规则是：优先有摘要的成员，其次标题更短的，再取最早出现的。
- **新鲜度**：用 `first_seen`，未用 `published_at`（P1 简化）。半衰期按信息源类型配置。
- **反馈作用于整个事件**：点一次 👍/👎/⏰，同一事件的每条报道都会各记录一次。否则另一来源的同一事件会在处理后再次出现。代价是同一事件在关键词学习中会被计入多次，P3 之前可接受。
- **二元组过滤**：设计未说明的细节。出现在超过 `max(60, 候选数×10%)` 条标题中的二元组不参与配对，用于控制 O(n²) 的开销。
- **稍后看**：不参与聚合，按条目去重，按加入时间倒序，最多 30 条。
- **分区互斥**：每个事件只归入一个分区，顺序为精选、多源热点、关注主题、其余，因此天然去重。
- **排名上升**：`merged.py` 新增 `first_rank`（窗口内首次出现的排名）。这是向后兼容的增量字段。
- **未创建 `state.json`**：只有 P2 的疲劳与已展示计数需要它。

### 11.3 P1 的分量公式（默认权重见 `config/settings.yaml` 的 feed 段）
- `interest`：`score_item` 的原始分在本批候选内做分位数归一化到 0~1；画像为空时整体乘以 `cold_start_factor`（0.3）。
- `source_affinity`：来源的 👍 与打开次数相对 👎 次数的比率（带先验平滑，K=5），与画像里来源权重的 sigmoid 各占一半。无数据时为 0.5。
- `freshness`：`0.5 ^ (距首次出现的小时数 / 半衰期)`。资讯流 12 小时，热榜 3 小时，订阅 72 小时。
- `importance`：`0.4 × 多源（log2）+ 0.4 × 最高排名（1/(1+(r-1)/10)）+ 0.2 × 排名上升（/10）`。
- `persistence_penalty`：只有“从未新增且出现快照数超过 12”的簇才扣分，最多扣 1。
- 总分 = 0.35·interest·(冷启动系数) + 0.15·source_affinity + 0.25·freshness + 0.25·importance − 0.3·penalty。
