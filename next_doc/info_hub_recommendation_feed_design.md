# info_hub 推荐信息流：设计方案（待确认，尚未实施）

> 状态：P1、P2、P3、P4 已实施（见第 11–14 节）。P4 中的“精选小批量重排”与“理由润色”未实施，见第 14.2 节。第 1–10 节为实施前的方案，保留原文以便对照。
> 目标：抓取内容越来越多后，不再让用户在平铺列表里自己找，而是由系统先筛选、去重、聚合、排序，再分区展示；放在一个**新的标签页**里，原有“抓取结果”页保持不变，作为原始数据视图。

---

## 1. 现状与问题

### 1.1 现有机制（已读代码确认）
- 排序只有一个维度：`core/profile.py` 的 `score_item`——标题/摘要的 2~4 字子串与“已学关键词权重”相加，加手写主题/屏蔽词、LLM 关键词、来源权重。输出是一个分数，**只在单个信息源内**排序。
- 反馈信号：👍/👎/⏰（含原因标签）、停留时长（≥30 秒才算正向）、打开记录。关键词权重按 30 天半衰期衰减。
- 合并视图（`core/merged.py`）能跨源、按时间窗合并，但只有三种简单排序，没有去重聚合、没有多样性控制。
- 评估（`core/evaluation.py`）记录曝光/打开/反馈，能比较 ranked 与 plain 两种视图。

### 1.2 数据变多之后暴露的问题
| # | 问题 | 现状表现 |
|---|------|----------|
| 1 | 没有分诊 | 用户面对几百条平铺列表，要自己扫、自己判断 |
| 2 | 重复 | 同一事件被多个源、同一源多次报道，各占一行 |
| 3 | 老条目霸榜 | 热榜里一直挂着的条目在“最近 24 小时”里每次都出现 |
| 4 | 处理过的还在 | 点过 👍/👎、打开过的条目下次仍原样出现 |
| 5 | 单一信号 | 只有“关键词命中”，没有新鲜度、重要性（多源同报、排名上升）、来源质量 |
| 6 | 回音室 | 越点越窄，没有探索；一个主题可能占满首屏 |
| 7 | 冷启动/稀疏反馈 | 新用户或新信息源没有画像，排序几乎无效 |
| 8 | 不可解释 | 只显示“推荐分”，用户不知道为什么推它，也无从纠正 |
| 9 | 无法验证好坏 | 只有线上统计，没有离线回放来比较“新排序是否真的更好” |

## 2. 设计原则
1. **先分诊，再阅读**：首屏给出少量精选，其余折叠；目标是“10 分钟内处理完今天最值得看的”。
2. **事件为单位，而不是链接为单位**：先聚合，再排序。
3. **多信号、可解释、可调**：每个分数分量可见，权重在配置里，默认值保守。
4. **反馈要便宜**：一键处理，处理过的不再打扰。
5. **不依赖 LLM 也能工作**；LLM 是可选增强，默认关闭（与现有“保守默认”约定一致）。
6. **纯文本存储、可回放**：不引入数据库；所有曝光与决策落 JSONL，便于离线评估。
7. **可验证**：上线前能用历史反馈做回放对比，不靠感觉。

## 3. 总体架构：五段流水线

```
抓取快照 ──► ① 候选池 ──► ② 聚合去重 ──► ③ 多信号打分 ──► ④ 重排(多样性+探索) ──► ⑤ 分区展示
                │                                              ▲                        │
                └── 已处理/已隐藏过滤                          └─── ⑥ 反馈与评估 ◄───────┘
```

### ① 候选池
- 来源：`core/merged.py` 已有的“时间窗合并”（同源同条目去重，带 first_seen / seen_count / is_new / rank）。
- 过滤：
  - 已反馈（👍/👎）、已打开、已被“不再显示”的条目默认不进候选（可在页面里切换“显示已处理”）。
  - ⏰“稍后看”的条目进入专门的“稍后看队列”，不重复出现在精选里。
  - 命中“屏蔽词”的条目直接剔除。
- 规模上限：候选最多取最近 N 条（默认 2000），防止首次打开卡顿。

### ② 聚合去重（“事件”）
- 方法：标题字符二元组 Jaccard 相似度 + 倒排索引分桶（只比较共享 n-gram 的条目，避免 O(n²)），并查集合并。URL 完全相同直接合并。
- 一个**簇**就是一个“事件”：代表标题取最短且信息完整的一条（或来源优先级最高的一条），保留全部成员（来源、链接、时间）。
- 小实验（手写的 7 组样例标题，**仅作可行性示意，不代表真实数据**）：

  | 标题对 | 关系 | 二元组 Jaccard |
  |---|---|---|
  | 央行发布三季度货币政策执行报告 / 央行三季度货币政策执行报告发布 | 同事件 | 0.75 |
  | 三季度GDP同比增长4.5% / 国家统计局：前三季度GDP同比增长4.5% | 同事件 | 0.65 |
  | 苹果发布新款M5芯片MacBook / 新款MacBook Pro搭载M5芯片发布 | 同事件 | 0.52 |
  | 英伟达财报超预期，股价盘后大涨 / 英伟达发布财报 营收创新高 | 同事件（弱） | 0.14 |
  | 央行发布三季度货币政策… / 央行宣布降准0.5个百分点 | 同主题不同事件 | 0.04 |
  | 苹果发布新款M5芯片MacBook / 苹果公司回应数据泄露传闻 | 同主体不同事件 | 0.04 |

  结论：阈值取 ≈0.45 能把前三类“同一事件”聚起来，且不会把“同主题不同事件”误并；像第四行这种措辞差异很大的同一事件会漏聚，这类只能靠可选的 LLM/向量层补（第 9 节）。**宁可漏聚，不要误并**，阈值默认偏保守，可配置。
- 簇的“重要性”信号：成员数、覆盖的**不同来源数**（多源同报）、最高排名、排名上升速度。

### ③ 多信号打分（可解释的线性组合）
每个簇得到若干 0~1 的分量，再按配置权重相加。默认权重给一个保守起点，后面可由数据学习（第 6 节阶段 3）。

| 分量 | 含义 | 来源 |
|---|---|---|
| `interest` | 与用户兴趣的匹配度 | 复用现有 `score_item`（关键词/手写主题/LLM 关键词），按分布做分位数归一化到 0~1，**不再用原始分数直接比较** |
| `source_affinity` | 来源偏好与质量 | 现有来源权重 + 该来源历史“被标记感兴趣/被打开”的比率（带平滑，样本少时回落到先验） |
| `freshness` | 新鲜度 | 距 first_seen（或 published_at）的指数衰减；半衰期按信息源类型区分（资讯流短、热榜更短、订阅较长） |
| `importance` | 重要性 | 多源同报数（对数）、窗口内最高排名、排名上升、热度分位数 |
| `persistence_penalty` | 老条目惩罚 | 只靠“一直在榜”出现（`is_new=False` 且 seen_count 很大）的簇降权，解决“热榜霸屏” |
| `fatigue_penalty` | 曝光疲劳 | 已被展示 ≥K 次却从未被点击/反馈的簇逐步降权（隐式负反馈） |

- 每个簇保存各分量值与最大贡献项，用于生成**一句话理由**：“命中关注主题『大模型』· 3 个来源报道 · 30 分钟前出现 · 排名上升 5 位”。
- 屏蔽词与“最近一次反馈为不感兴趣”的条目不进候选，而不是靠 -1000 分沉底。

### ④ 重排：多样性与探索
- **多样性（MMR 思路）**：逐个挑选时，对与已选结果同簇/同主题/同来源的候选减分；每个来源在一屏内设上限，避免一个源占满首屏。
- **探索位**：固定比例（默认 15%）的位置留给“画像之外”的候选——来自低证据主题或新信息源、但重要性高的簇，并明确标注“探索”。用户对探索项的反馈同样学习，防止回音室。
- **冷启动**：没有画像或反馈很少时，`interest` 分量权重自动降低，改由 `importance + freshness` 主导（即“今日要闻”模式）；并提供“快速分诊”模式（第 5 节）尽快积累反馈。

### ⑤ 分区展示（新标签页“推荐”）
不再是一张平铺表，而是按用途分区，每区有数量上限，其余折叠：

1. **今日精选**（Top 10）：综合得分最高的簇，带理由。
2. **多源热点**：被 ≥3 个来源同时报道的事件，卡片可展开看各来源链接。
3. **你关注的主题**：按画像里 Top 主题分组（每组 3~5 条），主题来自手写主题与已学关键词。
4. **探索**：画像之外但值得看的内容，标注为探索。
5. **稍后看**：⏰ 队列，按加入时间。
6. **其余**：折叠，需要时展开或回到“抓取结果”页看原始列表。

卡片统一：标题 · 来源（多源显示“+N”）· 首次出现时间 · 一句话理由 · 👍 👎 ⏰ 打开 · “不再显示此来源/此主题”快捷项。页面顶部筛选：时间范围（沿用 1 小时~30 天）、分类/类型（沿用现有筛选）、“显示已处理”开关。

## 4. 数据与存储（仍为纯文本）
| 文件 | 内容 | 用途 |
|---|---|---|
| `data/feed/state.json` | 每个条目：展示次数、最近展示时间、是否隐藏/稍后看；簇缓存（簇 id → 成员 id） | 疲劳惩罚、已处理过滤、避免每次重算聚类 |
| `data/feed/shown.jsonl` | 每次展示一批结果：时间、视图 `feed_v1`、条目 key、**位置**、所在分区、各分量值 | 离线评估、学习权重（位置是评估排序质量的必要信息） |
| `config/settings.yaml` 新增 `feed:` 段 | 权重、阈值、探索比例、分区数量、半衰期 | 全部可调，默认值保守 |

复用：反馈（`feedback/events.jsonl`）、停留与打开（`exposure`）、画像（`profile.json`）、合并窗口（`core/merged.py`）。曝光记录沿用现有 `record_impression` 的格式并增加 `position` 字段，向后兼容。

聚类缓存按“条目 id 集合”增量更新：新抓取的条目只与近期簇比较，不必每次全量重算。

## 5. 反馈回路

### 5.1 显式反馈（已有）
👍/👎/⏰ 与原因标签。新增两个更省力的入口：
- **快速分诊模式**：一次一张卡片，键盘/按钮 👍 / 👎 / ⏰ / 跳过，目标是几分钟内给 20~30 条打标，用来解决冷启动。
- **不再显示**：对来源或主题一键屏蔽（写入手写屏蔽词/来源权重，可在画像面板撤销）。

### 5.2 隐式反馈
- 打开、停留（已有）→ 正向。
- **展示但无动作**：同一簇被展示 ≥K 次（默认 3）仍无任何点击/反馈 → 疲劳惩罚，视为弱负向。注意这是**弱**信号，不并入画像关键词的负权重，只影响展示频率，避免误伤。
- 反馈结果回写到分量层面（该簇的哪些分量高、用户却点了 👎），为阶段 3 的权重学习提供样本。

## 6. 分阶段实施（每阶段都可独立上线、独立回退）

| 阶段 | 内容 | 是否需要 LLM/外部依赖 | 默认 |
|---|---|---|---|
| **P1 骨架** | 新标签页“推荐”；候选池 + 已处理过滤；聚合去重；`interest / source_affinity / freshness / importance / persistence_penalty` 打分；分区展示（精选、多源热点、关注主题、稍后看、其余）；一句话理由；曝光记录增加位置 | 无 | 新标签页本身默认可见，但**不替换**“抓取结果”页 |
| **P2 行为闭环** | 曝光疲劳；多样性重排与来源上限；探索位；快速分诊模式；“不再显示”；**离线回放评估**（见第 7 节） | 无 | 探索位默认 15%，疲劳默认开启，均可在配置关闭 |
| **P3 学习权重** | 用 `shown.jsonl + 反馈` 训练极简逻辑回归（纯 Python），在数据足够（如 ≥200 个带标签样本）且回放显示优于手工权重时才启用，否则回落默认权重 | 无 | **默认关闭**，需在页面明确开启 |
| **P4 LLM 增强（可选）** | 给 Top 簇生成主题标签与一句话摘要；补聚措辞差异大的同一事件；对精选做小批量重排与理由润色；按条目缓存、设每日调用上限 | 需要已配置的模型 | **默认关闭**，需明确开启，并显示本次预计调用量 |

建议先做 P1+P2，看实际数据效果与回放结果，再决定是否值得做 P3、P4。

## 7. 如何验证“更好”（不靠感觉）
1. **离线回放（P2 交付）**：取历史反馈作为标签（👍/打开/长停留=正，👎=负），对每次历史展示，比较“现有排序”与“新排序”的 **NDCG@10 / 精选前 10 的正例率 / 前 10 的 👎 率**。样本不足时页面明确显示“样本不足，结果仅供参考”。
2. **线上对比**：新视图的曝光、点击、👍 率、👎 率、停留，与现有 ranked/plain 并排显示（沿用评估面板，新增视图名 `feed_v1`）。
3. **体验指标**：首屏精选的 👎 率；重复率（首屏内同一事件出现次数，应为 1）；单来源占比上限是否生效；已处理条目是否再出现（应为 0）。
4. **单元与端到端测试**：聚合（正反例阈值）、各打分分量（边界与单调性）、多样性与探索位占比、疲劳衰减、已处理过滤、冷启动降级、渲染与按钮行为。

## 8. 风险与取舍
- **聚类误并**会让用户漏看内容：因此阈值保守、保留“展开成员”入口，宁可漏聚。
- **多信号权重**初期是经验值，可能不准：所以每个分量可见、权重可配、有回放可对比；P3 才引入学习。
- **探索位**会让一部分首屏内容看起来“不相关”：占比可调，且单独标注。
- **聚合后条目数变少**：首屏更干净，但需要“其余/抓取结果”作为兜底，保证不丢信息。
- **性能**：候选上限 + 倒排分桶 + 簇缓存；P1 要在真实数据量上测首屏耗时（目前沙箱里没有真实数据，**这一点未验证**）。
- **隐私**：全部在本机；P4 若启用才会把标题发给所选模型，需要明确提示。

## 11. P1 实施记录（2026-11-12）

### 11.1 第 9 节决策的采用情况
用户要求“按规划一个阶段一个阶段执行”，因此第 9 节的待决项按文档中的推荐值采用，请在后续阶段前确认：
1. **范围**：只做 P1。P2、P3、P4 未做。
2. **标签页**：新增“推荐”页签，位于“抓取结果”之前；“抓取结果”页保持原样。
3. **默认值**：已处理条目默认隐藏（已实施，可用“显示已处理”开关查看）。探索位与曝光疲劳属于 P2，尚未实施，因此现在没有开关。
4. **聚合阈值**：采用 0.45，宁可漏聚，不要误并。
5. **LLM 预留字段**：**未预留**。文档建议预留“主题/摘要”字段，但 P1 没有任何读取它的地方，空字段只会增加迁移成本。P4 启用时再增加。这是与文档建议的唯一偏差。

### 11.2 实现与设计的差异和具体化
- **代表标题**：设计写的是“最短且信息完整”。实现规则是：优先有摘要的成员，其次标题更短的，再取最早出现的。
- **新鲜度**：用 `first_seen`，未用 `published_at`（P1 简化）。半衰期按信息源类型配置。
- **反馈作用于整个事件**：点一次 👍/👎/⏰，同一事件的每条报道都会各记录一次。否则另一来源的同一事件会在处理后再次出现。代价是同一事件在关键词学习中会被计入多次，P3 之前可接受。
- **二元组过滤**：设计未说明的细节。出现在超过 `max(60, 候选数×10%)` 条标题中的二元组不参与配对，用于控制 O(n²) 的开销。
- **稍后看**：不参与聚合，按条目去重，按加入时间倒序，最多 30 条。
- **分区互斥**：每个事件只归入一个分区，顺序为精选、多源热点、关注主题、其余，因此天然去重。
- **排名上升**：`merged.py` 新增 `first_rank`（窗口内首次出现的排名）。这是向后兼容的增量字段。
- **未创建 `state.json`**：只有 P2 的疲劳与已展示计数需要它。

### 11.3 P1 的分量公式（默认权重见 `config/settings.yaml` 的 feed 段）
- `interest`：`score_item` 的原始分在本批候选内做分位数归一化到 0~1；画像为空时整体乘以 `cold_start_factor`（0.3）。
- `source_affinity`：来源的 👍 与打开次数相对 👎 次数的比率（带先验平滑，K=5），与画像里来源权重的 sigmoid 各占一半。无数据时为 0.5。
- `freshness`：`0.5 ^ (距首次出现的小时数 / 半衰期)`。资讯流 12 小时，热榜 3 小时，订阅 72 小时。
- `importance`：`0.4 × 多源（log2）+ 0.4 × 最高排名（1/(1+(r-1)/10)）+ 0.2 × 排名上升（/10）`。
- `persistence_penalty`：只有“从未新增且出现快照数超过 12”的簇才扣分，最多扣 1。
- 总分 = 0.35·interest·(冷启动系数) + 0.15·source_affinity + 0.25·freshness + 0.25·importance − 0.3·penalty。

### 11.4 验证
- 设计文档第 3 节的 6 组样例标题，用实现的二元组方法复算，Jaccard 与文档一致（0.75 / 0.65 / 0.52 / 0.14 / 0.05 / 0.04）。阈值 0.45 下，前三组合并，后三组保持分开。
- 2000 条合成标题（含 200 组重复）聚合约 0.66 秒，200 组重复全部找回，无误并。这是对设计文档“首屏耗时未验证”的部分回应，**真实数据量下的表现仍未验证**。

## 12. P2 实施记录（行为闭环）

### 12.1 实施内容与默认值（均可在 config/settings.yaml 的 feed 段关闭）
- **曝光疲劳**：窗口（7 天）内展示 ≥3 次、且从未被点击或反馈的条目，开始按 `(次数−3+1)/3` 线性降权，第 5 次展示时达到满值（1），权重 0.2。有任何反馈或打开的条目本来就被隐藏，因此疲劳只影响“展示了却没反应”的条目。
- **多样性与来源上限**：精选采用贪心挑选（MMR 思路）。每次选“扣掉同主题重复惩罚（每条 0.1）后”分最高的，同一信息源在精选中最多 3 条。
- **探索位**：精选条数 ≥4 时，取 `round(精选条数 × 15%)`（10 条精选即 2 条），从“没有命中任何关注主题”的簇里选重要性×新鲜度最高的，单独成“探索”分区。设为 0 即关闭。
- **快速分诊**：页面顶部开关。一次只显示一条，👍 / 👎 / ⏰ 直接记录，“跳过”看下一条。同一事件的全部报道一起记录。
- **不再显示**：卡片上的 🚫 隐藏该信息源（写入 `data/feed/prefs.json`，页面底部可恢复）；主题分组上的“屏蔽此主题”把词加入手写屏蔽词（可在画像面板撤销）。
- **离线回放**：见 12.3。

### 12.2 与设计文档的偏差
- **没有 `state.json`**。疲劳计数直接从 `data/feed/shown.jsonl`（append-only）按窗口统计。代价是每次构建都要读这个文件；展示记录增长后需要做分段或归档，已记入风险。
- **探索位的选择标准**采用“没有命中关注主题”，再按重要性×新鲜度排序。设计文档说的是“低证据主题或新信息源”，但这两个量在 P2 还没有可靠的统计来源，所以先用更简单的定义。
- **多样性只作用于精选**。其余分区不做重排；设计文档的 MMR 是对整个列表的，P2 先只保护首屏。
- **“不再显示”没有做成按主题独立存储**：屏蔽主题复用了手写屏蔽词，好处是画像面板可统一撤销，代价是它也会影响“抓取结果”页的排序（扣分，而不是过滤）。
- **线上对比（设计文档 7.2）未实现**：评估面板还没有 `feed_v1` 视图。本阶段只有离线回放。

### 12.3 离线回放的定义（`core/feed_eval.py`）
- 每一批次展示的条目，以之后 7 天内的反馈与打开为标签：有 👍 或打开为正例，只有 👎 为负例，其余无标签。
- 对比两种顺序，只在该批次展示过的条目之内排：推荐顺序（展示位置）与基线（按首次出现时间倒序，即抓取结果页的默认顺序）。
- 指标取前 10 条：正例率、👎 率、NDCG@10（二元相关性）。有标签的展示条目少于 20 条时只给数字，并标注“样本不足，仅供参考”。
- 已知偏差：位置偏差会让排在前面的条目更容易被打开，因此标签对推荐顺序有利。这是离线回放的固有问题，在第 7.1 节原文中也提到了。

### 12.4 验证
- `tests/test_feed_p2.py` 17 项通过，覆盖疲劳函数与降权方向、窗口统计、来源上限、主题惩罚、探索位数量与互斥、探索关闭、不再显示与撤销、屏蔽主题后的过滤、回放的正确性（推荐顺序 NDCG 高于基线）、回放的样本不足提示、快速分诊的看板冒烟。
- 测试数据的标题必须互不相似，否则会被正确地聚成同一事件，这次为此修过两次测试数据。
- info_hub 全量 450 通过，剩余 2 个失败是改动前就存在的账本测试。

### 12.5 P3 之前需要的数据

- 真实使用一段时间后，回放结果与线上 👍/👎 率是否一致。

## 13. P3 实施记录（学习权重，默认关闭）

### 13.1 做了什么
- `core/feed_learn.py`：用 `shown.jsonl` 中每次展示的 6 个分量（interest、source_affinity、freshness、importance、persistence_penalty、fatigue_penalty）与第 12.3 节的反馈标签，训练纯 Python 逻辑回归（批量梯度下降 + L2）。
- 训练结果落盘到 `data/feed/learned_weights.json`，包含样本数、权重、留出集的 NDCG@10（学习权重 vs 手工权重）、是否通过验证与原因。
- 生效条件，全部满足才使用学习权重：① 带标签样本 ≥200；② 按展示批次时间切分，较晚 30% 作为留出集，学习排序的 NDCG@10 比手工排序（当时展示的实际顺序）高 ≥0.02；③ 用户在页面上开启。否则回落到手工权重。
- “推荐”页新增“学习权重（P3，默认关闭）”面板：开关、重新训练、验证报告，并显示当前排序方式。
- `build_feed` 增加 `learned_weights` 参数，返回 `scoring: learned | hand`。学习权重只改变排序，不改变分量本身，因此疲劳、多样性、探索位等规则仍然生效。

### 13.2 与设计文档的偏差
- 学习的是线性权重，排序用权重与分量的点积，没有做 sigmoid 映射。排序只关心相对顺序，sigmoid 不改变结果。
- 留出集的“手工基线”用的是展示时的实际位置顺序，而不是重新计算的手工分数。原因是展示位置才是用户真正看到的排序，而且它已经包含了分区与多样性的影响。
- 只用分量训练，没有用标题或来源作为特征，避免过拟合到具体条目。

### 13.3 默认值（`config/settings.yaml` 的 `feed.learning`）
`min_samples: 200`、`min_gain: 0.02`、`holdout_ratio: 0.3`、`days: 60`。

### 13.4 验证
- `tests/test_feed_p3.py` 10 项通过：逻辑回归能学到有信号的特征；样本不足不通过；验证通过后用户未开启不生效；未通过验证的模型永不生效；提升不足时保持手工权重；开关不丢失隐藏来源；`build_feed` 只在生效时改用学习权重。
- 合成数据上（有真实信号，手工顺序随机）学习权重能通过验证，留出集提升明显超过门槛。
- info_hub 全量 460 通过，剩余 2 个为改动前即存在的账本测试。
- **未验证**：真实反馈数据下的学习效果。目前还没有 200 条带标签样本，学习权重不会生效，这是预期行为。

### 13.5 下一步
P4（LLM 增强）是可选项，默认关闭，需要已配置模型。它的前提是确认你是否需要 LLM 的主题标签与摘要。在有真实数据之前，P3 的验证数字仅供参考。

## 14. P4 实施记录（LLM 增强，默认关闭）

### 14.1 做了什么
- `core/feed_llm.py`，复用 info_hub 已有的 `core/llm.py::build_llm`（与对话生成信息源、画像归纳使用同一套模型配置）。
- **摘要**：为前 12 张卡片（精选、多源热点、关注主题）生成 2–4 字主题标签与不超过 40 字的摘要，显示在卡片上。结果按条目缓存到 `data/feed/llm_cache.json`，已有摘要的不再调用。
- **补聚**：对标题二元组 Jaccard 落在 [0.25, 聚合阈值) 之间的近似卡片对，让模型判断是否为同一事件。结论只写入缓存；聚合时只使用缓存里的“同一事件”结论合并簇，页面渲染永不调用模型。
- **每日上限**：默认 40 次，按日期计数（`data/feed/llm_usage.json`），达到上限即停止并如实报告。
- **分批**：每次调用包含 8 个条目或 8 对，减少调用次数。
- **开关与预计**：页面上开启（偏好 `llm_enabled`，默认关闭）后，先显示“本次预计调用 N 次、今日剩余额度”，点击“运行一轮”才会调用模型。
- **隐私**：页面明确提示标题会发送给所配置的模型。

### 14.2 未实施的部分（与设计文档不一致，需要你决定是否做）
- **精选小批量重排**：未做。模型给出的顺序没有可靠的评估手段，贸然接入会让离线回放失去意义。
- **理由润色**：未做。模型改写“一句话理由”会让它不再完全来自可检查的分量，违背“可解释”原则。
- 这两项在设计文档第 6 节的 P4 行中仍然存在，以本节为准。

### 14.3 与设计文档的其他偏差
- 提示词内联在 `core/feed_llm.py` 中，没有放入 `src/mini_agent/prompts/`。原因是 info_hub 是独立外部项目，现有的 `core/profile.py` 也是这样写的；保持一致。
- 摘要与补聚都放在一次按钮运行中完成，没有做后台异步任务。原因是 info_hub 的 LLM 调用沿用 Streamlit 同步按钮的既有模式（画像归纳也是这样），而且每次运行有明确的调用上限，耗时可控。

## 15. 交互修正：反馈不刷新列表（会话快照）

### 15.1 问题
点击 👍 / 👎 / ⏰ 后，整页重新读取数据。已处理的条目被过滤掉，列表整体跳变，用户刚看到的内容突然全部变了。

### 15.2 规则
- 推荐数据是**会话快照**：首次进入页面、切换筛选条件、点击“🔄 刷新推荐”或重新加载页面时才重建。
- 反馈（👍 / 👎 / ⏰）、🚫 隐藏来源、“屏蔽此主题”、恢复来源、开关、展开面板，都只读快照。
- 反馈在原地显示“✔ 已记录：…（点“刷新推荐”后从列表移除）”，按钮高亮当前状态；同一动作不重复记录。
- 快速分诊的“下一条”只推进分诊位置，不重建队列。
- LLM 增强的运行结果、学习权重的训练结果，都在下一次刷新时体现在列表里。

### 15.3 实现要点
- `app.py::_feed_snapshot`：按 (时间范围, 分类, 类型, 显示已处理) 作为快照键；快照与本地标记都保存在 `st.session_state`。
- 去掉了原先基于文件修改时间的 60 秒缓存（`_feed_version` / `_feed_cached`）。每个会话各自持有快照，两个浏览器页签互不影响。
- 反馈按钮只调用后端写入事件，然后普通 `st.rerun()` 重画同一份快照，列表不会变化。
- 没有使用 `st.rerun(scope="fragment")`：Streamlit 1.67 要求在片段重跑中才能使用该参数，而这里不满足；且快照已经保证数据不变，整页重画没有副作用。

### 15.4 取舍
- 同一会话里，别的页签产生的反馈不会自动出现在本页，需要手动刷新，这是预期行为。
- 快照只在本会话内保存，每次新会话都会完整计算一次。数据量大时首次加载会慢一些，去掉 60 秒缓存的代价即在此。

### 15.5 验证
- `tests/test_feed_snapshot.py` 3 项：点击 👍 后列表与标题不变且事件已写入；点击 🚫 后列表不变；无关的交互（切换分诊模式）不重建快照。
- 点击“刷新推荐”后，已处理条目从列表消失。
- info_hub 全量 477 通过，剩余 2 个为改动前即存在的账本测试。

## 18. “换一批”（已实施）

### 18.1 做法
- 推荐页“🔄 刷新推荐”旁新增“🔀 换一批”。点击时，把当前屏幕上展示的全部条目（精选、多源热点、关注主题、探索、其余前 `others_limit` 条，包括每个事件的所有成员报道）记入会话内的排除集合，然后重建快照。
- 排除发生在候选池阶段（聚合之前）：被排除的条目不参与聚类，因此不会以另一条报道的身份重新出现。
- 可以连续点击，每次都会把当前这一批加入排除集合，直到没有可换的内容为止。页面会显示“已换过 N 条条目”。
- 点击“🔄 刷新推荐”清空排除集合，从头开始；切换时间范围、分类、类型或“显示已处理”也会清空（排除集合只对当前筛选条件有效）。

### 18.2 与其它规则的关系
- “换一批”与第 15 节的会话快照不冲突：它是一次明确的快照重建，同样只在点击时发生；反馈、屏蔽等操作仍然只读快照。
- 已处理（👍 / 👎 / ⏰ / 已打开）的条目本来就被隐藏，“换一批”不改变这一点。
- 换一批的展示会照常写入曝光记录（`shown.jsonl`），因此疲劳与回放评估都能看到新的一批。

### 18.3 代码位置
- `core/feed.py::build_feed`：新增 `exclude` 参数，统计项 `stats["excluded"]`。
- `server/api.py::feed_view`：新增 `exclude` 参数（条目 key 列表），透传给 `build_feed`。

## 21. 探索条数可设置，默认调大（已实施）

### 21.1 变化
- 原来探索位按精选条数的比例取（`explore_ratio: 0.15`，10 条精选只有 2 条探索，且精选少于 4 条时不设探索）。
- 现在直接设置探索条数 `explore_size`，默认 **5**，0 即关闭。`explore_ratio` 与 `explore_min_featured` 已移除，不再影响探索条数。
- 看板“⚙ 显示数量设置”面板新增“探索条数”，范围 0–40，保存后刷新生效。优先级同其它显示参数：看板 > settings.yaml > 内置默认。

### 21.2 与其它分区的关系
- 探索仍只从“没有命中关注主题”的事件中选取。
- 新增约束：探索不选“多源热点”资格的事件（报道来源数 ≥ `hot_min_sources`），这类事件留给“多源热点”分区。否则当精选条数较少时，探索会抢走热点条目，导致热点分区为空。
- 实际条数受候选数量限制，不足时少于设定值。

### 21.3 代码位置
- `core/feed.py`：`DEFAULT_CONFIG["explore_size"]`、`_explore_size`、`DISPLAY_LIMITS` 新增 `explore_size`，`_assign_sections` 中探索的筛选条件。
- `config/settings.yaml`：`explore_size: 5`。
- `tests/test_feed_p2.py`：探索条数的直接设置、为 0 时关闭、配置覆盖；`tests/test_feed_display.py`：看板设置探索条数并生效。

### 21.4 验证
- 相关测试通过；info_hub 全量 532 项，剩余 2 个为改动前即存在的账本测试（`test_entrypoints`）。
- **未验证**：真实数据下探索内容的相关性是否合适，默认 5 条是否偏多，需要你在看板上观察后调整。
