## 1. 需求

一次性输入多个文档，排队后自动为每个文档创建项目并生成视频，不需要人逐个点「新建项目 → 运行流水线」。

## 2. 现状（已读代码）

- **单项目流水线已经具备批处理所需的全部能力**：`pipeline/run.py::run_pipeline(pdir, until, gear, max_images, max_minutes, approve, ...)` 可重入（已完成的步骤会跳过）、响应停止、有预算上限，结果写入 `pipeline.json`；G2 全自动要求设置预算。
- **导入是独立步骤**：`importer.py::import_article()` 只解析并登记，不调模型，返回项目 id；`unique_project_dir` 已处理重名。
- **后台任务只有项目级**：`ui/jobs.py` 按项目目录各开一个线程、同一项目同时只允许一个任务；没有「批次」「队列」的概念。线程随 Streamlit 进程存在，进程重启即丢失。
- **停止信号按项目登记**：`cancel.begin/request/bind`，对批次需要在其上再加一层。
- `project.yaml` 声明 `max_concurrency: 1`；文本模型、生图、配音都是有费用、有限速的外部调用。

结论：批量功能 = 在现有流水线之上加一层**持久化的队列 + 单工作线程**，不改动任何阶段的业务逻辑。

## 3. 设计

### 3.1 数据模型（落盘，重启可恢复）——一个持续的队列，而不是一次性批次

位置：`<projects_root>/_queue/`（`_` 开头，`list_projects` 只认含 `project.json` 的目录，不会把它当项目）。

```
queue.json
  params:   # 全队列共用；每篇开始处理时读取最新值，改动只影响之后开始的条目
    gear（默认 G3）, until, max_images, max_minutes（0=不限）, merge_all,
    max_retries（默认 3）, retry_delays（默认 30/60/120 秒）,
    settings / branding   # 与「新建项目」同一套字段，只写与全局默认不同的部分（沿用 R4）
  next_id, items: [
    { id: q0001, title, author,                # 入队时就必须设置好，逐篇各自一份
      source_name, source_path, sha256, chars,
      state: queued|running|done|failed|stopped|waiting|budget_exceeded,
      failures, project_id, error, outputs, enqueued_at, started_at, finished_at }
  ]
sources/    每篇原文的副本（入队时复制，之后不依赖上传组件或原路径）
stop.flag / runner.lock / queue.lock / logs/job.jsonl
```

- **可随时追加**：入队只是往 `queue.json` 里加一条（带文件锁，线程与进程安全）；运行者每处理完一篇都会重新读盘取队首，所以**运行中新加的条目会在同一次运行里被处理**。
- 项目在**轮到该条目时**才创建（懒导入），失败的条目不留下半成品项目；`project_id` 立刻写回条目，重试和续跑都复用同一个项目，由流水线的可重入性跳过已完成步骤。
- 标题、作者在入队时必填标题（作者可留空表示不署名），导入时**以入队时设置的为准**，不再由文章里的标题或「作者：」行覆盖。
- 单条详情不重复存：条目只存摘要，逐步进度读该项目自己的 `pipeline.json`。

### 3.2 执行

- 新模块 `article_to_video/batch/`：`store.py`（队列读写、入队、参数、停止标志、运行者锁）、`runner.py`（逐条取队首 → 导入 → 流水线 → 失败重试 → 下一篇）。预估（`estimate.py`）随第二期的界面一起做。
- **串行，一次一篇**：与 `max_concurrency: 1`、模型限速一致；并行留作以后的显式开关。
- **失败重试**：流水线失败（`state=failed`，含模型报错、校验不通过、配置缺失等异常）时，等待 `retry_delays` 后重试，最多重试 `max_retries`（默认 3）次，即最多 1+3 次尝试；仍失败则标 `failed` 并**继续下一篇**。导入失败（文章为空等）是确定性错误，不重试；`waiting`、`budget_exceeded`、`stopped` 不重试，记录后继续下一篇。重试等待期间每 0.5 秒检查停止。
- **停止**：`stop.flag`（跨进程）+ 对当前项目 `cancel.request`；当前条目标为 `stopped`，其余保持 `queued`，可再次「开始」继续（开始会清除停止标志）。
- **进程重启恢复**：运行者启动时把遗留的 `running` 条目改回 `queued`（不消耗重试次数），已做的步骤由流水线可重入性跳过。
- **同一时间只有一个运行者**：`runner.lock` 带心跳（15 秒一次，60 秒无心跳视为已死），避免两个进程同时抢模型额度。

### 3.3 无人值守：新增 G3 挡位（已确认）

流水线在 G0/G1 会停在人工检查点，批量场景下每篇都会停在第一步。已确认的做法：**新增 G3 完全无人值守档位**。

| 挡位 | 人工检查点 | 预算 |
|---|---|---|
| G0 / G1 | 沿用原有 | 无要求 |
| G2 | 无 | 必须设置上限（不变） |
| **G3（新）** | **无：大纲、口播、分镜自动确认，终审自动通过并导出** | **不要求，也不默认设置上限** |

G3 在单项目驾驶舱、设置页、命令行（`--gear G3`）里同样可选；全局默认挡位仍是 G0。G3 不改变代码校验：V1 大纲校验、口播校验等不通过时流水线记为失败（由队列重试），而不是被跳过。

队列的默认挡位是 G3，但队列**只有用户显式点击「开始」才会运行**，界面（第二期）会在启动处明确提示「G3 无预算上限，可能产生较多费用」。

### 3.4 成本预估（开跑前显示，不调用模型）

按每篇汉字数估算朗读时长（复用 `importer.summarize` 的 `est_full_read_minutes`）、分期数、章数与预估生图张数，汇总后在「开始批量」前展示，并与逐篇/整批预算对照，预估明显超预算时给出警告。预估口径沿用总体规划第 16 节，标注为估算。

### 3.5 界面

新增侧边栏页面「📦 批量生成」，三块：

1. **加入队列**：可以一篇一篇上传，也可以一次多选；**每篇上传时就要设置好标题和作者**（可编辑表格：标题、作者、预估汉字数/时长，疑似重复的标红）；队列开始运行后仍可继续加入。下方共用参数区（沿用新建项目表单的画幅、分辨率、模式、目标时长、视角、水印与署名；挡位与预算；失败策略；离线冒烟）。
2. **队列与监控**：队列表（序号、标题、状态、当前阶段、进度、耗时、成片路径），整批进度条与预算消耗；按钮：开始 / 暂停 / 停止 / 继续 / 重试失败项。用 `@st.fragment(run_every=…)` 局部刷新，不拖慢整页（符合看板侧对 fragment 的同类规范）。每个条目带「在驾驶舱打开」，进入该项目逐步检查或手动继续。
3. **已完成**：已完成与失败条目的结果汇总，可查看报告。

### 3.6 无界面入口（可选，第三期）

`entrypoints/batch_run.py`：用同一个 runner 在命令行/daemon 里运行与恢复队列，便于过夜跑或由 daemon 触发；`project.yaml` 里**不登记 cron**（保持「高成本操作只由人触发」的现有约定），只提供入口。

### 3.7 日志与报告

队列目录自带 `logs/job.jsonl`（`joblog` 以队列目录为 pdir 复用，scope=`queue`），每个条目的细日志仍写在各自项目的日志里。队列每次运行结束写 `report.json` + `report.md`（第三期）：每篇的状态、耗时、生图次数、成片路径、失败原因。

## 4. 不做 / 暂不做

- 不做并行生成（额度与限速风险，留待显式开关）。
- 不改任何阶段业务逻辑，不改流水线的门控与预算规则。
- 不做去重库；只做队列内与「已导入项目」的 sha256 重复提醒（提醒，不拦截）。
- 不做定时/自动触发队列。
- 逐篇单独设置挡位与画幅：第一期只允许逐篇覆盖标题和作者，其余共用（避免参数矩阵失控）。

## 5. 风险

| 风险 | 对策 |
|---|---|
| 一批很多篇，费用失控 | 逐篇预算必填 + 整批预算 + 开跑前预估；超限即停 |
| Streamlit 进程重启丢线程 | 状态全落盘，`running` 恢复为 `stopped`，一键继续；runner 也可由命令行恢复 |
| 单篇失败拖垮整批 | 默认 `continue`；失败原因进报告，可只重试失败项 |
| 磁盘占用（每篇有图、音频、中间视频） | 预估里提示体量；不自动清理，沿用现有整章重置 |
| 重复文档 / 同名项目 | sha256 提醒；`unique_project_dir` 保证目录不冲突 |
| 模型限速导致整批很慢 | 串行 + 沿用各 provider 的重试；监控页显示每条耗时 |

## 8. 已确认的决策（2026-11-19）

1. **挡位**：新增 **G3 完全无人值守**，预算没有上限（见 3.3）。
2. **失败策略**：失败后**重试三次**，仍失败则继续下一篇。
3. **输入方式**：队列式，**一篇一篇输入也可以**，开始之后还能继续往里加；文件夹导入放第三期（可选，默认关闭）。
4. **逐篇设置**：**上传时就要设置好每一篇的标题和作者**，其他参数全队列共享。
5. **预算**：G3 不设上限；G2 仍需逐篇预算。不另做「整批总预算」（队列是持续的，没有「一批」的边界）。
6. **命令行入口**：第三期做，只提供入口，不登记 cron。

### 9.3 与方案的差异和注意事项

- **没有「离线冒烟」选项**：现有离线模式（静音配音、占位生图）没有文本模型，写稿阶段必然失败，放进队列只会反复失败，所以队列参数里不提供；测试通过注入假运行器和假模型覆盖。
- **共用参数在每篇开始时读取**：修改参数不影响正在运行的条目，只影响之后开始的条目（界面里会明确这一点）。
- **跨进程安全是尽力而为**：文件锁与运行者锁足以防止界面与命令行同时跑两份队列、同时入队写乱 `queue.json`，但锁用文件实现，持锁进程被强杀后最多 30 秒（队列文件）/ 60 秒（运行者）恢复。
- **G3 下代码校验失败的重试通常无效**：例如大纲已存在但 V1 校验不通过，重试会得到同样的结果；重试对模型超时、网络波动这类瞬时失败有效。最终以 `failed` 记录原因，可在驾驶舱里打开项目人工处理后「重新排队」。
- **界面尚未提供**：第一期只有代码与测试，队列要到第二期的页面才能用。

### 10.3 偏差与注意事项

- **没有单独的「开始后才能加」限制**：队列是否在运行不影响加入；加入后若队列空闲，需要再点「开始」（有条目排队时「开始」可点）。如果希望「队列运行过之后，新加入的自动开始」，是一个小改动，但会让「必须由用户点击才运行」的保守默认变弱，暂不做。
- **费用预估只给体量**：显示汉字数与全文朗读时长，没有给出金额或生图张数（实际生图数取决于分镜，运行前无法准确估算）。
- **Streamlit 进程重启会停掉界面里启动的运行线程**：条目状态已落盘，重新打开页面点「开始」即可继续（遗留的运行中条目会自动改回排队）。
- 表格里清空标题再点「加入队列」会提示并拒绝；该分支由 `store.enqueue` 的标题必填校验兜底（有测试），界面层的提示文字未单独做界面测试。

## 13. 补充：批量导出成片自动化（2026-11-20）

### 13.1 需求

批量执行时，导出成片也要自动进行，不再停在终审等人工确认。

### 13.2 现状与原因

- 流水线的导出阶段在 G0、G1 下是人工检查点（终审），需要 `approve` 才会导出；G2、G3 下没有人工检查点，会直接导出（见 `pipeline/gates.py`）。
- 批量运行一直以 `approve=False` 调用流水线，因此即使是 G2 或 G3，只要导出阶段遇到终审门控就会停下。
- 批量界面的 G2 说明写的是「终审需要在驾驶舱里人工确认才会导出」，与 `gates.py` 的设计不一致，已更正。

### 13.3 规则与改动

- 新增共用参数 `auto_export`（默认开启，`store.DEFAULT_PARAMS`）。界面「共用参数」中的「自动导出成片（终审自动通过）」复选框。
- `batch/runner.py::default_pipeline_runner` 以 `approve=params["auto_export"]` 调用流水线。开启时终审自动通过并导出；关闭时保持第一、二期的行为，停在终审。
- 挡位仍决定大纲、口播、分镜是否需要人工。G0、G1 的大纲检查点仍会让队列停下，所以无人值守的批量通常使用 G2 或 G3。
- 批量界面的 G2 说明更正为「全自动（含终审与导出）；必须设置预算上限」。
- 驾驶舱的「确认终审」选项不受影响。

### 13.4 验收

- `tests/test_r23_auto_export.py`：默认开启、参数规范化、开启时调用流水线传 `approve=True`、关闭时传 `approve=False`、界面复选框默认开启且保存为关闭。

### 13.5 注意事项

- 自动导出意味着没有人看过成片就会导出。若需要审片，关闭该选项即可，每篇会停在终审等待确认。
