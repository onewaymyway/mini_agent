## 1. 现状

`autopilot.py` 的画像目前只有自由文本 `principles`（一段话描述
决策原则）+ `risk_preference` 枚举（如 `conservative`/`balanced`/
`aggressive`），两者都只是拼进 `_build_decision_context()` 生成的
prompt 里，影响 LLM 的自由发挥，没有任何"这条画像具体在哪一步
起了作用""用户是否认可 Agent 这次的选择"的反馈机制——画像一旦
写好，用户没有办法验证它是否真的按预期在起作用，也没有办法在
不满意时定位到底是哪条原则理解错了。

## 2. 目标与整体设计原则

三步分别解决三个不同的问题，**建议拆成三个独立的实施批次**，
每批完成后可以独立验收、独立决定是否继续下一批：

1. 情境化条件策略——让"倾向"从纯自由文本变成部分可结构化、可
   在 UI 上直接看到"这条原则命中了没有"。
2. Agent Preview——让用户在不消耗真实模拟数据的情况下，直接
   看到画像在标准情境下会怎么选，缩短"改画像 → 靠真实跑模拟才能
   看到效果"的反馈周期。
3. 用户反馈反哺画像——把用户对自动挡某次选择的不满，转成一条
   "画像修正建议"，供用户自己决定要不要采纳。

**贯穿全部三步的透明度红线**（同父文档"范围克制"）：**画像永远
只能由用户自己编辑修改，系统不会基于任何统计/反馈自动改写画像**。
第 2、3 步产出的都是"展示"和"建议"，不是"自动生效的调整"。

## 3. 第一步：情境化条件策略

### 3.1 数据结构

`autopilot` 画像新增可选字段 `conditional_policies`（与自由文本
`principles` 并存，不替代）：

```python
conditional_policies: List[Dict[str, str]] = field(default_factory=list)
# 例：[{"if": "reversible", "then": "倾向选择更有探索性的选项"},
#      {"if": "irreversible", "then": "倾向选择风险更低的选项"}]
```

`if` 的取值目前只支持匹配 4.1 已落地的 `ChoiceOption.
reversibility`/`risk_level` 两个枚举维度（`reversible`/
`hard_to_reverse`/`irreversible`/`low`/`medium`/`high`），**不做
自定义条件表达式解析**（不支持"如果现金低于 1000"这种自由条件，
那需要一个完整的条件求值引擎，成本和现有\"自由文本拼 prompt\"
比起来收益不成比例）——如果 `if` 不是这几个已知枚举值之一，`
app.py` 编辑界面直接用下拉框限制输入，从源头避免出现无法识别的
条件。

### 3.2 使用方式

`_build_decision_context()` 在拼 prompt 时，把 `conditional_
policies` 转成自然语言追加在 `principles` 之后：

```
此外，这个 Agent 有以下情境化倾向：当某个候选选项的可逆性为
"可逆"时，倾向选择更有探索性的那个；当某个候选选项的风险等级
为"高"时，倾向选择风险更低的选项。
```

**不做**"代码层面强制过滤/加权某个选项"——同现有 `principles`
的一贯取舍，情境化策略仍然只是喂给 LLM 的额外上下文，最终选择
权在 LLM（这也是为什么第二步 Agent Preview 有必要存在：条件策略
到底有没有实际影响 LLM 的选择，只有跑一次才知道，不能假设"写了
条件就一定生效"）。

### 3.3 展示："这条原则命中了没有"

`SimState`（或推进结果）里 `chosen_reason` 字段已经存在（现有
机制，LLM 给出选择理由）。本步骤**不新增**结构化的"命中了哪条
policy"字段（要求 LLM 精确指出命中了哪条结构化规则、并保证和
实际决策一致，容易出现"LLM 声称命中了但实际没有"的偏差，属于
不该由本方案兜底的可靠性问题）。改为在 `app.py` 自动挡运行记录
展示区，把这一步的 `chosen_reason` 和 `conditional_policies` 并排
展示，**由用户自己判断**这次选择是否符合预期的条件策略——保持
"系统只展示、用户自己判断"的一贯克制。

## 4. 第二步：Agent Preview

### 4.1 触发方式

画像编辑页新增"预览这个画像的决策倾向"按钮。点击后，用**几个
内置的通用测试情境**（与具体模拟实例、具体模板无关的独立小
情境，比如"你突然失业，有一笔够撑 3 个月的存款，面前有两个选项：
A. 立刻找一份不太满意但能马上上岗的工作；B. 花 1 个月准备再找
更合适的工作"）分别单独调用一次 LLM，让画像对这个测试情境做出
选择，**不写入任何 `data/<sim_id>/` 下的正式模拟数据**——这是
一次独立的、副作用完全隔离的 LLM 调用。

### 4.2 内置测试情境的设计

固定维护 3~5 个通用测试情境（存成 `world_simulator/agent_
preview_scenarios.py` 里的常量列表，不做成用户可编辑的配置——
测试情境需要覆盖"可逆 vs 不可逆""高风险 vs 低风险"等有代表性的
维度组合，让画像编辑者随便乱改测试情境反而会削弱这个功能的
参照价值），每个情境包含一段描述 + 2~3 个预设候选选项（选项本身
带 4.1 的 `risk_level`/`reversibility` 字段，这样情境化策略
（第一步）才有实际的匹配对象可以在 Preview 里验证）。

### 4.3 输出与展示

每个测试情境的调用结果展示为：

```
测试情境："你突然失业……"
Agent 选择了：B（花时间找更合适的工作）
理由：现金还能撑 3 个月，属于可逆的等待成本，值得为了长期匹配度
      多花一点时间。
引用的原则：conditional_policies[0]（可逆时倾向更有耐心的选择）
```

"引用的原则"这一行由 LLM 在同一次调用里一并给出（prompt 里
明确列出 `principles`/`conditional_policies` 各自的编号，要求
LLM 声明"如果有依据某条原则做选择，说明是哪条；没有依据任何
已声明原则，就如实说明是综合判断"）——**允许 LLM 说"没有明确
依据某条原则"**，不强迫每次都归因到一条规则上，避免为了凑一个
"引用了哪条"而编造。

用户可以对每条结果标"符合预期"/"不符合预期"（轻量按钮，不需要
写理由），这个标注**本步骤不做任何存储和聚合**——是否要把这类
标注长期记录下来，取决于第三步是否要复用（见下）。

### 4.4 成本与频率控制

每次 Preview 需要 3~5 次独立 LLM 调用，成本不可忽略。`app.py`
在按钮旁提示预计的调用次数，不做自动触发（比如不在画像每次
保存时自动跑一次 Preview），完全由用户手动点击触发。

## 5. 第三步：用户反馈反哺画像

### 5.1 复用现有入口

自动挡运行已有 `review_mode`（人工复核）机制，用户可以在复核时
标记某次选择"不符合预期"并写理由。本步骤**不新增新的反馈入口**，
只是让这个已有的"不符合预期 + 理由"反馈多做一件事：追加写入一条
"画像修正建议候选"记录。

### 5.2 数据结构：画像修正建议

```python
# 新增，可能落盘在 data/<sim_id>/policy_feedback.jsonl，
# 或画像本身所在位置（画像目前的存储位置需要先确认，如果画像是
# 跨模拟复用的全局配置，这条记录也应该是全局的，不挂在单个 sim_id
# 下——这一点在实施前需要先查清楚 autopilot.py 画像当前的存储
# 位置和作用域，本方案暂不假设）
@dataclass
class PolicyFeedbackNote:
    id: str
    sim_id: str
    step: int
    user_reason: str       # 用户当时写的"不符合预期"理由（原文）
    created_at: str
    acknowledged: bool = False  # 用户是否已经在画像编辑页看过这条
```

### 5.3 展示："最近 N 次反馈"提示

画像编辑页新增一个折叠区（同 4.26"因果线建议"折叠区"生成建议、
用户决定"的既有模式），展示最近若干条**未确认**的
`PolicyFeedbackNote`，如果同一大致方向的反馈出现多次（比如连续
3 次用户都觉得"Agent 太保守了"），额外给一句归纳提示——**这句
归纳提示由简单的关键词/次数统计生成，不用 LLM 做语义聚类**
（语义聚类的准确性无法保证，用简单统计更可靠、更可解释）：

```
最近 3 次人工复核里，你都提到 Agent 的选择"太保守"。要不要调整
风险偏好，或者在情境化策略里补一条"倾向更积极"的规则？
```

用户点击"已阅"后 `acknowledged` 置真，不再提示（但记录本身
保留，不删除）。**系统不自动修改 `risk_preference` 或
`conditional_policies` 的任何取值**——调整与否、怎么调整，
完全由用户自己在同一个编辑页手动操作。

### 5.4 触发提示的最小规则

为了避免"归纳提示"本身变成又一个需要维护的复杂子系统，第一版
用最简单的规则：统计最近 N 条未确认反馈里，`user_reason` 命中
预定义的几个关键词分组（"太保守/太谨慎/太犹豫" vs "太冒险/太
激进/不计后果"），任一分组达到阈值（比如 3 次）才生成提示；
不做任何 NLP 语义分析。命中不了预定义关键词的反馈，仍然原样
列在折叠区里供用户自己看，只是不会触发归纳提示。

## 6. 范围克制（重申，与父文档一致）

- 不做参考文档"Current Self / Ideal Self / Simulation Agent 三个
  自己"的完整建模——继续只维护一份"自动挡画像"的概念。
- 不做"画像自动学习"（用统计模型从历史选择拟合权重）——不管
  第三步的反馈有多少条，画像的实际取值永远只能由用户手动改。
- `conditional_policies` 的 `if` 条件不支持自定义表达式，只支持
  4.1 已有的枚举维度。
- Agent Preview 的测试情境固定内置，不支持用户自定义。

## 7. 分批实施与验收标准

**第一批：情境化条件策略**
- 涉及文件：`autopilot.py`（画像结构 + prompt 拼接）、`app.py`
  （编辑界面新增 `if`/`then` 结构化输入，下拉框限制 `if` 取值）。
- 验收：单元测试覆盖"有/无 `conditional_policies` 时 prompt 拼接
  是否正确""未知 `if` 取值时的处理"（编辑界面已经用下拉框限制，
  但反序列化旧数据/直接改文件的情况仍要有兜底，建议同 `risk_
  level` 一样归一化到最接近的已知值或原样保留由展示层判断）。

**第二批：Agent Preview**（依赖第一批，用来验证情境化策略是否
真的影响了选择）
- 涉及文件：新增 `world_simulator/agent_preview_scenarios.py`
  （内置测试情境常量）、新增 `world_simulator/agent_preview.py`
  （独立 LLM 调用逻辑，参照 `hypothesis.run_hypothesis_worlds()`
  "调用即弃、不写入正式数据"的隔离模式）、可能新增 `workflows/
  agent_preview.yaml`（`type: agent`，同 4.6 retrospective 的
  模式，不挂载具体模板 skill）、`app.py`（Preview 触发按钮 +
  结果展示）。
- 验收：Mock LLM 调用的单元测试验证"结果解析、成本提示展示是否
  正确"；**人工验证**：真实运行几次 Preview，检查"引用的原则"
  是否合理、测试情境的选项设计是否真的能体现风险/可逆性维度的
  差异（如果 LLM 在所有测试情境里选择都高度相似，说明测试情境
  区分度不够，需要调整情境设计而不是急于推进第三批）。

**第三批：用户反馈反哺画像**（依赖 `review_mode` 已有机制，
与第一、二批相对独立，可以并行或稍晚排期）
- 涉及文件：`state_model.py`（`PolicyFeedbackNote`，需要先确认
  画像/反馈的存储作用域，见 5.2 备注）、`autopilot.py`（`review_
  mode` 复核流程里追加写入反馈记录）、`app.py`（画像编辑页新增
  反馈折叠区）。
- 验收：单元测试覆盖"关键词分组统计触发提示的阈值逻辑"
  "acknowledged 状态的存取"；**不需要**人工验证 LLM 效果（这一批
  不涉及新的 LLM 调用，纯粹是记录和统计展示）。

## 8. 风险提示

- 本节是父文档标注的"改动面最大"的一节，实施前务必确认画像
  （`autopilot.py` 的 principles/risk_preference）当前的存储
  位置和作用域（是挂在单个 `sim_id` 下，还是跨模拟的全局配置）
  ——这直接决定第三批 `PolicyFeedbackNote` 应该挂在哪，本方案
  编写时未去核实这一点，实施前需要先读一遍 `autopilot.py` 现有
  代码确认。
- Agent Preview 的核心价值依赖"测试情境设计得有没有代表性"，
  这类似 4.3 belief_fields 依赖"LLM 能否稳定输出有意义的认知
  偏差"——如果第二批人工验证发现 LLM 选择不受情境化策略影响，
  应该先检讨 prompt 措辞或情境设计，而不是归咎于"这个功能没
  价值"就直接放弃；但如果反复调整仍然看不到区分度，也应该按
  项目一贯的节制原则及时止损，不无限投入。
