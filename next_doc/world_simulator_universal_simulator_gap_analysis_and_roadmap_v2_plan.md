## 1. 背景：完成阶段二十~二十六之后，相对理想目标还差什么

阶段二十~二十六已经把参考文档里"让单次模拟更靠谱"和"因果线成为
一等公民"这两大块基本落地：跨模拟因果知识库、Hypothesis Engine
自动识别关键不确定性、多尺度因果线（作为展示/归属维度）、Model
Regime Detection 允许结构在线修正、Reality Loop 完整反馈闭环、
因果线总览 UI、创建即有的未来因果树。

但逐条重新对照参考文档的核心论点（尤其是第七~十六节"多尺度耦合"
"因果线关系""Influence Field""Agent-World Co-evolution""反事实
模拟""因果贡献拆解"这几节），发现还有十个方向是"参考文档反复
强调、现状明确没有或只做了表层"的缺口：

1. **多尺度因果线是"标注"不是"并行运行"**——所有线仍然共享同一个
   全局 `step` 序列和 `time_granularity`，没有真正按各自节奏独立
   推进。
2. **因果线之间的耦合没有结构化建模**——`causal_links` 只是自由
   文本 + `line_id` 归属标签，不存在可查询回放的传播路径，无法
   区分单向/双向/间接/反馈循环四种关系。
3. **Influence Field（影响场）完全缺失**——没有任何"主体能影响
   谁、影响多大、传播路径、时间延迟"的显式建模。
4. **世界的"独立演化"很弱，Observer View 没有真正落地**——唯一
   体现"世界自己在动"的机制（背景角色线性外推）有已知的"冻结"
   缺陷，且本质仍由用户每次行动触发的一次 LLM 调用驱动。
5. **反事实模拟没有向导化的系统性矩阵**——Hypothesis Engine 能做
   单变量扰动分叉，但"控制变量法"式的正交反事实世界矩阵仍需用户
   手动逐个构造。
6. **缺少"最终归因/贡献拆解"报告**——只有 `key_drivers` 短语标签
   和统计摘要，没有面向"这个结果到底是谁造成的"的结构化归因视图。
7. **"顺势/逆势/改变趋势"判断未实现**——系统不会告诉用户这次结果
   是在利用趋势、对抗趋势，还是本身成为了趋势的一部分。
8. **关系（Relationship）作为一等公民缺失**——多主体之间的关系
   仍只能靠叙事自由文本表达，没有独立的关系图结构。
9. **开放世界闭环没有打通**——`structural_change` 采纳新实体/
   新机制后，不会自动为其生成对应因果线和未来树，闭环只连通了
   前半段。
10. **工程债务限制了继续往上堆功能的空间**——`engine.py` 已经
    52K、单体承担多个"引擎"职责；历史/知识库文件是整体重写落盘，
    不支持并发写入。

本文档把这十个方向拆成可评估、可选择性实施的具体改动，不强制
"六个方向必须全部做"，第 4 节逐条给出建议时机与理由。

## 2. 目标

不是把十个方向一次性全部实现，而是：

- 对每个方向给出"要做到什么程度算成立"的最小范围定义，避免像
  参考文档设想的完整架构那样无限扩张；
- 明确标注每个方向与已有数据结构（`causal_lines`/`causal_links`/
  `knowledge_base`/`branch_manager`）的复用关系，优先"接线"而不是
  推倒重来；
- 对暂不建议实施的方向，写清楚"为什么现在不做"和"什么信号出现时
  应该重新评估"，而不是简单地忽略。

## 3. 十个方向的依赖关系

```text
方向10（engine.py 拆分/存储追加写）──────────────┐  工程债务，建议优先
                                                    ↓
方向2（因果线耦合结构化）──→ 方向1（多尺度真正并行）
        │                              │
        ↓                              ↓
方向6（归因/贡献拆解）          方向9（开放世界闭环收尾）
        │
        ↓
方向5（反事实矩阵向导）

方向3（Influence Field）──→ 方向8（Relationship 图结构）──→ 方向4（Observer View / 世界独立演化）
方向7（顺势/逆势/改变趋势判断）：依赖方向6产出的归因结果，排在其后
```

- **方向10（工程债务）** 不依赖任何新概念，且后面所有方向都会继续
  往 `engine.py` 和落盘文件里加逻辑，建议在启动新方向前先做，降低
  后续改动的风险。
- **方向2（因果线耦合结构化）** 是方向1（多尺度并行）、方向6（归因
  拆解）、方向9（开放世界闭环）的数据基础，必须先把"因果关系"从
  自由文本升级为可查询结构，后面几条才有地方接。
- **方向3（Influence Field）** 和 **方向8（Relationship 图结构）**
  是同一类"主体间关系建模"的扩展，方向4（世界独立演化 / Observer
  View）依赖这两者才能让"世界自己按因果规律运行"有实际的传播基础，
  而不是继续靠线性外推这种简化规则。
- **方向5（反事实矩阵）** 依赖方向2提供的结构化因果关系，否则"控制
  变量法"式的正交世界只能靠用户自己猜哪些变量该固定。
- **方向7（顺势/逆势判断）** 依赖方向6的归因结果作为判断依据。

## 4. 改进方案

### 4.18（工程债务，**已全部完成**：存储层追加写见 `PROJECT.md` 阶段二十八；`engine.py` 拆分见阶段三十）`engine.py` 拆分 + 存储层追加写

**现状问题**：`engine.py` 52K，同时承担状态推进、资源校验、因果线
注册、结构变化解析、背景角色外推等多个职责；`store.py::
SimStore.append_state` 与 `knowledge_base.py::_save_all()` 都是
整体重写落盘，数据量大后有并发写入风险（PROJECT.md"已知限制"里
反复提到）。

**方案**：
- 按职责把 `engine.py` 拆成 `engine/` 包（如 `advance.py`/
  `resource_guard.py`/`structural_change.py`/`causal_lines.py`），
  对外接口（`advance()`/`materialize_simulation()`/
  `list_simulations()` 等）保持不变，纯内部重组，不改变任何
  持久化格式，回归测试（现有 169+ 个用例）作为唯一验收标准。
- `state_history.jsonl`/`causal_knowledge.jsonl` 改成真正的追加
  写（append-only，配合定期 compaction 或按 sim_id 分文件），
  解决"整体重写"的并发风险。

**范围克制**：不引入数据库，不改变任何字段的语义，纯粹是"同样的
行为，换一种代码组织/落盘方式"。这一节本身价值不取决于用户反馈，
属于随时可以做的维护性工作，建议排在其它方向之前。

**涉及文件**：`world_simulator/engine.py`（拆分）、`store.py`、
`knowledge_base.py`、全部现有测试（需要保持通过）。

**实施记录（阶段二十八）**：只落地了"存储层追加写"里`state_
history.jsonl` 这一半——`append_state()` 改成真正的追加写，验收
标准是"多次追加不再触发 `load_history()` 读回整份历史"，已有
专门测试覆盖。`causal_knowledge.jsonl` 评估后**刻意保留**整体
重写：`record_causal_links()`/`record_contradiction()` 会原地
更新已有条目（合并计数），和 `state_history.jsonl`"只增不改"的
语义不同，套用纯追加写反而需要额外 compaction 才能生效，见
`knowledge_base.py::_save_all()` docstring。`engine.py` 拆分
本阶段**未实施**——52K 单体文件的一次性拆分回归风险明显高于
存储层改动，且缺少清晰的"拆到什么粒度算完成"验收标准，留给后续
单独评估/排期。

**实施记录（阶段三十，`engine.py` 拆分收尾）**：把 1143 行的
`engine.py` 按职责拆成 `world_simulator/engine/` 包（10 个子
模块：`errors`/`ids`/`knowledge`/`resource_guard`/
`background_entities`/`materialize`/`structural_change`/
`causal_lines`/`advance`/`management`），验收标准延续原方案——
对外接口（`advance()`/`materialize_simulation()`/
`list_simulations()` 等）保持不变、不改变任何持久化格式、
现有测试全部通过（拆分前 198 个用例，拆分后仍是 198 个，一个
用例都没有改动）。子模块内部函数实现逐行照搬，只是换了文件
位置；跨子模块的调用（比如 `advance.py` 需要 `resource_guard.py`
的校验函数）改成显式 `import`。`state_model.py`"是否需要同步
精简"（原方案 4.18 节末尾提到的评估项）本阶段未纳入范围，见
`PROJECT.md` 阶段三十"已知限制"。

### 4.19（P1，**已完成，见 `PROJECT.md` 阶段二十七**）因果线耦合的结构化：从自由文本升级为可查询关系

**现状**：`causal_links` 是 `{driver, affected_fields, effect,
line_id}` 的自由文本列表，没有区分参考文档第九节的四种关系
（单向/双向/间接/反馈循环），系统无法回答"哪条因果线真正决定了
结果"。

**方案**：
- `causal_links` 每项新增可选字段 `relation_type`
  （`one_way`/`two_way`/`indirect`/`feedback_loop`，默认
  `one_way`，不声明按旧行为处理，向后兼容）和 `source_line_id`
  （与现有 `line_id` 分别表示"影响从哪条线出发"和"影响到哪条线"，
  `line_id` 语义不变，`source_line_id` 留空表示同线内部关系）。
- 新增 `world_simulator/causal_graph.py`：纯函数
  `build_causal_graph(history)`，从历史 `causal_links` 里聚合出
  一个"线到线"的邻接关系视图（谁影响谁、影响次数、关系类型分布），
  不做图数据库，只是一次性计算的展示用结构。
- `app.py` 因果线总览新增"跨线影响关系"小节，展示
  `build_causal_graph()` 的聚合结果（比如"技术线 → 产业线：3 次
  单向影响，1 次反馈循环"）。

**范围克制**：不引入图数据库/正式的 `CausalCoupling` 持久化对象，
关系仍然靠 LLM 在 `causal_links` 里如实标注 `relation_type`，
`causal_graph.py` 只做"读取历史、聚合展示"，不做任何传播模拟或
强制校验。

**涉及文件**：`state_model.py`（`causal_links` 字段扩展）、新增
`causal_graph.py`、`workflows/advance_step.yaml`、三个模板
`SKILL.md`、`app.py`。

### 4.20（P1，依赖 4.19，**已完成，见 `PROJECT.md` 阶段三十一**）多尺度因果线的真正并行推进

**现状**：所有因果线共享同一个全局 `step` 和 `time_granularity`，
"多尺度"目前只是展示层的分组标签。

**方案（最小可行版本）**：
- 不做"每条线独立异步跑"的完整实现（那需要重构整个推进循环，
  风险极高），而是先做"跳步"这一种最小机制：`causal_lines` 每条
  线新增可选 `advance_every_n_steps`（默认 1，即每步都推进）。
- `engine.advance()` 在构造 `advance_step` prompt 时，把"这一步
  哪些线预期会有动静、哪些线大概率维持不变"的提示信息
  （`_lines_due_this_step_hint`）喂给 LLM，供其参考，但**不强制**
  ——LLM 仍然可以在任何一步更新任何线，这是提示而不是约束，
  避免"错误估计节奏导致该更新的线被拦住"。
- 时间线 UI 在"因果线总览"里，对推进节奏慢的线（比如
  `advance_every_n_steps=5`）用更稀疏的视觉密度展示，避免长时间
  没有变化的线看起来像"卡住了"。

**范围克制**：这不是参考文档设想的"技术线按年、个人线按周各自
独立仿真循环"的完整多尺度引擎（那需要每条线有自己的时间轴和
独立的 LLM 调用，成本和复杂度都高一个数量级），只是"给 LLM 一个
节奏提示 + 展示层按节奏排布"的轻量版本。**建议时机**：先观察
真实使用中"因果线总览"页面里各线是否真的表现出明显不同的变化
频率，如果历史数据显示所有线几乎每步都在动（不符合现实中"经济
周期比个人行为慢得多"的预期），再考虑做本节；如果本来就符合
预期，本节可能没有必要。

**涉及文件**：`state_model.py`（`causal_lines[i].
advance_every_n_steps`）、`spec_generator.py`（hint 生成）、
`app.py`（因果线总览展示密度）。

**实施记录（阶段三十一）**：按上面的最小可行版本原样落地，未做
方案外的扩展。`spec_generator._lines_due_this_step_hint()` +
`resolve_hints(current_step=...)` + `engine.advance()` 传
`current.step + 1`；`app.py` 因果线总览标题追加"约每 N 步一动"。
测试见 `tests/test_spec_and_engine.py`。

### 4.21（P1，依赖 4.19，**已完成，见 `PROJECT.md` 阶段二十九**）归因/贡献拆解报告

**现状**：只有 `key_drivers` 短语标签和 `aggregate_field_stats()`
统计摘要，没有面向"这个结果到底是谁造成的"的结构化归因视图。

**方案**：
- 新增 `world_simulator/attribution.py`：`summarize_
  contributions(history, target_field)` 纯函数，从历史
  `causal_links`（依赖 4.19 的 `relation_type`/`source_line_id`）
  里筛出最终影响 `target_field` 的因果链条，按来源线（技术/经济/
  社会/个人……）分组统计"提及次数 + 涉及的具体因果关系"，输出
  一份"贡献来源清单"（不是虚假的精确百分比，延续项目"不做伪精确"
  的一贯风格，用"高/中/低相关"三档代替具体数字）。
- 如果该字段被 `uncertain_fields` 标注过低置信度，归因清单里
  会附带提示"这个结果本身包含较大不确定性，归因仅供参考"。
- `app.py` 在实例详情页新增"这个结果是怎么来的"折叠区（选择一个
  `objectives` 里声明过的目标字段，展示归因清单）。

**范围克制**：不做敏感性分析的自动量化打分（比如回归系数），
不构造反事实来验证归因（那是方向 4.22 的事）；完全基于已经落盘
的 `causal_links` 做统计聚合，不发起新的 LLM 调用。**建议时机**：
依赖 4.19 先落地，因为没有 `relation_type`/结构化关系，归因清单
的信息量会很有限（等同于把 `key_drivers` 重新排个版）。

**涉及文件**：新增 `attribution.py`、`app.py`；测试参照
`test_analysis.py` 的风格新增 `test_attribution.py`。

**实施记录（阶段二十九）**：按方案原样落地——`summarize_
contributions()` 只做统计聚合、不发起新的 LLM 调用，"相关程度"
按出现次数占比分高/中/低三档；`app.py` 新增的"这个结果是怎么来的"
折叠区只对 `objectives` 里声明过 `field` 的目标开放，没有声明时
展示引导文案而不是强猜字段。详见 `PROJECT.md` 阶段二十九。

### 4.22（P2，依赖 4.19，**已完成，见 `PROJECT.md` 阶段三十一**）反事实矩阵向导

**现状**：Hypothesis Engine（阶段二十一）支持"单变量扰动、
自动分叉、判断稳健性"，但要做参考文档第十六节"保持个人选择改变
经济环境 / 保持经济环境改变个人选择"这种正交矩阵比较，用户需要
手动逐个构造对比实验。

**方案**：
- `hypothesis.py` 新增 `build_counterfactual_matrix(fields,
  variants_per_field)`：给定若干个字段及每个字段的候选取值，
  生成"每次只变一个字段、其余保持基线"的正交世界列表（不是
  全排列组合，避免世界数量爆炸），复用已有的
  `run_comparison_experiment()` 执行。
- 结果展示复用现有"对比实验"页面的表格，新增"按变化的字段分组"
  视图，直接呼应参考文档"世界 A/B/C/D"的表达方式。

**范围克制**：只做"单变量控制"矩阵（一次只变一个字段），不做
多变量交叉的完整析因设计（组合数量会指数级增长，且当前 LLM
推进成本下不现实）。**建议时机**：现有 Hypothesis Engine
（阶段二十一）已经能满足"单变量扰动"的核心诉求，本节只是把
"用户手动构造几次"包装成"一次声明多个字段、批量生成"的向导化
体验，投入产出比中等，等用户在真实使用中确实需要频繁做多字段
对比、且抱怨"每次都要手动开好几次实验"时再排期。

**涉及文件**：`hypothesis.py`、`app.py`（对比实验页面）。

**实施记录（阶段三十一）**：按用户明确要求提前实施（不再等待
"用户抱怨手动开实验麻烦"这类反馈信号），实现与上面的方案一致：
`hypothesis.build_counterfactual_matrix()` 复用
`run_comparison_experiment()`，单变量控制，`app.py`"对比实验"
页面新增按字段分组的结果展示。测试见 `tests/test_hypothesis.py`。

### 4.23（P2，依赖 4.19，**已完成，见 `PROJECT.md` 阶段三十一**）"顺势/逆势/改变趋势"判断

**方案**：基于 4.21 的归因清单，做一个轻量分类规则：如果目标
字段的主要贡献来源集中在"外部因果线"（技术/经济/社会等非用户
所在实体的线），判定为"顺势/逆势"（再细分要看外部趋势方向和
结果方向是否一致）；如果贡献链条里出现"个人/所在实体的因果线
→ 反向影响了某条外部线"（即 `causal_links` 里存在 `line_id` 从
个人线指向宏观线的记录），判定为"正在改变趋势"。

**范围克制**：这是一个基于既有数据的启发式分类，不追求精确，
每次判断附带"依据是哪几条因果链"，让用户自己判断认不认同。
**建议时机**：排在 4.21 之后，且本身是这十个方向里价值相对
不确定的一个（文档强调这个诊断能力，但项目目前没有任何真实
使用反馈说明用户是否真的需要这个标签）——按项目一贯的节制
风格，**建议先不做**，等 4.21 归因报告上线并收集到"用户确实想
知道这是不是自己努力的结果"这类反馈后再评估。

**实施记录（阶段三十一）**：按用户明确要求提前实施（未等待
真实反馈信号）。`trend.classify_trend()` 的实现相比原方案有一处
调整：**没有**把"顺势"和"逆势"拆成两个判定，因为 `causal_links`
不记录数值变化方向，系统客观上无法判断"结果是顺应了外部趋势还是
与之相反"，强行拆分会是伪精确；改为给出一个更谨慎的 `with_trend`
判断 + 具体因果链明细，把"到底是顺势还是逆势"的最终判断留给用户
自己看着因果链内容判断。"改变趋势"信号优先于"顺势/逆势"信号。
需要用户手动指定"哪条因果线代表自己"（系统无法自动识别）。
测试见 `tests/test_trend.py`。这个方向本身仍然是价值相对不确定
的一个，上面这段"建议先不做"的分析依然成立，只是按要求提前做了
一个范围克制的启发式版本。

### 4.24（P3，暂不建议，**已完成最小起步版，见 `PROJECT.md` 阶段三十一**）Influence Field / Relationship 图结构

**方案设想**：为每个主体声明"影响半径"（能影响哪些对象、强度、
时间延迟、传播路径、可逆性），并把多主体之间的关系从自由文本
升级为显式的 `Relationship` 图（谁与谁、什么类型、强度）。

**为什么暂不建议现在做**：这是参考文档里改动范围最大的两个方向
之一（另一个是完整的多尺度独立引擎），需要新增持久化结构、
影响推进逻辑（谁的行动能改变谁），风险和收益都不确定。项目
目前唯一涉及多主体的场景是 `negotiation-template`（阶段十七，
主体数量最多两三个），远没到"需要显式影响半径/关系图才能撑住"
的复杂度——阶段十七的经验教训（在触发条件未满足时提前实施，
事后证明"字段粒度设计"风险偏高）也提示这类方向应该等真实场景
出现再做。

**触发条件**：出现真实的"多主体数量明显增多（超过个位数）、
且用户反馈现有 `entities`/`shared_vars` 结构不足以表达主体间
影响关系"的具体场景时，再重新评估。

**实施记录（阶段三十一）**：按用户明确要求实施了一个**范围
克制的最小起步版**——`world_simulator/relationship.py` 提供
`settings.relationships` 结构化关系列表（`from`/`to`/`kind`/
`strength`/`note`），仅仅是把关系从叙事自由文本升级为可独立
查看的列表，**没有**实现影响半径、传播路径、时间延迟、自动
推进逻辑这些完整 Influence Field 架构的核心机制，
`engine.advance()` 完全不读取也不消费这个字段。上面"为什么暂不
建议现在做"的分析和"触发条件"依然成立——如果真的出现触发条件
里描述的场景，仍然需要在这个最小版本基础上做更大范围的架构
改动。测试见 `tests/test_relationship.py`。

### 4.25（P3，暂不建议，**已完成最小起步版，见 `PROJECT.md` 阶段三十一**）世界独立演化 / Observer View

**方案设想**：让世界脱离用户交互也能自主推进（比如后台按固定
节奏跑一次"世界只演化、不等用户行动"的推进），并在 UI 上区分
"我的视角"和"世界发生了什么"两个视图。

**为什么暂不建议现在做**：`batch_advance_daily`（阶段五）已经
提供了"定时批量推进"的调度能力，某种程度上已经是"世界不完全
依赖用户手动点击"的雏形；`hierarchical_agent_mode`（阶段十九）
的背景角色外推也是"世界自己在动"的一种简化实现。要做到文档
设想的真正"Observer View"（世界按自己因果规律独立演化，用户
只是众多主体之一），需要重新设计推进循环本身（不再是"用户请求
一步、LLM 算一步"的同步模型），改动量极大，且阶段十九已经暴露
出"用简单规则替代真实推理"的局限（背景角色数值会冻结）。

**触发条件**：用户明确表达"想看到世界在我不做任何操作时也在
演化"这类具体诉求时，先从"给 `batch_advance_daily` 增加一个
只推进背景/宏观因果线、不要求用户决策的模式"这种更小的改动
开始验证，而不是直接上完整的双视角架构。

**实施记录（阶段三十一）**：按用户明确要求实施了触发条件里
建议的那个"更小的改动"——`settings.observer_mode`（默认
`False`），开启后 `autopilot._build_decision_context()`
追加一段提示，要求这一步优先让背景/宏观因果线自然演化、尽量
不产生需要立刻打断的"人生重大决策"新分支。**仍然是**
`batch_advance_daily`/自动挡代理发起的同步推进，**没有**独立的
后台推进循环，不是真正的双视角架构，只是提示（不强制，不改变
推进循环本身的同步模型）。上面"为什么暂不建议现在做"里提到的
"需要重新设计推进循环本身"这个更大的改动仍然没有做，如果后续
确实需要"世界按自己节奏持续演化、不依赖任何调度触发"，还是要
回到这里重新评估。测试见 `tests/test_autopilot.py`。

### 4.26（P2，依赖 4.19，**已完成，见 `PROJECT.md` 阶段二十九**）开放世界闭环收尾：新结构自动关联因果线

**现状**：`structural_change` 采纳新实体/新机制后（阶段二十三），
不会自动为其生成对应的因果线和未来树，PROJECT.md 已明确记录这个
已知限制。

**方案**：`apply_structural_change()` 被调用（用户点击"采纳"）
时，如果 `kind == "new_mechanism"` 或 `"regime_shift"`，顺带调用
`causal_tree.py` 里已有的 `build_default_future_tree()` 为这个
新结构生成一条默认因果线草稿（不自动登记进
`manifest.settings.causal_lines`，而是作为"建议"展示给用户，
由用户在因果线总览页面里选择"接受这条建议线"，复用现有的手动
覆盖入口）。`kind == "new_entity"` 场景本身可能不需要新增因果线
（新实体更多体现在 `vars.entities` 里），不强制生成。

**范围克制**：只补"采纳新机制后给一条默认线草稿建议"这一步，
不做"自动判断新结构应该长成什么因果关系"（那仍然是 LLM 在后续
`advance_step` 里自由发挥的范围）。

**涉及文件**：`engine.py::apply_structural_change()`、
`causal_tree.py`、`app.py`。

**实施记录（阶段二十九）**：按方案原样落地，新增
`settings.suggested_causal_lines`（建议列表，独立于正式的
`causal_lines`）承载"采纳新机制/regime_shift 后"的默认因果线草稿；
新增 `accept_suggested_causal_line()`/`reject_suggested_causal_
line()` 两个函数分别完成"接受→迁移进 causal_lines"和"忽略→直接
清除"，`app.py` 因果线总览页面新增对应的"💡 因果线建议"折叠区。
详见 `PROJECT.md` 阶段二十九。

## 6. 风险提示

- 十个方向里，4.24/4.25 是改动范围最大、也是参考文档里"最理想化"
  的两块——如果不顾真实反馈直接上马，重演阶段十七"字段粒度设计
  风险偏高"的教训的概率很大，本文档明确建议暂不做。
- 4.19（因果线耦合结构化）是后续多个方向的地基，一旦
  `relation_type` 字段的语义设计不合理，会连带影响 4.20/4.21/
  4.22/4.23 的实现质量，建议这一节单独先做小范围验证（比如先
  手动跑几次真实模拟观察 LLM 是否能可靠区分四种关系类型）再扩展
  消费方。
- 本文档所有新增字段均设计为可选、默认不改变现有行为，延续项目
  一贯的向后兼容原则；但字段数量持续增加（`SimState`/
  `SimManifest.settings` 已经相当庞大）本身是一种复杂度负担，
  4.18 的 `engine.py` 拆分建议里也应该评估是否需要同步给
  `state_model.py` 做分组/精简。
