## 0. 这份文档解决什么问题

v1 落地的九个方向本身是"从无到有"——把 1.5 节四条约束里明显缺失的
机制补上。落地之后回头看实现细节，发现几处"有了但不够"的地方：不是
缺了某个机制，而是已有机制在边界情况下的行为还有打磨空间。这份文档
记录五处这样的细节，按发现时的讨论顺序排列。

## 1. B1 增量质量校验：LLM 复核步骤仍未实现

**现状**：`evaluate_cycle_increment()`（v1 方向 B1）只做了规则式初筛
——比对相邻两轮 `covered_subtopics` 的集合差集占比，重叠比例过高就
标记"疑似低增量"。v1 方案文档本身提到的"LLM 复核"是可选的第二步：
对被规则式标记的轮次，再调一次 LLM 做语义级别的"这一轮相比上一轮是否
有实质推进"判断——规则式初筛只能发现"字面上没什么新词"，发现不了
"用大量新词把同一个意思重新讲了一遍"这种更隐蔽的低增量。这一步在 v1
实施时被明确标注为"本轮未实现，留在方案文档里作为后续可选增强"。

**改进方向**：

- 新增 `growth_advisor.evaluate_cycle_increment_llm()`（或者给现有
  `evaluate_cycle_increment()` 加一个可选的 `llm_helper` 参数），只在
  规则式初筛已经判定 `low_increment=True` 时才触发——不对每一轮都调用，
  维持"规则式路径优先、LLM 增强作为 opt-in 补充"的既有取舍。
- 复用 2.11 节 `tech_radar.quality_feedback_enabled` 的设计模式：
  独立开关（比如 `pursuit_increment_llm_review_enabled`，默认关闭）、
  失败不影响主流程、结果只影响诊断展示（是否计入 B2 的饱和度 streak），
  不新增强校验或阻断执行。
- LLM 复核的判断结果应该跟规则式判断做区分记录（比如
  `evaluate_cycle_increment()` 返回值里加一个 `llm_reviewed` /
  `llm_verdict` 字段），避免"规则说低增量、LLM 说不是"或反过来的场景
  被静默合并成一个结论——两种信号都应该在诊断面板/看板里可见，而不是
  谁覆盖谁。
- 具体触发点：`goal_cron_bridge._check_pursuit_saturation()` 已经是
  "一轮完成 → 算增量 → 记饱和度"这条链路的接入点，LLM 复核可以作为
  这条链路里的一个可选加分步骤，不需要新开一个入口。

## 2. 对齐分析的 LLM 建议缺一键确认入口 ✅ 已实施

**现状**：`goal_alignment_llm_enabled=True` 时，`goal_growth_
alignment()` 会额外对"规则没匹配上的兴趣方向"和"规则没匹配上的
Goal"做一次语义匹配，结果放进 `llm_suggested_matches`（比如兴趣叫
"数据分析能力"、Goal 叫"提升可视化技能"）。但这份建议目前**只停留
在"展示给你看"**——CLI `/growth align` 会打印这些建议，看板（v1 A3
新增的"🧭 有兴趣但还没建目标"分区）目前也只读取 `unmatched_
interests`，不展示 `llm_suggested_matches`，更没有任何"确认这条建议、
把兴趣方向正式关联到这个 Goal"的动作——要正式关联，用户仍然只能走
`/growth adopt-goal`（新建一个 Goal，跟建议的意思其实不一样，建议
说的是"这个兴趣已经有一个语义相关的 Goal 了，不需要新建"）或者手动
改标题让关键词匹配上。

**改进方向**：

- 这本质上是 v1 方向 A3（批量落地）的一个自然延伸——A3 解决的是"兴趣
  方向没有任何 Goal，需要新建"，这里要解决的是"兴趣方向有一个语义
  相关但字面不同的 Goal，需要关联而不是新建"，两者共享"批量操作 +
  节流"的设计骨架。
- 新增 `growth_advisor.confirm_llm_suggested_match(paths, topic, goal_id,
  goal_backlog=None)`：把一条 `llm_suggested_matches` 里的建议写成
  正式关联——具体做法是找到 `topic` 对应的候选（如果存在），把它的
  `linked_goal_id` 指向 `goal_id`（复用 `adopt_candidate_as_goal()`
  内部\"候选已关联 Goal 就不重复创建\"的判断逻辑，这里是反过来\"手动
  指定关联到哪个已存在的 Goal\"，不新建 Goal）。`topic` 没有对应候选
  记录时，跟 A3 一样只能跳过、提示先走一轮 `/growth scan`。
- CLI 新增 `/growth align --confirm-match <topic_index>`（或者复用
  candidate_id/goal_id 的显式参数写法，具体交互形式留给实施时决定）；
  API 新增 `POST /v1/growth/align/confirm_match`；看板"🧭 有兴趣但
  还没建目标"分区旁边新增一个"🔗 语义相关的建议"子分区，列出
  `llm_suggested_matches`，每条带一个"关联"按钮。
- 这条改进依赖 `goal_alignment_llm_enabled` 已经打开（默认关闭），
  跟 v1 里"新增能力默认 opt-in"的一贯克制一致——建议本身不常出现，
  确认入口的收益也主要在打开这个开关的用户身上。

## 3. 饱和度信号是一次性快照，没有历史趋势

**现状**：`get_pursuit_saturation()`（v1 方向 B2）只返回某个 Goal
**当前**的 streak/saturated 状态，`pursuit_saturation` 在
`growth_state.json` 里也只存最新一条，不是时间序列。这意味着看不出
"这个方向饱和之后，用户听了建议真的降频了吗？降频之后新增内容是不是
又回升了？还是说不管频率怎么调都一直低增量（说明方向本身讲完了，
不是频率问题）"——跟月度复盘里其它信号（比如证据数走势、类别采纳率）
一样，饱和度信号也值得有一条趋势，帮用户判断"降频建议有没有用"。

**改进方向**：

- `record_pursuit_cycle_signal()` 除了更新 `pursuit_saturation` 的
  当前状态，顺带追加一条降采样的历史记录——复用 v4 N1 健康度趋势
  （`_record_health_snapshot()` / `compact_health_trend_storage()`）
  已经验证过的"按天/按周降采样、旧数据自动压缩"模式，不需要另起一套
  存储机制，只是给 `pursuit_saturation` 这个子字典也接入同一套压缩
  逻辑（或者复用同一份 `growth_health_trend_path` 文件，按 goal_id
  区分记录类型）。
- 新增只读函数 `get_pursuit_saturation_trend(paths, goal_id, limit=30)`，
  返回最近若干个"这一轮是否低增量"的时间序列，供看板"🔄 正在自主
  推进"分区展开后画一条简单的走势（跟 D1 已有的"证据数走势"箭头展示
  风格一致，不需要引入图表库）。
- 关键判断点：如果一个方向被建议降频后用户**没有**调整频率（cron
  schedule 没变），后续 streak 是否继续增长——如果继续增长且用户
  一直不理会，这条趋势本身可以成为"要不要把回访问卡片再触发一次"的
  依据（而不是 v1 现在"同一次饱和状态只提示一次"的设计——注意这里
  不是要推翻这条既有取舍，而是让"新的一次饱和状态"判断得更准：目前
  只要 streak 归零过一次就算"缓过来"，趋势数据能帮忙区分"真的缓过来
  了"和"只是偶尔一轮凑巧不重复，很快又打回原形"）。
- 成本可控：只是多写一条降采样记录，不产生新的 LLM 调用或额外的
  Goal 触发，对齐 v1"诊断增强不影响主流程"的一贯设计。

## 4. A3 批量落地是"抢答式"，两次调用之间条目对应关系不稳定 ✅ 已实施（方案一）

**现状**：`batch_adopt_unmatched_interests()`（v1 方向 A3）每次调用
都重新跑一遍 `goal_growth_alignment()`，拿到当前的 `unmatched_
interests` 全量列表后再按 `evidence_count` 降序截断前
`goal_alignment_adopt_all_max_batch`（默认 3）条处理。如果用户需要
分好几次点"全部采纳"才能清空一个较长的列表，两次调用之间的间隔里，
候选的 `evidence_count` 可能因为新的信号扫描而变化，导致列表顺序
重排——第一次调用返回的 `remaining_count` 只是一个数字，不对应具体
是哪几条；用户看到"还有 5 条"，实际点第二次时，可能有条目在两次
调用之间被新的高证据数条目"insert 到前面去"，先前排在后面、以为
"下次会处理到"的条目反而又被顺延了。

**改进方向**：

- 这是一个边界情况（多轮批量操作场景下才会出现，绝大多数用户列表
  长度在一次批量上限内就能清空），不是紧急问题，但值得记录、且修复
  成本不高：
- 方案一（更简单）：`batch_adopt_unmatched_interests()` 返回结果里
  除了 `remaining_count`，把"本次跳过、留到下次"的具体 topic 列表也
  返回（`remaining_topics: list[str]`），供 CLI/看板明确提示"下面这
  几个方向还没处理"，即使顺序变化，用户至少知道具体是哪些，而不是
  一个模糊的数字。
- 方案二（更彻底，但增加状态）：批量操作维护一个"本次批量操作的
  处理进度"临时状态（比如存一份 `pending_batch_adopt_topics` 到
  `growth_state.json`，第一次调用时快照当前 unmatched 列表的 topic
  顺序，后续调用按这份快照的顺序继续，而不是每次重新排序），操作
  全部完成或超时（比如 1 小时未继续）后清空快照。这个方案能保证
  严格按"发起批量操作那一刻的顺序"处理完，但引入了新的状态和过期
  逻辑，复杂度明显高于方案一。
- 建议优先做方案一：成本低、解决了"用户不知道具体漏了哪些"的核心
  体验问题；方案二的"严格顺序保证"收益边际不大（毕竟 `evidence_
  count` 重排序本身也是"更值得优先处理的条目排到前面"，不完全是坏事），
  除非未来实际观察到用户反馈"批量操作总是漏处理某几个方向"，否则
  不建议直接上方案二。

## 5. 看板缺少"暂停成长顾问总开关"之外的颗粒度控制 ✅ 已实施

**现状**：v1 方向 D2 做到了"单个方向"这个颗粒度的暂停/恢复（看板
"🔄 正在自主推进"分区每条带"⏸ 暂停"/"▶ 恢复"按钮）；另一端是全局的
`growth_advisor.enabled` 总开关（关闭后信号扫描/候选生成/cron 全部
跳过）。中间缺一个"批量调整多个方向的调度频率"的颗粒度——比如用户
要出差/请假一段时间，现在如果同时有 5、6 个方向在自主推进，只能逐个
点进「🎯 目标」tab 改 cron schedule，或者逐个在成长顾问 tab 点"⏸
暂停"再一个个"▶ 恢复"，跟 D1/D2"就近控制、不用理解 Goal/Cron 内部
机制"的理念有一点落差——单个方向的操作路径已经很短，但"批量"这个
维度还没覆盖到。

**改进方向**：

- 在"🔄 正在自主推进"分区顶部（D1 已有的列表上方）新增一个"批量操作"
  入口，提供两个动作：
  - **全部暂停**：对列表里全部 `recurring=True` 的 Goal 依次调用
    `stop_goal_recurrence()`（复用 D2 已有的单条实现，只是循环调用），
    不需要新的后端能力。
  - **全部调整频率**：给一个频率选择（比如"每天"→"每周"），对列表
    里全部方向依次调用 `make_goal_recurring()` 传入新的 schedule
    （复用 v1 A3 提到的"批量操作要节流"原则——即使这里的操作不涉及
    LLM 调用、成本很低，仍然建议给一个用户可见的"共处理 N 个方向"
    的确认提示，避免误触）。
- 跟单个方向操作一样，批量操作只是**就近暴露已有的 Goal 管理能力**，
  不新增后端接口，也不引入任何"系统自动决定要不要暂停"的逻辑——
  仍然是用户显式点击触发，对齐 1.5 节"自主不等于替用户做主"。
- 需要一个"全部恢复"的对应入口吗？——建议不做：全部暂停后再批量恢复
  的场景比"批量暂停"少见得多（暂停通常是因为"要休息一阵"，恢复往往
  是回来之后一条条重新评估"这个方向还要不要继续"，而不是无脑全部
  按原样恢复），如果后续用户反馈确实需要，再补。

## 6. 优先级与实施顺序建议

供后续排期参考（不代表本文档要一次性做完）：

1. **A3 批量落地的 remaining_topics 修复**（方向 4 方案一）——成本
   最低，纯粹是返回值补一个字段 + 前端展示调整，不涉及新逻辑，随时
   可以插入实施。✅ 已实施（`docs/growth-advisor-guide.md` 2.16 节）。
2. **看板批量暂停/调整频率**（方向 5）——复用已有的 D2 后端能力，
   跟 A3 修复一样是"信息组织/就近暴露"性质，没有新算法，优先级仅
   次于成本最低的第 1 项。✅ 已实施（2.16 节）。
3. **对齐分析 LLM 建议一键确认**（方向 2）——依赖 `goal_alignment_
   llm_enabled` 已经打开的用户群体，收益范围比前两项窄，但实现上
   直接复用 A3 的批量骨架，工作量可控。✅ 已实施（`docs/growth-
   advisor-guide.md` 2.17 节）。
4. **饱和度信号历史趋势**（方向 3）——收益是"帮用户判断降频建议有没
   有用"，属于锦上添花性质，且要接入 v4 N1 那套降采样存储，工作量
   比前三项略高，放在中间偏后。
5. **B1 的 LLM 复核步骤**（方向 1）——涉及新的 opt-in LLM 调用点、
   需要设计"规则判断 vs LLM 判断如何共存展示"，是五项里设计取舍最多
   的一项，建议放在最后，且实施前最好先看一段时间"规则式初筛本身
   误判率高不高"的实际数据，再决定 LLM 复核这一步是否真的有必要。

## 7. 与既有设计哲学的一致性检查

延续 v1 及更早方案文档的惯例，逐条核对：

- **默认克制、增强 opt-in**：方向 1（B1 LLM 复核）、方向 2（对齐
  LLM 建议确认，依赖已经是 opt-in 的 `goal_alignment_llm_enabled`）
  都不应该默认开启新的 LLM 调用；方向 3/4/5 都不涉及新的 LLM 成本。
- **失败尽力而为，不阻塞主链路**：方向 1 的 LLM 复核结果、方向 3 的
  趋势记录都应该是诊断性质，失败不影响对应轮次/操作本身的正常完成。
- **用户始终有最终决定权**：方向 5 的批量暂停/调频仍然要用户显式
  点击触发，不因为"批量"就默认自动执行；方向 3 的趋势数据只是
  展示，不据此自动调整任何执行参数。
- **复用已有存储位置，不为单一功能新增文件**：方向 3 建议复用 v4
  N1 已有的降采样存储机制；方向 4 方案一不新增持久化，只是丰富
  返回值；方向 2 复用候选/Goal 已有的 `linked_goal_id` 字段。
