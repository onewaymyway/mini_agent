## 1. 结论（一页纸）

**推荐方式：做成「编辑改编 + 程序化排版 + 少量 AI 插图」的讲解视频流水线，而不是「朗读原文 + 配图」。**

1. **先改编，再配音。** 用 LLM 把书面文章改写成口播稿（长文先分段摘要，再提炼主线，再逐段写稿），严格保留作者的论点、数字与原话，不凭空添加事实。
2. **画面以「程序绘制」为主，「AI 生图」为辅。** 文字卡、关键词高亮、表格、流程图/循环图、时间线、引用卡由 PIL 程序绘制（文字准确、成本为零、风格统一）；AI 生图只用于少量隐喻插图（每分钟约 2～3 张），同一张图靠多次裁切 + 镜内动效复用。
3. **节奏由「句」驱动。** 配音按句合成，拿到每句真实时长；画面的逐条出现、关键词高亮、字幕全部按句时间轴对齐；每 3～6 秒必有一次画面变化。
4. **署名与水印放在最后一道工序。** 作者署名（片头、片尾、角标）与水印作为最终叠加层，改水印只重跑最后一步 ffmpeg，不重新渲染任何镜头。
5. **复用 novel_to_video 的基础设施（复制精简，保持自包含）**：provider（文本/生图/TTS）、ffmpeg 与动效、字幕 PNG 叠加技术、取消/日志/原子写入、挡位与审核思路；**不复用**角色、地点、道具、性别等小说专属逻辑。

## 2. 目标与非目标

**目标**
- 输入一篇 Markdown 文章（几千字到几万字），输出一个（或多期）讲解视频：配音 + 字幕 + 动态画面 + 署名/水印。
- 视频要「讲得进去」：有开场钩子、章节路线图、节奏变化、重点强调、结尾回扣，而不是逐段朗读。
- 全程不调用视频生成接口；只用文本 LLM、生图接口、TTS、ffmpeg、PIL。
- 每一步落盘、可断点续跑、可人工编辑、可定向重跑（沿用 novel_to_video 的工作方式）。

**非目标（本方案不做）**
- 不做数字人 / 口型 / 角色动画。
- 不做自动剪辑真人素材，不抓取网络图片（版权与来源风险）。
- 不做多语言翻译配音（中文优先；结构上不阻止以后扩展）。
- 不改动 novel_to_video 的任何代码与行为。

## 3. 输入分析：以参考文章为例

对参考文章《从康波周期到超级AI……》做了统计（文件 14,873 字符，其中汉字 7,022）：

| 特征 | 数量 | 对设计的含义 |
|---|---|---|
| 一级标题 `#` | 52 | 章节结构清晰，可作为切分与映射依据；但标题粒度太细（三十八个小节），不能一节一段视频 |
| 二级标题 `##` | 19 | 小节内的并列项 |
| 代码块（几乎全是 ASCII 流程/因果链） | 35 | **不能朗读**；必须转为图（`A ↓ B ↓ C` 的链、带回路的循环） |
| 表格行 | 14 行（约 2～3 张表） | 转为表格卡，逐行出现，配合口述对比 |
| 引用块行 `>` | 137 | 多数是「金句」，适合做强调卡 / 引文声线 |
| 公式 | 若干 | 且**写法不规范**：用单独成行的 `[` … `]` 包裹，而非 `$$`；解析器必须兼容 |
| 大量重复修辞（「不是……而是……」「这意味着……」） | 很多 | 口播时必须压缩与改写，否则听感拖沓 |

**时长推算**：按现有项目的语速常量（4.2 字/秒），7,022 个汉字逐字朗读约 **28 分钟**，而且包含大量重复；精简改编到 **10～12 分钟**（约 2,500～3,200 口播字，压缩到约 35%～45%）才是合适的观看长度。所以：

> 「把全文读完」不是目标，**「把论证讲清楚且讲得有吸引力」才是目标**。精简程度由 `target_minutes` 控制，另提供 `faithful`（不删节、只口语化）模式。

## 4. 让视频「不机械」的六个杠杆

| # | 杠杆 | 具体做法 |
|---|---|---|
| 1 | **叙事结构** | 开场钩子（5～15 秒，取自文章最强的问题/反差）→ 标题与作者 → 「这期讲三件事」路线图 → 各章（每章有角色：背景/主张/例证/转折/小结）→ 结尾回扣钩子 + 一句话带走 |
| 2 | **口语化改写** | 一句一个意思，单句 ≤ 30 字；书面连接词改口语；`A→B→C` 改成「先……再……最后……」；公式用话讲，不念符号；保留作者的类比（如「电气化早期」） |
| 3 | **节奏与韵律** | 长短句交替；金句前停顿、金句放慢；每句可带 `pace`（语速）与 `pause_after_ms`；引文用第二声线（区别于主讲） |
| 4 | **画面变化频率** | 场景类型交替（不连续 3 个相同）；逐条出现 / 关键词高亮；同一插图多次裁切；每章有章标题卡与常驻进度条 |
| 5 | **重点强调** | 关键词在卡片与字幕中高亮，且与配音时间对齐；金句独占一张强调卡 |
| 6 | **回顾与悬念** | 章与章之间用一句话承上启下（「前面讲了……，但问题是……」）；每期结尾预告下期（多期时） |

## 5. 总体流水线

```text
article.md
  │
  ├─ S0 导入与解析（纯代码）          → source/blocks.json（带稳定 ID）、meta.json
  ├─ S1 分节摘要（map，LLM）          → plan/digests.json
  ├─ S2 主线与大纲（reduce，LLM）     → plan/spine.json            ◆C0 大纲确认
  ├─ S3 分段口播稿（LLM，逐段）       → parts/P01/script.json …    ◆C1 脚本确认
  ├─ S4 分镜（LLM + 规则，逐段）      → parts/P01/storyboard.json  ◆C2 分镜确认
  ├─ S5 配音（逐句 TTS）→ 时间轴       → audio/*.wav、timeline.json（纯计算）
  ├─ S6 素材：卡片/图表（程序）+ 插图（生图，受预算限制）
  ├─ S7 渲染：beat 片段 → 章（part）视频
  └─ S8 成片：拼接、字幕、进度条、BGM(可选)、署名与水印、元数据
        → exports/<标题>.mp4、<标题>_clean.mp4（无水印）、.srt、封面图
```

约定（沿用 novel_to_video）：每步产物落盘；每步有输入指纹，未变化则跳过；上游变化时下游标记过期（stale），不静默覆盖人工编辑；停止请求可中断模型/生图/TTS/ffmpeg。

## 6. 各阶段设计

### 6.1 S0 导入与解析（纯代码，不用 LLM）
- 把 Markdown 解析成块序列：`heading / paragraph / list / table / code / quote / math / image`，每块有稳定 ID（`s03`、`s03.p02`），并记录源行号范围。
- **ASCII 链解析**：`A\n ↓\nB\n ↓\nC` 解析为有序节点；含 `……`/回指（如「超级AI … → 超级AI」）的标记为循环。参考文章 35 个代码块大多可无 LLM 直接转成图数据。
- **公式**：兼容 `$…$`、`$$…$$`、单独成行的 `[`…`]`、`\boxed{}`；保留原文，另由 S3 给出「口述版」。
- **作者与标题**：优先级 = 命令行/界面参数 > front matter（`author:` / `作者:`）> 文首「作者：」行 > 留空。**不让 LLM 猜作者**（参考文章里没有作者名，猜错会造成错误署名）；留空则不署名，界面提示补填。
- 原文拷贝到项目目录并记录哈希，源文件变更时提示「原文已变，下游可能过期」。

### 6.2 S1 分节摘要（map）与 S2 主线（reduce）——长文的关键
几万字不能一次塞给模型，也不能让它逐段各写各的（会失去主线、前后重复）。

- **S1**：按 S0 的标题树把文章切成若干「节组」（每组 ≤ 约 4,000 字符，优先在一级标题处切），逐组调用 LLM，输出：节组要点、核心论点、关键数字/术语、可用的类比与金句、与上下文的关系。可并发，可断点续跑。
- **S2**：只把 S1 的摘要（几千字）交给 LLM，产出 `spine.json`：
  - `thesis`（一句话主旨）、`audience`、`tone`；
  - `arc`：全文论证弧线（提出问题→类比→转折→推演→落点）；
  - `parts[]`：章划分（每章：标题、角色、覆盖的源节 ID、**重要度权重**、**时长预算**、本章一句话）；
  - `hook_candidates[]`（3 个开场钩子，供选择）、`glossary[]`（术语统一译法，供各章保持一致）、`golden_quotes[]`（金句，原文逐字）；
  - `cuts[]`（建议舍弃或合并的小节及理由）——**取舍报告**，让用户看到被删了什么。
- 章划分规则：参考文章的 38 个小节预计合并为 **5～7 章**，每章 1.5～3 分钟。
- **检查点 C0（界面可编辑）**：改章标题、合并/拆分章、恢复被舍弃的小节、选钩子、调整总时长。

### 6.3 S3 分段口播稿
逐章调用 LLM，输入：本章源文本 + `spine` + 术语表 + **上一章结尾摘要**（保证衔接）+ 本章字数预算。输出 `script.json`：

```json
{
  "part": "P02", "title": "AI 现在站在哪个位置", "budget_chars": 420,
  "beats": [
    {
      "id": "P02.b07", "role": "claim", "source_refs": ["s09", "s10.p2"],
      "sentences": [
        {"text": "今天的 AI，很像一百多年前的电气化早期。",
         "tts": null, "emphasis": ["电气化早期"], "quote": false},
        {"text": "当时的人做了什么？把蒸汽机，换成电动机。",
         "tts": null, "emphasis": [], "quote": false}
      ],
      "pace": "normal", "pause_after_ms": 350
    }
  ]
}
```

- **beat** = 一个画面意图（约 2～4 句、8～20 秒）；**sentence** = TTS 与字幕的最小单位。
- `text` 用于字幕与卡片，`tts` 可选，用于发音替换（「Agent」「GPU」「AgentOS」等；项目级 `lexicon.yaml` 统一维护），字幕仍显示原写法。
- `quote: true` 的句子必须是原文逐字摘录（由 V2 校验），朗读用「引文声线」。
- 视角（`persona`）：`host`（讲解人，必要时「作者认为 / 文章指出」）或 `author`（作者第一人称）。默认 `host`。
- 各章口播稿可在界面直接编辑；编辑后只让本章的分镜与后续产物过期，不影响其他章。

### 6.4 S4 分镜（视觉导演）
在口播稿**定稿后**再做，原因：改字不应让整套视觉重来，而且视觉设计需要看到最终文本。

每个 beat 选择一种场景类型，并给出结构化参数：

| 场景类型 | 用途（以参考文章为例） | 画面来源 |
|---|---|---|
| `title` | 片头/章标题卡（含作者署名） | 程序绘制，背景为 AI 底图或主题渐变 |
| `keypoint` | 一句核心论断，关键词高亮 | 程序绘制 |
| `illustration` | 隐喻/历史场景（蒸汽机、电网、铁路、数据中心） | **AI 生图** + 动效 + 少量叠字 |
| `diagram` | 因果链、反馈回路、「数字世界/物理世界」双层结构 | 程序绘制（节点、箭头、回路），逐节点出现 |
| `table` | 技术革命对照表、四层周期表 | 程序绘制，逐行出现 |
| `list` | 并列要点、三种世界 | 程序绘制，逐条出现 |
| `timeline` | 2022～2027 … 2035 年后的阶段 | 程序绘制 |
| `quote` | 金句 / 引用块 | 程序绘制，使用引文声线 |
| `formula` | 生产函数、反馈方程 | 程序绘制（等宽/数学字体）+ 口述解释 |

分镜规则（由代码校验）：
- 相邻三个 beat 不得同一场景类型；每章至少含一个 `diagram`/`table`/`list` 之一（视内容而定）；
- 单张卡文字密度上限（如 ≤ 60 字）；超出自动拆成多个逐步出现（reveal）；
- `illustration` 的生图提示词必须**不含任何文字内容**，并带项目级风格锚（见 7.3）；
- 每个 beat 必须有 `reveal` 计划：逐条/逐节点出现落在哪一句（按句边界对齐）。

### 6.5 S5 配音与时间轴
- **逐句合成**（沿用 `providers/tts.py` 的 CosyVoice → edge-tts 降级链、`sanitize_tts_text`、`has_speakable`、取消机制），得到每句真实时长。
- 主讲声线 + 引文声线（两个音色），每句可调 `rate`（edge-tts 支持语速参数，现有代码固定为 +0%，需小改）；句间静音由 `pause_after_ms` 控制。
- 产出 `timeline.json`：每个 beat/句的起止时间（纯计算），后续所有对齐（字幕、reveal、转场）都读它。
- 未装 CosyVoice 且 edge-tts 不可用时，明确报错，不悄悄降级为静音（静音只用于 stub 流程验证）。

### 6.6 S6 素材
- **卡片/图表**：本地程序绘制（PIL），免费、秒级，可随时重绘（改主题/配色只重绘，不重新生图）。
- **插图**：受预算约束，见 7.3。

### 6.7 S7 渲染
见第 7 节「视觉系统与渲染分层」。

### 6.8 S8 成片
- 拼接：片头 → 各章（章间淡化或叠化，沿用 `concat_fade/concat_dissolve`）→ 片尾。
- 叠加：字幕、进度条、署名角标、水印。
- BGM（可选，默认关闭）：见 9.4。
- 导出：`exports/<标题>.mp4`（含水印）、`<标题>_clean.mp4`（无水印）、`<标题>.srt`、`cover.png`（程序绘制的封面，含标题与作者）。
- 成片校验：时长、分辨率、帧率、音轨（沿用现有 F-4 思路）。

## 7. 视觉系统与渲染分层

### 7.1 画幅
沿用 `video_format.py`：横屏 16:9 / 竖屏 9:16，720P / 1080P。**默认横屏 1080P**（讲解类文字卡在 720P 下偏糊；竖屏作为选项）。排版器按画幅提供两套布局（横屏左右/上下分区；竖屏单列堆叠），并设置安全边距。

### 7.2 渲染分层（单个 beat）
```text
L0 背景     插图（zoompan 动效，沿用 media/motion.py）或主题背景（缓慢移动的渐变/纹理）
L1 内容层   卡片/图表的 reveal 步骤（RGBA PNG），按句边界 overlay，淡入（fade alpha）
L2 常驻层   章进度条 + 章名小标签
L3 字幕层   按句时间轴的字幕 PNG 序列
L4 品牌层   署名角标、水印（最终成片才叠加，见第 9 节）
```
- 技术路线沿用 `media/subtitles.py` 的做法：字幕/叠层先渲染成透明 PNG，再用 ffmpeg concat 时间表整体叠加，**不依赖 libass**，也避免「几百个 overlay 输入」导致滤镜图过大。
- 动效滤镜由纯函数生成，用 golden 字符串测试（沿用 `tests/test_still_motions_s5.py` 的方式）。
- 字幕与卡片文字重复时自动隐藏字幕（`subtitle: auto | always | off`，按 beat 可覆盖），避免同一句话出现两次。

### 7.3 插图与预算
- 默认 `max_images_per_minute = 2.5`（10 分钟约 25 张），超出时按重要度保留，其余 beat 改用程序绘制的场景类型。
- **一图多用**：一张横向宽图可裁出 2～3 个不同取景（从区域 A 平移到区域 B），在相邻 beat 里作为不同镜头使用。
- **风格统一**：项目级 `visual_bible`（风格提示词、色板、禁用元素、必含「无文字」约束），所有生图提示词拼接同一风格锚；同一章内把该章首张图作为**风格参考图**传给后续生图（现有接口最多 3 张参考图，`providers/image.py` 已支持）。
- 缓存键包含：提示词、风格锚、画幅、参考图哈希；任何一项变化才重新生成；旧版本保留（版本化，沿用 `stills/<id>_vNNN.png` 的做法）。

## 8. 配音与节奏细则

- 语速基线 4.2 字/秒（估算用）；实际时长以 TTS 返回为准。
- 开场钩子略快、金句略慢；章标题前后各留 0.4～0.6 秒静音。
- 引文声线仅用于 `quote: true` 的原文金句，数量受限（避免频繁换声造成割裂），默认每章 ≤ 2 句。
- `lexicon.yaml`：发音替换表（如 `AgentOS → 艾真特 O S`），在项目设置页可改，改动后只重配相关句。
- 配音试听：设置页可对任意一句试听（不影响项目状态）。

## 9. 作者署名与水印（Branding）

配置块 `branding`（项目 `project.json`），全部可在设置页修改：

```json
{
  "author": "作者名",
  "author_handle": "@xxx（可选）",
  "source_title": "文章标题（默认取 H1）",
  "source_url": "",
  "credits": {"title_card": true, "lower_third": true, "end_card": true, "corner_tag": false},
  "watermark": {
    "enabled": true, "type": "text", "text": "作者名 · 频道名", "image": null,
    "position": "top_right", "opacity": 0.35, "scale": 0.06, "margin": 0.03,
    "mode": "static"
  },
  "ai_disclosure": {"enabled": true, "text": "本视频配音与部分插图由 AI 生成"}
}
```

### 9.1 署名放哪里
| 位置 | 内容 | 出现时机 |
|---|---|---|
| 片头标题卡 | 标题 + 「作者：xxx」 | 开场钩子之后 |
| 下三分之一条 | 「原文｜标题 · 作者」 | 片头后 5～8 秒，之后淡出 |
| 片尾卡 | 原文标题、作者、来源链接（可选）、AI 生成声明 | 最后 4～6 秒 |
| 角标（可选，默认关） | 「原文作者：xxx」，位置可设置（默认右上，R22） | 全程 |
| 文件元数据 | `title`、`artist`（作者）、`comment`（来源） | 导出时写入 mp4 |

### 9.2 水印
- 类型：`text`（程序绘制，使用已解析的中文字体）或 `image`（PNG logo，保留透明通道）。
- 位置：四角、居中，或 `diagonal_tile`（半透明斜向平铺，防裁剪盗用，默认不开）。
- 模式：`static`（固定）；`drift`（缓慢在四个角之间移动，防止被一键去除，可选）。
- **实现**：最终成片阶段把水印渲染成单张 RGBA PNG，用一次 ffmpeg `overlay` 叠加到整片上；因为位于所有动效之上，水印**不会随推拉平移晃动**。
- **只重跑最后一步**：改水印/署名只需重新执行 S8 的叠加（一次重新编码），不触发任何镜头重渲染；同时保留无水印版本便于再加工。

### 9.3 AI 生成声明
默认**开启**（片尾 + 元数据）。这是对平台规则与观众的诚实披露，文案可改，也可关闭（由用户决定）。

### 9.4 BGM（可选，默认关闭）
用户指定本地音频文件（本项目不下载、不生成音乐，避免版权与接口问题）；按配音自动压低（sidechain 压缩），可调音量；循环/淡出处理。属于保守的 opt-in 功能。

## 10. 长文与多期拆分

| 输入规模 | 默认处理 |
|---|---|
| ≤ 1 万字 | 单期，`target_minutes` 默认 10 |
| 1～3 万字 | 单期 12～15 分钟，或按章边界拆成 2 期 |
| > 3 万字 | 按章边界拆成多期，单期 ≤ `episode_max_minutes`（默认 15）；每期有自己的钩子，期首「上期回顾」一句，期末「下期预告」一句 |

- 拆分只发生在 S2（章边界）；每期独立成片，另可选「全集合并」。
- 模式：`condensed`（默认，按 `target_minutes`）、`faithful`（不删节，只口语化与图表化，时长由内容决定）、`highlights`（≤ 3 分钟精华）。
- 时长控制：章预算 = 总预算 × 重要度权重；S3 写稿后校验 ±15%，超出则带「压缩/扩写」指令重写该章（有重试上限，超限留给人工）。

## 11. 质量门禁（代码校验，不依赖 LLM 自觉）

| 校验 | 内容 | 不通过时 |
|---|---|---|
| V1 覆盖 | 每个 beat 有 `source_refs`；`spine` 中的核心节至少被覆盖一次；被舍弃的节列入取舍报告 | 自动重写缺失部分；仍失败则标红待人工 |
| V2 忠实度 | 口播中的**数字、年份、专有名词、术语**必须出现在其引用的源节里（归一化后子串/集合匹配）；`quote:true` 必须是原文逐字子串 | 带具体不一致项的修复重试 |
| V3 可读性 | 无 Markdown 符号、无裸公式；单句 8～40 字；有可朗读字符；英文缩写在词典中 | 自动清洗或重写 |
| V4 节奏 | beat 时长分布、场景类型交替、卡片文字密度 | 自动拆分 reveal / 调整类型 |
| V5 视觉 | 生图提示词不含文字要求；风格锚齐全；预算未超 | 重写提示词 / 降级为程序绘制 |
| V6 成片 | 时长、分辨率、帧率、音轨、字幕不越界、水印位置在安全区 | 报告并阻止导出 |

V2 对应 novel_to_video 对白「原文子串校验」的思路，是防止 LLM 改写出作者没说过的话的核心手段。

## 17. 风险与限制

| 风险 | 应对 |
|---|---|
| LLM 改写偏离原意或编造 | V2 忠实度校验 + 取舍报告 + C1 人工确认 |
| 生图风格漂移、画面里出现乱码文字 | 风格锚 + 同章风格参考图 + 提示词禁文字 + 文字一律程序绘制 |
| edge-tts 403 / 不可用（项目历史上出现过） | 沿用降级链与现有排查提示；P3 冒烟时确认 |
| Windows 缺中文字体 | 沿用 `NOVEL_TO_VIDEO_FONT` 思路，新项目用独立环境变量并提供候选清单 |
| 复杂 ffmpeg 滤镜图过长、编码慢 | 叠层统一走「PNG 序列 + concat」；beat 级缓存，只重渲染变化的 beat |
| 版面质量不如 HTML/CSS 渲染 | PIL 主题模板化；是否引入 Playwright 渲染见 Q6，本方案先不引入 |
| 真实 API 路径在本期无法离线验证 | 与 novel_to_video 一样提供 `smoke_real_api.py`，如实记录「待本机冒烟」 |
| 无法验证真实观看体验 | 提供「前 30 秒 / 单章」快速预览，人工目视确认 |

### 21.2 两层模型（推荐方案）

- **全局默认层**：`<projects_root>/settings.json`，与项目集合同目录，随项目一起备份。只保存用户改过的值，未保存的字段取内置默认。
- **项目覆盖层**：`project.json` 中只保存**该项目显式覆盖的字段**（稀疏存储）。生效值 = 内置默认 ⊕ 全局默认 ⊕ 项目覆盖。
- **生效值与来源**：设置页对每个字段显示生效值，并标明来源（内置 / 全局 / 项目）。项目覆盖可一键「恢复为全局默认」。
- **不进入设置的内容**：API key、模型密钥（仍只来自环境变量，不写入任何 JSON）；本次运行的临时选择（运行到哪一步、是否确认终审、是否合并全集、离线冒烟、是否强制重写、选择哪一章）留在各页面。

### 21.3 页面结构

「⚙️ 设置」页分两个标签：

1. **全局默认**：按参数组折叠显示（讲解、视频、大纲、配音、视觉、合成、署名水印、BGM、流水线挡位与预算、日志）。保存后只影响之后新建的项目，以及没有覆盖该字段的已有项目。
2. **当前项目**：选择项目后，同样的分组，每个字段旁显示「生效值 · 来源」，可修改（写入项目覆盖）或恢复为全局默认。

各业务页面（大纲、口播稿、配音、分镜、合成导出、驾驶舱）**删除**自己的设置表单，只保留本次运行的临时选择，并在顶部显示「当前生效的关键设置」一行（只读，链接到设置页）。

### 21.4 与现有机制的衔接

- 所有参数仍经各模块已有的 `normalize_*` 校验，全局与项目两层都走同一校验，不新增校验规则。
- 过期判断不变：分镜、配音、画面渲染、合成已经用输入指纹或配置哈希判断是否过期。设置变化后，依赖它的阶段自动显示「已过期」，不会静默沿用旧结果。修改设置页时，列出会受影响的阶段。
- 只改合成类设置（转场、字幕、进度条）时，只需要重新合成，不需要重新渲染画面；这一点已在 P5/P6 中实现，R4 不改变。
- 测试：设置解析（默认 ⊕ 全局 ⊕ 项目）的纯函数测试；全局修改不改变已覆盖字段；恢复默认后回到全局值；过期影响列表。

## 22. 第三轮改进（R5）：大纲生成稳健性

> 来源：使用 R3 默认模型生成大纲时，节组 g01 两次输出的金句都被判为“不是原文逐字片段”，整个大纲失败。问题是：校验要求逐字相同，任何标点、引号、换行与大小写的差异都会判错，而且一组里的一条金句不合格就拖垮整个大纲。

### 22.1 原因分析

| 现象 | 根因 |
|---|---|
| 金句中的 `“智能”` 被输出成 `"智能"` 或去掉引号，判为不合格 | `squash()` 只去掉空白、`*`、反引号，标点与全角半角不统一即失配 |
| 跨段落引文 `它不再只是：\n\n> Software as a Tool\n\n而开始变成` 被合并成一句，判为不合格 | 原文中的 `>` 引用符与空行没有被去掉；模型合并时又补了标点 |
| 一条金句不合格，整组两次重试后失败，整个大纲失败 | 引文校验与结构校验共用同一条“重试”路径；重试的代价是整组再调一次模型 |
| 失败时前面几组的摘要全部丢失 | 摘要只在全部组完成后才写入 `digests.json` |
| 重试提示只告诉模型“不合格”，没有给出能对上的原文 | 模型没有依据修正，下一次仍可能不一致 |

### 22.2 方案

**R5a 归一化校验（`validators/fidelity.py`）**
- 比较键 `norm_key`：NFKC 归一化、转小写，去掉所有标点、符号、空白与控制字符。中文引号、英文引号、全角半角、换行与 Markdown 标记都不影响比较。
- 对齐 `locate(quote, source)`：在原文中找到归一化相同的片段，返回**原文中的规范写法**（去掉换行、引用符与加粗标记）。模型给的金句内容对得上，就用原文的写法替换，下游拿到的始终是原文来源。
- 太短的片段（归一化后不足 4 个字符）不参与对齐，避免“是”之类的误配。
- `repair_digest`：金句与数字能对齐的替换为规范写法，对不上的剔除，返回剔除说明。

**R5b 流程（`planning/llm.py`、`planning/runner.py`、`planning/prompts.py`）**
- **只有结构性问题才重试**：JSON 不合法、摘要或核心论点为空。引文和数字对不上只剔除、记入日志，不再让整组失败。
- **大纲金句对齐到摘要登记的金句**：`repair_golden_quotes` 把大纲中的金句映射回摘要的规范写法，不在清单中的剔除；覆盖校验同样改用归一化比较。
- **分组断点续跑**：每组摘要完成即写入 `plan/digests_partial.json`；失败后保存已完成的组，下次只重算未完成的组。输入未变的组复用，成功后删除部分结果。
- **提示词**：金句限制为最多 3 条、每条 8～40 字；说明标点与大小写可以略有差异，对不上的会被剔除，减少无效输出。提示词版本升为 `p1-v2`，因此旧的摘要缓存会重新生成一次（输入指纹包含版本号）。
- 日志：每个被剔除的条目、每次结构性重试、续跑复用的组数量都写入运行日志，便于在界面上看到发生了什么。

### 22.3 决策与取舍

| 决策 | 选择 | 理由 |
|---|---|---|
| 引文对不上时的处理 | 剔除并记录，不重试 | 重试得到的仍是模型自由生成的文字，成本高、成功率不稳定；剔除不影响忠实度（被剔除的内容不会进入大纲） |
| 对齐后的写法 | 原文规范写法（去掉换行与引用符） | 保证进入大纲的文字与源文一致，只是排版不同 |
| 忽略的差异 | 标点、大小写、空白、Markdown 标记、NFKC 形式 | 用户要求；这些差异不改变内容 |
| 仍需严格判断的 | 数字（归一化后仍须出现在原文）、金句必须能对齐到摘要登记的清单 | 数字错误与编造原话是忠实度的核心风险 |
| 提示词版本 | 升级为 p1-v2 | 提示词变化后，旧摘要的依据已不同 |
| 口播校验（P2 V2） | **本期未改**，仍使用旧的 `squash` | 口播校验的范围与风险不同，单独评估后放到后续期次 |

### 22.4 验收

- 单元测试 `tests/test_r5_outline_robustness.py`（14 项）：归一化规则；真实失败的跨行引文与引号差异能对齐到原文；大小写不敏感；编造与过短片段被拒绝；数字归一化；金句对齐与剔除；覆盖校验的归一化比较；结构性问题才重试；续跑与过期部分结果的处理。
- 修改 `tests/test_p1_runner.py`：原“编造原话即失败”的断言改为两条测试——结构性失败仍不写结果并归档原始输出；编造金句被剔除后流程继续，且不进入大纲。
- 端到端检查（使用文档 `从康波周期到超级AI…md`）：5 个节组，每组的两条原文金句被人为破坏（去标点、改大小写、换引号、去 Markdown 符号）后，全部对齐回原文；每组另加入的一条编造金句全部被剔除。
- 全量测试：332 项通过；1 项失败（`test_r1_joblog_timeline` 的界面测试）原因是沙箱未安装 `streamlit`，与本期无关；其余界面测试在本环境跳过。

### 22.5 偏差与未做

- 只做了离线的端到端检查（模拟模型输出）；真实模型的摘要质量与剔除比例未评估，需要在本机用真实模型运行一次并查看日志。
- 节组仍是串行调用；并发生成摘要留待后续（需要考虑模型的速率限制）。
- 口播校验（P2 V2）仍用旧的宽松比较，其引文与数字检查没有改为忽略标点与大小写。
- 剔除的金句和数字目前只写入运行日志，没有单独的取舍清单供界面查看。
- 数字归一化后，`3.5` 与 `35` 视为相同；如果原文中有这类差异，需要在后续期次收紧。
- 沙箱缺少 `streamlit`，界面相关测试未在本环境执行。

## 24. R7 界面结构重构：驾驶舱为主入口（已完成，2026-11-18）

- **侧边栏**：只保留「🧭 驾驶舱」「📥 新建项目」「📚 项目」「⚙️ 设置」。大纲、口播稿、配音、分镜、合成导出不再是侧边栏页面。

  - 顶部选择项目；

### 24.2 流程总览的判断规则（`ui/cockpit_page.py: overview`）

| 步骤 | 判断 |
|---|---|
| 大纲 | 无大纲 → 未生成；有但未确认 → 待确认；已确认 → 已确认（说明：章数） |
| 口播稿 | 无大纲 → 等待大纲；全部章已确认 → 已确认；部分确认 → n/m 章已确认；有草稿无确认 → 未完成 |
| 配音 | 每章存在 `timeline.json` 时计为完成 |
| 分镜 | 全部章确认 → 已确认；任一章过期 → n 章过期；部分确认 → n/m 章已确认 |

## 27. R10 大纲金句：直接加入（已完成，2026-11-18）

> 来源：用户反馈。第 25 节（R8）的“被剔除条目 → 输入原文片段 → 加入”设计有三个问题：①“加入”到哪里不清楚——实际只写入 `digests.json` 的摘要字段，大纲页、口播稿、分镜、字幕都看不到，也不影响任何后续步骤；②必须先在原文中找到对应文字才能加入，这是把忠实度规则误用到人工操作上；③用户应该可以直接加入。本节修正这一设计。

### 27.1 R8 设计的问题（如实记录）

- 恢复后的条目只进入 `digests.json` 的 `quotable` / `key_numbers`。这两个字段只在**下一次生成大纲**时作为参考被读取一次，之后没有任何环节使用。
- 大纲的 `golden_quotes` 只由模型生成，用户无法编辑；口播、分镜、字幕也不读取它们（代码检索已确认）。因此用户加入的内容在视频中不会出现。
- “必须先在原文中找到”的规则只适用于模型自动产生的内容（防止编造）。用户手动输入是人工决定，不需要这个限制。

### 27.2 现在的设计

- **金句列表（大纲页，“金句（写稿时原样使用）”）**：spine 新增字段 `quotes`，每条为 `{text, part_id, origin}`。
  - 直接在表单中输入文字、选择所属章节即可加入；`origin` 标注“原文”（能在原文中找到，忽略标点与大小写）或“人工”（不在原文中，只做提示，不阻止加入）。
  - 可删除。
- **写稿**：所属章节的口播提示词增加“必须原样使用的金句”一节（`quote=true`，文字不得改动）。校验时，这些金句不要求出现在原文中（`manual_quotes` 豁免）。写稿的输入指纹包含金句列表，金句变化后该章口播会被标记为需要重写。
- **被剔除的内容（大纲页，“模型给出但未在原文中找到的内容”）**：
  - 金句：显示可修改的文字与章节选择，点“加入金句”即加入大纲；或“忽略”。
  - 数字：目前没有任何下游使用者，因此**只提供“忽略”**，并注明“数字暂未接入口播”。
- **报告**：人工加入、不在原文中的金句在“忠实度”类别中提示，不影响确认。
- 编辑金句会取消大纲的确认（与其它编辑一致），写稿前需重新确认。

### 27.3 被替换的 R8 功能

- 删除 `restore_digest_item`（按原文片段恢复）。R8 中对应的测试已删除，界面按钮“加入”改为“加入金句”。
- 失败保护：`promote_dropped_quote` 先加入金句，成功后才从剔除列表移除；加入失败时剔除列表保留原条目。

### 27.4 验收

`tests/test_r10_outline_quotes.py`（14 项）：

## 28. R11 口播稿局部修正（已完成，2026-11-18）

> 来源：用户反馈（日志）。P02 的稿件因一句金句“不是原文逐字片段”而被判不合格，整章重新调用模型，耗时约 3 分钟，且每次只因一句话出错就重写整章，并不合理。用户建议：用 LLM 做修正；校验不要机械逐字比较，只要意思一样即可。

### 28.1 问题

- 任何句子级错误（一个数字、一个金句的引号差异）都会触发整章重写。P02 连续两次重写，合计约 6 分钟。
- 金句的判断是字符串比较（R9 已放宽为忽略标点与大小写），但“意思一样、措辞不同”仍被判错。

### 28.2 设计

- **校验记录位置**（`script/validate.py`）：每条句子级错误带上段落、句序号与问题类型（`flags`）；段落级错误（缺少 source_refs、引用本章之外的小节、没有句子、没有段落）标记为硬错误（`hard`）。
- **局部修正**（`script/repair.py`）：校验发现句子级问题时，把出问题的句子（带 id、问题说明、当前文字、处理提示）交给模型，要求只返回这些句子的修正。最多 2 轮（`MAX_REPAIR_ROUNDS`）。修正提示中附带编号的原文句子列表。
- **金句交给模型判断**：对不上原文的金句，模型可以指出原文中意思相同的句子（`source_index`），系统直接采用那一句原文，不做逐字比较。
- **兜底**：存在硬错误、修正输出不是有效结构、或两轮后仍有问题时，回到原来的整章重写（最多 3 次）。
- 节奏问题（字数偏离预算）仍整章重写，因为它需要改变篇幅，不是某一句的问题。

### 28.3 有意保留的机械校验

- **数字**：必须以完整记号出现在原文中（R9 的规则）。数字是事实，不做语义判断，避免把编造的数字判为“意思一样”。
- **英文词**：仍按归一化后的子串比较，同样属于事实类。

### 28.4 尚未覆盖的部分

- 大纲的摘要校验（R5 的金句与数字）仍是机械比较，被剔除的条目只能人工处理。同样的“模型判断意思”可以用于摘要，本期未改动。
- 人工保存的口播稿（`save_script`）不触发模型修正，仍然只报错，由人工修改。

### 28.5 验收

- `tests/test_r11_script_repair.py`（7 项）：句子 id 与修正提示；修正只作用于已知 id；模型通过 `source_index` 指定的原文句子被采用；段落级错误不修正，直接整章重写；修正输出无效时回退整章重写；校验给出的位置与硬错误标记。
- `tests/test_p2_writer.py`：两条原有测试改为反映新流程（编造的数字由局部修正解决，调用次数为 2；无法修正的编造内容仍报错，且不写入结果）。
- 全量测试：435 项通过，2 项需联网跳过。

### 28.6 偏差与未做

- 修正调用的耗时取决于模型速度。假模型测试只验证流程，真实模型上的修正质量与耗时需要在本机运行确认。
- 修正提示中的原文句子列表是按标点切分的，句子边界不完美；模型指出的句子若过长，会被单句检查拦下，进入下一轮修正。
- 摘要阶段的语义校验（见 28.4）是下一步可以做的事情。

### 32.9 补充：渲染后分镜预览报错（2026-11-18）

现象：「渲染本章画面」成功后，分镜页报 `StreamlitAPIException: Slider min_value must be less than the max_value. The values were 0 and 0.`

### 37. R19 时间设置只重建时间轴

问题：修改章封面停留、章首静音、句间停顿或章尾停顿后，要求全部重新生成，不合理。这些设置只影响时间轴（每句的起止时刻），而不影响配音音频、口播稿、分镜或生图。

核对结果（改动前）：

- 分镜的输入指纹（`input_sha`）只包含口播稿、本章时长、生图配置与引擎，不包含时间设置，修改时间设置不会让分镜过期；
- 画面渲染的缓存键（`_scene_sha`）同样不包含时间设置，图片可复用；渲染清单中的章首段与时间起点每次渲染都会重算；
- 真正受影响的只有时间轴 `timeline.json`，以及依赖它的渲染清单（章首段结束时刻）。
- 之前的合成检查提示「重新配音」，那是因为旧流程只能通过配音生成时间轴，提示与实际需要不符。

改动：

- `audio/synth.py` 新增 `rebuild_timeline(pdir, part_id)`：从配音清单读取每句的时长、音色与引擎，用当前时间设置重新调用 `build_timeline`，写回 `timeline.json`。不调用 TTS，不改动音频文件。缺任一句配音、或口播稿未确认时拒绝执行，并说明原因。
- `ui/voice_page.py`：新增两个按钮：「按当前时间设置重建本章时间轴」「重建全部已确认章的时间轴」。
- `compose/part.py`：合成前的检查改为指向正确的操作：时间轴章封面不足 3 秒时，提示在配音页重建时间轴；画面与时间轴不一致时，提示在分镜页重新渲染（复用图片，不重新生图）。
- `app_settings.py`：四项时间设置的影响说明改为「只重建时间轴，再重新渲染画面、合成（不重新配音、不重写分镜、不重新生图）」。

需要的操作（改时间设置之后）：配音页「重建时间轴」→ 分镜页「渲染本章画面」（几乎只有合成，因为图片已缓存）→ 导出页「合成」。

验收：`tests/test_r19_timeline_rebuild.py`（5 项）：改章封面停留后，时间轴与首句起点正确更新，音频文件、分镜指纹与图片都保持不变，分镜不过期；句间停顿与章尾停顿精确生效；缺句配音时拒绝；口播稿未确认时拒绝；旧时间轴（0.5 秒）被正确替换。全量测试：493 项通过、3 项跳过。

偏差与未做：

- 重新渲染画面目前是手动一步（分镜页按钮）。它不需要生图，但渲染函数的图片提供者在 UI 中由页面构造，自动触发需要统一调用入口，之后可以做。
- 重建时间轴不保留配音时的音色与引擎警告（只保留模拟配音的警告）；如果需要，之后可把配音的警告一并存入清单。

### 38. R20 渲染所有章的画面

### 39. R21 封面不淡入

现象：别人预览成片时，开头和每章封面看到的是黑屏。

原因：淡入淡出转场下，`compose/post.py` 的 `join` 对每一段都加淡入（`fade=t=in:st=0`），因此每段（包括片头卡与每章封面）都从黑场开始。成片第一帧是黑的，预览的首帧也是黑的。

改动：

- `compose/post.py` 的 `join` 新增 `holds` 参数：第 i 段开头是封面的秒数。封面段不加淡入，从第一帧直接显示，只保留它结尾的淡出（`holds` 未给出或为 0 的段落保持原来的淡入淡出）。
- `compose/export.py`：按段记录封面秒数：片头卡为 `TITLE_SEC`，每章为时间轴的 `lead_in_sec`（新增 `_cover_hold`，没有时间轴时为 0），片尾卡为 `END_SEC`。拼接指纹包含 `holds`，所以改动后会重新拼接。
- 切换（cut）与叠化（dissolve）模式不变：叠化本来是从前一段过渡，不会出现黑屏。

验收：`tests/test_r21_cover_no_fade.py`（4 项）：封面段没有淡入、仍有淡出；第二章（无封面开头）保持淡入淡出；未给出 `holds` 时行为不变；切换模式不受影响；章封面时长取自时间轴。全量测试：502 项通过、3 项跳过。

偏差与未做：

- 封面段结束后的内容也不淡入（封面之后直接是正文），这是为了让封面的过渡更干脆；如果希望正文也淡入，可以只对封面段生效，之后再调。
- 封面之前的淡出仍然会先变黑再切到封面，这是转场的一部分；如果希望完全没有黑场，请使用切换或叠化模式。

## 41. R22 角标（作者）位置可设置（已完成，2026-11-19）

需求：视频合成时，角标（作者）的显示位置改成可设置，默认右上角。按「一个阶段一个阶段」执行，本阶段只做这一项。

### 41.2 改动

- 配置：`branding.credits.corner_position`，取值 `top_left / top_right / bottom_left / bottom_right`，默认 `top_right`；非法值回退默认并给出警告（`project_store.normalize_branding`，新增常量 `CORNER_POSITIONS`）。角标开关 `credits.corner_tag` 仍默认关闭（保守默认不变）。

## 44. R28 新方案：幻灯片规划不合格时由模型自动修复（已完成，2026-11-21）

需求：新方案（G3）运行时 P04 的幻灯片规划经三次分页仍不合格而直接失败。遇到问题应把具体问题交给文本模型修复并不断重试，而不是停下来。按「一个阶段一个阶段」执行，本阶段只处理规划这一步。

### 44.1 原因

- 日志中的失败（`只有标题或前言`、`前言留在页尾`）是规则分页的缺陷：三级小标题后紧跟前言段时，二者各自标为“前言”，`_groups` 只把“一个前言 + 下一个元素”成组，于是“小标题 + 前言”被分成一组、放不下时单独成页。收紧每页条目上限（12→8→5）只会让这种情况更多，所以重试无效。
- 随机构造 2000 篇文章：640 篇在三档上限下都失败；修复规则后降为 230 篇（均为连续堆叠大量前言等极端排布，规则无法满足）。
- 规则无法覆盖所有排布，失败时不应终止整条流水线。

### 44.2 改动

- 规则修复（`deck/plan.py::_groups`）：连续的前言（含三级小标题）与它们最终引出的内容成为同一组。未提升 `DECK_VERSION`，已生成的规划不会因此过期。
- 模型修复（新增 `deck/repair.py`）：规则三档分页仍不合格时，把**本章原文块、当前规划、校验给出的具体错误**交给文本模型，要求输出修正后的完整幻灯片列表；程序规整输出（重新编号、统计字数与时长）后用同一套校验检查；不通过则带着“最新一版规划 + 新的具体错误”再改，最多 `REPAIR_ATTEMPTS = 30` 次（安全上限，可随时停止）。
  - 校验标准不放宽：内容须原样出自原文、原文内容块全部承载、页面不只有标题或前言、前言不留页尾、条目不超上限（修复阶段按 12/12 校验，提示中建议每页不超过 8 条）。

### 45.3 R30 新方案排版：不再一味缩小，内容多时分两栏（已完成，2026-11-21）

原因：`deck/compose.py::page_state_images` 把每个元素都按「独占整页」的大字号各自渲染，裁掉留白后纵向堆叠；放不下就把所有位图**整体等比缩小**。因此一页元素多时文字被缩得很小（实测最低约 14px），而且从不分栏。

改动：
- 新增 `deck/layout.py`，排版顺序为：
  1. 单栏：按各元素自然高度的比例给出高度预算，二分搜索最大可行预算，让渲染器自己缩字号、换行；固定字号的元素（表格、金句、公式）按同一比例缩小字号基准后重新渲染（不缩放位图，保持清晰）；

### 45.5 R32 文字页整页网格排版（已完成，2026-11-21）

用户反馈：很多页明显分两列更好，却只显示一列、字特别小；没有充分利用屏幕；对齐不对劲，带重点句子（金句）的页尤其明显。

复现（测试文章渲染图）发现的问题，不是参数问题，而是结构问题：
1. 旧做法是「每个元素各自渲染成图 → 裁掉留白 → 居中堆叠」。元素宽度互不相同、各自居中，所以左边缘参差不齐；
2. 内容只占页面中间约 40% 的窄条，左右大片空白；字号被「元素各自占满整页」的前提和位图缩放压得很小；
3. 前言（「于是：」「今天：」）也占一整张卡片，一两个词的条目也占整张卡片；
4. 金句的引号与竖条悬在文字外面，不在对齐线上；
5. R30 的分栏只在元素之间切分，且只在字号低于下限时才尝试，所以绝大多数页仍是单栏。

新做法（新增 `deck/textlayout.py`，只处理文字类元素 keypoint / list / quote）：
- **占满页面**：内容区取页面宽度 88%（页标题同步改为与内容区左对齐，起点 6%）、标题以下的全部高度；
- **搜索而不是阈值**：字号从大到小（横屏 56→18px，竖屏 50→…），栏数 1–3，找到第一个能把全部条目放下的组合，即「能放下的最大字号」。栏数多了字号能更大时就自然分栏，不再要求「先缩到下限以下才分栏」；多栏时每栏至少约 9 个字宽；
- **栏内统一**：同一栏的条目同宽、同左边缘；要点是卡片、列表是编号行、金句是整宽强调底色 + 竖条的标注（不再悬在外面）；前言排成无卡片的强调色小标题，与后面的条目同栏、不拆开；文字按行中线对齐，卡片内上下对称；
- **顺序与均衡**：按元素顺序先左栏自上而下、再右栏；各栏按最小高度均衡，整体垂直居中；
- **逐个出现**：整页位置一次算定，每个状态只画已出现的元素，页面不会跳动；
- 含表格、流程、公式的页仍走 R30 的 `deck/layout.py`（这些元素是整块位图，暂不改）。
- `RENDER_VERSION` 升为 `deck-render-v3`；`deck_layout.columns` 开关继续有效（关闭则只用单栏）。

量化（测试文章 85 页，1920×1080）：
- 85 页中 68 页走网格排版（其余为含表格/流程/公式的页）；
- 最小实际字号：旧排版约 14px（R30 后约 26–28px）→ 现在约 34px；偏小页 0；
- 少量条目的页用 1 栏、最大 56px；条目多的页自动 2–3 栏，仍保持 40px 以上；
- 渲染全章 85 页（只算排版与出图）约 7 秒；不再反复二分渲染位图。

偏差与未做：
- 含表格、流程、公式的页还是位图堆叠，对齐与空间利用仍是 R30 水平，下一步可把它们也纳入网格（表格整宽置顶、流程独占一行，文字条目在其余空间分栏）；
- 强调词（emphasis）目前规划阶段不产生，网格排版也没有绘制强调着色；
- 竖屏参数按比例给出，未逐页目测；
- 单个很长的条目（超过一栏高度）不会被拆开，会降字号；规划阶段已限制每页条目与元素数量，实际未遇到。

### 45.6 R33 列表整体放一栏 + 语义连续的分页（已完成，2026-11-21）

用户反馈（样本：《从一个人的一生，到社会，到AI,再到整个宇宙》）：① 列表不要拆成左右两边；字少时在一边就能分栏显示；② 分页时注意语义连续，同一段内容尽量在同一页，避免一页末尾是另一页开头的标题。

**一、列表（`deck/textlayout.py`）**
- 一个列表是一个整体条目，只放在一栏内，不再按条目拆到左右栏；
- 栏内的列数按条目多少与字数决定：5 条及以下单列竖排；6–8 条 2 列；9–11 条 3 列；12 条及以上最多 4 列（行优先编号：1 2 3 / 4 5 6…）；子列宽度至少约 4 个字，且条目折行不超过 2 行；取高度最小者；
- 只有整个列表一栏也放不下时，才退回逐条排列（可跨栏）；
- 顺带修正：标点不再单独占一行（如“…人的寿命有限”下面孤零零一个“。”）。

**二、语义分页（`deck/plan.py`，规划版本升为 `deck-rules-v5`，已生成的规划需重新生成）**
用新文章规划发现的问题：「为什么？」与「因为：」被拆到两页；引语之后的「还有：」另起一页；一页只有 1 个元素的孤页；更隐蔽的是「# 语义带宽。」这类标题后面没有内容、直接接下一个标题，被当作空章节丢弃，而它前面的「但还有一个更加重要的问题：」被孤零零挪到下一章。
- **整节动态规划取代逐页贪心**：每节内以「组」（前言 + 引出的内容）为最小单位，用动态规划选分页点，最小化「页面空疏代价 + 断点代价」。页面容量不变（条目、字数、每页元素 ≤ 6）。
- **断点代价**：完整的金句 / 列表 / 表格 / 流程之后断开最便宜；以问句结尾（答案应紧随其后）、短过渡句之后、同一原文块中间（一段或一个列表被切开）、下一页以「还有 / 但 / 因此…」接续上文，代价都很高；避免只有一个元素的孤页；节的最后一页允许不满。
- **短问句是前言**：不超过 12 个字、以问号结尾的段落（如「为什么？」）视为前言，与后面的回答同组不拆。
- **空章节标题变金句**：一、二级标题后面没有任何内容就是下一个标题，且它前面是前言、或它本身是一句完整的话（以句末标点结束）时，把它作为金句放回正文流（与前言同页），不再新开页、不再丢失；「大标题紧跟小标题」这种真正的层级标题不受影响。
- 删除按页贪心装填与尾页合并（动态规划已覆盖）。

量化（新文章，同一章）：校验无错误无警告；「语义带宽。」回到「互联网极大地解决了通信带宽问题。」同一页；每页最多 6 个元素；单元素孤页 2 个；页数 90 → 94（R31 贪心分页 → 动态规划，孤页减少、页更均衡）。

验收：`tests/test_r33_semantic_pages.py`（10 项）；新增样本 `tests/fixtures/intelligence_article.md`。

偏差与未做：
- 只用启发式（问号、冒号、短句、接续词）判断语义，不调用模型；个别地方仍可能不理想。如果需要更好的语义分页，可以让文本模型在规划后复核分页点（可作为 R28 模型修复的延伸，默认关闭）；
- 一个小节若只有一句话（如「七、…」只有一句引入语）仍单独成页；
- 公式、表格、流程页仍用 R30 的位图排版。

### 45.7 R34 页面背景插图（方案；已确认并实施，实施记录见 45.8）

需求：PPT 模式也可以生成插图当背景，让视频更好看。现有基础：`providers/image.py`（agnes / stub、限流 `images.max_per_minute`、一图多用）、`render_illustration_background`（铺满、水平取景、压暗保证叠字可读）、视觉风格锚 `bible.style_anchor`、插图费用预算（`max_images` / G2 预算）。

设计（建议）：
1. **粒度**：按「节」生成背景（同一节的各页共用一张，用不同取景/压暗度区分），不按页生成：每页一张太贵、画面跳动；每章 3–8 张量级，沿用 `images.max_per_minute` 上限。
2. **提示词**：由文本模型根据「节标题 + 本节要点」写一个与主题相关的画面描述，并强制套用 `style_anchor`（不出现文字）；主体尽量取原文的具象类比；抽象内容用风格化的抽象背景。
3. **可读性**：背景压暗（默认 0.55）+ 卡片半透明，文字仍用网格排版；保证对比度；不放在内容区，只做氛围。
4. **默认关闭**（沿用「新功能保守默认」）；新增设置 `visual.deck_background.enabled`、`darken`；关闭时和现在完全一致。
5. **费用与缓存**：按提示词与风格锚的指纹缓存，改排版不重新生图；生图失败自动回退渐变背景并记录日志，不中断（符合「遇到问题自动处理」）。
6. **验收**：缓存命中不再生图；失败回退；压暗后文字对比度达标；节内多页取景不同；关闭时画面与 R33 一致。

需要你确认：① 按「节」共用背景是否可以（还是希望按页）；② 是否允许使用生图服务的费用（按每分钟上限）；③ 对没有 AI 生图 key 的情况，是否提供程序生成的几何/渐变背景作为替代（零费用）。

### 45.9 R35 分栏顺序修正（已完成，2026-11-21）

**问题**：列表与条目分栏时，内容左一个、右一个交替排列，不符合阅读习惯。原因：列表网格（R33）按行排（第 1 行 1 2 3，第 2 行 4 5 6），条目分栏（R32）按高度均衡装箱，二者都会左右交错。

**规则**：先填满左边，再填右边；按个数分栏，左栏最多比右栏多一个（靠左的栏多取一个）。

**改动**（`deck/textlayout.py`）：
- 新增 `_count_split(n, cols)`：按个数从左到右切分；替代原来的 `_balanced` 高度均衡装箱（已删除）。
- 列表网格：按列排（左列自上而下 1–4，右列 5–8），不再按行排。
- 条目分栏（一个页面内的要点、金句）：按个数切分；若某栏超过可用高度，则减小字号或增加栏数重算，不再为了高度均衡而打乱顺序。
- 渲染版本与分栏逻辑相关的版本号不变（列表与条目的排版位置有变化，但 `RENDER_VERSION` 仍为 `deck-render-v4`，已生成的章视频需要重新合成才会更新）。

**验证**：`tests/test_r35_column_fill_order.py`（3 项）：分栏切分的性质（顺序、左边最多多一个）；拆开的要点左栏序号全部小于右栏；8 条短列表为两列网格，左列 1–4、右列 5–8。另目视检查两张预览页（列表网格与要点分栏）顺序正确。受影响的 R32、R33、R34 测试通过。

**需要的操作**：已合成过的章节需要重新「合成」，排版才会更新。

### 45.10 R36 生图未生效排查与日志诊断（已完成，2026-11-21）

**现象**：生成的视频里没有 AI 图；生成过程中看不到任何调用生图的提示。

**原因分析**

1. **key 没找到，静默降级**。`providers/keypool.py` 只读环境变量 `AGNES_API_KEYS` / `AGNES_API_KEY`。而 mini_agent 的生图 skill（`.claude/skills/gen_image_with_text`，`novel_to_video` 也通过它生图）解析 key 的顺序是：环境变量 `AGNES_API_KEYS` → `providers.json`（`AGNES_PROVIDERS_JSON` 指定，或从 skill 目录向上查找）→ 环境变量 `AGNES_API_KEY`。用户的 key 在 `providers.json` 中、并未设置环境变量时，本项目取不到 key，`make_image_provider` 返回 `None`，插图与背景全部退回卡片或渐变，页面不报错。
2. **日志缺失**。生图提供者为 `None` 时，只有真正需要生图的那一步才写一条警告，且新方案背景的提示只在合成时出现；流水线开始时、分镜页与渲染入口都不说明“生图是否开启、用了哪个服务、key 从哪里来”；生图请求本身（尝试次数、限流切换、耗时）也没有日志，因此无法判断是“没调用”还是“调用失败”。
3. **构造入口分散**。流水线、分镜页（两处）、渲染命令行各自读设置、各自构造提供者，行为与日志不一致。

**改动**

- `providers/keypool.py`：`resolve_keys(env, start)` 按 skill 的顺序解析 key（与 skill 相同的 providers.json 结构：`providers.agnes.api_keys` / `api_key`，或 `llm_fallback_chain` 中 agnes 的 key；去重保序）。返回来源、数量与检查过的位置，**不返回 key 内容**。传入环境字典时只读该字典（测试确定性）。
- `providers/image.py`：
  - `image_diagnosis(name)`：provider、是否可用、key 数量与来源、检查过的位置；
  - `log_image_diagnosis(diag, enabled, scope)`：写入任务日志（“已开启，服务 agnes，N 把 key，来源 …”；未找到时列出检查过的位置；关闭时写明“已在设置中关闭”）；
  - `project_image_provider(pdir, scope)`：项目统一入口（读生效设置 → 诊断 → 写日志 → 构造提供者），替代各处重复的构造代码；
  - 生图请求日志：每次请求（模型、尺寸、参考图数、提示词字数）、限流切换（第几把 key）、非重试错误、失败次数、成功（用时、文件大小）；
  - 提供者 `describe()`：如 `agnes（模型 …，N 把 key，来源 …）`。
- 调用点统一改为 `project_image_provider`：流水线（`default_providers`）、分镜页（渲染本章 / 渲染全部）、命令行 `render_visuals`。
- 新方案背景（`deck/background.py`、`deck/compose.py`）：开始时写明“生图服务 …”或“生图服务不可用（…），本章各节使用渐变色”；未生图时写明原因（背景开关关闭 / 「启用 AI 插图」关闭）。
- `entrypoints/health.py`：新增 `agnes_image_key` 检查（默认不花钱，只检查 key 能否找到，并列出检查过的位置）；`health --probe-image` 才真正调用一次生图接口，用来确认接口能否正常使用。

**行为变化**

- 有 `providers.json`（即使没有设置环境变量）时，生图会自动启用，这与 `novel_to_video` 的行为一致。
- 之前“没有 key 就静默渐变”的行为保留，但现在日志会写明原因。

**验证**

- `tests/test_r36_image_key_diagnostics.py`（11 项）：环境变量优先；providers.json 与 skill 一致（去重、fallback 结构）；显式 `AGNES_PROVIDERS_JSON`；找不到时列出检查过的位置；传入环境字典不读磁盘；诊断不泄露 key；日志写入任务日志（未找到、检查过、已开启、已关闭）；生图请求日志（限流换 key、成功耗时）；`project_image_provider` 随设置开关变化；新方案背景日志。
- `health` 实测：沙箱中正确列出四个检查位置，并给出未找到的提示。
- 全量回归结果见交付说明。

**需要你确认 / 排查步骤**

- 运行 `python entrypoints/health.py`（或在界面运行流水线后看日志）：若出现“已开启，服务 agnes，N 把 key，来源 providers.json（…）”，说明生图已可用。
- 若仍显示“未找到”，日志中的“检查过”列表会给出实际查找的位置；把 `providers.json` 放到 mini_agent 仓库根目录，或设置 `AGNES_PROVIDERS_JSON` 指向它即可。
- `python entrypoints/health.py --probe-image` 会真实生成一张测试图（会计费一次），用于确认接口可用。
- 沙箱中没有用户的 `providers.json`，因此 providers.json 的读取只在单元测试（模拟仓库结构）中验证；真实 key 需要在你的环境中运行一次确认。

### 45.12 R38 新方案自动保证大纲（已完成，2026-11-21）

**现象**：批量队列选择新方案后，G3 挡位每篇都在第一步失败，报“请先确认大纲（C0），再运行新方案”，并按重试策略重试 5 次后记为失败。

**原因**：新方案的 `_parts()` 要求大纲已生成且已确认，但新方案流水线从不生成大纲；大纲只在旧方案的「大纲」阶段生成，且 G3 本应自动确认。批量队列导入的新项目没有大纲，因此新方案必然失败。

**改动**（`deck/pipeline.py`）：新增 `ensure_outline(pdir, gear, llm, now)`，在新方案规划之前执行，规则与旧方案的大纲阶段一致：

- 没有大纲：按生效设置生成（模型版或离线规则）；模型版但没有文本模型时报错；
- 已确认：直接通过；
- 挡位设有 C0 人工检查点（G0、G1）：返回等待原因，流水线停在「大纲」，等待在界面确认；
- 其余挡位（G2、G3）：自动确认（`confirm_spine`，未通过 V1 校验时失败并走重试）。

大纲的生成与确认写入任务日志，不计入流水线步骤（保持既有的步骤列表约定）。

**行为变化**：驾驶舱中的新方案在大纲缺失时，原来报“请先确认大纲”，现在会生成大纲；G0/G1 会停在大纲等待确认，G2/G3 直接继续。

**验证**

- `tests/test_r38_deck_outline_gate.py`（4 项）：缺失大纲时生成并在 G3 自动确认；已确认直接通过；G0 停在 C0 等待确认且不确认；模型版没有文本模型时报错。
- 新方案流水线既有测试（`test_deck_pipeline.py`、phase1–5）共 46 项通过；其中 G3 端到端用例最初因多记了一个步骤失败，去掉该记录后通过。
- 批量队列既有测试（R23 核心）与 R37 测试通过。

**未做（如实记录）**：没有对真实的批量队列做一次端到端运行（需要模型与生图 key），目前由单元测试覆盖大纲门控逻辑。

### 45.13 R39 批量队列显示每篇的详细运行日志（已完成，2026-11-21）

**现象**：批量队列运行时只看到队列层面的几行（开始处理、已创建项目、第 N 次失败），看不到流水线内部的详细步骤。

**原因**：
1. 批量运行器调用新方案的 `run_deck_pipeline` 时没有绑定项目日志上下文（`joblog.bind`），新方案内部所有 `bound_log` 写入都被丢弃。旧方案的 `run_pipeline` 自己绑定了，所以旧方案不受影响。
2. 批量运行器本身的启动日志（“本篇使用新方案/旧方案”）也因为同样的原因写不进项目日志（R37 的测试是在外层手动绑定后才通过的，掩盖了这个问题）。
3. 批量监控页只显示队列日志，没有显示当前正在运行那篇文章的项目日志。

**改动**

- `batch/runner.py`：`default_pipeline_runner` 统一用 `joblog.bind(pdir, scope)` 包住整个运行过程，新方案使用 `deck`，旧方案使用 `pipeline`（与各自方案的日志 scope 一致）。
- `ui/batch_page.py`：监控区在队列表格下方新增「当前文章的运行日志」，显示正在运行那篇的项目日志最近 160 条，随监控自动刷新（约每 REFRESH_SECONDS 秒）。
- 测试：`tests/test_r39_batch_item_logs.py`（2 项）：不做外层绑定时，新方案内部日志与启动日志都写入项目 `deck` scope；旧方案日志写入 `pipeline` scope。`test_r37_batch_scheme.py` 中合并版提示的断言改为检查 `deck` scope（旧测试依赖外层绑定，掩盖了问题）。

**验证**：R37、R38、R39 测试共 12 项通过；批量队列既有测试（R15、R23 各项）共 92 项通过。界面部分（日志区）通过代码审查确认，未做浏览器内的实际点击验证。
