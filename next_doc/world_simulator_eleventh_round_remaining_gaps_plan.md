## 1. 第一优先：验证债务（不是代码任务，是"实际跑一遍 + 记录结论"）

> 对应第九轮文档第 2 节。这三项本身在更早的
> `world_simulator_remaining_minimal_systems_gap_survey_plan.md`
> 第 2 节就已经提出，第九轮复核仍然成立，本轮是第三次被写进
> 待办——**如果本轮又不跑，建议至少在 PROJECT.md 里明确记一句
> "决定继续搁置，因为……"，不要让它变成第四次被无声地重复提醒**。

### 1.1 验证项 A：`belief_fields`/`beliefs`（State/Belief 分离）

**要验证的问题**：认知值（`beliefs`）是否真的会和真实值（`vars`）
产生有意义的偏差，还是 LLM 偷懒让两者长期保持一致，导致这个字段
形同虚设。

**怎么算验证过**：
1. 开一个已经声明了 `belief_fields` 的 `life_sim` 实例（或新建一个，
   在创建时声明至少 2~3 个认知型字段，比如"团队对项目成功概率的
   估计"这种主观性强、容易和客观进展脱节的字段）。
2. 实际推进 15~20 步，覆盖至少一次"客观情况和主观认知明显该分叉"
   的剧情转折（比如发生了一次隐藏风险爆发、或一次信息不对称事件）。
3. 检查历史记录：`beliefs` 字段的值和对应的 `vars` 字段是否在那次
   转折前后出现了有意义的差异（不是数值上的噪音，是方向性的、
   叙事能自洽解释的分歧）。
4. 记录结论到 `PROJECT.md`（或本文档"验证结论"占位区，见下）：
   - 如果确实分叉了：`belief_fields` 验证通过，可以考虑要不要把
     "认知与现实的落差"接入更多下游逻辑（比如作为 `problems` 自动
     扫描的一个信号来源——但这需要新开一轮设计，不在本文档范围内）。
   - 如果没有分叉（LLM 让两者一直相等）：需要判断是 prompt 没有
     明确要求 LLM 区分两者，还是这个概念本身对当前的模板场景
     价值有限；前者可以尝试改进 prompt 再验证一次，后者建议记录
     "验证不通过，暂不继续投入"，不要在没有额外证据的情况下就
     动代码。

### 1.2 验证项 B：Agent Preview（自动挡决策预览）

**要验证的问题**：这个功能是否真的帮用户提前发现了自动挡"要犯的
错"，还是用户很少点开看、或者看了也看不出问题。

**怎么算验证过**：
1. 开一个自动挡实例，运行前先打开 Agent Preview，记录预览展示的
   候选决策和理由。
2. 让自动挡实际推进那一步，对比预览内容和实际发生的选择/后续走向
   是否一致、预览是否提供了"如果不看预览就不会注意到"的信息
   （比如预警了一个明显不划算的选项即将被选中）。
3. 重复 5~8 次（不同步骤、不同剧情阶段），记录"预览提前发现问题"
   的命中次数。
4. 记录结论：命中率高、确实帮用户提前拦下过明显不合理的自动挡
   决策 → 验证通过，值得继续投入完善；命中率低或用户反馈"从不看"
   → 记录"验证不通过"，评估要不要简化甚至下线这个功能（不建议
   本轮就下线，先记录观察结论）。

### 1.3 验证项 C：独立推进因果线（`independent_line_advance`）

**要验证的问题**：允许某条因果线独立于主线推进，是否会导致"某条线
很久没动静、体验割裂"的问题。

**怎么算验证过**：
1. 开一个有多条因果线的实例（`branch_manager`/`causal_tree` 已经
   支持的场景），至少开出 2 条独立线，主线继续推进 10 步以上。
2. 检查：那 2 条独立线在主线推进期间是否被晾在一边太久（比如
   一条线开出来之后再也没有被提及/推进过，用户是否会感知到"割裂"）。
3. 记录结论：如果割裂感明显 → 需要考虑要不要加一个"提醒用户某条
   线太久没动"的机制（类似 1.3 节 desired_state 提示的思路，纯
   UI 提示，不强制自动推进）；如果没有明显割裂感（比如用户本来
   就是有意识地按需切换线）→ 记录"验证不通过担忧不成立，暂不
   需要额外机制"。

### 验证结论记录位置

三项验证做完后，把结论追加到本文档末尾新增的"验证结论"一节（先
占位，见文末），并同步一条 `PROJECT.md` 变更记录（哪怕结论是
"验证过，暂不需要改代码"，也要留痕，避免同一个问题被第四轮、
第五轮文档反复重新提出）。

### 2.1 `desired_state` 动态提示（对应第九轮 1.3 节）

**参考文档要求**（第九节）：理想状态不该是固定终点，应该随能力/
问题的变化而演化。

**做法**（第九轮文档已给出，本节直接采纳）：不自动改写
`desired_state`（这是用户的价值判断，代码不该替用户决定"理想
应该变成什么"），只做**提示**：`app.py` 在检测到"这一步
`capabilities_gained` 非空"或"某个 `problems` 状态变为
`solved`/`transformed`"时，在详情页顶部新增一条不打断流程的提示条
——"这一步出现了新能力/问题状态变化，要不要重新看看理想状态是否
需要调整"，点击跳转到"⚙️ 模拟设置"的 `desired_state` 编辑区。

**实现要点**：
- 判断时机：复用 `advance()` 返回的 `next_state`（`capabilities_
  gained`/`problems` 都是这一步落盘状态的字段，不需要额外查询），
  在 `app.py` 渲染详情页时对"当前展示的这一步"做一次轻量判断即可，
  不需要在引擎侧新增任何持久化标记。
- 提示条**只是建议**，不需要"已读/已处理"这种状态追踪（用户看到
  但没点，下一步继续满足触发条件时再提示一次是可以接受的，避免
  引入额外的"是否已提示过"持久化字段——这是本节故意的范围克制，
  不是遗漏）。
- 不判断"理想状态是否真的需要改"——任何非空 `capabilities_gained`
  或任何一条 `problems` 状态变化都触发提示，把"值不值得改"完全
  交给用户判断，代码不做启发式过滤（避免"过滤逻辑本身猜错、反而
  漏掉真正该提示的时机"这种更难排查的问题）。

**风险**：低——纯 UI 提示，不改任何数据结构或引擎逻辑。

**验收**：
- 单元测试覆盖"触发条件判断"这个纯函数（`capabilities_gained`
  非空 → True；某条 `problems` 状态是 `solved`/`transformed` →
  True；都不满足 → False），不需要测试 Streamlit 渲染本身。
- 人工验证：实际推进几步，触发一次能力/问题变化，确认提示条
  出现且能跳转到设置区。

### 2.2 Causal Engine 字段扩展：`delay_steps`/`magnitude`
### （对应第九轮 1.4 节）

**参考文档要求**（第十七节）：因果引擎应该能描述"延迟多久生效、
影响幅度多大"这类信息。

**项目既有取舍（第九轮文档已明确，本节继承）**：不做真正的传播
计算引擎（这是远超当前项目定位的研究课题），只做"让记录更接近
参考文档设想"这一层——字段扩展 + 展示层区分，不做计算。

**做法**：
1. `causal_links` 每条记录新增两个可选字段：
   - `delay_steps`：这条因果关系从 cause 到 effect 隔了几步生效
     （整数，选填），同 `relationship.py` 已有的 `delay_steps`
     字段风格保持一致（复用同一个字段名，语义类比）。
   - `magnitude`：自由文本定性描述（"轻微"/"明显"/"剧烈"这类，
     不做量化、不限定取值集合，同 `reversibility` 一贯的"不认识
     的取值原样保留"取舍一致）。
2. `causal_graph.py` 的图视图（`_causal_graph_edges_to_dot()`）
   给 `delay_steps` 非空的边加一个不同线型（比如 `style="dashed"`
   表示"延迟生效"），帮助用户在看图时区分"即时影响"和"滞后影响"。
   这一步直接复用第十轮批次三 `_problem_graph_edges_to_dot()`
   刚验证过的"纯函数 + DOT 字符串拼接"模式，改动 `_causal_graph_
   edges_to_dot()` 内部的边生成逻辑即可，不需要新函数。
3. `workflows/` 下涉及生成 `causal_links` 的 prompt（因果链相关
   的 workflow yaml）补一句：如果能判断出来，顺带给这两个字段，
   判断不出来留空，不强行编造——措辞风格同第十轮批次二对
   `problem_discovery.yaml` 的改法。

**范围克制**：不做任何基于 `delay_steps` 的自动调度/提醒（比如
"这条延迟因果关系还有几步生效，到时提醒用户"）——这会让"记录"
变成"引擎逻辑"，超出本节范围；这类需求如果将来真的出现，应该
另开一轮方案讨论，不在字段扩展这一步顺带做。

**风险**：低——纯字段扩展 + 展示层线型区分，不碰引擎主循环。

**验收**：
- 单元测试覆盖字段的默认值（缺省时不出现在解析结果里）、透传
  （给定值时原样保留）；`_causal_graph_edges_to_dot()` 新增测试
  覆盖"`delay_steps` 非空的边使用虚线、为空的边使用默认线型"。
- 旧数据兼容性：`causal_links` 缺失这两个字段时展示/解析都不报错
  （历史 `causal_links` 目前是自由字典透传存储，天然兼容，同第十轮
  批次二 `problems` 字段的既有结论一致，不需要额外迁移代码）。

### 2.3 Capability 九段生命周期字段：`maturity_stage`
### （对应第九轮 1.2 节，批次一）

**参考文档要求**（第十二、十三、十六节）：技术/能力应该有阶段性
生命周期（不可行→实验室可行→专家可用→开发者可用→普通用户可用→
成本足够低→大规模应用→基础设施化→社会常态化），而不是一个百分比
成熟度。

**做法**：
1. `capabilities_gained[]` 新增可选字段 `maturity_stage`，取值
   限定为参考文档九段中的一个精简枚举（同项目一贯"精简子集，不
   照搬全部术语"的取舍，类比 `problems.status` 只取四段而不是
   参考文档完整九段生命周期）：`"lab"`（实验室可行）/`"expert"`
   （专家可用）/`"developer"`（开发者可用）/`"consumer"`（普通
   用户可用）/`"cheap_at_scale"`（成本足够低、可大规模应用）/
   `"infrastructure"`（基础设施化，含"社会常态化"，不单独区分
   最后一段——两段界限在叙事层面很难清晰区分，合并成一段更符合
   "不认识的取值原样保留、不强行精确分类"的既有风格）。允许 skill
   在同一项能力被反复提及时更新它的阶段（即同一实例历史里，同名
   能力可能在不同步骤有不同 `maturity_stage`，取最新一次即可，
   同第十轮批次三 `problems.status` "按 id/名称去重、保留最新
   状态"的处理方式一致）。
2. **不做**自动阶段推进算法——阶段变化仍然完全由 LLM 在叙事里
   体现、由 skill 声明，代码只做存储和展示，不做"满足什么条件就
   自动升级到下一阶段"的判断（同 `problems.status` 的既有取舍
   一致，不引入这个项目一直刻意回避的"规则引擎"）。
3. `app.py` 新增一个按能力名称分组、展示 `maturity_stage` 时间线
   的只读视图——复用第十轮批次三"按 id/名称去重、取最新状态"和
   "遍历历史收集节点"这两个刚写过的函数模式（`_collect_problem_
   graph_nodes()` 的姐妹实现，命名可以是 `_collect_capability_
   maturity_timeline()`），展示形式可以比问题关系图更简单——不需要
   graphviz 连边，一个能力一行、按 `maturity_stage` 出现顺序列出
   即可，不需要引入新的可视化库。

**风险**：低偏中（字段扩展 + 新展示逻辑，不碰引擎主循环，但涉及
"按能力名称做历史归并"这个此前没有过的聚合维度，需要考虑能力
名称在不同步骤措辞不完全一致时怎么处理——**建议做法**：按
`capabilities_gained[].name`（如果该字段目前叫别的名字，以实际
代码字段名为准）做精确字符串匹配去重，**不做**模糊匹配/语义归并
（"新能力 A"和"能力 A（升级版）"会被当成两个不同的能力展示，这是
刻意的，交给用户自己判断是否是同一个能力在演进，代码不做自动
归并判断）。

**验收**：单元测试覆盖字段透传/默认值缺省、按名称归并取最新阶段
的聚合函数（同批次三 `_collect_problem_graph_nodes()` 的测试
风格）；旧数据兼容（历史 `capabilities_gained` 缺失该字段不报错）。

### 2.4 能力清单接入决策生成 prompt（对应第九轮 1.2 节，批次二）

> **本文档改动面/不确定性最大的一项，第九轮文档明确建议放在最后，
> 且先小范围验证"喂能力清单是否真的提升选项质量"，不理想就退回。
> 本节保留这条建议，不因为写文档方便就调整顺序。**

**做法**（第九轮文档已给出）：`engine/advance.py` 组装下一步
prompt 时，把当前活跃分支历史里 `capabilities_gained` 的累计
列表作为一段"已获得能力"上下文喂给生成 `options` 的 prompt，
明确要求 LLM"候选行动应该体现已获得能力带来的新可能性，而不是
忽略它们"。**不是**代码层面强制"有能力 X 就必须出现选项 Y"，只是
把此前只存在于展示层的信息接入决策生成的输入侧。

**建议的验证节奏**（不同于前面几节可以直接实施，这一节建议分两步）：
1. 先在一个测试实例上人工对比"喂能力清单前后，生成的候选选项是否
   真的体现了已获得能力"——如果 LLM 本来就经常自然而然地用上
   已获得能力，这一步的边际价值可能有限；如果确实有明显改善，
   再进入第二步。
2. 确认有价值后，再接入 `engine/advance.py` 的正式 prompt 组装
   逻辑，同时写回归测试确认"没有 `capabilities_gained` 累计记录
   时（新实例/还没获得过能力），prompt 组装行为与改动前完全一致"。

**刻意不做的部分**（第九轮文档已明确，本节继承）：不做"能力→可选
行动"的结构化自动映射表（这本质上是回到参考文档批评的"技术树"
思路，只是换了个名字）。

**风险**：中——改动面涉及 `engine/advance.py` 的 prompt 组装
逻辑，属于"影响每一步推进结果"的核心路径，不是纯展示层扩展，
需要先有人工验证支撑再决定要不要正式接入。

## 3. 明确不建议现在做的部分（原样继承第九轮文档结论）

### 3.1 制度/组织/技术协同演化（对应第九轮 1.5 节）

**结论不变**：没有真实场景需求。现有三个模板（life_sim/
group_evolution/negotiation）都不是以"制度设计"为核心场景的
模板；参考文档自己也承认这是"开放世界"阶段（第六十四节）才需要
的复杂度，MVP 阶段（第六十一节）明确说"不要一开始就模拟整个
世界"。**触发条件**：等某个新模板明确需要"多个主体的制度性协作/
冲突"这个场景时，再回头评估要不要把"制度"提升为独立概念。

### 3.2 Fact/Hypothesis 类型标签（对应第九轮 1.6 节）

**结论不变**：边际价值低于前面几项。`KnowledgeItem` 的
`confidence` 连续值已经能回答"这条知识现在有多可信"这个核心
问题，额外加一个离散 `kind` 标签主要是"分类展示更直观"。**如果
