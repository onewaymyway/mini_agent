## 3. 关键实现与决定
| 事项 | 做法 | 理由 |
|---|---|---|
| 缺口检测 | 全部规则；每条缺口有稳定的 `key`（类型:主体） | 可审计；同一缺口跨轮次可识别，用于去重与拒绝记录 |
| 候选生成 | 模板（标题、类型、层级、必须覆盖、互链）；标题不经模型润色 | 方案 §6.2 的“LLM 只负责润色”未做，见第 5 节 |
| 概念重叠 | 候选的必须覆盖概念 vs 每篇已摘要文章的概念集合，取最大 Jaccard | 方案 §6.3 |
| 中等区间 | 0.3 ≤ J < 0.6 交模型逐条判断（批量，结果必须覆盖每个 id）；无模型则保留并标记“未判重” | 方案 §6.3 中间区间交 LLM；无模型时不静默丢弃 |
| 标题相似 | 字符二元组 Jaccard ≥ 0.7 剔除，与已有标题及队列中待办标题比较 | 防止换个说法重复提议 |
| 打分 | `value = severity × (1 + min(links,5)/5) × min(1, 0.5 + 0.1·links) − max(重叠)` | 方案 §6.3 公式的可取证度用库内文章数估计 |
| 预算 | 每轮新增 ≤ `budget.max_topics_per_cycle`，超出的记入“超出每轮上限” | 方案 §9 硬上限 |
| 自动放行 | 仅当挡位为 G2/G3 且 `auto_approve` 为真；历史中记录“自动放行” | 方案 §9 挡位表 |
| 状态机 | 转换表固定；拒绝必须有原因并写入拒绝记录；终态不可再转 | 方案 §6.4 |
| 开放命题 | 默认关闭；输出的节点必须是已有主题、类型与层级合法、必须覆盖非空；经过同样的去重与范围过滤 | 方案 Q11 |

## 5. 在 P2 代码中发现并修复的缺陷
**现象**：`build_wiki --force` 只重写概念定义，关系与冲突仍然命中缓存。测试 `test_planning` 中，先构建（无关系）再用新模型配置构建（期望出现关系），结果仍然没有关系。

**原因**：P2 的关系与冲突缓存只按“文章内容哈希 + 概念对”判断，`force` 没有被传入这两个步骤。这违背了方案 §5.2 中“--force 全部重做”的语义。

**修复**：`force=True` 时关系与冲突也忽略缓存；新增回归测试 `test_force_bypasses_edge_and_conflict_caches`。这一改动影响 P2 的行为，但只在 `force` 时生效，常规增量行为不变。

## 6. 与方案的偏差 / 未做
- **G5 没有专门的自动化测试**：测试库中所有文章都是入门级，无法触发该缺口；代码路径已写，但只能靠手工在真实库中验证。
- **标题与角度未经 LLM 润色**：方案 §6.2 允许润色，首版用模板。
- **G6 的“外部新进展”部分未实现**：需要 info_hub 信号，按方案 §10 计划为后续可选项。
- **可取证度是估计值**：只按库内提及文章数估算，尚未检查网络来源（P5 再校准）。
- **“已放弃”（dropped）状态未有自动转换**：状态机中已定义，但目前只能手动放弃（通过 `reject`）；“预算/证据不足自动放弃”属于 P5/P7。
- **看板没有批量放行**。
- **中等区间判重的阈值（0.3/0.6）与标题阈值（0.7）是首版默认值**：方案 §21-7 要求用 20 篇样本校准，尚未做。
