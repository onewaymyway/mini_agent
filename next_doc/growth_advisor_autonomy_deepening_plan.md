## 0. 这份文档解决什么问题

`docs/growth-advisor-guide.md` 1.5 节记录了一条与用户明确讨论确认过的
定位："成长顾问应该自主根据用户需求规划成长方向，并在用户选择的方向
上自主、持续地收集整理素材供用户学习"。2.12 节的"采纳即启动"是这条
理念在当前版本的第一次落地：把"采纳"和"自动开始持续调研"绑在了一起。

但"采纳即启动"只解决了"链路要不要自动衔接"这一个维度。对照 1.5 节列出
的四条约束（采纳是起点不是终点 / 持续不能原地打转 / 素材要能沉淀成
可学习的东西 / 自主不等于替用户做主）逐一检视现状，还有多处明显差距。
这份文档系统梳理这些差距，按 1.5 节的四条约束分组，并给出可执行的
改进方向、优先级和实施顺序建议——是"已识别但尚未实施"的规划文档，
不是这次就要全部做完的任务清单，具体哪几项进入下一轮实施，由后续
单独排期决定。

**这份文档本身不引入新的执行代码**，只做方向梳理，方便后续按需认领。

## 1. 现状差距总览（按 1.5 节四条约束分组）

| 分组 | 现状问题 | 对应方向 |
| --- | --- | --- |
| A. 采纳应是起点不是终点 | 报告刷新仍是人工触发，跟 Goal 周期性推进是两套并存机制；回访机制在 Goal 停滞时只会"发问卷"而不会自诊断；对齐分析发现的"有兴趣但没建 Goal"仍要逐个手动 adopt | 方向 A1/A2/A3 |
| B. 持续不能原地打转 | `per_cycle_criteria` 完全依赖人工审阅，没有自动的重复度校验；没有"饱和度"概念，一个方向可以无限期每天空转；相近主题之间没有去重/关联 | 方向 B1/B2/B3 |
| C. 素材要能沉淀成可学习的东西 | wiki 页面只会线性追加，轮次一多就失去结构；用户没有"这周新增了什么"的轻量摘要，只能整页翻看 | 方向 C1/C2 |
| D. 自主不等于替用户做主 | 看板看不到"哪些方向正在被自主推进、进展到哪一步" | 方向 D1/D2 |

## 2. 方向 A：把"采纳即启动"延伸到其余人工衔接点

### A1. report/refresh 与 Goal 周期性并轨

**现状**：2.4 节（P4-4）的 `reports_needing_refresh()` / 看板"🔄 刷新"
按钮，是候选**没有**关联 Goal 时"要不要重新生成报告"的机制；2.12 节的
`growth_pursuit` 模板则是候选**已经**关联 Goal 后"每天自动往 wiki 页面
追加素材"的机制。两者本质上回答的是同一个问题（"这个方向的素材是不是
该更新了"），现在却是两套并存的、概念不完全对齐的系统——一个候选一旦
被自动落地成 Goal（`auto_pursue_on_accept` 默认开启后，这会是大多数
候选的归宿），report/refresh 这条路径实际上就不再需要了，但代码和 UI
都还留着，容易让用户搞不清"我该看报告刷新提示，还是看 Goal 的执行
进度"。

**改进方向**：
- 候选一旦有 `linked_goal_id` 且该 Goal 处于 `recurring=True`，
  `reports_needing_refresh()` 直接跳过这个候选（它的"刷新"已经由
  Goal 周期性执行接管），看板的"值得刷新"列表天然收敛为"还没有走上
  自主持续调研这条路的候选"。
- 长期看，report/refresh 应该被视为"没有 Goal 时的简化版持续调研"，
  而不是一个独立概念；是否值得把 `generate_growth_report()` 的模板
  质量改进（阶段 1~4，见 `growth_advisor_research_quality_plan.md`）
  也复用到 `growth_pursuit` 模板每一轮的正文生成上（外部资讯摘录、
  两段式生成、来源标注、忽略原因驱动调整），是一个自然的后续合并点。

### A2. Goal 停滞时先自诊断，而不是直接发问卷

**现状**：2.9 节阶段 C 已经做到"回访优先看 Goal 真实状态"——Goal
停滞时展示回访卡片，问法是"这个方向对应的目标看起来有一阵没动了，
要不要先放一放，或者重新规划一下？"。这仍然是把"怎么办"整个抛给
用户决定，没有先尝试自己判断"为什么停了"。

**改进方向**：Goal 停滞的原因粗略可以分成几类，值得先自动区分：
- **执行失败类**（LLM 调用异常、cron job 被 disable、执行规范生成
  失败导致 Goal 循环没有真正跑起来）——这类是系统自身的问题，理论上
  应该自愈或至少不需要用户在"要不要继续"这个层面做选择，而是需要一条
  独立的"自动重试 / 报错提醒"通路。
- **素材饱和类**（周期性任务本身在正常跑，但 `growth_pursuit` 模板
  连续多轮的增量很薄，见方向 B2 的"饱和度"信号）——这类才是真正需要
  用户决策"要不要降低频率/告一段落"的场景，回访卡片应该只在这类场景
  下出现，并且问法可以更精确（"最近几轮新增的内容不多了，是这个方向
  已经了解得差不多，还是希望我换个角度继续挖？"），而不是笼统的"有一阵
  没动了"。
- 需要先有方向 B2 的饱和度信号落地，这里的"自诊断"才有区分"失败"和
  "饱和"的依据，因此 A2 依赖 B2，实施顺序上 B2 应该先行或同批。

### A3. 对齐分析发现的方向支持批量落地

**现状**：`/growth align`（2.9 节阶段 A）能找出"有兴趣信号但没建
目标"的方向列表，但只是展示，落地还是要对每一条分别调用 accept +
（如果 `auto_pursue_on_accept` 关闭）adopt_goal。

**改进方向**：给对齐分析结果里的"未匹配兴趣"列表加一个批量操作
入口（CLI `/growth align --adopt-all` 或看板的"全部采纳"按钮），
复用已有的 `auto_pursue_candidate()`，对列表里的每一项分别调用。
需要注意节流：这类批量操作一次性会触发多个 LLM 调用（生成报告 +
生成执行规范），应该复用 `max_reports_per_run` 类似的每次上限，
不能无限制一次性全部触发，避免"批量"变成一次意外的成本爆炸。

## 3. 方向 B：让"持续"真正意味着往深走，而不是原地打转

### B1. 增量质量的自动校验

**现状**：`growth_pursuit` 模板的 `per_cycle_criteria` 目前全部是
`verification_method: "manual_review"`——校验是否有实质增量完全依赖
人工审阅，如果没人去看，一个 Goal 可以连续很多轮产出高度重复的内容
而不会被发现。

**改进方向**：
- **规则式初筛（零成本，优先做）**：每轮产出落盘前，做一次轻量的
  文本重叠度检查——比对本轮新增内容跟上一轮 `handoff.covered_
  subtopics`/`last_source_urls` 的重合程度（简单的关键词/URL 集合
  交集即可，不需要 embedding），重合度超过阈值时标记为"疑似低增量"，
  计入诊断面板，不强行拦截（避免误伤真正需要复述背景的场景），但
  给用户一个可见信号。
- **LLM 复核（opt-in，第二步）**：对被规则式初筛标记的轮次，可选
  再调一次 LLM 做语义级别的"这一轮相比上一轮是否有实质推进"判断，
  连续 N 次被判定"低增量"时触发方向 B2 的饱和度信号。这条路径应该
  像 2.11 节 `tech_radar.quality_feedback_enabled` 的设计一样，是
  独立的、默认开启但零强制拦截的诊断反馈闭环，而不是新增一个会阻塞
  执行的强校验（"持续调研"整体应该保持容错，偶尔一轮质量不高不该
  让整条自动链路卡住）。
- 这两步都应该复用 2.11 节已经验证过的模式：**连续低质量触发冷却/
  降级，而不是拉黑**——避免"这个方向永久不再更新"这种一次性判死刑
  的结果。

### B2. 饱和度信号：知道什么时候该"慢下来"

**现状**：`auto_pursue_candidate()` 绑定的周期性执行没有任何自动
停止或降频机制，一个方向一旦开始自动推进，会按固定节奏（默认每天）
无限期跑下去，即使这个方向的可挖掘素材已经基本讲完。这既是对 LLM
成本的浪费，也违背"持续不等于无限空转"这条约束。

**改进方向**：
- 复用方向 B1 产出的"每轮是否有实质增量"信号，累计一个简单的
  **饱和度计数**：连续 N 轮（比如 3~5 轮）都被判定为低增量，标记
  这个 Goal 进入"疑似饱和"状态。
- 疑似饱和不代表自动停止（自主不等于替用户做主，见 D 组约束）——
  而是触发一次**主动降频建议**：看板/通知提示"这个方向最近几轮新增
  内容不多，要不要把频率从每天改成每周，或者先告一段落？"，用户
  选择后系统据此调整 `schedule` 或调用 `stop_goal_recurrence()`。
  这也是 A2 依赖 B2 的地方——回访卡片的触发条件应该从"单纯停滞"细化
  为"疑似饱和"，问法也应更具体。
- 需要一个新的轻量状态字段记录"连续低增量轮次数"，建议直接放进
  Goal 执行规范的 handoff 数据里（每轮更新），不需要新开一份持久化
  文件——对齐"复用已有存储位置，不为单一功能新增文件"的既有取舍
  （参见 `growth_advisor_research_quality_plan.md` 的类似决定）。

### B3. 相近主题的去重/关联提示

**现状**：多个候选各自独立走完整条"信号扫描 → 候选 → 采纳 → 自主
持续调研"流程，即使两个方向语义上高度相关（比如"数据分析"和"数据
可视化"），也会各自开一条独立的周期性任务、各自维护一份 wiki 页面，
互不知晓对方的存在。

**改进方向**：这是四个方向里工作量最大、也最容易过度设计的一项，
`growth_advisor_research_quality_plan.md` 在"非目标"里已经明确把
"跨候选知识复用"列为需要先有主题相似度判断能力的独立工作，本方案
延续同样的判断——**不在本轮规划的优先实施范围内**，先记录问题，
留待后续单独排期时再决定具体做法（关键词重叠的粗筛 vs 引入轻量
embedding 都可能是候选方案，取决于届时的实际候选数量规模是否值得
投入）。

## 4. 方向 C：让素材真正沉淀成"可学习"的东西

### C1. 定期整理：从"线性追加"到"结构化沉淀"

**现状**：`growth_pursuit` 模板要求"追加到同一份 wiki 页面，不要
每轮新建一份报告"，这解决了"素材不衔接"的问题，但轮次一多，页面会
变得越来越长、缺乏组织——用户真正打开页面学习时，体验未必比"多份
独立报告"更好。

**改进方向**：引入一种特殊轮次——每累计 `reorganize_every_n_cycles`
（建议默认 10 轮左右）轮，下一次执行时在模板里额外注入一条指令：
"这一轮除了新增内容，先对现有页面做一次重新组织：合并重复表述、
按子话题分节、把 `open_questions` 里已经解决的问题移出"。这仍然是
同一个执行循环里的一种特殊模式，不需要新增独立的 cron job 或数据
结构，只是 `_append_execution_spec_context()` 拼接给模型的上下文
在满足轮次条件时多一段说明。

### C2. 轻量的"本轮新增摘要"推送

**现状**：用户想知道"这个方向最近有什么新进展"，只能自己打开 wiki
页面通读，没有"这周新增了什么"这类摘要。

**改进方向**：复用 2.4 节已有的推送节流机制（`notification_
frequency` / `notification_max_per_day`），把"某个正在自主推进的
方向本轮新增了什么"也纳入可推送的内容类型之一，而不是新增一套独立
的通知逻辑——具体做法是每轮执行结束后落一条"本轮摘要"（可以直接是
`handoff` 里新增的 `covered_subtopics` 差集 + 一两句话概括），按
用户已经配置好的推送节奏批量呈现，不额外增加打扰频率上限。

## 5. 方向 D：自主要让用户看得见、控制得住

这是 1.5 节明确点名"尚未完全做到"的部分，也是投入产出比最高的一项——
不需要新的 LLM 调用或复杂算法，主要是信息已经存在（Goal 的 recurring
状态、cron job 的 next_run_at、wiki 页面内容、handoff 数据），缺的是
把它们组织到用户能一眼看懂的界面里。

### D1. 成长顾问 tab 内的"正在自主推进"总览

**现状**：已采纳候选如果关联了 Goal，看板目前只在"📄 查看调研报告"
折叠区里显示一行"🔄 已落地为 Goal（xxx），成长顾问正在按此方向自主
持续调研"，用户想看具体进展（第几轮、下次什么时候跑、当前 wiki 页面
写了什么）还是要跳到「🎯 目标」tab，需要理解 Goal/Cron 的内部机制。

**改进方向**：
- 在成长顾问 tab 新增一个"🔄 正在自主推进"分区，列出全部
  `linked_goal_id` 非空且对应 Goal `recurring=True` 的候选，每条
  直接展示：方向标题、当前轮次（可以从 cron job 的 `run_count`
  取）、下次执行时间（`next_run_at`）、最近一次执行状态（成功/失败/
  跳过）。
- 点开某一条，直接展示当前 wiki 页面内容摘要（复用 2.4 节风格的
  正文渲染）和最近几轮的 `handoff`（`covered_subtopics` 增长轨迹），
  不需要用户理解"这背后是一个 Goal + 一个 cron job"这件事——对用户
  暴露的心智模型应该始终是"成长顾问在帮我调研 X"，不是"我的目标
  管理里有一个周期性任务"。
- 这一项需要新增一个聚合查询（跨 GrowthBacklog + GoalBacklog +
  CronScheduler + 执行规范 handoff 数据），建议做成一个新的只读 API
  端点（`GET /v1/growth/pursuits`），复用各自现有的数据源，不新增
  持久化。

### D2. 成长顾问 tab 内的就近暂停/调整入口

**现状**：暂停一个正在自主推进的方向，要去「🎯 目标」tab 对相应
Goal 调用 `unrecur`，成长顾问自己的界面里没有任何"暂停这个方向"的
入口——这跟"用户随时能暂停"的理念有落差：不是做不到，而是操作路径
绕远了，容易让用户误以为"停不下来"。

**改进方向**：在 D1 新增的"正在自主推进"列表里，每一条直接带
"⏸ 暂停"/"▶ 恢复"/"⚙ 调整频率"三个操作，分别调用已有的
`stop_goal_recurrence()` / `make_goal_recurring()`，不需要新的
后端能力，只是把已有的 Goal 管理能力就近暴露到成长顾问的界面里，
对齐"用户应该以成长顾问的心智模型操作，而不是被迫理解 Goal/Cron"
这条原则。

## 6. 优先级与实施顺序建议

按"离理念缺口最大 / 投入产出比"排序，供后续排期参考（不代表本文档
本身要一次性做完）：

1. **D1 + D2（看板可见性 + 就近控制）**——纯信息组织 + 复用已有能力，
   不涉及新算法，是 1.5 节唯一被明确点名的未完成项，优先级最高。✅ 已
   实施（`docs/growth-advisor-guide.md` 2.13 节）。
2. **B1（增量质量自动校验）**——不做的话"持续调研"容易在用户看不到
   的地方悄悄退化成低质量重复输出，侵蚀"素材可学习"这条核心承诺。✅
   已实施（2.13 节）。
3. **B2（饱和度信号）**——依赖 B1 的产出，同批或紧随其后实施；是
   "持续不等于无限空转"这条约束的直接落地，也是成本节制哲学的自然
   延伸。✅ 已实施（2.13 节）。
4. **A2（Goal 停滞自诊断）**——依赖 B2 区分"失败"和"饱和"两类停滞
   原因，放在 B2 之后。✅ 已实施（2.13 节）。
5. **A1（report/refresh 并轨）**——概念收敛，不新增能力，可以独立
   于其余项、随时插入实施。✅ 已实施（2.13 节）。
6. **C1 / C2（定期整理 / 新增摘要推送）**——用户体验的进一步打磨，
   优先级低于"先保证增量质量和可见性"这两个更基础的问题。✅ 已实施
   （`docs/growth-advisor-guide.md` 2.14 节）。
7. **A3（批量落地）/ B3（跨主题去重）**——工作量和收益都有较大不
   确定性（A3 涉及节流细节需要谨慎设计，B3 明确留待后续单独评估
   规模是否值得投入），排在最后，且不承诺进入下一轮实施范围。仍待
   实施。A3 已实施（`docs/growth-advisor-guide.md` 2.15 节）——批量
   落地本身按方案要求做了节流（单次最多处理
   `goal_alignment_adopt_all_max_batch` 条），复杂度可控；B3 仍暂缓。

## 7. 与既有设计哲学的一致性检查

延续 `growth_advisor_research_quality_plan.md` 等既有方案文档的
惯例，逐条对照检查这些方向是否偏离整套机制一贯的设计取舍：

- **默认克制、增强 opt-in**：本文档里除 D1/D2（纯信息展示，无成本）
  外，其余涉及新增 LLM 调用的部分（B1 的 LLM 复核、方向 A3 的批量
  触发）都应该延续"规则式路径优先、LLM 增强作为 opt-in 补充"的既有
  取舍，不应该因为"自主"这个定位就默认开启更多 LLM 调用——2.12 节
  已经明确 `auto_pursue_on_accept` 是"少数默认开启的例外，因为它本身
  就是自主定位的直接体现"，这个例外不应该被滥用来给其余增强能力也
  默认开启找借口。
- **失败尽力而为，不阻塞主链路**：B1 的增量校验、B2 的饱和度判断都
  应该是诊断性质，校验/判断本身失败时不应该阻止这一轮内容正常落盘，
  对齐 `auto_pursue_candidate()` 现有的"任一步骤失败不影响已完成
  部分"的容错设计。
- **用户始终有最终决定权**：B2 的降频建议、A2 的自诊断结果都只是
  "建议"，不自动执行"停止"或"降频"这类会改变用户已经做出的选择的
  动作——这是 1.5 节"自主不等于替用户做主"最直接的检验点，任何时候
  实现细节偏向"系统自己决定"，都应该先回头对照这一条。
- **复用已有存储位置，不为单一功能新增文件**：B2 的饱和度计数放进
  执行规范 handoff、C2 的推送复用现有推送节流机制、D1 的聚合视图
  不新增持久化，均延续这条取舍。
