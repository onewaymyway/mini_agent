## 一、定位

一个独立于小说创作项目的「构思项目」：用来交互式地把一个模糊的念头打磨成结构化的**构思包**（灵感、题材卖点、核心命题、世界观、主要角色、剧情骨架、备选方案）。构思包定版后，可以一键创建对应的小说创作项目，作为新书的种子输入。

它不写正文，不生成章节，也不替代现有流水线。

## 二、与现有功能的关系（边界要清楚）

| 已有功能 | 位置 | 关系 |
|---|---|---|
| 新建向导（intake） | 新建小说时的一张表单 | 保留。构思包的 `brief` 直接映射到 intake 的字段，作为新书的起点 |
| 构思审核（ideation_review） | 小说内部的检查点 | 保留。它审的是小说自己的构思产物，不是这里的 |
| 构思修订（concept_revision） | 小说内部，按新思路改写产物 | 保留。构思工作室做的是「开书前」的修订，修订在小说内部做的是「开书后」的修订 |
| 灵感箱（idea-catcher） | 小说内部，写作中记录与评估灵感 | 保留。它面向已经写到某一章的灵感，新工作室面向「还没开书」的灵感 |

结论：新增的是**上游**，不替换任何现有功能。

## 三、产出什么（构思包的结构）

构思包是一个带版本的目录，人类可读（Markdown）与机器可读（JSON）并存，两者由同一份数据生成。

| 模块 | 文件 | 内容 | 形态 |
|---|---|---|---|
| 灵感池 | `ideas.json` | 每条灵感：原文、标签、来源（作者/AI 发散）、状态（保留/搁置/丢弃/已采用） | 列表 |
| 题材与卖点 | `brief.json` | 与 intake 字段对齐：题材、主题、平台、主角、欲望、障碍、冲突、结局倾向、参考风格 | 字段表 |
| 核心命题 | `premise.md` | 一句话 logline + 三段式扩展（是什么、为什么有张力、读者得到什么） | 短文 |
| 世界观 | `world.json` + `world.md` | 规则卡（硬约束与代价）、地理、势力、历史时间线、禁忌 | 结构化卡片 |
| 主要角色 | `cast/<id>.md` + `cast.json` | 每人：定位、想要 / 需要 / 缺陷 / 谎言、弧光起止、与他人的关系 | 一人一卡 |
| 剧情骨架 | `plot.json` + `plot.md` | 三幕或五幕的关键转折点、悬念线、可选的反转、结局候选 | 节点列表 |
| 备选方案 | `options/<n>/` | 对同一个模块的多种走向（例如两种结局），含优缺点对比 | 分支 |
| 开放问题 | `open_questions.md` | 尚未决定的事，作者可随时关闭 | 清单 |

**为什么这样切分**：每个模块恰好对应现有小说流水线里的一个消费点（brief → intake；world → build_world；cast → 人设卡；plot → 蓝图的输入）。这样交接时不需要重新整理格式。

## 四、如何和用户交互

### 4.1 三种工作状态

1. **对话区**：自由交流，每轮用户输入与 AI 回复。AI 可以提问、发散、质疑。
2. **卡片区**：各模块的当前内容，可直接手动编辑。
3. **提议区**：AI 提议对卡片的修改（以补丁形式列出：新增、修改、删除），作者逐条「采纳 / 拒绝 / 改后采纳」。

**原则：AI 不直接写卡片。** 所有写入都经过作者确认。这样才能避免「聊着聊着设定被悄悄改了」。

### 4.2 四种对话模式（作者随时切换，也可以让 AI 建议切换）

| 模式 | 作用 | AI 的行为 |
|---|---|---|
| 发散 | 给出大量灵感碎片 | 每次 5–8 条，标注题材/情绪/反差，不做评价 |
| 追问 | 把模糊的想法补全 | 每次只问 1–2 个问题，优先问「代价」「谁受影响」「为什么是现在」 |
| 收敛 | 从多个想法选一个主线 | 列出 2–3 个方案，逐项对比，给出推荐但不替作者决定 |
| 质检 | 检查已有设定的内部矛盾 | 只报告，不修改。指出具体的冲突位置（哪条规则与哪个情节不符） |

### 4.3 推进方式：引导式，而不是强制流程

顶部显示一个「构思进度」指示（灵感 → 题材 → 世界 → 角色 → 剧情 → 定版），每一步都有「建议下一步」，但作者可以跳过、回退、同时推进多个模块。

每个阶段结束时，AI 给出一段**阶段小结**（已定的、待定的、与前面有冲突的），作者确认后该阶段标记为完成。

### 4.4 快捷回复

AI 的提问尽量附带 2–4 个选项按钮（用现有的选项机制），同时保留自由输入。这对移动端尤其重要。

## 五、如何整合到当前外部项目里

### 5.1 目录与类型

```
external_projects/novel_writer/
  novel_writer/
    brainstorm/            # 新增子包
      workspace.py         # BrainstormWorkspace（与 Workspace 并列，不共用路径表）
      cards.py             # 卡片读写、补丁应用（新增/修改/删除）、版本快照
      patches.py           # 提议区的补丁结构与校验
      session.py           # 对话记录、模式、阶段进度
      handoff.py           # 构思包 → 新小说的映射与种子导入
  skills/
    brainstorm-spark/      # 发散
    brainstorm-probe/      # 追问
    brainstorm-converge/   # 收敛与对比
    brainstorm-critic/     # 质检
  ui/
    brainstorm.py          # 构思工作室页面（独立入口，或书架中的一个分区）
```

工作目录与小说相同，放在 `data/brainstorms/<名称>_<时间戳>/`，内部有 `_studio/`（对话记录、版本、设置）。书架索引增加 `kind` 字段（`novel` / `brainstorm`），现有小说默认为 `novel`，旧数据无需迁移。

### 5.2 复用什么，不复用什么

- **复用**：skill 运行机制（`invoke_child` / 受限 agent）、`atomic_write_*` 文件写入、书架注册、选项按钮组件、现有的 `read_json` 容错。
- **不复用**：小说的步骤流水线（`steps.py` 的 DAG 与 gate）。构思是对话驱动的，不是批处理，强行套用会让对话变得别扭。
- **需要确认的依赖**：对话的多轮上下文。当前 novel_writer 的步骤是「一次调用一次结束」，没有看到会话续接。需要确认 mini_agent 的 agent 接口是否支持以会话 id 续接（有记忆里提到的 resume session 机制，但要确认 novel_writer 能否调用）。如果不支持，备选方案是每轮把「对话摘要 + 当前卡片 + 最近 N 轮」整体注入，成本更高但可行。

### 5.3 交接：构思包 → 新小说

「开始创作」按钮的流程：

1. 选择构思包版本（默认最新定版；只允许定版版本交接）。
2. 调用 `create_novel(title, ...)` 创建小说工作目录；标题、题材等来自 `brief.json`。
3. 把 `brief.json` 映射为该小说的 intake（字段一一对应，见第三节），写入 `_studio/intake.json`。
4. 把构思包整体复制到 `_studio/seed/brainstorm/<版本号>/`（只读快照），并在 `PROJECT` 信息中记录来源（构思包 id、版本、内容哈希），便于追溯。
5. 在小说的相关步骤里，把种子作为**参考输入**注入：世界观 → `build_world`，角色 → 人设设计，剧情骨架 → 蓝图规划。

**关键原则：种子是建议，不是约束。** 蓝图步骤仍是小说内部的权威。如果蓝图与种子冲突，以蓝图为准，并在审核清单里列出差异，让作者决定是否回到构思包修订。

交接后两者不再自动同步。之后的修改只能显式地「从构思包重新导入」（覆盖前先备份）。

## 六、数据与版本

- **版本**：每次「定版」生成不可变快照 `versions/v<n>/`。编辑过程中的草稿在 `working/`。
- **回退**：可以回到任一版本，回退本身生成新版本，不删除历史。
- **分支**：备选方案 `options/` 可以在任一版本上派生；定版时只能选一个分支为主线。
- **溯源**：每条卡片和每个灵感都记录来源（作者输入、AI 提议且被采纳、AI 发散），便于后续判断哪些内容是作者自己的想法。
- **对话记录**保存在 `_studio/session.jsonl`，支持导出。

## 八、风险

1. **对话上下文**：若 agent 不支持会话续接，每轮成本随对话变长而上升。需要在 B2 之前验证。
2. **AI 悄悄改设定**：靠「提议区 + 显式确认」避免，测试要覆盖「未确认的补丁不得落盘」。
3. **设定膨胀**：角色与世界观可能无限扩展。建议每个模块有「本阶段够用」的最小集合，超出部分进入开放问题而不是强行补全。
4. **交接后的漂移**：种子与小说内部的版本分叉。靠单向导入和溯源记录缓解，不做自动同步。

## 九、需要你确认的问题

1. **形态**：独立页面（`streamlit` 里新入口）还是书架里的一个分区？我倾向独立入口，书架只显示为一种类型。
2. **交互强度**：AI 是否可以在对话中**主动**提议补丁（我的建议：可以，但永远需要确认），还是只在作者请求时提议？
3. **会话续接**：你是否知道 mini_agent 的 agent 支持以会话 id 续接？如果你确认支持，我先在 B2 前做一次验证；如果不支持，我们采用摘要注入方案。

5. **阶段顺序**：是否按 B0→B5 依次进行，还是希望先做 B1+B2（最小可用的对话 + 灵感池），验证交互后再决定后续？
