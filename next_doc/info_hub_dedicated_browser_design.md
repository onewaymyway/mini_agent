# info_hub 专用浏览器与反馈插件设计

> 状态：第一步（反馈插件、本地接收服务、看板打开与服务管理）与第二步（抓取附着到专用浏览器，CDP）均已实施；真实浏览器上的端到端验证待本机完成。
> 关联：`next_doc/info_hub_feedback_loop_improvement_plan.md`

## 1. 目标

- 只使用一个专用的有头浏览器，用于抓取和日常阅读；它使用 info_hub 自己的数据目录，与系统默认浏览器的配置、登录态完全隔离。
- 反馈按钮以浏览器插件形式出现在页面上，反馈经本地接收服务写入 info_hub 的反馈存储。
- 看板上可以把任意条目"在专用浏览器中打开"，页面在这个浏览器里显示，反馈按钮随之可用。
- 抓取不应打断用户的阅读。

## 2. 架构

```
┌────────────── 专用浏览器（独立 user-data-dir） ──────────────┐
│  用户阅读的标签页  +  插件(content script 工具条)            │
│  抓取任务的后台标签页（CDP 创建，不抢焦点）                  │
└──────────────┬───────────────────────────────┬──────────────┘
               │ 插件 background → fetch        │ Playwright connect_over_cdp
               ▼                                ▼
   本地接收服务 127.0.0.1:18765               浏览器调试端口（仅本机）
   /v1/feedback  /v1/open                      （第二步实施）
               │
               ▼
   info_hub 存储（feedback / exposures）  ←── 看板（Streamlit）
                                              “在专用浏览器中打开”按钮
```

### 2.1 专用浏览器

- 数据目录：`browser/dedicated_profile/`（相对 info_hub 根目录，可配置）。
- 启动：`<浏览器可执行文件> --user-data-dir=<目录> <URL>`。若同一目录的浏览器已在运行，Chrome 会在已有窗口中新开标签页，不会启动第二个实例。
- 可执行文件：优先使用 `config/settings.yaml` 中的 `dedicated_browser.executable`；留空时在常见安装路径中查找 Chrome / Edge。
- 插件需要在这个浏览器中"加载已解压的扩展程序"一次，之后保留。

### 2.2 插件

- Manifest V3，目录 `extension/infohub-feedback/`。
- 内容脚本按三级顺序识别条目上下文：① URL 片段 `#ihk=...`；② 当前标签页 sessionStorage 中保存的上下文；③ 凭当前地址向接收服务查询看板登记的“待匹配打开记录”（见 §14）。都没有时默认不显示工具条；仅当扩展选项开启“在所有页面显示”时，以手动反馈模式显示。
- 工具条使用 Shadow DOM，避免与页面样式互相影响；面板 `position:fixed` 悬浮在视口右侧（§15），不随页面滚动。
- 反馈与"打开"记录通过 background service worker 发送到本地接收服务（内容脚本不直接跨域请求）。
- 连接端口与令牌保存在 `chrome.storage.local`；令牌通过看板“插件配对”自动取得（§16），扩展选项页仍可手动填写作为排错手段。

### 2.3 本地接收服务

- 默认端口 18765（8765 是主项目 daemon 的默认端口，已被占用）。可在看板“服务管理”中修改，修改后插件选项里的端口需同步。
- 由看板启动、停止，状态以 `/v1/ping` 为准；启动记录写入 `data/state/receiver_process.json`，日志写入 `data/logs/receiver.log`。

- `server/feedback_receiver.py`，只监听 `127.0.0.1`。
- 每个请求必须带 `X-InfoHub-Token`，令牌首次启动时生成，保存在 `data/state/receiver_token.txt`。
- CORS 只允许 `chrome-extension://` 来源。
- 写接口：`/v1/feedback`、`/v1/open`、`/v1/dwell`；另有只读查询 `/v1/context`（§14）。内部复用 `server/api.py` 的校验与存储，反馈与曝光的存储格式不变。
- 请求体限制 16KB。

### 2.4 看板

- 看板上所有显示抓取内容地址的地方都有“打开”按钮（§16），点击后构造 `原始URL#ihk=<条目key>&ihs=<信息源>&ihv=<排序视图>&iht=<标题>` 在专用浏览器中打开，并由服务端记录一次"打开"（模式 `dedicated`）。看板不再提供阅读模式、内嵌页面、新标签页三种打开方式。
- 插件连接令牌通过看板“服务管理 → 插件配对”一键完成（§16），不再需要在扩展选项里手填。

## 3. 能否只开一个浏览器

**结论：能做到只有一个浏览器进程，但需要分两步，并且不能做到"完全不可见"。**

### 3.1 为什么现在需要两个

目前抓取使用 Playwright 自己启动 Chromium，并通过 `launch_persistent_context` 独占 profile 目录。用户日常浏览的是另一个浏览器进程，两者无法共享同一 profile，登录态也不通用。

### 3.2 统一的做法（第二步）

1. 专用浏览器以 `--remote-debugging-port=<端口>` 启动，只绑定本机。Chrome 136 之后，远程调试对**默认** profile 目录受限，但对独立的 `--user-data-dir` 仍可用，这正是专用目录的一个额外好处。
2. 抓取时用 Playwright `connect_over_cdp` 附着到该浏览器，使用它的默认上下文（也就是持久化登录态所在的上下文）。
3. 抓取页面以新标签页打开。在 CDP 中创建目标时尝试设置后台标签（`background`），使其不切换前台窗口。这一参数是否在目标 Chrome 版本上生效，需要实测确认。
4. 抓取完成后关闭该标签页。

### 3.3 无法避免的影响

- **浏览器必须先运行**：若用户关闭了专用浏览器，抓取会失败。看板应明确提示"专用浏览器未运行"，并提供一键启动（带调试端口）。这意味着抓取依赖一个正在运行的浏览器，不再能完全后台执行。
- **标签栏会短暂出现新标签**：即使是后台标签，任务栏和标签栏仍会有变化。要彻底无感知只能使用无头模式，而无头模式正是风控拦截的主要原因之一，因此不推荐。
- **抓取与阅读会共享会话**：同一账号的请求来自同一个浏览器，站点可能对频繁请求做风控。抓取频率需要保守，并且抓取与阅读最好错峰。
- **同一时间只能有一个进程控制该目录**：所以抓取、阅读、插件都必须通过这个浏览器完成。需要在代码中统一入口，不再保留独立的 Playwright profile。

### 3.4 迁移策略

- 第一步（本次实施）：专用浏览器与抓取 profile 仍然分开。阅读与反馈在专用浏览器中完成，登录需要在两边各做一次。这一步不影响现有抓取。
- 第二步：抓取切换为 CDP 附着到专用浏览器，并删除独立 profile 的使用路径。登录只需一次。

## 4. 安全

- 接收服务只监听回环地址，所有写请求需要令牌，不接受非扩展来源。
- 令牌不写入日志，不放在 URL 中。配对接口 `/v1/pair` 只在看板开启的 5 分钟窗口内向 chrome-extension 来源返回令牌，一次性，窗口外一律拒绝（§16）。
- 插件只在带 `#ihk` 参数的页面激活，manifest 的 `matches` 仍覆盖 http/https，可按需收窄到信息源所在的域名。
- 插件不读取页面内容，只读取标题与 URL；阅读正文仍由看板或抓取完成。

## 5. 限制与风险

- 插件需要手动加载一次（开发者模式），不随 Chrome 商店分发。
- Chrome 137 起移除了命令行参数 `--load-extension`，因此不能自动挂载插件，只能手动加载。
- 停留时长目前只在插件内统计为"打开"，尚未纳入反馈模型。
- 若用户在专用浏览器中登录的站点要求验证，验证操作需要在该浏览器中完成。

## 7. 看板服务管理（已实施）

- 看板"🧩 服务管理"面板统一管理两项服务：
  - 反馈接收服务：显示运行状态（由看板启动 / 非看板启动 / 未运行），可修改端口、启动、停止，查看最近 20 行日志与连接令牌。
  - 专用浏览器：显示运行状态与进程号，可设置浏览器程序路径、启动、关闭。
- 关闭专用浏览器只针对本项目的数据目录：有 psutil 时按命令行中的 `--user-data-dir` 精确匹配主进程；没有 psutil 时在 POSIX 上读取 `SingletonLock`；Windows 无 psutil 时显示"无法检测"，不会误杀其他浏览器。
- 停止接收服务只能停止由看板启动的进程。由终端启动的服务，看板只显示状态，需要在对应终端中停止。

## 8. 抓取附着到专用浏览器（CDP，已实施）

- 专用浏览器启动时带 `--remote-debugging-port=9223 --remote-debugging-address=127.0.0.1`，调试端口只绑定本机。
- `dedicated_browser.scrape_mode` 可选：
  - `launch`（默认）：Playwright 独立启动浏览器，与旧行为一致。
  - `cdp`：`connect_over_cdp` 附着到专用浏览器，在它的默认上下文中打开后台标签页抓取，完成后关闭标签页并断开连接（不会关闭用户的浏览器）。
- 看板"服务管理 → 专用浏览器"可切换抓取方式。未开启调试端口或浏览器未运行时，抓取会给出明确提示，不会静默失败。
- 后台标签：通过 CDP `Target.createTarget` 并设置 `background: true`，是否真正不抢焦点取决于浏览器版本，需要实测。
- 安全：调试端口可以完全控制浏览器，只能绑定 127.0.0.1，不要改为对外监听；专用数据目录内的登录态因此也可被本机进程访问。

## 9. 停留时长（已实施）

- 插件只统计页面可见的时间：隐藏或关闭页面时，发送本段增量到 `/v1/dwell`（可多次累加，不重复计数）。
- 记录写入曝光文件（kind=dwell）。评估面板显示两种排序视图的平均停留时间。
- 停留满 30 秒的条目，在画像学习中作为较弱的正向信号（权重随时长增加，封顶 300 秒）。

## 10. 报告按画像排序（已实施）

- 每个信息源的新条目在按单源上限截断之前，先按画像排序，因此排在前面的是用户更可能感兴趣的条目。
- 配置 `profile.rank_reports`，默认开启；画像不可用时保持原始顺序，不影响报告生成。

## 11. 缺陷修复与验证记录

- 缺陷："无法在专用浏览器中创建后台标签页"。根因：用 `time.sleep` 轮询 `context.pages` 等待新页面。Playwright 同步 API 只在调用其方法时处理浏览器事件，睡眠期间新页面事件不会被处理，所以永远等不到。修复：改用 `context.expect_page()`；后台创建失败时退回普通 `new_page()`。
- 已在无头 Chromium（带调试端口）上复现旧问题并确认修复，见 `tests/test_cdp_real.py`（本机无 Chromium 时自动跳过）。

## 12. 仍需手动验证

- 确认抓取标签打开与关闭时，不会打断正在阅读的标签页。
- 插件在专用浏览器中的实际显示与停留统计。

## 13. 工具条不出现的问题（已修复）

- 现象：看板"在专用浏览器中打开"后，地址栏中的 `#ihk=...` 标记消失，工具条不出现。
- 根因：小红书等单页应用加载后用 `history.replaceState` 改写地址，删掉了片段；插件原先在 `document_idle` 阶段才读取片段，已经晚了。
- 修复：内容脚本改为 `document_start` 注入，最早读取标记，保存在内存，并写入当前标签页的 sessionStorage（同路径内地址被改写后仍可识别）。"打开"记录只在首次带标记打开时发送。
- 验证：有头 Chromium（xvfb）中加载扩展，打开改写地址的页面，工具条出现，打开记录经接收服务写入数据（`tests/test_extension_e2e.py`）。
- 注意：Playwright 的无头模式不加载扩展，插件相关测试必须在有头模式下运行。
- 注意：修改 manifest 或内容脚本后，需要在 chrome://extensions 中点击"重新加载"。
- 未验证：点击工具条按钮的完整路径（工具条使用封闭的 Shadow DOM，自动化脚本无法直接点击）。

## 14. 片段丢失后的上下文恢复与“所有页面显示”（已实施）

- 现象：小红书笔记（`/explore/<id>?xsec_token=...`）从看板“在专用浏览器中打开”后，地址栏里完全没有 `#ihk=...`，工具条不出现。§13 只覆盖了“脚本读到片段之后被改写”的情况；若片段在脚本运行之前就已丢失（站点跳转、浏览器已在运行时的打开方式等），内容脚本无从获知条目，工具条自然不出现。
- 做法（不再只依赖地址片段）：
  1. 看板打开时，除了拼接片段，还把条目上下文登记到 `data/state/pending_open.json`（`core/pending_open.py`）。
  2. 插件在片段与 sessionStorage 都没有上下文时，由 background 向接收服务 `POST /v1/context {url}` 查询；命中则恢复条目 key、信息源、视图与标题，并写入 sessionStorage。
  3. 匹配规则：只比较“主机（去 www.）+ 路径”，忽略查询参数与片段（`xsec_token` 会变）；路径被站点重定向改变时，退化为同主机下“路径最后一段 ID（至少 8 位）”匹配。登记 24 小时过期，最多保留 200 条，同一匹配取最近一次。
  4. 接收服务不可用、令牌未设置或查询失败时静默视为“未找到”，不会影响页面。
- 查询接口同样需要令牌并限制扩展来源；只返回看板自己登记过的条目，不会读取任何浏览记录。注意：开启后，专用浏览器里每打开一个 http(s) 页面，插件都会把该页面地址发给本机接收服务做一次查询（仅限回环地址，不落盘）。
- 是否在所有专用浏览器页面显示反馈组件：**做成扩展选项“在所有页面显示反馈工具条”，默认关闭**（保守默认：避免在普通浏览中打扰，也避免产生与看板条目无关的反馈数据）。
  - 开启后，没有匹配上下文的页面以“手动反馈”模式显示：信息源记为 `manual`，条目 key 由页面地址（去片段）与标题计算；反馈使用点击时的页面标题与地址（适合单页应用中路径变化的场景）。
  - 手动模式没有看板条目 key，不统计“打开”和停留时长。
  - 开启后工具条是否出现还可以作为“插件是否已加载”的直观自检。
- 升级步骤：插件版本 0.1.0 → 0.2.0，需要在 `chrome://extensions` 中点击“重新加载”；需要手动反馈的用户在扩展选项中勾选开关并保存。
- 验证：`tests/test_pending_open.py`（登记/匹配/过期/容量/损坏文件/接收服务接口/手动反馈，11 用例）；`tests/test_extension_e2e.py` 新增 3 个有头 Chromium 用例——地址完全没有片段时工具条出现、未登记页面默认不显示、开启“所有页面显示”后显示。
- 未验证：真实小红书页面（沙箱无法访问）；真实 Windows Chrome 上的显示；手动模式下点击工具条按钮的完整路径（封闭 Shadow DOM，同 §13）。
- 已知限制：手动模式下的反馈 `source_id=manual` 不对应任何信息源，画像学习按标题与地址使用，但“按来源”的统计里不会有对应来源。
- 排查：知乎有工具条而小红书没有，是因为知乎的 `#ihk` 片段保留，小红书靠 `/v1/context` 恢复。最常见原因是接收服务或看板还是旧进程（没有 `/v1/context`，查询 404 被静默当作“未找到”）。需在看板“服务管理”停止并重新启动接收服务，并重启看板（看板的 api 才会登记上下文），再重新点“在专用浏览器中打开”。扩展选项里的“测试连接”现在会检测该接口，旧版本会明确提示；`/v1/ping` 的 version 升为 2。页面控制台（F12，Info 级别，可用 info_hub 过滤）会输出内容脚本加载、上下文来源或未找到的具体原因。临时对照：开启“在所有页面显示”后若小红书出现工具条，说明显示本身没问题，问题只在上下文识别。

## 15. 工具条悬浮在页面侧边（已实施，插件 0.3.0）

- 现象：知乎页面里工具条“在最下面”，小红书页面完全看不到（控制台显示内容脚本已加载、上下文识别成功，说明不是识别问题）。
- 根因：`content.css` 只是占位，Shadow DOM 内也没有任何样式，工具条是追加在 `<html>` 末尾的普通块元素，位于文档最底部。知乎页面可以滚动到底部所以能看到；小红书页面高度固定、不可滚动，工具条落在可视区之外。§13 的识别修复与 §14 的上下文恢复都不涉及显示位置，所以此前一直没发现。
- 改动：宿主元素 `position:fixed`，面板固定在视口右侧（默认纵向 35% 处），`z-index` 取最大值，不随页面滚动。
  - 标题栏上下拖动可调整位置；“×”不再删除工具条，而是收起为右侧边缘的竖向小标签，点击标签重新展开。
  - 位置与收起状态保存在 `chrome.storage.local`（键 `ui`），在专用浏览器内各页面共用。
  - 备注输入框内的按键不会冒泡到页面，避免触发站点自己的快捷键。
  - 按钮改为纵向排列，状态文字显示在按钮上方。

## 16. 插件配对与看板打开方式简化（已实施，插件 0.4.0）

### 16.1 插件配对（免手填令牌）
- 看板“🧩 服务管理 → 插件配对”点击“配对插件”，开启 5 分钟窗口（`core/pairing.py`，状态文件 `data/state/pairing.json`，看板写、接收服务读）。
- 窗口内，插件向接收服务 `POST /v1/pair`（不带令牌，必须是 `chrome-extension://` 来源）取得令牌并存入 `chrome.storage.local`；取得后窗口立即关闭（一次性），记录配对来源与时间，看板显示“已配对”。窗口之外的配对请求一律 403，所以平时令牌不会被动泄露。
- 触发时机：工具条出现时（`ensure` 消息）、上下文查询时、点击反馈按钮时，凡发现没有令牌都会尝试配对一次；令牌失效（401）时清掉旧令牌并在窗口开着时自动重新配对。
- 取舍：窗口开启的 5 分钟内，同一浏览器里的其他扩展理论上也能抢先取走令牌（来源只能判断是“某个扩展”，无法钉死具体扩展 ID）。专用浏览器里通常只装本插件，且令牌只能写入反馈与曝光数据，风险可接受；若在意，可在配对完成后看板立即显示“已配对”即可确认是本插件取走的。
- 端口：插件默认连 18765；看板里改过端口时，需要在扩展选项里同步一次端口（令牌不用填）。
- 手动路径保留：扩展选项仍可手填端口与令牌；看板“手动配置（排错用）”折叠区显示令牌与令牌文件路径。

### 16.2 看板打开方式简化
- 移除：阅读模式（加载正文）、内嵌页面（iframe）、新标签页，以及“设为默认打开方式”。看板只保留“在专用浏览器中打开”。
- 所有显示抓取内容地址的地方都增加“打开”按钮（统一由 `app.py` 的 `open_button` 实现）：
  - 抓取结果：列表改为逐行显示（排名、标题、摘要、热度/发布时间/推荐分、反馈图标），每行右侧有 👍 / 👎 / “打开”三个按钮（👍👎 见 §18）；默认显示 30 条，可“显示更多”。原来的表格“链接”列已去掉，不再需要先选条目。
  - 订阅页：当前进度与最近更新每条各一个按钮。
  - 报告页：单条朗读选中的条目旁有按钮。
  - 阅读与反馈面板：选中条目的按钮；反馈表单保留（记录的打开方式固定为 `dedicated`）。
  - 候选信息源与“编辑信息源”里的地址：这类地址不是条目，按钮只打开原始链接，不绑定条目、不显示条目工具条（开启“在所有页面显示”时按手动反馈处理）。
- 打开记录：改为 `open_in_dedicated_browser` 在服务端打开成功后统一记录一次，插件不再上报“打开”。此前看板与插件各记一次，会重复计数。
- 反馈事件的 `open_mode` 现在接受 `dedicated`（此前被当作未知值丢弃为空）。
- 后端暂留：`core/reader.py`、`api.read_article` / `view_prefs` / `set_default_open_mode`、配置 `view.default_open_mode` 已不被看板使用，保留以免一次改动过大，待确认后清理（同时清理对应测试）。
- 验证：`tests/test_pending_open.py`（纯打开不登记不记录、打开失败不记录、半填条目被拒、配对窗口一次性/过期/损坏文件、`/v1/pair` 端到端）；`tests/test_feedback_dashboard.py`、`tests/test_streamlit_app.py`（旧打开方式已移除、每行有按钮、点击调用专用浏览器并只记录一次）；`tests/test_extension_e2e.py` 新增两个用例（窗口开启时插件自动配对；窗口关闭时不配对）。

## 17. 看板“反馈记录”页签（已实施）

## 18. 抓取结果行内的“感兴趣 / 不感兴趣”（已实施）
