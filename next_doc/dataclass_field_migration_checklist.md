# 给现有 dataclass 加字段时的迁移期检查清单

> 触发背景：`next_doc/growth_advisor_improvement_plan_v3.md` P5-1。
> `GrowthReport.evidence_count_at_generation`（P4-4 新增）默认值是 `0`，
> 上线当天所有此前生成的旧报告（反序列化时这个字段缺失，落到默认值）
> 被下游 `reports_needing_refresh()` 误判为"证据从 0 涨到了现在这么多，
> 该刷新了"，触发一批批量误报。这不是那次改动本身的 bug，是"给一个已经
> 有历史数据的 dataclass 加新字段"这类改动通用会踩的坑，值得沉淀成固定
> 检查项，而不是每次都靠事后 review 才发现。

## 适用范围

任何给**已经落盘过历史数据**的 dataclass（`from_dict()`/JSON 反序列化
会遇到旧记录里缺失新字段的情况）新增带默认值的字段，都过一遍这份清单。
纯内存态、不落盘或者项目刚上线还没有历史数据的 dataclass 不适用。

## 检查项

1. **明确写一句：老数据在这个默认值下，会被下游哪些函数如何解读？**
   不要只想"这个字段本身要不要有默认值"，要往后看一步——`from_dict()`
   之后这个字段会被谁读取、参与什么判断、判断结果会不会触发用户可见的
   行为（提示、通知、批量操作）。

2. **如果第 1 步的答案是"会触发一批批量提示/通知"，二选一：**
   - **调整默认值，让老数据表现为"中性"，而不是"看起来符合触发条件"。**
     常见做法：默认值改成一个跟"字段本身合法取值范围"不重叠的哨兵值
     （比如整数字段默认 `0` 容易被误读成"真实的 0"，改成 `-1` 表示
     "快照缺失"，下游判断逻辑显式识别这个哨兵值并跳过，而不是参与正常
     的数值比较）。
   - **或者在上线说明/PR 描述里显式提一句这个副作用**，让复核的人知道
     "这批老数据会被怎么对待"是有意为之还是遗漏。
   两者选其一即可，但不能都不做——"默认值凑合能跑"不代表"老数据的解读
   结果是对的"。

3. **哨兵值不是唯一解法，视字段语义选择：**
   - 数值型字段（计数、时间戳）：哨兵值（如 `-1`）+ 下游显式跳过，通常
     是最简单的方案（参考 `evidence_count_at_generation` 的修法）。
   - 布尔型字段：如果"未知"和"False"语义不同，考虑用
     `Optional[bool] = None` 而不是 `bool = False`，让"没有这个信息"和
     "明确是 False"可区分。
   - 字符串/枚举字段：同理，`Optional[str] = None` 通常比"编一个看起来
     合理但其实是瞎猜"的默认字符串更安全。

4. **落一条回归测试**：构造一条"字段缺失"的旧数据（直接从 dict 里
   `pop()` 掉这个 key，而不是用当前 dataclass 构造后转 dict——后者永远
   会带上新字段，测不出真实的反序列化缺失场景），验证下游函数不会把它
   误判为"触发条件成立"。参考
   `tests/test_growth_advisor.py::test_legacy_report_missing_evidence_snapshot_not_flagged_for_refresh`。

5. **把这次踩过的坑记录进对应模块的实施记录**（"已知限制"/"迁移期
   说明"风格的章节），作为以后同一模块再加字段时的直接参照，不需要每次
   重新推导一遍。

## 已应用过这份检查清单的案例

- `GrowthReport.evidence_count_at_generation`（`src/mini_agent/evolution/
  growth_advisor.py`）：默认值从 `0` 改为 `-1`（哨兵值，语义是"生成时的
  证据数快照缺失"），`reports_needing_refresh()` 显式跳过负值，不参与
  "证据是否显著增长"的判断。见
  `next_doc/growth_advisor_implementation_record.md` P5 章节。
