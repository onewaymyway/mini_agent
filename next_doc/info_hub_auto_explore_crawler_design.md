## 1. 目标

自动探索不再局限于 RSS。系统应能：

1. **发现新站点**：从已有来源的页面、外链与种子目录出发，找到此前没有订阅过的站点。
2. **发现新信息源**：同一站点内的多个栏目、列表页、订阅入口、接口，各自作为独立信息源候选。
3. **覆盖多种形态**：RSS/Atom、sitemap、公开 JSON 接口、普通 HTML 列表、**浏览器渲染后才有内容的页面**（SPA、脚本加载列表）。
4. **持续扩展**：以类似爬虫的方式，按预算逐步扩大发现范围；产出高的方向多投入，产出低的方向自动减少。
5. **仍然安全**：不登录、不绕过验证、不保存完整正文、新源默认停用、全程可审计、用户可随时停止。

## 2. 与现状的差距

| 能力 | 现状（已核对） | 目标 |
|---|---|---|
| 站点发现 | 固定种子 + 最近三天条目的站点首页 | 图式扩展：从页面外链持续发现 |
| 探索深度 | 只看首页 | 有限深度的站内遍历（分类页、列表页、订阅页） |
| 形态识别 | 重复容器、JSON 形态；无订阅发现、无 sitemap | 订阅发现、sitemap、站内 JSON 接口、浏览器渲染列表 |
| 浏览器 | 共享登录态 profile（`browser/profile`） | 探索使用**一次性隔离 profile**，与登录态彻底分离 |
| 网络观察 | 无 | 渲染页面时记录 JSON 响应，识别列表型接口 |
| 持续运行 | 只在用户点击时运行 | 后台按预算定期运行，可暂停 |
| 产出评估 | 只有一次性的跳过计数 | 按站点/形态/栏目统计产出，驱动资源分配 |

## 3. 总体架构

```
种子（目录 + 已接受来源的页面）
   │
   ▼
Frontier（待访问队列，纯文本 jsonl，可断点续跑）
   │  取出：按预算与礼貌间隔
   ▼
Fetcher ── HTTP（默认）｜ 浏览器渲染（隔离 profile，仅在需要时）
   │
   ▼
Classifier：页面形态与链接分类
   ├─ 订阅入口（RSS/Atom/JSON Feed）→ 候选：rss / json_api
   ├─ 站点地图 → 候选：文章流（html_list，基于路径模式）
   ├─ 列表页（重复容器）→ 候选：html_list（http 或 browser）
   ├─ 网络接口（渲染中捕获的 JSON 列表）→ 候选：json_api
   └─ 普通链接 → 入 Frontier（若属于同站且深度未超限，或属于新站且通过门槛）
   │
   ▼
Gate：质量（条目数、字段完整度）→ 相关性（画像）→ 新颖性（与已启用源相似度）→ 合规
   │
   ▼
候选收件箱（默认停用，用户确认）
   │
   ▼
Yield 统计 → 反馈给 Frontier 的优先级与预算分配
```

## 4. 发现的五种形态

### 4.1 订阅入口（最便宜，优先）
读取页面 `<link rel="alternate">`，以及常见路径（`/feed`、`/rss`、`/atom.xml`，仅在首页没有声明时尝试）。生成 `rss` 或 `json_api` 候选，不需要浏览器，不需要模型。

### 4.2 Sitemap
读取 `robots.txt` 中声明的 sitemap。从近期 URL 的路径模式推断文章栏目（如 `/news/...`、`/p/<id>`），按栏目生成 `html_list` 候选，并用栏目页自身做预览验证。

### 4.3 站内列表页
从首页与分类导航中找出“看起来像列表”的页面（重复容器、多链接、标题样式一致），每个列表页作为一个独立候选。这是“栏目即信息源”的关键：同一个站可以产生多个候选。

### 4.4 浏览器渲染页面
当 HTTP 获取的 HTML 没有列表容器、但页面脚本加载后出现时，启用浏览器渲染：
- 使用**一次性隔离 profile**（每次探索新建，结束即删除），绝不复用共享登录态；
- 只渲染公开页面；遇到登录墙、验证码、付费墙立即放弃；
- 不点击、不提交表单、不输入任何内容，只允许等待与滚动；
- 屏蔽图片、字体、媒体、广告与第三方追踪域的请求，减少负载与噪声；
- 单页超时与内存上限；同一站点每日渲染次数有上限。

### 4.5 网络接口观察（浏览器渲染的副产物）
渲染页面时记录 JSON 响应（仅记录 URL 模式、状态码、结构摘要，不保存响应正文）。若某个接口返回的是“数组 + 标题字段”形态，生成 `json_api` 候选，并把接口请求的参数规律记下来（如分页参数）。这是发现“没有 RSS、但有内部接口”的站点的主要方式。

## 5. 爬虫机制（Frontier）

### 5.1 队列与状态
- `data/discovery/frontier.jsonl`：每行一个待访问 URL，字段 `url / host / depth / source_page / priority / enqueued_at / status`；
- 去重键：规范化 URL（去掉追踪参数与锚点）；
- 持久化：每次取出与完成都追加记录，重启后从文件恢复；
- 容量上限：全局与每站点各有上限，超出则丢弃低优先级项。

### 5.2 深度与范围
- 种子深度为 0；页面中发现的链接深度加 1；**最大深度默认 2**。
- 同站链接优先；跨站链接只在“新站点发现”模式下入队，且必须来自**种子或已接受来源的页面**（不从任意页面跳转到陌生站点）。
- 每个页面最多入队 N 个链接（默认 20），按链接文本与路径模式打分（列表、订阅、栏目类优先；登录、注册、下载、购物类直接丢弃）。

### 5.3 优先级与预算分配
- 每个站点有“产出分”：该站候选的采纳率、预览质量均值、近期可用栏目数。
- 每轮预算在站点之间按产出分分配：高产出站点多获得访问次数，但单站点仍受上限约束，避免过度集中。
- 长期无产出的站点降低优先级，并定期（如每 30 天）仅做一次低成本复查。

### 5.4 停止条件
- 单轮预算用尽；
- 连续 N 次失败或被限流（429/503）的站点进入冷却；
- 全局错误率超过阈值，整轮暂停并在看板提示；
- 用户点击“暂停探索”。

## 6. 持续运行（后台）

- 新增“自动探索”后台任务，由 `tick` 调度，默认**关闭**；用户在看板显式开启后才运行。
- 运行窗口可配置（如仅夜间）；每轮有时间与请求预算上限。
- 每轮结束生成一份摘要：检查站点数、新发现站点数、新候选数、被拒原因分布、各形态产出。摘要写入运行记录，不推送外部。

## 7. 护栏（比 P12 更严格）

| 护栏 | 规则 |
|---|---|
| robots.txt | 必须遵守；读取不到按不允许处理；遵守 `Crawl-delay`（取较大者） |
| 站点级请求预算 | 每站点每天默认最多 30 次请求（含渲染），每次渲染计为 5 次 |
| 全局预算 | 每天全部探索请求默认最多 500 次，渲染默认最多 40 次 |
| 最小间隔 | 同一站点两次请求至少间隔 `max(Crawl-delay, 5 秒)` |
| 退避 | 遇到 429/503 按指数退避，并遵守 `Retry-After` |
| 身份 | 固定、可识别的 User-Agent，包含项目名与联系说明 |
| 禁止项 | 不登录、不输入账号、不绕过验证码与风控、不访问付费墙内容、不提交表单 |
| 内容 | 只保存标题、链接、时间与结构摘要；不保存完整正文或响应体 |
| 站点名单 | 项目维护的禁止名单（明确禁止抓取的站点），命中即不访问；用户可额外屏蔽站点 |
| 审计 | 每次请求记录时间、域名、路径模式、结果码、耗时；可在看板查询 |
| 终止开关 | 看板一键暂停；暂停后立即停止新请求，已排队的项保留 |

## 8. 新源的生命周期

1. **发现**：进入 Frontier 或直接成为候选（订阅入口、接口）。
2. **验证**：预览通过质量、相关性、新颖性门槛。
3. **入箱**：默认停用，显示形态（RSS / JSON / 列表 / 渲染列表）、需要的渲染方式、预览样例、门槛结果。
4. **确认**：用户启用。启用后按其形态正常调度；渲染型源需要用户已安装浏览器，否则提示。
5. **复查**：每 30 天一次，失效则尝试同站替代入口，生成候选，由用户决定替换。
6. **退役**：连续失效或被用户停用，记录原因，不再尝试。

注意：渲染型源（需要浏览器）会比 HTTP 源消耗更多资源，候选卡片需明确标注，并在源列表中单独计数。

## 9. 数据与文件

| 文件 | 内容 | 格式 |
|---|---|---|
| `data/discovery/frontier.jsonl` | 待访问队列与状态 | jsonl |
| `data/discovery/sites.json` | 站点索引：产出分、冷却状态、最近访问 | json |
| `data/discovery/explore_log.jsonl` | 请求审计（域名、路径模式、结果、耗时） | jsonl |
| `data/discovery/yield.jsonl` | 每轮产出汇总 | jsonl |
| `config/discovery.yaml` | 预算、深度、门槛阈值（用户可调） | yaml |
| `config/denylist.yaml` | 禁止抓取的站点（项目维护） | yaml |
| `browser/explore_profiles/` | 一次性隔离 profile，每次探索后删除，不纳入备份 | 目录 |

所有文件保持纯文本，人可直接查看与审计。

| **P16** Frontier | 队列持久化、深度限制、链接打分与过滤、禁止名单 | 重启后队列可恢复；深度超限与禁止站点不被访问 |
| **P17** 产出驱动与持续运行 | 站点产出分、预算分配、后台任务（默认关闭）、运行摘要、看板暂停开关 | 连续运行多轮后，高产出站点获得更多访问；暂停开关生效 |

每阶段完成后更新文档，并单独确认后再进入下一阶段。P14 与 P15 的浏览器相关能力风险最高，建议先在测试页面与一个你自己确认可用的站点上验证。

## 11. 风险与边界

- **合规风险**：更广的访问范围会增加与站点条款冲突的可能。缓解：robots 严格遵守、低频、禁止名单、可随时暂停；但**不能保证所有站点都允许自动访问**，需要你对目标站点自行判断。
- **站点负载**：渲染与爬取会增加对方服务器压力。缓解：预算上限、渲染单独限额、指数退避。
- **误判噪声**：更多候选意味着更多需要审阅的内容。缓解：门槛、相关性、产出驱动、拒绝学习。
- **维护成本**：站点改版频繁，渲染型与接口型源更脆弱。缓解：复查与替代入口（P18），以及源健康机制。
- **隐私**：探索使用隔离 profile，不携带任何登录态；画像不发送到外部。

## 12. 需要你确认的参数与决定

1. **总体方向**：是否接受“形态扩展 + 有限深度爬取 + 产出驱动”的设计？
2. **浏览器渲染**：是否允许探索使用无头浏览器（隔离 profile，默认关闭）？
3. **深度与站点范围**：最大深度 2；跨站只从种子和已接受来源页面出发——是否可以？
4. **预算默认值**：站点每天 30 次请求（渲染计 5 次），全局每天 500 次、渲染 40 次——是否合适？
5. **后台持续运行**：默认关闭，仅在你开启后运行，是否接受？
6. **禁止名单**：由项目维护，初始为空，还是你希望先提供一批明确不访问的站点？

确认后从 P14 开始实施。我的建议：先确认第 1、2、5 项，它们决定了风险边界。
