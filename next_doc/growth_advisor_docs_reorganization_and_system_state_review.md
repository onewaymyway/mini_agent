# 成长顾问（Growth Advisor）文档体系梳理、重组建议与系统现状回顾

> 沿用 `goal_cron_docs_reorganization_and_system_state_review.md` 同一套
> 方法论，这次聚焦成长顾问这条主线。一致性核对的详细过程记在
> `goal_cron_docs_status_audit_record.md`"第三轮核对"小节，本文档只
> 总结结论 + 给重组建议 + 系统现状分析，不重复过程。

## 1. 一致性核对结论摘要

核对范围：`docs/growth-advisor-guide.md`（唯一用户指南，1700+ 行）+
`next_doc/` 下 16 篇 `growth_advisor_*` 方案/记录文档。

**发现 1 处真实不一致（已修正）**：`growth_advisor_ideal_advisor_gap_
and_roadmap_plan.md` 规划的 6 个方向里，方向 4（跨方向全局视角摘要，
`pursuits_portfolio_summary()`）和方向 5（学习效果自测环节，
`self_check_hint_for_cycle()`）代码/API/看板均已落地，但从未被写入
`docs/growth-advisor-guide.md`——既没有对应的 §2.x 小节，4 个相关配置
字段里有 3 个连表格都没有列。已新增 §2.24a 小节 + 补齐 §5 配置表 4 行。

**其余核对内容一致**：24 个"本次新增"标注的小节逐条核实函数名/配置项/
测试文件均存在；16 篇方案文档的状态栏与彼此的引用关系、与用户指南对应
小节的完成度描述均吻合。

这次的问题类型跟上一轮（goal/cron 主线）不同——上一轮是"汇总索引文档
忘了同步新增条目"，这次是"用户指南本身就漏写了一部分已完成的功能"，
根因见 §1.1。

### 1.1 根因：批量规划、分批落地时的"写回"步骤缺失

`growth_advisor_ideal_advisor_gap_and_roadmap_plan.md` 一次性规划了
6 个方向，实际落地是分批进行的（方向 1/2/3/6 分别对应用户指南 2.19/
2.9 第二步/2.9 第一步/2.20 等小节），每批落地时都执行了"改代码 + 写
用户指南"两步，唯独方向 4/5 这一批只执行了"改代码"，用户指南这一步
被跳过——方案文档自己的状态栏是准确的（`_implementation_record.md`
也如实记录了），只是这份"内部记录准确"没有传导到"面向用户的指南也
准确"。这比 goal/cron 主线那次更隐蔽：那次是"内容存在但索引没更新
（顺着任何一条线索都能找到）"，这次是"用户指南本身就是唯一的检索
入口，而这个入口里根本没有这部分内容"。

## 2. 文档重组建议

### 2.1 现状：单篇文档已经过大，检索成本是主要问题

跟 goal/cron 主线（多篇平级用户指南）不同，成长顾问只有**一篇**用户
指南，但这篇指南本身已经膨胀到 1700+ 行、24 个"2.x"小节 + 8 个"5.x"
小节，绝大多数小节标题都带着"（本次新增）"这个不再有信息量的后缀
（因为几乎每个小节都是"本次新增"，这个标注早就失去了区分度）。这是
成长顾问这条主线特有的问题，不是 goal/cron 那种"多文档索引缺失"。

### 2.2 建议：拆分 + 保留时间线索引，而不是简单加索引层

单篇超长文档比多篇平级文档更适合"拆分"而不是"加索引"，因为拆分能
直接降低单次阅读需要加载的上下文：

1. **`docs/growth-advisor-guide.md` 保留为"总览 + 核心机制"**——精简
   到 §1（这是什么）+ §1.5（设计理念）+ §2.1-2.4（信号扫描→候选→
   报告→推送这条最核心的主链路）+ §3/§4（默认行为、怎么用）+ §6/§7
   （数据存放、当前局限）。这部分是几乎不变的"骨架"，长期稳定。

2. **新增 `docs/growth-advisor-directions-history.md`**——把现有
   §2.5-2.24a（全部带"本次新增"标注的能力性小节）整体迁移过去，按
   **时间线**（而不是按当前的功能分类）重新组织成一份"演进日志"：

   ```markdown
   ## 2025-xx：v2/v3/v4 迭代（关键词学习、报告质量分级、通知策略细化……）
   ## 2026-0x：Goal/Cron 打通（对齐分析、一键落地、回访用真实进度）
   ## 2026-0x：调研信息获取与整理（真摘录、有来源）
   ## 2026-0x：自主性深化 A/B/C/D（本次新增的九个方向）
   ## 2026-0x：理想形态对照与改进路线图 方向 1-6（含本轮补写的方向 4/5）
   ```

   这样"本次新增"这个失去意义的标注可以去掉，改成按批次的日期/主题
   分组标题，天然就是"历史改进轨迹"的直接呈现，且跟 goal/cron 主线的
   `next_doc/README.md` 时间线索引是同一种设计语言，两条主线的文档
   体验保持一致。

3. **§5 配置项表格保留在主指南**，但表格里每行的"说明"列已经在标注
   对应小节（如"2.9 节"），拆分后改成标注"演进日志 § xxx"，链接方式
   不变，只是目标文件换了。

4. **`next_doc/` 侧不需要拆分**——16 篇方案文档本身粒度已经合适（每篇
   对应一轮独立的规划批次），问题是"批次内容有没有完整写回用户指南"，
   而不是"方案文档本身太大"。`next_doc/README.md`（若按 goal/cron 那份
   文档 §2 的建议新建）里给成长顾问也建一个时间线分组即可，跟 goal/
   cron 分组并列。

### 2.3 防止"批次遗漏"复发的具体建议

针对 §1.1 的根因，给这条主线补一条特有的检查动作（比 goal/cron 那边
"汇总索引"的问题更具体，可以写成一个可执行的检查清单）：

- 一份 `growth_advisor_*_plan.md` 如果一次性规划了多个方向/子任务
  （比如"方向 1-6"这种结构），落地后除了给方案文档自己打勾，还要
  **逐个方向**确认是否已经写回用户指南（或按 §2.2 拆分后的演进日志）
  ——不能因为方向 1/2/3 写了就假设方向 4/5/6 也写了，本轮暴露的正是
  这种"批内遗漏"。
- 拆分后的演进日志文档如果新增一节，方案文档自己的状态栏可以直接
  写"已落地，已写入 `growth-advisor-directions-history.md` § xxx"，
  把"代码完成"和"文档完成"两个勾选项分开列，不合并成一句"已完成"
  （这是本轮发现问题的直接教训，比空泛地说"以后要注意"更可执行）。

## 3. 成长顾问子系统现状与后续方向

### 3.1 现状：已经从"单一推送功能"演进成一套完整的自主学习顾问

成长顾问最初的定位（`growth_advisor_design.md`）是"信号扫描 → 候选
生成 → 调研报告 → 推送"的单向链路，复用自我进化闭环的架构模式。经过
v2/v3/v4 + 五轮左右的深化方案，现在已经形成了一个多维度的系统：

- **纵向**：候选 → 报告 → 采纳 → 落地为 Goal → 绑定周期性执行 → 持续
  产出学习素材 → 定期自测/整理/风格适配 → 饱和度检测 → 归档，覆盖了
  一个"成长方向"从被发现到被长期跟踪的完整生命周期。
- **横向**：多个方向并行推进时有饱和度/参与度信号（方向 1/B2）、全局
  视角摘要（方向 4，本轮补写文档的部分）、调研路径关联信号（2.24 节）
  三层递进的"多方向管理"能力，不再是假设用户同时只关注一个方向。
- **反馈闭环**：忽略原因区分"方向错/报告差"（P6）、报告质量自动闭环
  （方向 7）、推送情境感知（2.23 节）——推送策略本身在根据历史反馈
  自我调整，不是一套固定阈值用到底。

从 §5 的 49 个配置项规模也能看出这套系统的复杂度——但设计上坚持了
"规则式默认 + LLM opt-in"的一贯克制（`llm_signal_augment_enabled`/
`goal_alignment_llm_enabled`/`pursuit_style_llm_enabled` 等十余个 LLM
增强开关全部默认关闭），核心链路（信号扫描→候选→报告）本身零 LLM
成本可用，这条设计边界在 5 轮迭代里一直没有被突破，是这条主线目前
最值得延续的架构纪律。

### 3.2 值得关注的结构性观察

1. **文档规模已经跟功能复杂度不匹配**——§2 直接推动了 §2 的拆分建议，
   这里不重复；但值得指出的是，如果后续再有类似"理想形态对照"这种
   一次规划多个方向的大批量方案，建议在规划阶段就想清楚"这次落地后
   用户指南准备怎么组织"，而不是等落地完再回头补，本轮的遗漏本质上
   就是"落地节奏比文档组织规划跑得快"的结果。

2. **LLM 增强开关数量已经不少（十余个 opt-in 开关）**，目前每个都是
   独立配置、独立默认关闭，长期看如果用户想要"整体上更信任 LLM 增强、
   一次性打开一批"，现在需要逐个手动开启。是否需要一个"LLM 增强总
   开关"（类似 `llm_signal_augment_enabled` 但作用域覆盖全部十余个
   opt-in 点）目前没有方案讨论过，值得在后续如果收到相关用户反馈时
   评估——但不建议在没有实际诉求前主动设计，容易做成"为了整齐而整齐"
   的过度设计。

3. **调研风格分类（2.20/2.21 节）和话题类别系统（2.5 节）是两个正交
   维度，目前各自独立演进**——如果后续再引入第三个分类维度（比如
   "优先级"），需要注意维度之间会不会产生耦合（比如某个风格只适用于
   某些类别），现在两个维度互不影响的设计如果扩展到三个维度时未必
   还能保持这种简单性，值得在真正引入第三个维度之前先想清楚正交性
   是否还能维持。

4. **§1.1 揭示的"批次遗漏"模式，理论上也可能出现在其它同样"一次规划
   多方向"的主线里**（比如 goal/cron 主线的 `goal_cron_task_
   optimization_holistic_plan.md` 就是类似的"方向 A/B/C/D"结构）——
   建议下次核对 goal/cron 主线时，把"分方向规划的文档是否每个方向都
   写回了对应用户指南"也纳入核对方法，而不是只核对状态栏文字本身，
   这是本轮相对上一轮核对方法的一个改进点，值得沉淀成通用做法。

### 3.3 优先级建议

1. **最低成本、立即见效**：§2.2 的文档拆分（迁移 §2.5-2.24a 到独立
   演进日志文档），跟 goal/cron 主线的索引层建设是同一批"文档基建"
   投入，可以一起做。
2. **按需触发**：LLM 增强总开关，等有明确的用户诉求（比如多个用户
   反馈"想一次性开启所有增强"）再设计，不提前投入。
3. **持续纪律，无需专项投入**：维持"规则式默认 + LLM opt-in"的架构
   边界，以及 §2.3 提出的"代码完成/文档完成分开打勾"检查动作，这两条
   都是习惯性维护，不需要单独立项。
