## 3. 设计要点

### 3.1 两种模式

| 模式 | 入口 | 写入 | 告警 |
|---|---|---|---|
| collect（P4.5） | `run_collect` / `output_patrol.py collect` | `metrics.jsonl`（追加） | 无 |
| report（P5） | `run_report` / `output_patrol.py report` | `patrol/<时间戳>.json`、`patrol/latest.json` | findings（建议） |

### 3.2 采集的指标

每个产出项目一行：文件数（上限 5000）、最近文件修改时间距今天数、最新版本、距上次发布天数、是否有未发布变更、状态、所属目标及其状态、关联数、断链目标、是否受管、是否有介绍文件。

### 3.3 评估规则

| finding | 触发条件 | 建议 |
|---|---|---|
| `missing_intro` | 缺少 PROJECT_INFO.md | 补充介绍 |
| `stale` | 距最后一次文件变动超过 `stale_days` | 确认是否仍在推进，结束则归档 |
| `version_gap` | 有未发布变更，且距上次发布超过 `version_gap_days` | 考虑发布版本 |
| `never_released` | 受管项目有变更但从未发布 | 发布首版或确认仍在构建 |
| `orphan` | 所属管理项目为 completed / abandoned / cancelled / failed | 重开管理项目，或转为游离/归档 |
| `broken_link` | 关联指向不存在的管理项目或目标 | 解除关联或恢复目标 |
| `floating` | 状态为游离 | 绑定到已有管理项目，或派生新的管理项目 |

所有 finding 都只是建议，没有任何自动执行路径。

### 3.4 只读保证

- 采集与评估只读取产出目录、`goals.json`（原始 JSON）、注册表分表与总表；
- 不调用 `GoalBacklog.load()`，不写 `goals.json`；
- 写入位置限定在 `.agent/output_registry/` 下。测试 `test_patrol_does_not_modify_projects_registry_or_goals` 对产出目录（含 `_registry/`）与 `goals.json` 做逐字节哈希比对。

### 3.5 阈值的未校准状态

默认值：`stale_days=30`、`version_gap_days=30`，`calibration="uncalibrated"`。

这些值是占位，不是依据。每份报告都会原样附上阈值与 `calibration` 字段，使读者不会把它当作经过验证的结论。校准必须基于 P4.5 在真实项目上积累的数据，而测试数据不能作为校准依据。

### 5.3 阈值校准的前置条件

P5 的阈值不能在本阶段校准，原因是：

1. 没有真实项目的采集数据；测试数据的时间分布是人为构造的；
2. 停滞和版本缺口的合理阈值取决于用户的实际工作节奏（有的项目每天更新，有的以月为单位），需要观察分布后决定；
3. 计划要求"在 P5 前用实际数据校准"，因此校准是后续工作，不是本阶段的遗漏。

**建议做法**：先在真实的产出项目上每天运行一次 `collect`，积累至少 4 周的数据，再用 `metrics.jsonl` 中的 `days_since_update`、`days_since_release` 分布确定阈值，并把结论写回本文档。

## 6. 已知限制

1. **阈值未校准**（见 5.3）。
2. **报告不通过通知渠道呈现**，只写文件。
3. **没有定期调度**，需要手动或由外部 cron 调用。
4. **采集只统计文件修改时间**，不检查 git 状态（未提交的变更、未推送的提交等）。
5. **文件数上限 5000**：超过时 `file_count_truncated=true`，但 `days_since_update` 只基于已扫描的文件，可能偏旧。
6. **`broken_link` 的判定依赖 goals.json 中是否存在目标 id**。若目标树被整体重建，历史关联会全部显示为断链，这是有意的保守行为。

## 7. 需要确认的问题

1. **采集频率**：每天一次是否合适？这会决定积累数据所需的时间。
2. **报告呈现**：是否接入现有的 `reports_store` 与通知渠道？如果接入，需要确认通知的分级（P5 要求只在真正需要时打扰用户）。
3. **阈值校准的时机**：是否在积累数据后由你确认新阈值，再把它们写回默认值？
4. 之前仍未确认的三个问题：
   - P1：`executable=false` 的 goal 视为结构节点、objective 不允许不可执行，是否接受；
   - P3：快照是否包含 `.git`，以及快照只读的强度；
   - P4：绑定后 `output/` 下出现的四目录骨架是否接受，会话产出是否纳入路由，以及非目标测试是否需要补跑。
