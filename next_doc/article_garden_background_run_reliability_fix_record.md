# article_garden 后台运行可靠性修复记录

- **触发**：运行日志出现两类问题：
  1. 摘要 a-0016 以 `StepTimeout: 单步超时` 失败（217 秒），随后整批“文章摘要”失败，剩余文章未处理；
  2. 停止后日志显示“已停止（0.0 秒）”，但紧接着的新运行立即被判为停止；页面上其它位置仍显示“正在执行”。
- **完成日期**：2026-11-23
- **范围**：`budget.py`（停止信号、超时）、`joblog.py`（运行状态）、`digest/runner.py`（单篇超时隔离）、`cycle.py`（运行开始时间）、各页面的“运行中”判断、`planning/topics.py`、`wiki/placement.py`、`entrypoints/draft_charter.py`（补齐运行记录）。

## 1. 根因

| 现象 | 根因 |
|---|---|
| 超时过早出现，整批失败 | `budget.guard(...)` 在整批任务开始时只创建一次，超时截止时间从创建时算起，覆盖了整批所有文章。截止后，之后每一篇的调用都超时；而 `StepTimeout` 是 `BaseException`，直接穿过单篇的异常处理，终止整批。 |
| 新运行一开始就显示“已停止（0.0 秒）” | 停止信号是一个没有时间戳的文件。上一次停止请求一直留在磁盘上，之后启动的每个新任务都会读到它。只有 cycle 会清除它。 |
| 其它页面仍显示“正在执行” | 九处页面和顶栏用“最近 90 秒内日志是否有新行”判断运行中。停止后最后一行是“已停止”，于是 90 秒内都显示为运行中。判断依据是时间，不是实际状态。 |
| 个别步骤在运行日志中没有记录 | 选题、挂载提案、章程草稿没有运行开始/结束记录，所以无法被判断为运行中。 |

## 2. 修改

| 文件 | 修改 |
|---|---|
| `budget.py` | 停止请求写入时间戳；`GuardedLLM` 记录自己的开始时间，只响应**之后**发出的停止；超时改为每次模型调用各自计时（语义：单次调用的最长等待）。 |
| `cycle.py` | 运行开始时记录一个时间点，每个步骤的调用保护都使用它，因此闭环内的停止对所有步骤生效，而旧的停止信号不会影响。 |
| `digest/runner.py` | 单篇超时只让这一篇失败（记录原因），继续其它文章；用户停止与预算耗尽仍然整批结束。 |
| `joblog.py` | 运行开始记录写入进程号；新增 `run()` 上下文管理器（成功 / 停止 / 失败都会写结束记录）；新增 `running_runs()` / `is_running()`：有开始记录、没有结束记录、且进程仍存在，才算运行中；Windows 上改用心跳时间近似判断。 |
| `planning/topics.py`、`wiki/placement.py`、`entrypoints/draft_charter.py` | 补齐运行记录。 |
| `ui/*.py`（9 处）、`ui/topbar.py` | “运行中”改用 `is_running`，不再使用时间启发式。 |
| `ui/runs_page.py` | 显示当前正在运行的任务；“正在停止……”提示；没有运行中的任务时停止按钮不可用。 |
| `tests/test_runtime.py` | 新增 8 项回归测试。 |

## 4. 语义说明（请注意）

- **超时**：现在是“单次模型调用的最长等待”（默认设置 40 分钟，可在设置中改）。它不再是“整批任务的时长”。超时的那一篇/那一次调用失败，其它继续。
- **停止**：只影响停止请求**之后**开始的运行中调用；请求在调用发出前生效，等待中的调用会在约 0.2 秒内返回；已经发出、尚未返回的模型请求会在后台线程结束，结果被丢弃。
- **运行中的判断**：依据运行记录与进程是否存在。进程被强行杀死时，它只会作为“中断”的历史留在日志里，不会一直显示为运行中。

## 5. 未验证 / 需要你确认

- 没有在你的真实模型上验证超时与停止的实际体验（模型请求的时长取决于服务端）。
- Windows 下的运行中判断只是近似（用心跳时间），没有在 Windows 上实际运行过。
- 多个进程同时运行时，日计数仍是本进程内加锁（与 P7 记录一致）。

## 6. 追加修复：旧版停止文件导致新任务立即“已停止”

- **现象**：没有点击停止，新运行在 0.0 秒就显示“用户请求停止”。
- **根因**：上一版把停止文件写成 ISO 时间字符串；本版改为数字时间戳后，读取时无法解析旧文件，原逻辑在无法解析时返回“已请求停止”。磁盘上残留的旧文件因此让每个新运行立即停止。
- **修复**：停止判断改用文件修改时间（`st_mtime`），不再解析文件内容；无法读取时视为陈旧（不停止）。停止请求统一写入 `stop` 文本，内容不再参与判断。
- **测试**：新增 2 项（旧格式文件、无法解析的内容）。把判断改回“解析内容”后，新增测试失败。
- **注意**：修改时间的精度取决于文件系统；多数本地文件系统为纳秒级，但某些 FAT 类文件系统只到秒，停止请求与任务开始落在同一秒内时可能不生效（需要重新点击）。

## 7. 追加修复：运行日志误显示“正在停止”

- **现象**：没有点击停止，运行日志页面仍显示“正在停止……”。
- **根因**：页面只要磁盘上存在停止文件、且有运行中的任务，就显示该提示，没有检查停止请求是否发生在该任务开始之后。遗留的停止文件因此被误认为是本次停止。
- **修复**：只有停止请求的时间晚于某个运行中任务的开始时间，才显示“正在停止”。没有运行中的任务时，页面会删除遗留的停止文件。
- **测试**：新增 2 项（遗留文件不显示提示、无运行时自动清理）。恢复旧判断后，测试失败。
