## 1. 背景

第二轮（阶段二十七~三十一）完成后，`world_simulator` 已经具备：
因果线耦合结构化（`causal_graph.py`）、归因/贡献拆解
（`attribution.py`）、顺势/逆势/改变趋势判断（`trend.py`）、
反事实矩阵向导（`hypothesis.py`）、Relationship 与 Observer Mode
最小起步版、跨模拟因果知识库（`knowledge_base.py`）、最小版
Reality Calibration Loop（`reality_check.py`）等能力。

重新通读参考文档全文后，发现文档反复强调的几条核心原则，在当前
代码里**要么完全没做，要么只在小范围模板里做了最小版**，直接影响
"模拟是否真实、用户能不能看懂决策逻辑、模拟结果能不能真正用于
未来决策"这三件事：

1. **State 与 Belief 分离**（参考文档第六、十三节）：目前只在
   `multi_entity_mode`（多方谈判模板）里做了"每个主体私有 vars"
   的最小版，`life_sim`/`group_evolution` 这些主流模板里 LLM 对
   "当前经济形势""市场真实需求"是全知的，不存在信息延迟、认知
   偏差——这是"真实感"缺口里最大的一块。
2. **Fact / Assumption / Inference / Unknown 分层**（第十七、十八
   节）：`uncertain_fields`（已有 `confidence: low/medium/high`）
   只覆盖少数关键不确定字段，初始 `vars` 整体是一坨没有标注来源
   的 JSON，用户分不清"我说了啥、系统猜了啥"。
3. **Action Space 结构化**（第二十三、二十四节）：`ChoiceOption`
   只有 `id`/`label`/`description` 三个字段，选项之间没有
   成本/风险/可逆性/涉及因果线这些结构化维度，用户是在"选剧情"
   而不是"理解世界后做选择"。
4. **Agent Profile 情境化 + Preview + 反馈修正**（第三十一~三十九
   节）：自动挡画像目前只是自由文本 `principles` + 一个
   `risk_preference` 枚举，没有"条件策略"、没有生成后的预览验证、
   用户对自动挡选择的纠正也不会反过来修正画像。
5. **预测错误分类 + 模型版本化**（第四十五~四十七节）：
   `reality_check.py` 已有"记录预测→回填真实结果→反向影响知识库
   置信度"的最小闭环，但判定结果只有 `matched/partially_matched/
   diverged` 三档，不区分错误来源，也没有版本号，无法回答"改了
   prompt/skill 之后预测质量是不是真的变好了"。
6. **模拟复盘 / 经验教训总结**（用户本次明确提出的新需求，参考
   文档虽未单独设章节，但第四十四~四十七节"Reality Calibration
   Loop"和第五十四节"模拟器的最终输出不是答案，而是一整套结构化
   信息"的精神与此一致）：模拟推进到某个节点或结束后，用户目前
   只能自己翻时间线/归因报告/因果图谱来总结经验，系统没有一个
   "帮我把这一路的决策和结果整理成经验教训"的入口。

以上六条构成本轮的核心范围。参考文档里另外几条原则性较强、但
落地成本或必要性暂不明确的方向（Base Rate 外部数据接入、完整
Event-Driven 决策点引擎、反身性）放在第 4.7/4.8 节讨论，本轮
**不建议实施**，原因见对应小节。

## 2. 目标

- 让每一次模拟"看起来更像一个有认知局限的真实世界"，而不是一个
  对用户/Agent 全知全能的叙事生成器。
- 让用户在做每一个选择之前，就能看到这个选择的成本、风险、
  可逆性，而不是选完之后才靠归因报告倒推。
- 让自动挡代理的决策方式可验证、可迭代、可被用户"教"得更像自己。
- 让"预测有没有变准"这件事变得可追踪，而不是模糊的主观感觉。
- 新增"模拟复盘"能力，让用户在任意节点（尤其是模拟结束时）能
  拿到一份结构化的经验教训总结，真正把模拟结果沉淀成对未来决策
  有用的东西，而不是看完时间线就完事。
- 对不建议实施的方向，写清楚"为什么现在不做"和"什么信号出现时
  应该重新评估"。

## 3. 六个方向的依赖关系

```text
4.1 Action Space 结构化 ──────────────┐
4.2 Fact/Assumption/Inference/Unknown  ├─→ 4.6 模拟复盘
4.3 单主体最小 State/Belief 分离 ──────┤   （复盘报告引用前面几条
4.4 预测错误分类 + 版本号 ─────────────┤    产生的结构化数据，越
4.5 Agent Preview + 情境化策略 ────────┘    完整复盘质量越高，但
                                             4.6 本身不强依赖任何
                                             一条，可以独立先做）
```

4.1/4.2 相互独立，都是纯展示+prompt 层改动，风险最低，建议最先做。
4.3（State/Belief）改动面较大，建议单独验证。4.4（预测错误分类）
只是扩展已有的 `reality_check.py`，成本低。4.5（Agent Profile）
改动面同样较大，建议排在最后、单独出一份更细的子方案。4.6（模拟
复盘）不依赖以上任何一条就能做出一个可用版本，但如果 4.1/4.2/4.4
先落地，复盘报告能引用的结构化信息会更丰富——因此建议顺序上
4.1/4.2 之后、4.6 可以插进来先做一版，不必等 4.3/4.4/4.5 全部
完成。

## 4. 改进方案

### 4.1（P0）Action Space 结构化：选项不再只是一句话

> **实施状态：已完成**（阶段三十二，2026-09-19）。`ChoiceOption` 新增
> 字段、prompt 更新、`app.py` 展示均按下方方案落地，未做本节"范围
> 克制"里排除的部分。详见 `PROJECT.md` 阶段三十二条目 1。

**现状**：`state_model.ChoiceOption` 只有 `id`/`label`/
`description` 三个字段，`advance_step`/`generate_scenario` 的
prompt 也只要求 LLM 给出这三样。用户选择时看不出这个选项的成本、
风险、可逆性、会牵动哪条因果线——呼应参考文档第二十三、二十四节
"选项应该告诉用户 行动/成本/潜在影响/风险/主要不确定性/可逆性/
可能改变的因果线"。

**方案**：
- `ChoiceOption` 新增可选字段：`risk_level`（`low`/`medium`/
  `high`，不认识的值归一化为 `medium`，延续项目"不做伪精确"的
  一贯风格）、`reversibility`（`reversible`/`hard_to_reverse`/
  `irreversible`）、`affected_lines`（字符串数组，引用
  `causal_lines` 的 `id`，选填）、`key_uncertainty`（一句话，
  这个选项最大的不确定性是什么，选填）。全部可选、默认空/
  `medium`，不出现就是"未声明"，不强制 LLM 每次都填全。
- `spec_generator.py` 的 `advance_step`/`generate_scenario`
  prompt 增加这几个字段的说明和示例，但**不做代码层面的强制
  校验**（同 `causal_links`/`resource_relations` 等结构化字段
  的一贯做法——LLM 偶尔漏填不应该导致整次推进失败）。
- `app.py` 选项卡片渲染这几个字段（比如风险等级用不同颜色的小
  标签、可逆性用图标），没有声明的字段不展示（不用"未知"占位
  制造伪信息）。

**范围克制**：不做参考文档第二十五节"Value of Information"那种
"获取信息"选项类型的专门建模（比如把"先花3个月验证市场"识别成
一种特殊的"购买信息"选项并单独计算价值）——这需要引擎理解选项的
"类型"，改动更大，作为后续可选方向（见触发条件）。不做选项数量
的"Decision Frontier"筛选（文档建议控制在3~5个）——目前选项数量
由 `options_count` 设置已经控制，暂不需要额外收窄逻辑。

**涉及文件**：`state_model.py`（`ChoiceOption`）、
`spec_generator.py`（prompt 模板与解析）、`app.py`（选项卡片
展示）。

### 4.2（P0）Fact / Assumption / Inference / Unknown 分层标注

> **实施状态：已完成**（阶段三十二，2026-09-19）。详见 `PROJECT.md`
> 阶段三十二条目 2。

**现状**：`generate_scenario` 生成的初始 `vars` 是一坨没有来源
标注的 JSON，用户说的"我年收入40万"和 LLM 自动假设的"未来收入
增长5%"在数据结构上没有任何区别。已有的 `uncertain_fields`
（`confidence: low/medium/high`）只覆盖少数关键不确定字段，不是
对整个初始状态的系统性标注——呼应参考文档第十七、十八节。

**方案**：
- `spec_generator.ScenarioDraft` 新增可选输出
  `field_provenance`：`{字段路径: "fact"|"assumption"|
  "inference"|"unknown"}` 的映射，`generate_scenario` prompt
  要求 LLM 在生成初始 `vars` 的同时，对每个顶层字段标注来源——
  `fact` 只用于"用户在意图描述里明确提到的信息"，其余都应该标
  `assumption`（合理默认值）/`inference`（LLM 从上下文推断）/
  `unknown`（缺了但暂时先给个占位值）。
- 存入 `SimState.field_provenance`（初始状态才有意义，`advance`
  产生的后续状态不强制维护，因为世界会持续演化，"最初是不是用户
  说的"这个标签的价值主要在创建时）。
- `app.py` 创建向导预览/详情页初始状态展示时，给每个字段加一个
  小标签（"你说的"/"系统假设"/"系统推断"/"未知，先占位"），用户
  可以在创建向导里直接看到并修正——不新增修正入口，复用已有的
  "编辑初始 vars"能力。

**范围克制**：不做"用户修正后自动把标签从 assumption 升级为
fact"这种自动化逻辑（用户编辑了字段之后，标签需不需要变，这是
一个"要不要重新调用 LLM 判断"的问题，成本收益不明确，先手动在
UI 上提供"标记为已确认"的按钮，用户自己点）。不追溯覆盖存量
模拟——已经创建的模拟没有这个字段，展示层要兼容"没有
`field_provenance`"的情况（不展示标签，不是报错）。

**涉及文件**：`state_model.py`（`SimState.field_provenance`）、
`spec_generator.py`（`generate_scenario` prompt 与解析）、
`app.py`（创建向导 + 初始状态展示）。

### 4.3（P1）单主体模式的最小 State/Belief 分离

> **实施状态：第一、二批代码均已完成**（第一批同日追加，第二批
> 阶段三十五，均 2026-09-19），**⚠️ 应用户明确要求跳过了子方案要求
> 的人工验证**，不代表 LLM 真的能稳定产出有意义的认知偏差——详见
> `next_doc/world_simulator_belief_state_separation_plan.md`（含
> 分批计划）顶部的风险说明。

**现状**：`multi_entity_mode` 已经做了"每个主体私有 `entities`
vars + 共享 `shared_vars`"的结构，但只用于多方谈判这种明确的
多主体场景。单主体的 `life_sim`/`group_evolution` 完全没有
"用户自己对某个关键外部变量的认知 vs 这个变量的真实值"这种区分
——呼应参考文文档第六节的核心例子"市场需求真实是100，Agent 认为
是70~130"。

**方案（比 `multi_entity_mode` 更小的最小可行版本）**：
- 新增可选设置 `settings.belief_fields`：字符串数组，声明
  `vars` 里哪几个字段是"用户/Agent 只能通过有限信息估计、不能
  直接看到真实值"的（比如 `market_demand`、`competitor_
  strength`）。
- 对声明了的字段，`SimState.vars` 里继续存"真实值"（引擎/LLM
  推进用的就是这个），另外新增 `SimState.beliefs: Dict[str,
  Any]`（可选），存"当前 Agent 认为的估计值/区间"，由
  `advance_step` 在叙事里体现"角色觉得情况是怎样"时顺带输出。
- `app.py` 时间线/详情页，如果某个字段同时存在于 `vars`（真实值）
  和 `beliefs`（认知），展示"真实：X，你以为：Y"这种对比——这是
  能不能让用户"感觉到认知偏差"的关键展示点。

**范围克制**：不做完整的"信息延迟建模"（比如"这个信息要3步之后
才会被主体知道"）——只做"认知可能与真实不同"这一层，不做"認知
何时更新"的时间机制。不强制所有模板都声明 `belief_fields`，
留空（默认）表示不启用，行为完全不变，向后兼容。不做
`multi_entity_mode` 那种"每个主体各自私有"的完整版——这里只有
一份 `beliefs`（对应"用户视角"），不是每个 NPC 都有独立认知
（那种场景应该用已有的 `multi_entity_mode`，不重复造轮子）。

**建议时机**：改动涉及 `SimState` 新增字段 + `advance_step`
prompt 改动，属于"字段粒度设计"这类阶段十七暴露过风险的改动，
建议先在一个模板（比如 `life_sim`）里小范围验证 LLM 能不能
稳定输出"真实值"和"认知值"两套一致的数据，跑几次真实模拟观察
效果后再考虑推广到其它模板。

**涉及文件**：`state_model.py`（`belief_fields` 设置 +
`SimState.beliefs`）、`spec_generator.py`（`advance_step`
prompt）、`app.py`（真实值/认知值对比展示）。

### 4.4（P1）预测错误分类 + 模型/Skill 版本号

> **实施状态：已完成**（阶段三十二，2026-09-19）。详见 `PROJECT.md`
> 阶段三十二条目 3。

**现状**：`reality_check.py` 已经有"记录预测（含关键假设）→
用户手动回填真实结果 → 用户手动选 `matched`/`partially_matched`/
`diverged` → 反向影响 `knowledge_base.py` 里相关因果知识的
`confidence`"这条最小闭环。但不区分"为什么错"，也没有版本号——
呼应参考文档第四十六、四十七节。

**方案**：
- `reality_check.py` 的 `RealityCheckRecord`（回填结果时）新增
  可选字段 `error_category`：`data_error`（状态判断错）/
  `causal_error`（因果机制错，比如忽略了政策限制）/
  `agent_behavior_error`（Agent 行为预测错，比如高估了用户会
  选择的行动）/ `random_event`（纯随机事件）/
  `unknown_variable`（模型压根没考虑到的变量）/ `none`（
  `matched` 时不需要分类）。由用户在回填时选择（同 `verdict`
  一样，不做自动语义判定，避免不成熟算法给出看似客观实则不可靠
  的判断）。
- 新增 `settings.model_version`（字符串，用户自己维护的一个
  标签，比如换了一版 skill prompt 之后手动改一下，默认
  `"v1"`），随 `RealityCheckRecord` 一起记录快照。**不做自动
  版本管理**（不追踪 skill 文件的 git commit/hash 之类），只是
  给用户一个"自己标一下现在用的是哪版"的地方，成本极低。
- `app.py` 的复盘/回填页面新增一个"按错误分类统计"的小视图（比如
  "5次预测偏差里，3次是因果机制错、2次是随机事件"），帮用户判断
  该往哪个方向改进（是该丰富因果线，还是该接受"世界本来就有随机
  性，不是模型的锅"）。

**范围克制**：不做"model_version 变了自动重新评估历史预测"这种
自动化对比分析（那需要更复杂的统计），只做记录 + 简单分类统计。

**涉及文件**：`reality_check.py`、`state_model.py`
（`model_version` 设置）、`app.py`（回填表单 + 统计视图）。

### 4.5（P2）Agent Preview + 情境化条件策略 + 用户反馈反哺画像

> **实施状态：三个批次已全部完成**（情境化条件策略、Agent Preview
> 于同日追加，第三批"用户反馈反哺画像"于阶段三十四，均 2026-09-19）。
> 细化子方案见 `next_doc/world_simulator_agent_preview_and_adaptive_
> policy_plan.md`；第二批 Agent Preview 仍未做子方案要求的人工验证。

**现状**：`autopilot.py` 的画像只有自由文本 `principles` +
`risk_preference` 枚举，纯粹靠拼进 prompt 影响 LLM，没有可验证、
可迭代的结构——呼应参考文档第三十一~三十九节。

**方案（分三步，建议拆成独立的实施批次，不要求一次做完）**：
1. **情境化条件策略**：`autopilot` 画像的 `principles` 支持一种
   可选的结构化写法（在自由文本之外新增，不替代）：
   `{"if": "可逆", "then": "倾向探索"}` 这种简单的
   条件-倾向对，拼进 prompt 时转成自然语言（"当某个选项可逆时，
   倾向选择更有探索性的那个"）。这需要依赖 4.1 的
   `reversibility` 字段才有实际的匹配对象，所以建议排在 4.1
   之后。
2. **Agent Preview**：创建/编辑自动挡画像后，提供"用几个内置的
   通用测试情境（比如'突然失业你会怎么办'）跑一次单独的、不影响
   任何实际模拟数据的 LLM 调用，看画像会怎么选"，展示"选择 +
   理由 + 引用了哪条 principle"，用户可以标"符合"/"不符合"。
3. **用户反馈反哺画像**：用户在自动挡运行时对某次选择标记"不
   符合"并给出理由时（复用已有的 `review_mode` 人工复核入口），
   系统不自动改画像（避免"用户一句话就悄悄改了画像"这种不透明
   的自动化），而是把这次反馈存成一条"画像修正建议"，用户在
   画像编辑页看到"最近3次你都觉得 Agent 太保守了，要不要调整
   风险偏好"这样的提示，由用户自己决定要不要采纳（同 4.26
   "因果线建议"折叠区"生成建议、用户决定"的既有模式）。

**范围克制**：不做参考文档第四十一节"Current Self / Ideal Self /
Simulation Agent 三个自己"的完整建模——那需要额外维护两份画像
并对比差异，成本较高，且用户目前只有一个"自动挡画像"的概念，
强行拆三个会显著增加认知负担，作为更远期的方向、不在本轮范围。
不做"画像自动学习"（比如用统计模型从历史选择里拟合权重）——
始终保持"系统提建议、用户决定"这个透明度红线。

**涉及文件**：`autopilot.py`（画像结构 + Preview 调用）、
`state_model.py`（画像修正建议的存储，可能复用
`suggested_causal_lines` 类似的"建议列表"模式）、`app.py`
（Preview 界面 + 画像编辑页的建议提示）。

**建议时机**：改动面是本轮里最大的一个，建议单独针对这一节再写
一份更细的子方案（拆解三步的具体数据结构和 prompt），本文档
只定方向，不直接进入实施。

### 4.6（P1，用户本次明确要求）模拟复盘 / 经验教训总结

> **实施状态：已完成**（阶段三十二，2026-09-19）。详见 `PROJECT.md`
> 阶段三十二条目 4；已知限制（`counterfactual_summaries` 目前恒为
> 空数组）也记录在该条目下方。

**现状**：模拟推进到任意节点，用户只能自己翻时间线、归因报告
（`attribution.py`）、因果图谱（`causal_graph.py`）、顺势/逆势
判断（`trend.py`）来自己总结"这一路走下来学到了什么"，系统没有
一个专门的入口把这些信息整合成一份"经验教训"。

**设计理念**：呼应参考文档第五十四节"模拟器的最终输出不是一个
答案，而应该包括 关键事件/关键变量/失败模式/成功模式/决策点"这
一整套结构化信息，以及第四十四~四十七节 Reality Calibration
Loop"把每一次的经验沉淀下来，而不是跑完就忘"的精神。复盘报告
的价值不在于"预测未来"，而在于**把这一次模拟里已经发生的决策和
结果，转成用户下次面对类似情境时能直接参考的经验**——这是"让
模拟结果真正服务于未来决策"里除了预测本身之外，同样重要、甚至
更容易落地的一块（不依赖模型预测准不准，只是对已发生内容的
结构化总结，风险更低）。

**方案**：
- 新增模块 `world_simulator/retrospective.py`，提供
  `generate_retrospective(cfg, workspace_root, data_dir, sim_id,
  branch=None)`：
  - 收集素材：指定分支（默认当前活跃分支）从 step 0 到当前的
    完整 `state_history`（summary/narrative/chosen_option/
    causal_links）、`causal_graph` 关键节点、`objectives` 声明的
    每个目标字段的 `attribution.summarize_contributions()` 结果
    （如果 4.1 已完成，选项的 risk/reversibility 也一并带上）、
    `trend.classify_trend()` 结果（若用户声明过 `self_line_id`）、
    `reality_checks.jsonl` 里针对这个分支的记录（若有）、
    `hypothesis`/`build_counterfactual_matrix` 曾经跑过的对比
    分支结果（若有，用于"如果当初选了别的会怎样"这类对照，只
    读取已经存在的历史运行记录，不在复盘时临时新开分叉重新跑）。
  - 复用现有的 workflow/skill 机制，新增一个 `retrospective`
    阶段的 prompt（类似 `advance_step`/`generate_scenario` 的
    模式），要求 LLM 基于收集到的素材，**只对已经发生的内容做
    总结，不做任何面向未来的新预测**，输出结构化的
    `RetrospectiveReport`：
    - `turning_points`：关键转折点列表，每项引用具体 `step` +
      当时选择的 `chosen_option` + 一句话说明为什么关键。
    - `what_went_well`：做得好的地方（决策符合目标、抓住了
      机会），每项附带依据（引用哪个归因结果/哪条因果链）。
    - `what_to_reflect_on`：值得反思的地方（错过的机会、被外部
      因果线打乱的假设、被资源约束卡住的地方），同样要求附带
      依据，**不允许输出没有具体因果链/状态支撑的空泛评价**（比如
      "你应该更谨慎"这种没有依据的话直接算不合格输出，
      prompt 里明确要求"每条结论都要能在 `state_history`/
      `causal_links` 里找到对应的具体记录"）。
    - `lessons`：抽象成"下次遇到类似情境可以参考"的经验条目
      （每条一句话，附带来源于哪个 `turning_point`/
      `what_to_reflect_on`），**不写成心理层面的性格评价**（不
      对用户本人下判断，只针对"这个模拟世界里发生的具体决策和
      结果"）。
    - `caveats`：局限声明，固定包含一句"这是基于这次模拟内部
      记录的总结，不是对你个人能力或决策方式的心理分析，模拟
      本身也可能和现实有偏差"。
- 落盘：`data/<sim_id>/retrospectives.jsonl`（与
  `reality_checks.jsonl` 平级，同样的降级导入方式），每条记录
  `{id, created_at, branch, up_to_step, report}`，允许对同一
  分支在不同时间点多次生成，留存历史版本（不覆盖），方便用户
  比较"模拟继续推进之后，复盘结论有没有变化"。
- `app.py` 详情页新增"📖 模拟复盘"标签页：
  - "生成复盘报告"按钮（**不自动触发**——LLM 调用有成本，且
    复盘本身应该是用户主动想回顾时才做的事，不是每步都算一次）；
    `manifest.status == "ended"` 时额外展示一句"这个实例已经
    结束，是个复盘的好时机"的提示，不强制。
  - 历史复盘记录列表，按生成时间倒序，每条展开显示
    `turning_points`/`what_went_well`/`what_to_reflect_on`/
    `lessons`/`caveats` 五个板块。
  - `turning_points` 里的每个转折点提供"跳转到该步"的链接（复用
    时间线定位），方便用户回去看原始上下文。

**范围克制**：
- 只对**单个分支**生成复盘，不做跨分支/跨实例的"元复盘"（比如
  "你这半年跑的10个模拟总体上有什么共同的决策倾向"）——那是更大
  的范围，见下方"触发条件"。
- 不自动把 `lessons` 写入 `knowledge_base.py` 的因果知识库——
  复盘产出的是"针对这个用户这次具体情境的经验"，和知识库"跨模拟
  可复用的因果机制"是两类不同性质的知识，混在一起会污染知识库
  的检索质量；如果用户想手动把某条经验记进知识库，后续可以在
  UI 上加一个"添加为知识条目"的按钮，本轮不做。
- 不做定时/自动生成（比如"每推进10步自动生成一次复盘"）——延续
  项目"新能力先做成用户主动触发的可选功能，观察真实使用后再
  考虑要不要自动化"的一贯节制风格。
- `prompt` 要求"每条结论必须有具体依据"这条约束只能通过 prompt
  引导，**不做代码层面的自动校验**（校验"这句话是不是真的能在
  历史记录里找到依据"需要额外的语义匹配能力，成本高、可靠性存疑，
  同 `reality_check.py` 不做自动语义匹配判定的一贯取舍）。

**触发条件（后续可选方向，本轮不做）**：如果用户在多个实例上都
用过复盘功能、并且明确表达"想看看这些实例放在一起有没有共同
规律"，再评估要不要做跨实例的元复盘（这需要额外设计"多个
`RetrospectiveReport` 之间怎么聚合"的机制，现在做为时过早）。

**涉及文件**：新增 `world_simulator/retrospective.py`；
`spec_generator.py`（新增 `retrospective` 阶段 prompt，或者
放在 `retrospective.py` 自己的 prompt 常量里，参照
`hypothesis.py`/`reality_check.py` 独立管理自己 prompt 的先例）；
`app.py`（"模拟复盘"标签页）。

### 4.7（P3，暂不建议）Base Rate 外部数据接入

**为什么暂不建议现在做**：参考文档第四十八节强调预测应该结合
真实的历史统计基准（创业存活率、行业平均增速之类），当前
`knowledge_base.py` 只是"模拟内部产生的因果知识"的自循环，确实
没有接入任何外部真实数据源。但这需要稳定可信的数据源接入（
不能让 LLM 现编"根据统计，创业3年存活率是X%"这种听起来像数据、
实际是幻觉的内容），涉及数据授权、更新维护成本，和项目目前"本地
单机小工具"的定位不太匹配。

**触发条件**：如果后续有明确、稳定、可以合法接入的统计数据源
（比如某个开放数据集/API），且用户反馈"模拟的数字听起来没有
现实依据"是一个高频抱怨时，再评估最小可行的接入方式（比如先做
一个用户可以手动录入"参考基准数据"的字段，供 prompt 引用，而不
是自动联网抓取）。

---

### 4.8（P3，暂不建议）完整 Event-Driven 决策点引擎 + 反身性

**为什么暂不建议现在做**：
- 参考文档第二十~二十二节设想的"平时快进、只在关键事件出现时
  暂停生成决策点"，和当前"每一步 `advance_step` 都会生成
  `options`"的同步推进模型不同，要做到位需要重新设计推进循环
  本身（判断"这一步算不算关键事件"本身就是一个不轻松的子问题），
  改动量极大。4.25（Observer Mode，已完成最小起步版）已经是
  朝这个方向的一小步——建议先观察 Observer Mode 的真实使用效果，
  如果用户反馈"这个提示不够、真的需要系统自动判断哪些步该跳过
  决策"，再重新评估要不要做完整版。
- "反身性"（模拟预测本身影响现实，参考文档第五十二节）在单机
  本地工具场景下缺少前提条件（没有"大量用户看到同一份预测"这种
  情况），暂不建议投入。

## 6. 风险提示

- 4.3（State/Belief 分离）和 4.5（Agent Profile 情境化）都涉及
  新的字段语义设计，是阶段十七暴露过风险的那类改动（"字段粒度
  设计不合理会连带影响下游"），本文档明确建议这两条先小范围验证
  或单独细化方案，不要和 4.1/4.2/4.6 一起批量上马。
- 4.6（模拟复盘）虽然本身风险较低（纯读取 + 一次 LLM 调用 +
  落盘新文件，不修改任何已有数据结构的语义），但 prompt 质量
  直接决定复盘报告"有没有依据、会不会空泛"，建议实施后先人工
  抽查几次真实模拟的复盘输出，确认没有出现"没有依据的评价"再
  推广。
- 本轮新增字段延续"可选、默认不改变现有行为"的向后兼容原则；
  `state_model.py` 字段数量会继续增加，第二轮已经在文档末尾加了
  分组索引，本轮如果全部实施完，建议再检查一次索引是否需要更新
  分组。
