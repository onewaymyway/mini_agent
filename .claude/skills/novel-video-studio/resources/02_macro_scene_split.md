# 阶段2：大场景切分 (macro_scene)

**依赖**：无外部 API，纯 Agent 推理 + 文件读写。
**校验脚本**：`scripts/check_macro_scenes.py`。

本阶段只做"粗切"——把全文按剧情节奏切成几个大段落，不涉及镜头级别的
细节（那是阶段3的工作），也不生成任何素材或音频。

## Step 1：通读全文，识别切分点

结合已有的 `global/characters.json`/`locations.json`，重新通读全文，
标记"剧情转折/时间跳变/地点切换"的位置作为候选切分点（比如：场景从
客栈转到山道、时间从当晚跳到次日清晨、叙事视角切换、一场冲突从爆发到
结束）。

## Step 2：按硬约束确定最终切分

每个候选大场景必须同时满足：
- **原文字数 ≤ 1000 字**；
- **预估口播时长 ≤ 120 秒**（按 4.5 字/秒估算）。

若某个候选大场景超限，在其内部继续寻找次一级的转折点（哪怕转折不如
主转折点明显），强制二次细分，直到每个大场景都满足约束。

超短的大场景（不到 100 字）不强制合并，独立性优先于凑数；数量爆炸
（几十上百个）说明切分粒度出了问题，需要自查是否过度细分（个位数到
十几个是合理范围）。

## Step 3：写入 `macro_scenes.yaml`

**一次性把全部大场景切分完再整体写入**（不同于阶段1的"边处理边写"，
因为切分需要通盘考虑剧情节奏）。

```yaml
macro_scenes:
  - id: macro_01
    title: "青石客栈初遇"        # 简短概括，便于检索，不是口播文案
    source_span: "第1章 第1-3段"
    raw_text: "...(该大场景对应的原文全文，逐字保留，不做任何改写)"
    summary: "一两句话剧情梗概"
    estimated_duration_sec: 95
    char_count: 480
    uses_characters: [char_01, char_02]
    uses_locations: [loc_01]
    status: pending        # 阶段3处理完回写 planned
```

- `raw_text` 必须原文逐字复制，因为下游要从这里摘录对话原文，改写过
  的文本会导致对话校验失败；
- `char_count = len(raw_text)`；`estimated_duration_sec = char_count / 4.5`
  （四舍五入）；
- `uses_characters`/`uses_locations` 引用的 id 必须已存在于全局库；
  这个大场景涉及的角色/地点在全局库里还没有时，**先调用阶段1模式B**
  （单点补抽取），拿到新 id 后再继续写本大场景记录，不要引用不存在的 id。

## Step 4：校验

```bash
python .claude/skills/novel-video-studio/scripts/check_macro_scenes.py \
  <output_dir> --novel-text-file <原文文件路径>
```

不通过（超限、引用不存在的 id、原文覆盖率异常）→ 回 Step 2/3 调整，
重新跑校验，直到通过才能进入阶段3。

`--novel-text-file` 可选：不传时跳过"原文覆盖率"检查，只做字数/时长/
引用完整性检查；传了则额外检查所有 `raw_text` 拼接后总字数与原文总
字数的比例是否在合理范围（默认 ±15%）。

**向用户展示**：切分出的大场景清单（标题+梗概+字数+预估时长一览表）、
校验通过结果。

## 已知限制

- 覆盖率检查是粗粒度字数比例检查，不是逐字比对，仍需人工核对切分是否
  合理；
- 大场景数量没有硬性上限，但下游每个大场景都要走完整的阶段3-5链路，
  数量越多整体耗时越长，长篇处理建议提前和用户确认预期数量级。

`status: pending` 逐个来），不是一次性处理全部。
