# 阶段4：大场景切分 (macro_scene)

**依赖**：无外部 API，纯 Agent 推理 + 文件读写。
**输入**：**阶段0产出的 `script.md`（剧本），不是小说原文**——剧本已经
按"场次"把剧情/时间/地点分好，本阶段不需要再重新通读原文找转折点。
**校验脚本**：`scripts/check_macro_scenes.py`。

本阶段只做"粗切"——把剧本按剧情节奏归并/细分成几个大段落
（`macro_scene`），不涉及镜头级别的细节（那是阶段5的工作），也不生成
任何素材或音频。

## Step 1：以剧本场次为基本单位

读取 `script.md`，**每个"场次"默认就是一个候选 `macro_scene`**——因为
场次本身已经是按地点/时间/内外景切好的最小叙事单元。不需要再对场次
内部重新找转折点；本阶段的工作主要是"**归并**"（相邻的短场次如果剧情
紧密相连，可以合并成一个 `macro_scene`，减少下游阶段5-7的循环轮数）和
"**拆分**"（单个场次如果篇幅/时长过大，见 Step 2 的弹性判断决定是否
需要细分）。

## Step 2：按弹性约束确定最终切分（不再是硬上限）

每个候选大场景的**预估口播时长**（按 4.5 字/秒估算）：

- **默认目标 ≤ 120 秒**——这是建议值，优先按这个来切；
- **允许放宽到 ≤ 240 秒**——当且仅当这段剧情连续性很强、戏剧张力
  是一整段递进（例如一段大段独白/一场连续对峙），机械二次拆分会破坏
  节奏时，可以保留超过120秒但不超过240秒的大场景；
- **超过 240 秒是硬上限**，必须在内部寻找次一级的转折点强制二次细分。

**判断原则**：拆不拆，先问"拆开之后两半各自还能不能独立成一段完整的
戏"，能就拆，不能（拆开会把一句话/一个情绪高潮硬生生切断）就优先保留
完整性，允许时长超过120秒（不超过240秒硬上限即可）。不要为了凑
120秒这个数字而机械切断连续剧情——这正是本次调整要解决的问题。

超短的大场景（不到 100 字）不强制合并，独立性优先于凑数；数量爆炸
（几十上百个）说明切分粒度出了问题，需要自查是否过度细分（个位数到
十几个是合理范围）。

## Step 3：写入 `macro_scenes.yaml`

**一次性把全部大场景切分完再整体写入**（不同于阶段2的"边处理边写"，
因为切分需要通盘考虑剧情节奏）。

```yaml
macro_scenes:
  - id: macro_01
    title: "青石客栈初遇"        # 简短概括，便于检索，不是口播文案
    source_span: "场次1"          # 对应 script.md 里的场次编号（可以是多个场次合并）
    raw_text: "...(该大场景对应的剧本原文全文，逐字保留，不做任何改写)"
    summary: "一两句话剧情梗概"
    estimated_duration_sec: 95
    char_count: 480
    uses_characters: [char_01, char_02]
    uses_locations: [loc_01]
    status: pending        # 阶段5处理完回写 planned
```

- `raw_text` 必须是**剧本 `script.md` 对应场次的原文逐字复制**（不是
  小说原文），因为下游阶段5要从这里直接映射旁白/对话行，剧本里已经是
  `旁白：...`/`角色名：台词` 的结构化格式，改写过的文本会导致下游对话
  校验失败；
- `char_count = len(raw_text)`；`estimated_duration_sec = char_count / 4.5`
  （四舍五入）；
- `uses_characters`/`uses_locations` 引用的 id 必须已存在于全局库；
  这个大场景涉及的角色/地点在全局库里还没有时，**先调用阶段2模式B**
  （单点补抽取），拿到新 id 后再继续写本大场景记录，不要引用不存在的 id。

## Step 4：校验

```bash
python .claude/skills/novel-video-studio/scripts/check_macro_scenes.py \
  <output_dir> --novel-text-file <script.md 路径>
```

- **errors 非空（引用不存在的 id、字段不一致、超过240秒硬上限、原文
  覆盖率异常）→ 必须回 Step 2/3 调整**，重新跑校验，直到 errors 清空；
- **warnings 非空（超过120秒建议值但未超240秒硬上限）→ 允许通过**，
  但要按 Step 2 的判断原则确认"是否值得为保持剧情连续性而保留"，不是
  无脑放行。

`--novel-text-file` 传入的是**剧本文件 `script.md`**（不是小说原文，
因为阶段4的输入源已经是剧本），不传时跳过"覆盖率"检查，只做字数/时长/
引用完整性检查；传了则额外检查所有 `raw_text` 拼接后总字数与剧本总
字数的比例是否在合理范围（默认 ±15%）。

## 已知限制

- 覆盖率检查是粗粒度字数比例检查，不是逐字比对，仍需人工核对切分是否
  合理；
- 大场景数量没有硬性上限，但下游每个大场景都要走完整的阶段5-7链路，
  数量越多整体耗时越长，长篇处理建议提前和用户确认预期数量级；
- 时长弹性判断（120秒建议/240秒硬上限）依赖 Agent 对"剧情是否值得
  保持连续"的语义判断，脚本只能识别数字是否超限，无法判断超限是否
  合理，超过120秒但未超240秒时务必回读一遍这段剧情，确认确实值得
  保留而不是偷懒没有细分。

## 下一步

进入阶段5，**每次处理 `macro_scenes.yaml` 里的一个大场景**（按
`status: pending` 逐个来），不是一次性处理全部。
