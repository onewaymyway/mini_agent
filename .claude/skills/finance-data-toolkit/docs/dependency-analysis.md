## 2. 关键脆弱环节

### 2.1 网络请求层

**问题 1：HTTP 客户端未复用**
- 每个 scraper 都创建新的 `httpx.AsyncClient()`
- 未实现连接池复用，导致频繁建立/关闭连接
- 建议：在模块级创建共享客户端，或使用上下文管理器统一管理

**问题 2：超时配置不一致**
- 部分请求未设置超时（默认无限等待）
- 部分超时时间过长（30s+）
- 建议：统一设置合理超时（如 10s），并区分读取超时和连接超时

**问题 3：缺少请求限流**
- 高频请求可能触发目标网站的反爬机制
- 建议：添加请求间隔控制（如 0.5s-1s）

### 2.2 重试机制

**问题 4：重试逻辑分散**
- `fetchers.py` 中有 `retry_with_backoff` 和 `retry_akshare` 两个装饰器
- `resilience.py` 中有异步版本的 `retry_with_backoff`
- 存在重复实现，维护成本高

**问题 5：重试策略不统一**
- 同步和异步使用不同的重试逻辑
- 部分函数有重试，部分没有
- 建议：统一使用 `resilience.py` 中的重试机制

### 2.3 异常处理

**问题 6：错误处理不一致**
- 部分使用 `print(..., file=sys.stderr)` 打印错误
- 部分使用 `logger.warning/error` 记录日志
- 建议：统一使用结构化日志

**问题 7：错误信息丢失**
- 异常被捕获后仅打印，未记录到结构化日志
- 未返回给调用方，导致上层无法感知错误
- 建议：使用自定义异常类，并记录完整错误上下文

### 2.4 数据验证

**问题 8：验证逻辑未集成**
- `validation.py` 有验证逻辑，但未在抓取流程中调用
- 数据质量问题无法及时发现
- 建议：在抓取完成后自动调用验证

**问题 9：缺少数据质量监控**
- 无法统计验证失败率
- 建议：添加验证结果统计和告警
