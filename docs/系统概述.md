# mini_agent 项目设计说明

> 本文面向开发者和维护者，基于当前代码结构梳理 mini_agent 的整体设计、关键子系统、核心能力、项目亮点与后续改进方向。

## 1. 项目定位与目标

mini_agent 是一个用 Python 实现的命令行 Agent 框架，定位为“简化版 Claude Code”。项目目标是把 **LLM 对话、工具调用、Skill 上下文注入、会话持久化、权限控制、并发 Sub-Agent 编排** 等能力组合成一个可扩展的本地智能体运行时。

它的核心设计目标包括：

- **模型提供商解耦**：主 Agent 只依赖统一的 `LLMClient` 抽象，不直接耦合 Anthropic、OpenAI、Ollama 或 NVIDIA SDK。
- **工具系统统一**：文件、Shell、搜索、计划、用户交互、子任务编排等能力都通过统一工具注册表暴露给 Agent。
- **Prompt 可维护**：系统提示词、片段和用户模板集中存放在 `prompts/`，避免硬编码散落在业务逻辑中。
- **可观测与可恢复**：会话、统计、调试日志和任务状态均可持久化或查询。
- **复杂任务可并发拆解**：主 Agent 可以通过任务管理器派生多个 Sub-Agent，并通过依赖关系和并发信号量控制执行。

## 2. 整体架构

### 2.1 顶层模块关系

```text
│ - 对话历史                                                   │

│ - LLM 调用                                                   │
│ - 工具执行                                                   │

└───────┬───────────────┬──────────────────┬─────────────────┘

```

### 2.2 一轮用户请求的执行链路

1. `main.py` 解析命令行参数，创建 `AppConfig`、默认工具注册表、SkillLoader、权限守卫和 Agent。
2. 交互模式下 REPL 获取用户输入；单次命令模式下直接把命令传入 Agent。
3. `Agent.run_turn()`：
   - 检测文件变化并注入提示（可选）。
   - 根据用户输入自动激活匹配的 Skill。
   - 将用户消息追加到会话历史。
   - 进入 `_agentic_loop()`。
4. `_agentic_loop()`：
   - 构建 system prompt 和工具 schema。
   - 调用 LLM，支持流式与非流式。
   - 如果模型请求工具调用，则通过工具注册表执行工具，并把结果写回历史。
   - 重复调用 LLM，直到模型给出无工具调用的最终回答，或达到最大轮数。
5. 每轮结束后，Agent 根据配置自动保存 Session，并在满足条件时生成摘要或写入长期记忆。

## 3. 核心系统设计

### 3.1 CLI / REPL 系统

**主要文件**：`main.py`、`repl_input.py`、`terminal.py`、`renderer.py`

CLI 层负责应用启动、参数解析、交互输入和 slash 命令。它不直接处理 Agent 推理细节，而是把用户输入交给 `Agent.run_turn()`。

关键职责：

- **启动模式**：支持交互式 REPL 和单次命令模式。
- **配置入口**：通过命令行参数传入 provider、model、sandbox、debug、并发数、session 目录等配置。
- **slash 命令**：提供 `/help`、`/clear`、`/stats`、`/skills`、`/model`、`/provider`、`/session`、`/tasks`、`/plan`、`/concurrency`、`/compact` 等管理命令。
- **终端表现**：`renderer.py` 和 `terminal.py` 使用 Rich / prompt_toolkit 处理流式输出、状态栏、权限确认、Markdown 渲染和工具调用结果展示。

设计特点：

- CLI 层通过 `Agent`、`TaskManager` 和 `PromptManager` 的公开 API 完成操作，避免把业务逻辑写进命令处理函数。
- Slash 命令承担“运维控制台”的角色，使用户可以在运行时切换 provider、查看任务、恢复 session 或压缩历史。

### 3.2 配置系统

**主要文件**：`config.py`、`agent_config.json`

配置系统以 `AppConfig` 数据类为中心，统一承载模型、路径、运行策略、调试、会话、感知和记忆等参数。

配置来源与优先级：

1. JSON 配置文件（默认读取项目根目录 `agent_config.json`，也可通过 `--config` 指定）。
2. 命令行参数。
3. 环境变量。
4. 内置默认值。

主要配置类别：

- **LLM 配置**：provider、model、base_url、max_tokens、max_llm_calls。
- **运行策略**：stream、sandbox、auto_approve、verbose、max_turns。
- **Session**：session_dir、session_fmt、auto_save_session。
- **Prompt 上下文**：CLAUDE.md 内容、额外 system 文本、agent_name。
- **感知与记忆开关**：长期记忆、session 摘要、自动压缩、工具结果截断、技能语义匹配、项目扫描、文件监听、工具缓存、token 估算、工具统计等。

这种设计把实验性能力集中为开关，便于逐步启用和回归测试，也避免核心 Agent 逻辑被大量全局变量污染。

### 3.3 Agent 核心循环

**主要文件**：`agent.py`

Agent 是项目的核心运行时对象，负责维护对话历史、构建 prompt、调用 LLM、执行工具和保存 session。

关键对象组合：

- `AppConfig`：控制运行行为。
- `ToolRegistry`：提供可用工具定义和调用入口。
- `SkillLoader`：提供 Skill 自动激活和上下文注入。
- `PermissionGuard`：在工具执行前进行权限检查。
- `LLMClient`：统一的模型调用接口。
- `SessionManager`：会话持久化。
- 感知组件：ProjectScanner、FileWatcher、ToolResultCache、MemoryStore。

核心方法：

- `run_turn(user_message)`：处理一轮用户输入，执行 Skill 激活、历史追加、agentic loop 和自动保存。
- `_agentic_loop()`：循环调用 LLM 和工具，直到得到最终文本。
- `_call_llm()`：构建 system prompt 与工具 schema，处理流式输出和 provider 异常。
- `_execute_tools()`：解析 LLM 返回的工具调用，权限校验后调用工具注册表。
- `_build_system()`：组合 CLAUDE.md、Skill、项目扫描、长期记忆、计划状态、沙箱提示等上下文。
- `_auto_compress_history()`：当 token 估算超过阈值时压缩历史。

Agent 循环的关键设计是：**模型输出和工具执行之间通过 provider 无关的数据结构连接**。LLM 返回 `LLMResponse`，其中的 `ToolCall` 被 Agent 统一执行；工具结果再以统一消息格式写回历史。这样工具执行不依赖具体模型厂商，模型厂商也不需要知道工具的 Python 实现。

### 3.4 LLM 抽象层

**主要文件**：`llm/base.py`、`llm/factory.py`、`llm/providers/*`、`llm/providers/_base_mixin.py`

LLM 层的核心是 `LLMClient` 抽象基类和一组 provider 无关的数据结构：

- `ToolCall`：模型请求调用某个工具的名称、参数和调用 ID。
- `LLMUsage`：输入、输出和总 token 统计。
- `LLMResponse`：文本、工具调用、usage、stop_reason、reasoning、raw 响应。
- `ToolSchema`：统一的工具 schema 表示。
- `LLMConfig`：provider、model、api_key、base_url、max_tokens、temperature 等配置。

Provider 实现：

| Provider | 文件 | 设计要点 |
|----------|------|----------|
| Anthropic | `llm/providers/anthropic.py` | 使用 Anthropic SDK 原生 message / tool 格式。 |
| OpenAI | `llm/providers/openai.py` | 将 `ToolSchema` 转为 Chat Completions function tools。 |
| Ollama | `llm/providers/ollama.py` | 使用本地 HTTP API，支持工具格式转换。 |
| NVIDIA | `llm/providers/nvidia.py` | 使用 HTTP 客户端，支持 reasoning 流式回调。 |

`llm/factory.py` 通过 provider 名称创建客户端，并提供 `register_provider()` 支持运行时扩展。Agent 只依赖 `LLMClient.chat()` 和 `LLMClient.stream()`，因此新增 provider 通常只需要实现 provider 类并注册到工厂。

### 3.5 系统工具调用协议

**主要文件**：`llm/system_tool_call.py`、`llm/providers/_base_mixin.py`

项目同时支持两种工具调用路线：

1. **原生工具调用**：provider 将 `ToolSchema` 转成对应 API 的 tools 格式。
2. **System Prompt 工具调用**：把工具列表渲染到 system prompt，要求模型用文本块表达工具调用，再由解析器提取。

System Prompt 工具调用机制适用于不稳定支持原生 tools 的模型或本地模型。其关键函数包括：

- `render_tool_list()`：把工具 schema 渲染成模型可读的工具清单。
- `parse_tool_calls()`：从模型文本中解析工具调用块。
- `strip_tool_use_blocks()`：从最终展示文本中剥离工具调用内容。
- `convert_tool_use_to_text()`：把历史中的 tool_use 结构转换为普通文本，兼容不支持结构化工具消息的 provider。
- `postprocess_response()`：统一处理文本、工具调用和 reasoning 块。

该设计增强了模型兼容性，是 mini_agent 能接入本地模型和非标准 API 的关键。

### 3.6 工具系统

**主要文件**：`tools/__init__.py`、`tools/builtin.py`、`tools/plan.py`、`tools/orchestration.py`、`tools/user_input.py`

工具系统采用装饰器注册模式。每个工具函数通过 `@tool(...)` 声明名称、描述、JSON Schema 和是否需要审批。`ToolRegistry` 保存工具定义并执行调用。

工具类别：

| 类别 | 代表工具 | 说明 |
|------|----------|------|
| Shell | `bash` | 执行 Shell 命令，危险命令由权限守卫处理。 |
| 文件 | `read_file`、`write_file`、`create_file`、`delete_file`、`patch_file` | 支持读取、写入、创建、删除和补丁式编辑。 |
| 搜索 | `glob`、`grep`、`web_search` | 文件匹配、正则搜索和 Web 搜索。 |
| 计划 | `create_plan`、`add_task`、`start_task`、`complete_task`、`fail_task`、`get_plan_status`、`clear_plan` | 维护结构化执行计划。 |
| 编排 | `spawn_agent`、`spawn_agents`、`get_task_status`、`list_tasks`、`cancel_task`、`wait_for_tasks` | 创建和管理并发 Sub-Agent 任务。 |
| 用户交互 | `ask_user`、`ask_user_confirm`、`ask_user_choice` | 在 Agent 运行中向用户请求补充信息。 |

设计特点：

- 工具 schema 与 Python 函数绑定，便于统一暴露给不同 provider。
- 工具是否需要审批由工具定义声明，再由 `PermissionGuard` 决策。
- Agent 不需要知道每个工具的实现细节，只通过 registry 调用。

### 3.7 权限与沙箱系统

**主要文件**：`permissions.py`

权限守卫的核心职责是在工具执行前判断是否允许执行，尤其是写文件、删文件、执行 Shell 等高风险操作。

关键能力：

- **auto_approve**：自动批准工具调用，适用于受信任环境或 Sub-Agent。
- **sandbox**：沙箱模式下对危险写入或破坏性命令进行阻断或降级。
- **危险命令识别**：根据命令字符串识别 `rm -rf`、权限修改、重定向覆盖、包安装等风险模式。
- **用户确认**：非自动批准时通过终端提示用户确认。

该系统把“模型想做什么”和“运行时是否允许做”分离开，是本地 Agent 安全边界的重要组成部分。

### 3.8 Prompt 管理系统

**主要文件**：`prompts/manager.py`、`prompts/system/*`、`prompts/fragments/*`、`prompts/user/*`

PromptManager 负责加载、渲染和组合所有提示词。系统 prompt 的构建顺序大致为：

1. Agent 核心身份与行为规则。
2. Plan 模式能力说明。
3. 当前时间。
4. CLAUDE.md 项目上下文。
5. 已激活 Skill 的列表和内容。
6. 用户或 CLI 传入的额外 system 文本。
7. 编排能力说明。
8. 当前执行计划状态。
9. 沙箱模式警告。

设计优势：

- 提示词片段可单独维护和测试。
- `PromptManager.list_prompts()` 支持在 REPL 中查看可用 prompt。
- 当前计划、Skill、沙箱等动态上下文由统一入口注入，便于追踪模型实际看到的内容。

### 3.9 Skill 系统

**主要文件**：`skills/__init__.py`

Skill 系统通过发现 `SKILL.md` 文件，为 Agent 动态注入专门领域的操作说明。支持两种目录结构：

```text
skills/
  docx/
    SKILL.md
  pdf/
    SKILL.md
  my-skill.md
```

关键能力：

- **发现**：递归扫描 Skill 目录中的 `SKILL.md` 和平铺 `.md` 文件。
- **解析**：支持 YAML-like front matter 中的 `name`、`description`、`triggers` / `trigger_words`。
- **自动激活**：根据用户输入与触发词匹配自动启用 Skill。
- **上下文构建**：把已激活 Skill 的内容拼接进 system prompt。
- **内容裁剪**：支持按章节和 query 相关度返回最相关的若干片段。

Skill 是项目扩展领域能力的主要方式：它不需要修改 Agent 代码，只需要补充文档化的操作规范。

### 3.10 Session 与长期记忆系统

**主要文件**：`session.py`、`perception/memory_store.py`

Session 系统负责保存和恢复对话历史、模型信息、统计数据和摘要。它支持 JSON 和 JSONL 两种格式，并提供列表、搜索、加载、删除等能力。

核心设计：

- `SessionMeta`：保存 session 的轻量元信息。
- `Session`：保存完整历史、统计、摘要和时间戳。
- `SessionManager`：负责创建、保存、加载、搜索和删除 session 文件。

长期记忆由 `MemoryStore` 实现，使用 JSONL 文件保存会话摘要、关键结果、标签和模型信息。搜索采用轻量关键词评分，适合在不引入向量数据库的情况下提供基本跨 session 召回能力。

### 3.11 感知系统

**主要文件**：`perception/project_scanner.py`、`perception/file_watcher.py`、`perception/tool_cache.py`、`perception/token_counter.py`、`perception/memory_store.py`

感知系统是一组可选增强能力，默认通过配置开关启用：

| 子系统 | 功能 |
|--------|------|
| ProjectScanner | 扫描项目树、识别语言、读取 manifest、提取依赖、读取 Git 信息，并生成 prompt block。 |
| FileWatcher | 追踪文件 hash，检测外部修改，并在下一轮用户输入时注入变化提示。 |
| ToolResultCache | 缓存工具调用结果，并在相关文件变化时失效。 |
| TokenCounter | 粗略估算上下文 token，用于告警和自动压缩。 |
| MemoryStore | 保存和检索跨 session 的长期记忆。 |

这些能力的共同目标是提升 Agent 的环境感知能力，同时通过配置开关保持核心路径简单。

### 3.12 Plan 执行计划系统

**主要文件**：`orchestrator/plan.py`、`orchestrator/plan_display.py`、`tools/plan.py`、`docs/plan-and-task-guide.md`

Plan 系统维护一个结构化执行计划，帮助 Agent 在多步骤任务中追踪进度。它不负责启动后台任务，而是作为“工作记忆”和 UI 状态来源。

关键概念：

- **ExecutionPlan**：当前目标与任务树。
- **PlanTask**：计划中的任务节点。
- **parent_id**：表示视觉层级和归属关系。
- **depends_on**：表示执行顺序约束。
- **状态机**：pending → running → done / failed，并支持失败传播为 skipped。

Plan 状态会被注入 system prompt，使模型在后续 LLM 调用中能看到已经完成的步骤、失败原因和下一步可执行任务。

### 3.13 Sub-Agent 并发编排系统

**主要文件**：`orchestrator/task.py`、`orchestrator/task_manager.py`、`orchestrator/sub_agent.py`、`orchestrator/concurrency.py`、`tools/orchestration.py`

Sub-Agent 系统用于把独立子任务并发执行。它由两层组成：

1. **TaskManager**：任务调度器，负责提交任务、检查依赖、启动 SubAgent、记录状态、取消任务和查询结果。
2. **SubAgent**：在独立线程中运行的 Agent 包装器，继承基础配置并可覆盖 model / provider / system_extra。

任务数据结构：

- `Task`：不可变配置，包含 prompt、id、name、system_extra、model、provider、max_turns、depends_on、tags 等。
- `TaskRecord`：运行时状态，包含 status、result、started_at、finished_at 和日志。
- `TaskResult`：保存输出、错误、token、工具调用次数和 turns。

并发控制：

- `CountingSemaphore` 同时记录 active、waiting、available 和 waiters。
- 项目维护两个信号量：任务并发数和 LLM 调用并发数。
- 调度器使用纯线程模型，不依赖 asyncio。

编排工具允许模型在运行时：

- 派生一个或多个子 Agent。
- 查询任务状态和日志。
- 等待任务完成。
- 取消任务。
- 按状态或标签列出任务。

这是项目处理复杂任务、并行探索和多模型协作的核心亮点。

### 3.14 调试与可观测性

**主要文件**：`llm/debug_logger.py`、`renderer.py`、`orchestrator/task_display.py`、`orchestrator/status_bar.py`

可观测能力包括：

- **LLM 调试日志**：记录请求、响应、错误、provider、model、token usage、消息和工具 schema，输出到 JSONL 文件。
- **终端渲染**：工具调用、工具结果、错误、统计、Markdown、reasoning 块等都有统一展示格式。
- **任务看板**：Sub-Agent 任务可以表格化展示状态、耗时和结果摘要。
- **状态栏**：显示活跃任务数、等待队列、LLM 并发占用等运行时信息。
- **Session stats**：保存 turns、tokens、tool_calls、tool_stats、skill_activations。

## 4. 关键功能清单

### 4.1 多 Provider 模型接入

项目支持 Anthropic、OpenAI、Ollama、NVIDIA，并且保留 provider 注册扩展点。通过统一 `LLMClient` 接口，Agent 核心不需要关心 SDK 差异。

### 4.2 原生工具与文本工具双协议

对支持原生 tools 的模型使用结构化工具调用；对本地模型或非标准 API，可使用 system prompt 工具协议解析文本工具块。这显著提升了模型兼容性。

### 4.3 交互式 REPL 与管理命令

用户可以在同一个会话中切换模型、查看任务、查看并发状态、压缩历史、管理 Skill、恢复 session。这让 mini_agent 更像一个可持续运行的开发助手，而不是一次性脚本。

### 4.4 文件与 Shell 操作

内置工具覆盖读取、写入、创建、删除、补丁编辑、目录列举、glob、grep、bash 等本地开发任务常用能力。

### 4.5 权限守卫与沙箱

工具执行前通过 `PermissionGuard` 做审批和风险控制，既支持用户确认，也支持自动批准和沙箱模式。

### 4.6 Skill 动态注入

通过 `SKILL.md` 文件扩展 Agent 行为，降低新增领域能力的成本。Skill 可被手动启用，也可根据触发词自动激活。

### 4.7 Session 保存、恢复和搜索

会话历史和统计信息自动持久化，用户可以列出、加载、搜索历史 session；摘要和长期记忆提供跨会话延续能力。

### 4.8 计划与并发 Sub-Agent

Plan 负责结构化追踪当前工作；TaskManager 和 SubAgent 负责真正的并发执行。两者结合后，Agent 可以一边保持主线计划，一边把独立工作分派出去。

### 4.9 感知与自动上下文管理

项目扫描、文件监听、工具缓存、token 估算、自动压缩、工具结果截断等能力使 Agent 能更好地管理上下文窗口和环境变化。

## 5. 项目亮点

1. **良好的分层解耦**  
   CLI、Agent、LLM、Tools、Prompt、Skill、Session、Orchestrator 各有清晰边界，核心 Agent 不直接依赖 provider SDK 或具体工具实现。

2. **Provider 无关的 Agentic Loop**  
   `LLMResponse` 和 `ToolCall` 作为统一中间结构，使不同模型供应商接入后仍能复用同一套工具循环。

3. **双工具调用协议**  
   同时支持原生工具调用和 system prompt 文本工具调用，兼顾强结构化能力和本地模型兼容性。

4. **并发能力完整**  
   Sub-Agent 不只是简单线程启动，还包含任务数据模型、依赖关系、状态查询、取消、日志、并发信号量和状态展示。

5. **Prompt 工程可维护**  
   Prompt 被拆分到独立 Markdown 文件，并通过 PromptManager 统一组合，有利于迭代行为规则和测试 prompt 输出。

6. **安全边界明确**  
   工具声明 `requires_approval`，运行时由 `PermissionGuard` 综合 auto approve、sandbox 和危险命令识别进行判断。

7. **可扩展能力开关化**  
   感知、记忆、压缩、统计、缓存等增强能力通过配置开关启用，降低实验功能对主路径的影响。

8. **开发者体验较好**  
   REPL 命令、状态栏、Rich 渲染、调试日志、session 恢复和测试用例共同提升了可调试性和可操作性。

## 6. 后续改进方向

### 6.1 架构与代码质量

- **统一命名**：README 中存在 `mini_claude_code` 与 `mini_agent` 命名混用，可统一为 `mini_agent`。
- **结构改进路线**：根目录脚本较多，详细的包布局、模块边界和迁移建议见 [代码结构改进建议](code-structure-improvement-suggestions.md)。
- **拆分 Agent 类**：`agent.py` 承担了会话、LLM 调用、工具执行、感知、压缩等多重职责，可拆分为 `HistoryManager`、`ToolExecutor`、`ContextBuilder` 等组件。
- **减少循环导入风险**：PromptManager 会尝试读取 TaskManager 和 Plan 状态，建议进一步定义更明确的上下文提供接口。
- **明确配置优先级语义**：当前注释说明“JSON 配置文件优先于 CLI”，这与不少 CLI 工具习惯相反；可以保留但需在 README 中显著说明，或调整为 CLI 覆盖配置文件。

### 6.2 工具与权限

- **更细粒度的权限策略**：按工具、路径、命令类型、工作目录设置 allow/deny 规则。
- **审计日志**：记录所有需要审批或被拒绝的工具调用，方便安全回溯。
- **Shell 沙箱增强**：当前沙箱主要是策略层阻断，后续可接入容器、chroot、seccomp 或受限用户。
- **Patch 工具增强**：增加基于 unified diff 的多文件补丁、冲突检测和回滚能力。

### 6.3 LLM 与工具协议

- **更多 Provider**：支持 Gemini、OpenRouter、Azure OpenAI、Mistral 等。
- **统一流式 usage 处理**：不同 provider 的流式 usage 字段差异较大，可做更鲁棒的归一化。
- **工具调用容错**：文本工具协议可增加更强的 JSON 修复、重复调用去重、schema 校验和错误重试。
- **模型能力描述**：为 provider / model 增加 capabilities，如 supports_tools、supports_reasoning、supports_system_role、max_context 等。

### 6.4 计划与并发

- **Plan 与 TaskManager 融合**：当前 Plan 是执行计划，TaskManager 是并发执行任务；后续可建立显式映射，让计划节点可绑定 Sub-Agent 任务 ID。
- **任务持久化**：Sub-Agent 任务记录目前主要存在内存中，可持久化便于崩溃恢复。
- **取消机制增强**：运行中的线程无法强制杀死，只能标记取消；可引入子进程或协作取消 token。
- **结果聚合策略**：并发任务完成后，可提供自动摘要、冲突合并和引用来源标注。

### 6.5 记忆与上下文管理

- **向量检索**：长期记忆目前基于关键词评分，后续可引入 embedding 与向量库。
- **项目索引**：ProjectScanner 可扩展为代码符号索引、依赖图和测试覆盖关系。
- **更智能的历史压缩**：压缩时保留决策、文件修改、未完成任务和用户偏好，避免丢失关键信息。
- **上下文预算管理**：按 system、history、tool results、skills、memory 分配预算，防止某类上下文挤占全部窗口。

### 6.6 测试与质量保障

- **Provider Mock 测试**：为每个 provider 的 chat / stream / tool parsing 加更多 mock 测试。
- **端到端 Agent 测试**：模拟模型多轮工具调用，覆盖 tool loop、权限拒绝、错误恢复、session 保存。
- **并发压力测试**：覆盖任务依赖、排队、公平性、取消、失败传播和 LLM 信号量。
- **Prompt 快照测试**：对 system prompt 组合结果做 snapshot，防止无意改变核心行为。
- **类型检查与格式化**：引入 mypy / pyright、ruff、black 或 equivalent 工具。

## 7. 新增 Provider 的建议流程

1. 在 `llm/providers/` 下创建新的 provider 文件。
2. 继承 `LLMClient`，实现 `chat()` 和 `stream()`。
3. 将 provider SDK / HTTP 响应转换为 `LLMResponse`。
4. 将 `ToolSchema` 转换为目标 API 的工具 schema。
5. 在 `llm/factory.py` 注册 provider 加载函数。
6. 增加 provider 单元测试，覆盖普通文本、工具调用、流式输出和错误处理。
7. 在 README 或配置文档中补充环境变量、base_url 和示例命令。

## 8. 新增工具的建议流程

1. 在 `tools/` 中选择合适文件或新建模块。
2. 使用 `@tool` 声明名称、描述、JSON Schema 和 `requires_approval`。
3. 实现纯 Python 函数，返回字符串或 JSON 字符串。
4. 对可能修改文件、执行命令或访问外部资源的工具开启审批。
5. 确保模块被 `tools.get_default_registry()` 导入，从而完成注册。
6. 增加单元测试，覆盖正常路径、参数错误、权限相关行为和异常输出。
7. 如果工具会产生大量输出，考虑配合工具结果截断或缓存策略。

## 9. 维护建议

- 把“核心稳定能力”和“实验性能力”继续通过配置开关隔离。
- 对 prompt、provider 和工具协议建立回归测试，避免模型行为被隐性破坏。
- 对并发系统重点维护状态一致性和可观测性，避免后台任务静默失败。
- 对所有写入类工具保持最小权限原则，并持续改进审批信息的可读性。
- 对文档保持“架构文档 + 使用文档 + 子系统指南”三层结构：README 面向用户，`docs/project-design.md` 面向维护者，专题文档面向具体子系统。
