# 文档规范指南

> 本文说明 `docs/`、`next_doc/`、`release_logs/` 三个文档目录各自的定位、
> 边界，以及新增/维护文档时应遵守的具体规则。这是一份"规则现状"文档，
> 描述规则本身，不记录某一次具体的整理过程——整理 next_doc/docs 现状
> 的执行计划见 [next_doc/docs_governance_reorganization_plan.md](../next_doc/docs_governance_reorganization_plan.md)。

## 1. 核心理念

三个目录分别回答三个不同的问题，互不替代、互不省略：

| 目录 | 回答的问题 | 内容性质 | 生命周期 |
|---|---|---|---|
| `docs/` | **现在是什么样** | 当前行为、配置、使用方式、已知问题/局限 | 系统变了就同步改，不新开一篇 |
| `next_doc/` | **为什么这样设计、怎么一步步做出来的** | 设计方案、否决过的方案、改进计划、实施记录、bug 修复记录 | **永久保留**，不因功能"已完成"而删除或搬走 |
| `release_logs/` | **什么时候上线的** | 按版本号 + 日期的变更摘要 | 永久只读，不再修改 |

一句话原则：**"现在是什么样"永远只有一个去处——`docs/` 里对应那一篇；"为什么这样、怎么做出来的"永远只有一个去处——`next_doc/`；"什么时候上的"永远只有一个去处——`release_logs/`。三者不应该互相复制内容来补全自己。**

### 1.1 `docs/` 与 `next_doc/` 的引用关系

`docs/` 文档必须能**独立**回答"现在怎么用、现在是什么行为"，不依赖读者去翻 `next_doc/` 才能拼出当前用法。但"想知道为什么这么设计、之前踩过什么坑、否决过哪些方案"，`docs/` 应该主动链接到 `next_doc/` 对应文档，而不是把这些内容搬进 `docs/`——这类背景信息属于"为什么"，不属于"现在是什么样"。

反过来，`next_doc/` 文档不需要（也不应该）在功能实现后被删除、清空或"精炼进 docs/ 后销毁"——它是这个系统的设计考古记录，跟 `docs/` 是并列关系，不是"草稿→定稿"的先后关系。

## 2. `docs/` 具体规则

1. **一个子系统一篇文档**，禁止用"XX-update.md"/"XX-补充说明.md"的方式拆分新增内容。新增能力时直接编辑原文档对应章节；如果内容确实过大需要拆分，拆分后的文档之间必须是"总览 + 子专题"关系（总览里有目录链到全部子专题），不能是"正文 + 补丁"关系。
2. **命名统一 kebab-case + 英文文件名**：`<subject>-<type>.md`，`type` 从 `guide`（使用指南）/`reference`（参考手册）里选。标题和正文仍然用中文，但文件名不用中文——中文文件名在部分打包/传输场景下会出现编码乱码，跨平台不安全。
3. **同一份清单/表格如果被复制到多篇文档**（例如某个功能列表在指南 A 里有完整版、在指南 B/C 里有简化摘录版），新增/变更条目时必须**同时更新所有副本**，并在源头文档里注明"以下文档存在同步副本，变更时需一并更新"。
4. **超过 5 篇同主题前缀的文档群**（如 `goal-*`、`self-evolution-stage*`），必须有一篇总览文档给出阅读顺序，其余文档在开头注明"本文是 XX 总览的一部分，建议先读总览"。
5. **每篇文档开头一段"这篇文档管什么、不管什么"**，尤其当同一主题存在多篇文档时（例如两套微信接入方案分别是 `weixin-bot-guide.md` 与 `weixin-plugin-guide.md`，后者开头明确说明与前者的定位差异，这是应当遵循的样板写法）。
6. **允许包含"已知问题/局限"小节**，不需要等问题解决了才写文档——记录当前已知但未解决的问题本身就是"现状"的一部分。

## 3. `next_doc/` 具体规则

1. **命名统一 snake_case + 英文文件名**，同一子系统的文档使用统一前缀（如 `goal_cron_*`、`growth_advisor_*`），后缀按性质固定为四类：
   - `_design.md` —— 初始设计方案
   - `_plan.md` —— 改进计划；同一方向多轮迭代时用 `_v2.md`/`_v3.md` 递增，不要覆盖旧版本
   - `_implementation_record.md` —— 实施记录，与对应的 `_plan.md`（或 `_design.md`）一一对应，记录实际怎么做的、和原方案有何出入
   - `_bugfix.md` —— 纯缺陷修复记录，不构成功能设计变更
2. **新开一篇文档前，先看 `next_doc/README.md` 里该子系统已有哪些文档**，续用同一前缀，避免同一主题出现命名风格不一致的文档。
3. **超过 3 篇同前缀文档时，必须同步更新 `next_doc/README.md` 对应分组的时间线索引**——这是从已发生过的"汇总索引遗忘更新"问题里提炼出的强制动作。
4. **不要求、也不建议在功能上线后删除或清空**——完整保留设计过程本身就是这个目录存在的意义。如果某个方案被后续方案推翻，在新方案文档开头注明"取代 xxx_plan.md"，旧文档原样保留。

## 4. `release_logs/` 具体规则

沿用现有 `vX.Y.Z.md` 命名与结构：版本号 + 日期 + 覆盖的时间范围 + 分主线的变更摘要，保留 `_raw.txt` 原始 commit 记录做溯源。只做版本级摘要，不重复 `next_doc/` 里的设计细节，也不需要跟 `docs/` 保持逐条对应。

## 5. 发布前检查

新增/修改文档后，建议做一次链接存在性检查（遍历 `.md` 提取形如 `](xxx.md)` 的相对路径链接，确认目标文件真实存在），避免链接文字与实际目标不符、或链接目标文件已被移动/删除却未同步更新的问题。
