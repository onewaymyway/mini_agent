# mini_agent 执行机制总览与选型指南

> 本文回答一个反复出现的问题："我这个需求该用 skill 还是 workflow？该开
> 一个 sub_agent 还是接 hybrid_exec？" mini_agent 里"能让一件事被做完"的
> 方式不止一种，且它们不是互相替代关系，而是分布在**成本-泛化能力-确定
> 性-自主程度**这几个维度上的不同取舍。本文梳理当前项目里所有这类机制、
> 各自的定位与边界，并给出选型对照表。每种机制的完整细节见对应的专门
> 文档（本文只做横向比较，不重复其内部实现）。

---

## 1. 全景图

按"谁来发起、跑在哪、产出什么"分类，mini_agent 里能"执行"的机制大致有
以下几类：

```
┌─────────────────────────────────────────────────────────────────┐
│ 原子层：tools（工具）                                             │
│   一次函数调用，无 LLM 参与，是其它所有机制的最终落点              │
└─────────────────────────────────────────────────────────────────┘
                              ▲
                              │ 被下面所有机制调用
┌─────────────────────────────────────────────────────────────────┐
│ 上下文增强层：skill（技能）                                       │
│   不独立执行，往主 Agent 的 system prompt 里注入领域说明           │
└─────────────────────────────────────────────────────────────────┘
                              ▲
        ┌─────────────────────┼─────────────────────────────┐
        │                     │                             │
┌───────────────┐   ┌──────────────────┐         ┌─────────────────────┐
│ sub_agent      │   │ workflow          │         │ hybrid_exec          │
│ 主 Agent 主动   │   │ 预定义 DAG，       │         │ 脚本优先、自动降级   │
│ 派生的并行任务  │   │ 多种 step 类型     │         │ LLM/Agent 兜底       │
└───────────────┘   └──────────────────┘         └─────────────────────┘
        │                     │                             │
        └─────────────────────┴─────────────────────────────┘
                              │
        ┌─────────────────────┼─────────────────────────────┐
        │                     │                             │
┌───────────────┐   ┌──────────────────┐         ┌─────────────────────┐
│ role_agents    │   │ ensemble          │         │ goal_mode             │
│ 框架被动触发的  │   │ 同一任务多候选     │         │ 跨多轮 run_turn 的    │
│ 质检/建议角色  │   │ 取优（Best-of-N）  │         │ 外层驱动循环          │
└───────────────┘   └──────────────────┘         └─────────────────────┘
                              │
┌─────────────────────────────────────────────────────────────────┐
│ 调度/后台层：cron job / AutonomousLoop（自主守护循环）              │
│   无人值守，定时或规则触发，产出物是对上面各机制的一次调用           │
└─────────────────────────────────────────────────────────────────┘
                              │
┌─────────────────────────────────────────────────────────────────┐
│ 自我修改层：evolution（StateRepo / EvolutionWorkspace）             │
│   特殊执行类型：改动对象是项目自身（技能/配置/代码），风险分级 T0-T3 │
└─────────────────────────────────────────────────────────────────┘
```

## 2. 逐个机制说明

### 2.1 tools（工具）—— 原子执行单元

**是什么**：注册在全局 `ToolRegistry` 里的一个个函数（文件读写、bash、
搜索、`run_workflow`、`run_hybrid_exec_task`……），供 LLM 通过 function
calling 直接调用。**没有自己的"执行策略"**——调不调、调几次，完全由
调用方（主 Agent 一次 `run_turn` 内的推理，或某个 step/脚本里的显式
调用）决定。

**特点**：无自主性、无重试/降级逻辑、单次调用即返回；是下面所有机制
最终落地的地方（workflow 的 `tool_call` step、hybrid_exec 脚本内部、
sub_agent 的工具箱，用的都是同一套 `ToolRegistry`）。

**适用场景**：任何"需要 LLM 之外能力"的最小单元；不单独作为"选型对象"
出现，而是被其它机制组合使用。

详见 `docs/commands-and-tools-reference.md`。

### 2.2 skill（技能）—— 上下文增强，不是独立执行体

**是什么**：`SKILL.md` 描述的一段"怎么做某类事"的说明，按需（关键词
匹配/工具调用）注入主 Agent 的 system prompt，让主 Agent **用自己的推理
+ 已有工具**去完成任务，而不是把执行权转移出去。

**特点**：
- 不消耗独立的 LLM 调用/线程，只占用 context 空间；
- 可读写状态：`SkillUsageTracker` 追踪实际使用情况，压缩历史时按 LRU
  重新附加；
- 有一种例外把 skill "升级"成独立执行：workflow 的 `skill_agent` step
  类型（`SkillAgentStepExecutor`）会为指定 skill 拉起一个专属的轻量
  Agent 单独跑，这时它的执行模型退化为 §2.3 的 sub_agent。

**适用场景**：一类会反复遇到、有固定最佳实践、但每次输入差异较大、不
适合固化成脚本的任务（比如"写 Word 文档要注意的格式规范"）；本质是
"教会主 Agent 怎么做"，而不是"帮主 Agent 做"。

详见 `docs/skill-system-guide.md`。

### 2.3 sub_agent（Sub-Agent）—— 主 Agent 主动派生的并行执行单元

**是什么**：对主 Agent 的轻量包装，在独立线程里跑一份完全独立的对话
历史（`orchestrator/sub_agent.py`）。主 Agent 通过 `dispatch_task` 类
工具显式派发，可以一次派发多个、通过依赖关系和信号量（`concurrency.py`）
控制并发度，结果写回 `TaskRecord` 供主 Agent 汇总。

**特点**：
- **临时性**：跑完即销毁，不沉淀任何可复用产物（不像 workflow 会存
  YAML、不像 hybrid_exec 会存脚本）；
- **完全隔离**：独立对话历史、独立统计，仅继承主 Agent 的
  provider/model 配置（可覆盖）；
- **多轮 + 工具**：和主 Agent 能力对等，可以自主推理、多轮调用工具；
- ensemble 的 `subagent` 粒度、goal_mode 内部驱动，本质都是对
  sub_agent 机制的复用。

**适用场景**：一次性的、需要并发拆解的复杂任务（"同时调研三个方案，
分别写报告再汇总"），不要求下次遇到类似任务时能直接复用。

详见 `docs/subagent-mechanism.md`、`docs/plan-and-task-guide.md`。

### 2.4 workflow（工作流）—— 预定义 DAG，确定性编排

**是什么**：用 YAML/JSON 描述一组有依赖关系的 step，`WorkflowRunner`
按依赖图调度执行，支持条件分支、并发分批、断点续跑、人工审批门。保存在
`.agent/workflows/`，可反复调用、可版本管理（`workflow history`/`diff`
直接复用 git）。

**step 类型**（`workflow/executors.py`，可通过 `register_step_executor()`
插件扩展，如本项目的 `hybrid_step`）：

| step 类型 | 执行内容 |
|---|---|
| `agent` | 主 Agent 风格的一次 LLM+工具调用 |
| `role_agent` | 调用某个已定义的角色 Agent（见 §2.5） |
| `sub_workflow` | 调用另一个已保存的 workflow（可组合/复用） |
| `tool_call` | 直接调用一个已注册工具，不经过 LLM 推理 |
| `human_input` | 暂停等待人工输入后继续 |
| `script` | 执行一段固定脚本（无 LLM/Agent 能力） |
| `python_step` | 子进程隔离执行 Python，脚本内可选调用 `ctx.llm`/`ctx.run_agent_turn` |
| `skill_agent` | 为指定 skill 拉起一个专属 Agent 单独跑（见 §2.2 末尾） |
| `foreach` / `wait` / `merge` | 流程控制：批量展开 / 等待 / 合并分支 |
| `hybrid_step`（插件） | 接入 hybrid_exec（见 §2.6） |

**特点**：
- **确定性强**：DAG 结构、依赖关系、条件判断都显式写在 YAML 里，跑
  第二次不会"重新决定怎么做"；
- **可持久化执行状态**：支持后台执行、暂停/恢复、审批门，适合长流程；
- **不产出脚本**，本身就是可复用产物（YAML 文件）。

**适用场景**："流程本身是确定的、每一步该做什么是已知的"，比如代码
审查流程、发布检查清单、多阶段数据处理管道——重点是**编排的确定性**，
而不是"某一步怎么算便宜"。

详见 `docs/workflow-guide.md`。

### 2.5 role_agents（角色 Agent：Evaluator / Coach）—— 框架被动触发

**是什么**：与 sub_agent 相反，role_agent **不由主 Agent 主动召唤**，
而是框架根据配置的触发时机（`trigger_on: output` / `tool_use:bash` /
`turn_end`）自动介入，结果以消息形式注回主 Agent 的对话历史。两类内置
角色：

- `EvaluatorAgent`：对主 Agent 输出质检打分，可触发循环修订（发生在
  **一次 `run_turn` 内部**，受 `max_turns` 约束）；
- `CoachAgent`：在特定工具调用后给策略建议。

**特点**：主 Agent 感知不到"被评判"这件事本身发生在哪一步，只会收到
一条注入的反馈消息；触发是配置驱动、非侵入式的。

**适用场景**：需要对主 Agent 的行为做**持续质量把关**，但不想在每个
任务里手写"检查一下"的逻辑——配置一次，对所有匹配的 turn/工具调用
生效。

详见 `docs/role-agents-guide.md`。

### 2.6 hybrid_exec（脚本/LLM/Agent 混合执行）—— 脚本优先、自动降级

**是什么**：一套独立于 workflow 的执行系统。核心逻辑：脚本优先执行
（成本最低）→ 报错先尝试自动修复脚本 → 修不好再降级到 LLM 单轮 → 最后
Agent 多轮兜底。首次调用会探索出一版脚本并存入
`.agent/hybrid_exec/scripts/<task_id>/`，之后同一 `task_id` 直接命中
脚本，**越用越省钱**。

**特点**：
- **围绕 `task_id` 沉淀复用**，与 sub_agent 的"一次性"正好相反；
- 三条接入路径共享同一份脚本仓库：`import` 独立调用、
  `mini-agent hybrid-exec run/list/show` 命令行、主 Agent 工具
  `run_hybrid_exec_task`/`list_hybrid_exec_tasks`/`show_hybrid_exec_task`、
  以及 workflow 的 `hybrid_step`；
- 有版本管理、成功率统计、连续失败自动退役重探索。

**适用场景**：**会被重复调用、输入结构基本稳定**的任务（格式转换、
统计、抽取类），值得为"以后调用更便宜"多付一次探索成本；不适合一次性
或输入形状高度多变的任务（那种直接用 sub_agent 或工具更划算）。

详见 `docs/hybrid-exec-guide.md`；构建/调试新任务用配套 skill
`.claude/skills/hybrid-exec-task-generator/`。

### 2.7 ensemble（Best-of-N / 多结果合并取优）

**是什么**：对同一任务获取多个候选结果，再综合评判出最优结果，用于
降低单次输出的偶然性误差。两种粒度：

| 粒度 | 说明 | 成本 | 适合 |
|---|---|---|---|
| `llm_call` | 相同输入多次调用 LLM（温度抖动） | 低 | 单个开放式问题的质量兜底 |
| `subagent` | 多个 sub_agent 用不同人设/上下文各跑一遍（可用工具、多轮） | 高 | 任务本身存在多种合理解法路径 |

触发模式 `off`/`manual`/`auto`/`always` 可配置，`auto` 由规则 + 模型
自判是否值得多花这份成本。

**适用场景**：单次结果质量方差大、又没有明确的 `output_validator` 可以
自动判定对错的任务（有明确校验标准时优先考虑 hybrid_exec 的
dry-run/退役机制，成本更低）。

详见 `docs/ensemble-best-of-n-guide.md`。

### 2.8 goal_mode（Goal 模式）—— 跨多轮 run_turn 的外层驱动循环

**是什么**：设定一个目标，`GoalRunner` 在外层反复驱动主 Agent 做
`run_turn`，直到达成目标或触发安全阀（次数上限/明显不再前进）。与
EvaluatorAgent 的修订循环的关键区别：**Evaluator 循环在一次 `run_turn`
内部**，受 `max_turns` 硬顶约束；**goal_mode 是外层循环**，能在撞到
轮次/上下文上限时自动压缩历史后继续，并支持进程被杀死后从上一个完整
轮次恢复。

**适用场景**："把测试覆盖率提上去"这类没有单一步骤能完成、需要反复
尝试-检查-调整、且目标本身可以用自然语言验收标准描述的长任务。

详见 `docs/goal-mode-guide.md`。

### 2.9 cron job / AutonomousLoop（定时任务 / 自主守护循环）

**是什么**：daemon 进程里的后台调度层，不是"新的执行方式"，而是"谁在
什么时机触发上面这些机制"的调度器：

- **cron job**：`CronJobExecutor` 走独立执行通道（不经过普通消息的
  `InputQueue`），带墙钟超时、卡死检测（`StuckDetector`）、跨次续跑
  （`CronJobWorkspace`），触发到期后调用一个"跑一步"的实现（通常是
  一个轻量 sub-agent）；
- **AutonomousLoop**：三档位调度（`passive`/`active`/…），
  `passive` 档只做周期性巩固任务，更高档位会读 `GoalBacklog` 主动派生
  子目标、经 `ResourceArbiter` 分配资源执行。

**适用场景**：需要"无人值守、按时间/规则自动发生"的任务，比如每日
简报、定期知识回顾——本身不决定"怎么做"，只决定"什么时候让谁去做"。

详见 `docs/cron-jobs-reference.md`、`docs/autonomous-daemon-design.md`、
`docs/self-evolution-stage9-guide.md`。

### 2.10 evolution（自我演化：StateRepo / EvolutionWorkspace）—— 特殊执行类型

**是什么**：当"执行"的对象是**项目自身**（新增/调整 skill、改配置、
甚至改代码）时的专用通道，不允许绕过：

- `StateRepo`：所有自我修改的唯一写入入口，统一纳入 git 仓库，用
  `T0`~`T3` 风险分级决定校验严格度；
- 验证流水线：分级校验，失败则不落盘、不 commit；
- `EvolutionWorkspace`：基于 `git worktree` 的进程级隔离，先在隔离环境
  验证改动可用再合入。

**特点**：这是唯一一个"执行结果会改变系统自身能力边界"的机制，因此
治理最严格，其它机制（包括 hybrid_exec 的脚本仓库、workflow 的保存）
都不需要过这条通道——它们的产物是"新增的可复用配置"，不是"对现有
核心代码/配置的修改"。

**适用场景**：Agent 自主决定"我应该学会/调整某个技能或参数"时。

详见 `docs/self-evolution-stage2-guide.md` 及 Stage3-9 系列文档。

## 3. 选型对照表

| 维度 | tools | skill | sub_agent | workflow | hybrid_exec | role_agents | ensemble | goal_mode | cron/AutonomousLoop | evolution |
|---|---|---|---|---|---|---|---|---|---|---|
| **发起方** | 任意调用方 | 主 Agent（context 触发） | 主 Agent 主动派发 | 用户/工具调用 `run_workflow` | 任意调用方（CLI/工具/库） | 框架按配置自动触发 | 调用方/规则判定 | 用户 `/goal` | daemon 调度器 | Agent 自主提议 |
| **是否独立 LLM 调用** | 否 | 否（仅注入 prompt） | 是（独立对话） | 部分 step 是 | 视 tier（脚本层否） | 是 | 是（多次） | 是（多轮） | 视被调用机制 | 视被调用机制 |
| **是否产出可复用制品** | 否 | 否 | 否 | 是（YAML） | 是（脚本+版本） | 否 | 否 | 否 | 否（调度配置本身是制品） | 是（技能/配置改动） |
| **确定性 vs 自主性** | 确定 | 引导自主 | 高自主 | 高确定 | 首次自主，之后确定 | 中（配置驱动） | 高自主（多候选） | 高自主（外层驱动） | 确定（时机）+ 视被调用机制 | 高自主（受严格治理） |
| **典型成本** | 最低 | 低（仅 context） | 高 | 中（视 step 组成） | 首次高，之后低 | 中 | 高（N 倍） | 高（多轮） | 视被调用机制 | 中高（含验证开销） |
| **是否可持久化/恢复执行状态** | 否 | 否 | 否 | 是（断点续跑） | 是（脚本仓库统计） | 否 | 否 | 是（跨进程重启恢复） | 是（cron state） | 是（git 历史） |
| **典型场景** | 原子操作 | 教会怎么做 | 一次性并发拆解 | 流程确定的多步任务 | 重复调用、值得沉淀 | 持续质量把关 | 结果质量方差大 | 长期目标、反复尝试 | 定时/后台自动触发 | 修改系统自身能力 |

## 4. 快速判断口诀

1. **只是需要 LLM 之外的一个能力？** → 直接用 tool，不用套任何一层。
2. **这类任务有固定最佳实践、但每次输入差异很大，希望主 Agent 自己
   按套路做？** → skill。
3. **任务是一次性的、需要并发拆几个子任务？** → sub_agent（`Task`）。
4. **流程本身固定、每步做什么已知，希望能反复调用同一套编排？**
   → workflow。
5. **任务会被重复调用、输入结构基本稳定，想要"越用越便宜"？**
   → hybrid_exec。
6. **不是"做任务"而是"持续检查主 Agent 做得好不好"？** → role_agents。
7. **单次结果质量不稳定、又没法用规则自动判对错？** → ensemble。
8. **目标明确但没有单一步骤能完成，需要反复尝试直到达成？**
   → goal_mode。
9. **希望这件事按时间/规则自动发生，不用人触发？**
   → cron job（+ 上面任一机制作为"具体做什么"）。
10. **要调整的是系统自身的技能/配置/代码？** → evolution（`StateRepo`），
    不走以上任何一条"业务任务"通道。

多数真实需求会组合使用（比如 cron 定时触发一个 workflow，其中某个
step 是 `hybrid_step`），选型时先按"这一层具体在做什么"逐层拆解，而
不是整体套用某一种机制。
